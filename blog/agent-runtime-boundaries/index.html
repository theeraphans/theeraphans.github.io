Designing the handoff between conversation and agent execution

What the runtime loader makes explicit, and which decisions belong outside the model.

Theeraphan Sukchok · 9 October 2026 · Engineering research note

On this page

Where this question comes from

This note draws on the local runtime loader and the platform architecture notes. The loader prepares flow and team data and exposes routing and completion tools. Evaluation and promotion are separate design responsibilities. Local source inspection does not establish live end-to-end reliability.

This engineering note develops a testable question from my work. It does not report a new experiment or claim a novel algorithm.

Keep the conversation separate from execution

The chat service owns the channel and conversation: receiving messages, maintaining conversation state, identifying an inquiry, and collecting missing information. Once a request is ready, it hands the runtime a task and its context. That separation lets a conversation change channels without making the execution engine responsible for every webhook and messaging format.

The core loads a selected agent configuration and builds its execution graph. Routers and loaders prepare the required data before execution; graph nodes work with the state they receive and return updates. Database access belongs in the preparation layer rather than being scattered through the graph.

An agent definition has distinct parts: persona, rules, skills, and tools. A persona describes its role. Rules set constraints. Skills describe how to approach a task. Tools define which external capabilities it can use. Keeping these separate makes a proposed change easier to inspect than a single growing prompt.

Make business actions visible

The runtime connects to MCP servers instead of embedding every business integration in the agent itself. A tool can expose an order lookup, shipment information, a document operation, or another bounded capability. The public diagram groups those tools; it does not mean each request calls every integration.

The implementation separates read-only data tools from business tools that can change state. That boundary matters because retrieving information and taking an action carry different risks. A tool call should be an inspectable operation with an explicit input, not a side effect hidden inside an answer.

Execution records preserve the run and tool activity. They provide a way to investigate what the agent actually did, beyond reading its final message. This is also the evidence an evaluation service needs when the answer sounds reasonable but the workflow is wrong.

Follow one request through the system

Consider an illustrative shipment inquiry: “Has my order shipped?” This is an explanatory example, not a recorded customer interaction. The channel service collects enough information to identify the order. The core receives the prepared task, loads the configured team, and coordinates a capability. A shipment tool returns business evidence, and the conversation layer presents a response.

The local loader assembles an orchestrator prompt from the flow definition and agent configuration. Its routing tool exposes an explicit list of agent names. The orchestrator can route a task or complete the flow with a summary. An allowed agent name constrains the choice, although it does not prove the task was routed correctly.

Useful evidence includes the selected version, the order reference supplied to the lookup, the returned shipment status, and the answer shown to the user. A failed lookup needs a different explanation from a successful lookup that found no shipment.

More agents mean more boundaries to inspect

Splitting work across agents can make specialized instructions easier to maintain. It also adds routing decisions, handoff context, model calls, and possible failure points. A short lookup may need one bounded capability rather than several agents exchanging summaries.

The local orchestrator favors the configured step sequence. That gives a readable workflow, but the design still needs evidence that the sequence is appropriate for a given task. A useful comparison would hold the task set constant and compare a single-agent baseline with the configured team on answer quality, tool correctness, latency, and cost. No such comparative result is reported here.

The evaluation loop should also preserve the baseline configuration. A proposed improvement that passes answer checks but repeats a business action should fail promotion. Authorization and replay tests need acceptance criteria independent of prose quality.

What I would test next

Compare explicit request preparation with a model-only handoff on the same incomplete shipment inquiries. Inspect the selected route and exact tool inputs alongside answer quality. Keep the model and available capabilities fixed so the comparison measures the handoff policy.

This is a proposed test, not a completed result. A future report needs its fixtures, baseline, and execution evidence.
