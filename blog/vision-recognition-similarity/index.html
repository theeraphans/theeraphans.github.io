Detection, recognition, and similarity search on retail shelves

Why locating a package and identifying its SKU need separate evidence.

Theeraphan Sukchok · 9 October 2026 · Engineering research note

On this page

Where this question comes from

This note starts from my retail vision work: YOLO detection, CNN and ViT recognition, similarity search, API serving, and shelf analytics. Public materials report 750+ SKU classes and an audit-time change from 45 to 15 minutes. Training details and evaluation conditions are not public.

This engineering note develops a testable question from my work. It does not report a new experiment or claim a novel algorithm.

Find the product before naming it

YOLO locates products in shelf photographs. Recognition then combines classification models, including CNNs and Vision Transformers, with similarity search using FAISS and KNN. These components address different parts of the recognition problem rather than asking one model to handle the entire photograph.

OpenCV post-processing prepares predictions for shelf analytics. Flask APIs expose the pipeline, and Docker packages the serving environment. Downstream systems can use the product and availability data instead of interpreting raw model outputs themselves.

A bounding box and a product identity are different predictions

A detector can locate a package accurately while recognition assigns the wrong SKU. Conversely, a classifier can work well on clean product crops while the shelf detector misses partly hidden items. Looking only at one stage obscures that difference.

For this system, YOLO locates products, and classification and similarity search contribute to recognition. The public account names CNN and Vision Transformer models but does not publish their training configuration or fusion rule. The architecture describes those responsibilities without reconstructing confidential implementation details.

Consider two packages that differ only by a small volume label. This fabricated example explains why a crop can contain enough evidence to identify the brand but too little to identify the exact SKU. Lighting, occlusion, and crop resolution affect whether that label is visible at all.

Downstream shelf analytics needs to know the consequence of that uncertainty. An uncertain item, a confidently identified item, and an undetected item represent different evidence about availability. They should not all become the same default SKU.

Use neighbors as evidence, with a clear distance meaning

FAISS provides efficient similarity search over dense vectors. Its documentation describes several index choices, trading search speed, memory, and exactness. This establishes what the library can do; it does not reveal which index or parameters this project used. FAISS documentation.

A feature vector represents a crop in the embedding space created by a model. Nearby reference vectors can supply candidate identities. Whether “nearby” is useful depends on the embedding model, normalization, distance function, and reference data.

The practical comparison is between visually similar candidates. A nearest neighbor always exists when the index is populated, including when the crop is a product the system has never seen. A candidate result alone should therefore not be interpreted as proof of identity.

A public evaluation plan could include known products, similar packaging, unreadable crops, and unknown products. The test would inspect recognition and uncertainty behavior separately. This plan is proposed analysis, not an assertion that the production system uses a specific rejection threshold.

What I would test next

Compare classification alone with the documented recognition approach on fixed labeled crops. Include similar packaging and products absent from the reference index. Report unknown-product behavior separately. Choose any rejection threshold on development data before evaluating held-out cases.

This is a proposed test, not a completed result. A future report needs its fixtures, baseline, and execution evidence.
