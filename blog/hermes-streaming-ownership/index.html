Session ownership and streaming in an AI workspace

Why a browser connection, a user session, and a runtime credential need different identities.

Theeraphan Sukchok · 9 October 2026 · Engineering research note

On this page

Where this question comes from

This note draws on the documented Hermes prototype described in my project materials: a Next.js portal, FastAPI backend, session ownership, runtime streaming, and optional knowledge integration. The default local setup uses mock mode. No new live integration or security experiment was run for this article.

This engineering note develops a testable question from my work. It does not report a new experiment or claim a novel algorithm.

Keep runtime credentials out of the browser

The Next.js portal talks to a FastAPI backend-for-frontend. That backend owns the runtime credential, checks session ownership, and proxies execution. The browser does not need direct access to the Hermes backend credential.

SQLite stores portal records that map users to sessions and agent versions. For conversations, the backend proxies server-sent events from the runtime so the interface can show streamed responses and tool activity. Honcho supplies persistent memory context.

These are application boundaries, not evidence of completed enterprise security. SSO, RBAC hardening, and live multi-user reliability remain work to verify.

Follow a conversation across the boundary

An illustrative conversation begins when a user selects an available team and submits a message. The portal sends it to the application backend, which checks the session mapping and forwards execution to the runtime. The backend then streams runtime events to the interface.

That sequence contains separate identities: the portal user, the conversation session, and the runtime credential. Collapsing them into one browser-supplied identifier would make ownership difficult to enforce. The backend needs to derive access from its authenticated context and stored records.

The prototype's session-ownership checks are useful application behavior, while its local mock mode limits what a demonstration proves. A working interface in mock mode does not validate the real provider's authentication, timing, cancellation, or failure behavior.

A stream is delivery, not a completion record

Server-sent events carry server-to-client messages over an HTTP stream. MDN documents the event-stream format and browser event handling. That helps explain the transport used by the workspace, although this application's authenticated proxy should not be assumed to use a particular browser client simply because SSE is involved. MDN: using server-sent events.

A disconnected tab leaves an important question: did execution stop, or did the user merely stop receiving its events? The interface needs a way to distinguish delivery state from execution state. Reconnecting to a stream should not silently launch a new conversation run.

My proposed integration test would close the client connection during a fake long-running response, inspect the backend and runtime state, then reconnect. The expected behavior needs to be declared before the test: cancellation, continued execution with later inspection, or another explicit policy.

A visible partial answer also needs a status. Treating an interrupted response as a completed answer hides the failure from the user. A completion event or durable run status would provide stronger evidence than the last text token that arrived.

What I would test next

Disconnect the browser during a controlled long-running response. Inspect runtime state and reconnect without starting another execution. Repeat with two users and attempt access to the wrong session. Delivery recovery and permission checks need independent acceptance criteria.

This is a proposed test, not a completed result. A future report needs its fixtures, baseline, and execution evidence.
