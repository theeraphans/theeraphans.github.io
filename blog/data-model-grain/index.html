A shared data model starts with the meaning of one row

Grain, reusable transformations, and the logic behind Power BI totals.

Theeraphan Sukchok · 9 October 2026 · Engineering research note

On this page

Where this question comes from

This note starts from my work with Airflow, dbt, SQL, Docker, and Power BI to provide shared models for reporting and automation. Internal schemas, loading policies, and warehouse details are outside the public record. Modeling and test examples below are illustrative.

This engineering note develops a testable question from my work. It does not report a new experiment or claim a novel algorithm.

From operational sources to shared models

Airflow schedules extraction and loading. SQL and dbt transform the loaded data into warehouse models, and Power BI and automation consume those shared models. Docker packages the pipeline environment so its dependencies are not left to individual machines.

The distinction between a pipeline and a model is useful. A pipeline moves and prepares data on a schedule. A model expresses reusable business logic. A report should consume that logic, not quietly implement a competing version of it.

Decide what one row means

A dashboard can join correct tables and still produce a wrong total. If one order has several lines and several shipment events, joining both detail sets can multiply rows. The problem starts with the meaning of a row, before the chart or calculation is written.

As an illustrative modeling exercise, an order-line dataset and a shipment-event dataset should each declare their grain. A report combining them needs a defined relationship or an aggregation step that preserves the intended totals. This example describes a common design risk, not an incident from the project.

A model contract should state its keys, timestamps, units, and interpretation of missing values. A monetary amount also needs a currency and a decision about whether it represents a quotation, booked order, or another business event. A field called “sales” leaves those choices hidden.

Let each transformation answer a smaller question

dbt's project-structure guide separates staging, intermediate work, and business-facing marts. That provides a useful vocabulary for organizing transformations: prepare source data, compose reusable logic, then expose models for consumers. It is external design guidance, not a claim that this project's internal folders match the guide. dbt project structure guide.

Illustrative layerResponsibilityQuestion to inspect
Source preparationStandardize types, names, and identifiersCan records be interpreted consistently?
Reusable transformationsApply shared relationships and business rulesIs the join grain explicit?
Consumer modelProvide a stable reporting interfaceCan the report explain its totals?

This separation reduces the amount of source-specific knowledge a report needs. It also makes a definition change easier to trace: locate the model that owns the rule, inspect its dependencies, and examine affected consumers.

There is a cost to excessive layering. A model used once and containing no reusable logic may add another file without making the computation clearer. The useful boundary is a responsibility someone can name and verify.

What I would test next

Use one order with several lines and shipment events. Write expected totals before constructing joins, then inspect each consumer result for multiplication. Change one shared definition and trace affected reports. This tests calculation correctness and the ownership of reusable business rules.

This is a proposed test, not a completed result. A future report needs its fixtures, baseline, and execution evidence.
