From a failed agent run to a reviewed version change

Separating execution evidence, failure diagnosis, and promotion in the Agentic AI Platform.

Theeraphan Sukchok · 9 October 2026 · Engineering research note

On this page

Where this question comes from

This note draws on the local runtime loader and the platform architecture notes. The loader prepares flow and team data and exposes routing and completion tools. Evaluation and promotion are separate design responsibilities. Local source inspection does not establish live end-to-end reliability.

This engineering note develops a testable question from my work. It does not report a new experiment or claim a novel algorithm.

Evaluate the version, not just the answer

Evaluation runs beside the core. The design starts with curated cases and reviewable expectations, then executes a selected agent version in a sandbox. Scoring can inspect answer structure, tool evidence, and behavioral constraints separately. A missing tool call and an incorrect answer should not collapse into the same unexplained score.

The improvement loop is harness engineering, not model fine-tuning. It diagnoses failures and proposes changes to the agent configuration. A person reviews the proposed difference before a new version is promoted. Immutable snapshots make the tested configuration identifiable and allow an earlier version to be selected again.

Held-out cases belong outside the diagnosis loop. Expected answers are supplied to scorers, not to the agent prompt. Otherwise an apparently better score could reflect access to the test rather than a better agent.

Separate the failure before changing the prompt

A case can fail because of retrieval, routing, tool inputs, service availability, response formatting, or the evaluator itself. Labeling all of those “prompt quality” can hide an integration bug behind a configuration change.

Here is a proposed diagnostic record. It is an illustrative format, not a published API schema or an actual result.

case_id: shipment-inquiry-example
expected_capability: shipment_lookup
observed_capability: order_lookup
answer_check: insufficient shipment evidence
failure_category: wrong_capability
review_action: inspect routing definition

A deterministic check can identify an absent field or required tool call. A model-based judge can assess answer quality against a rubric, but its judgment should remain attached to the evidence it saw. Disagreement across repeated judgments deserves investigation rather than a precise-looking average.

Candidate and baseline versions should run against the same cases and evaluator configuration. Development cases help diagnosis; held-out cases check generalization. Answer keys must stay outside the agent's prompt and retrieval context. Otherwise the experiment measures access to answers rather than the intended capability.

Conversation history and execution state have different jobs

A transcript records what people and agents said. Execution state records where a workflow is and which results it already has. A generated sentence saying that an action happened is weaker evidence than the business system's acceptance record.

LangGraph documents checkpoints as thread-scoped snapshots that support resuming execution and inspecting earlier state. Long-term stores serve a separate role across threads. This is background for the design, rather than a claim that every persistence feature has been verified in the project. LangGraph persistence documentation.

My proposed recovery tests interrupt a run after a read-only lookup, after an action is proposed, and after an action succeeds but before its response arrives. Each resumed run needs inspection. Repeating a lookup may be acceptable; repeating a customer-facing action may be harmful.

A checkpoint preserves workflow state. An idempotency record answers whether a particular external action has already been accepted. I would verify both with a fake business endpoint that records accepted actions and deliberately delays responses. This is a test plan, not a claim of exactly-once execution.

A tool call needs an authorization decision

The model proposes an operation; the business boundary decides whether the caller can perform it on the requested resource. A valid schema and a human approval each provide useful information, but neither independently establishes permission.

MCP security guidance discusses audience validation and the risks of passing upstream tokens through to unrelated services. Application authorization still needs to constrain the business operation. MCP security best practices.

For an email action, approval should identify the recipient and content that will actually be sent. If the payload changes afterward, the old decision should not authorize the new payload. The execution gateway needs to bind the decision to the operation and reject missing or mismatched authorization. This is a requirement to verify across the project, not a declaration that all paths already satisfy it.

Read operations need ownership checks too. A valid order number is not enough to grant access to another customer's information.

What I would test next

Preserve the baseline version and evaluator configuration. Compare one proposed change on development cases, then use a separate held-out set for promotion. Attach failed cases, tool evidence, and the configuration diff to the review. Inspect judge disagreement rather than treating an average score as sufficient evidence.

This is a proposed test, not a completed result. A future report needs its fixtures, baseline, and execution evidence.

Research context and references
