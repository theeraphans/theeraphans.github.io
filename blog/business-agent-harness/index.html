Beyond the prompt: designing an agent harness for business workflows

A literature-informed proposal for authorization, recovery, and evaluation around business agents.

Theeraphan Sukchok · 9 October 2026 · Engineering research note

What makes an agent safe to use for business work?

An agent can answer a shipment question correctly and still fail the workflow. It might look up another customer's order, send an unapproved message, or repeat an action after a timeout. Answer quality captures only part of that behavior.

This research note asks how to design the software around a language model so business actions remain authorized, inspectable, and recoverable. I use “agent harness” to mean the execution loop, context preparation, tool interfaces, state handling, and evaluation surrounding the model.

This is a selective literature synthesis and a proposed engineering framework. It reports no new benchmark, completed experiment, or novel algorithm. The business examples are fictional. I separate source findings from my interpretation and proposed tests.

Reasoning and acting still need an execution system

ReAct studies interleaving reasoning and actions, using observations from an environment to inform later decisions. Its results concern the tasks and experimental settings in that paper. They do not establish authorization or replay safety in an enterprise integration.

Anthropic's Building effective agents distinguishes predefined workflows from agents that choose their own process and tools. Its engineering guidance favors simple patterns before adding complexity. I read that as a useful design question: which decisions genuinely need model discretion, and which should remain explicit application rules?

Agentic Context Engineering studies adapting context rather than updating model weights. It organizes improvement around generation, reflection, and curation. This provides a research example of revising the material supplied to an agent, but its reported gains cannot be assumed for a different business task or runtime.

Lilian Weng's Harness Engineering for Self-Improvement motivated this reading. This article develops a narrower business-workflow perspective rather than reproducing that post or its figures.

Give each decision an owner

My proposed framework separates the model's proposal from the application's decision to execute it. A model can select a plausible tool and arguments. The gateway still has to validate the operation, establish access to the resource, and enforce any required approval.

BoundaryDecision ownerEvidence
Interpret a requestConversation and agent layerAvailable fields and source context
Propose an operationModel-assisted runtimeTool name and structured arguments
Authorize executionBusiness gatewayCaller, resource, scope, approval
Perform the actionBusiness serviceAccepted action identifier and result
Assess the runEvaluation serviceCase expectations and captured events

These are conceptual responsibilities, not a requirement for five deployed services. A small application can implement them in one process while keeping the decisions distinguishable in code and records.

The separation matters most when the agent changes its plan. If it proposes a different recipient or message after approval, the old approval should no longer match. Permission needs to describe the actual operation, rather than a broad intention such as “help this customer.”

Approval should bind to the payload

Imagine a fictional customer asking for a delivery update. The agent retrieves shipment evidence and drafts an email. A reviewer approves a recipient and body. If the agent later edits either field, the gateway must evaluate the changed operation again.

A proposed approval record would identify the resource, action type, payload digest, expiration, and reviewing identity. At execution, the gateway would compare the current operation with that record and fail closed when permission is missing or mismatched. This is my design proposal, not a claim of a standardized MCP approval format.

The MCP security guidance discusses audience validation and risks such as token passthrough. Protocol authentication is part of the boundary; business-specific ownership and payload rules still need application enforcement.

Read-only operations deserve the same ownership scrutiny. An order lookup can leak private information even when it changes nothing. Authorization should therefore constrain the data returned as well as the actions taken.

A retry needs to know what already happened

The dangerous interruption is an action accepted by the business service followed by a lost response. The runtime sees a timeout, while the destination has already acted. Repeating the request can create a second email, task, or order mutation.

My proposed harness keeps workflow state and accepted action identity separate. Workflow state says where execution stopped. An action record says whether a specific external operation was accepted. Neither a chat transcript nor a generated success message provides that assurance.

A recovery test should deliberately simulate an accepted action followed by a timeout. Resume the run and inspect the destination's action count. Repeat the scenario after changing the payload; that must be treated as a different operation with its own authorization decision.

Exactly-once behavior depends on the destination and integration contract. I would state the observable replay guarantee for each action instead of promising exactly-once execution across unrelated business services.

Compare the harness while holding the model fixed

A useful experiment would compare a baseline tool-calling agent with a candidate using explicit payload authorization, action records, and structured failure evidence. Keep the model version, tool fixtures, case set, decoding settings, and execution budget fixed. Otherwise a change in model capability can be mistaken for a harness improvement.

The test set should include normal lookups, missing fields, unauthorized resources, expired approvals, changed payloads, accepted-action timeouts, and unavailable dependencies. These cases probe distinct properties rather than one broad success score.

MeasureObservable definition
Task completionExpected business outcome is reached
Authorization failureAn unauthorized operation reaches the fake destination
Duplicate actionMore than one accepted action for the same logical request
Evidence completenessRequired operation and result records are inspectable
Cost and latencyMeasured per case under the same budget

Deterministic assertions should check authorization and action counts. A model-based judge may assess answer quality, with an explicit rubric and inspectable inputs. Judge uncertainty should not decide whether an unauthorized action occurred.

Development cases can guide revision. A held-out set should remain outside diagnosis and context updates. Repeated runs help reveal unstable behavior, and failures should remain visible rather than being averaged away. No experiment has been run for this article, so there is no results table.

Use the platform as a place to test the proposal

My Agentic AI Platform separates runtime execution from evaluation and version review. That creates a place to investigate these questions, but an architectural separation alone does not prove the safety properties described here.

The next research artifact should be a small reproducible fixture with a fake shipment service and an email endpoint that records accepted actions. A published run should include the tested configuration, case definitions, event records, and scorer output, with no real customer data.

Context improvement should come after the baseline works. When a candidate changes instructions, compare it against the preserved baseline and the same acceptance criteria. An answer-quality gain that increases unauthorized or duplicate actions would be a failed tradeoff for this application.

What this note leaves open

This is not a systematic literature review. The sources were selected for reasoning-and-action loops, context adaptation, engineering patterns, and protocol security. It does not survey every agent benchmark or establish novelty.

The proposed fixture would test controlled application behavior. Live-provider variation, real identity systems, organizational policy, and production concurrency need separate validation. A passing local test would justify a narrower claim about that fixture, not general enterprise readiness.

The central hypothesis is testable: explicit action boundaries can improve observable authorization and replay behavior under a fixed model and task budget. Until the comparison is run, it remains a hypothesis.
