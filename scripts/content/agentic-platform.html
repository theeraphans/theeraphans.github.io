An agent is more than its prompt

A useful business agent needs to understand a request, find the right information, call a tool, and know when to stop. A convincing answer is not enough if the agent looks up the wrong order or takes an action it should not take.

I started this independent project to make those responsibilities explicit. Rather than building a new application around every agent, I am building a common runtime for agent definitions, business tools, execution records, and version evaluation. The implementation is local; the platform is not presented here as a deployed enterprise product.

Keep the conversation separate from execution

The chat service owns the channel and conversation: receiving messages, maintaining conversation state, identifying an inquiry, and collecting missing information. Once a request is ready, it hands the runtime a task and its context. That separation lets a conversation change channels without making the execution engine responsible for every webhook and messaging format.

The core loads a selected agent configuration and builds its execution graph. Routers and loaders prepare the required data before execution; graph nodes work with the state they receive and return updates. Database access belongs in the preparation layer rather than being scattered through the graph.

An agent definition has distinct parts: persona, rules, skills, and tools. A persona describes its role. Rules set constraints. Skills describe how to approach a task. Tools define which external capabilities it can use. Keeping these separate makes a proposed change easier to inspect than a single growing prompt.

Make business actions visible

The runtime connects to MCP servers instead of embedding every business integration in the agent itself. A tool can expose an order lookup, shipment information, a document operation, or another bounded capability. The public diagram groups those tools; it does not mean each request calls every integration.

The implementation separates read-only data tools from business tools that can change state. That boundary matters because retrieving information and taking an action carry different risks. A tool call should be an inspectable operation with an explicit input, not a side effect hidden inside an answer.

Execution records preserve the run and tool activity. They provide a way to investigate what the agent actually did, beyond reading its final message. This is also the evidence an evaluation service needs when the answer sounds reasonable but the workflow is wrong.

Evaluate the version, not just the answer

Evaluation runs beside the core. The design starts with curated cases and reviewable expectations, then executes a selected agent version in a sandbox. Scoring can inspect answer structure, tool evidence, and behavioral constraints separately. A missing tool call and an incorrect answer should not collapse into the same unexplained score.

The improvement loop is harness engineering, not model fine-tuning. It diagnoses failures and proposes changes to the agent configuration. A person reviews the proposed difference before a new version is promoted. Immutable snapshots make the tested configuration identifiable and allow an earlier version to be selected again.

Held-out cases belong outside the diagnosis loop. Expected answers are supplied to scorers, not to the agent prompt. Otherwise an apparently better score could reflect access to the test rather than a better agent.

What I am working toward

The repository contains runtime, chat, and evaluation services with local implementation and tests. That is different from proving the complete system reliable against live providers and real users. The next step is to verify those boundaries together: the version a run used, the evidence an evaluator captured, and the exact change a reviewer approved.

The goal is a platform where an agent can improve without losing the ability to explain what changed. Execution, evaluation, and promotion remain separate responsibilities throughout that process.
