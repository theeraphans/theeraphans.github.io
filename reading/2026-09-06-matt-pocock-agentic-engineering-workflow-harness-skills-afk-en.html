Matt Pocock's Agentic Engineering Workflow

A practical operating model for keeping humans in charge of strategy while agents execute scoped work through reusable skills, isolated sandboxes, queues, reviews, and feedback loops.

Executive summary

The model is only one part of the engineering system

Matt Pocock's central argument is that the AI coding conversation overweights model capability and underweights everything the engineer can actually control: the harness, task definition, skills, codebase architecture, tests, documentation, execution environment, review process, and feedback loop. A stronger model helps, but a well-designed environment can make a cheaper model productive while a tangled codebase can waste the intelligence of an expensive one.

He describes AI as having absorbed much of tactical programming: producing syntax, tracing a local bug, making a commit, or completing a tightly scoped implementation. The human's leverage therefore shifts toward strategic programming: deciding what should exist, designing boundaries and interfaces, breaking work into independent tasks, establishing tests, prioritizing the roadmap, and judging whether the result serves the product.

The workflow is deliberately human-directed. Pocock prefers user-invoked procedural skills over a large catalog of abilities automatically available to the model. The human chooses when to clarify an idea, write a product requirement, split it into issues, launch an implementation agent, or request review. This preserves judgment and prevents every skill description from consuming the agent's context before the work even begins.

Execution increasingly happens away from the keyboard. Scoped tasks are placed in a queue, picked up by agents running in isolated sandboxes, and returned as commits or pull requests. Human checkpoints move later as evidence and trust improve, but do not disappear blindly. The engineer reviews both the code and the system that produced the code, then converts recurring failures into better tests, instructions, architecture, or automated checks.

Core takeaways

Ten ideas worth keeping

  1. Optimize the harness, not only the model. Models change rapidly; good task boundaries, tests, documentation, isolation, and code structure survive model cycles.
  2. Keep strategic work human-owned. Product direction, architecture, interfaces, priorities, and acceptance criteria are the high-leverage decisions.
  3. Treat domain expertise as an AI multiplier. The quality of delegation and review is constrained by what the operator understands.
  4. Use skills to encode repeatable process. A useful skill makes a method predictable; it should not be a large pile of generic instructions.
  5. Separate procedure from ability. A procedure is intentionally invoked to run a workflow. An ability is selected by the agent when relevant and therefore carries discovery and context costs.
  6. State changes what a skill can do. A teaching skill becomes more valuable when it remembers the learner's mission, progress, misconceptions, and next step.
  7. Make AFK work scoped and isolated. Parallelism comes from safely delegating independent tasks, not from letting an unrestricted agent wander indefinitely.
  8. Think in queues, not magical infinite loops. Real engineering has a backlog, triage states, work ownership, completion signals, and multiple workers.
  9. Review the production system as well as its output. A discovered bug should improve the test suite or harness so the same class of failure becomes less likely.
  10. AI accelerates implementation, not customer discovery. Teams still need direct conversations, product judgment, and the discipline to remove unnecessary features.

Visual workflow

The operating model behind the interview

1 · Intent

Human sets mission and constraints. Define the product problem, the user, the desired outcome, and the boundaries that cannot be delegated.

2 · Clarify

Use an adversarial interview. A short procedural skill such as “grill me” exposes consequential decisions and ambiguity before implementation begins.

3 · Design

Human owns the hard interfaces. Establish architecture, module boundaries, data contracts, risk points, and acceptance tests.

4 · Queue

Turn the design into bounded work items. Issues carry enough context for an independent worker and move through explicit exploration, implementation, and review states.

5 · Execute

An AFK agent works inside a sandbox. It receives one task, runs tools and tests, and returns commits or a pull request without unrestricted access to the host.

6 · Review

Agents prepare evidence; humans judge risk. Automated checks, review agents, screenshots, demonstrations, or narrated videos make inspection faster and richer.

7 · Integrate

Merge only when the defined gate is satisfied. Low-risk changes may become more automated over time; consequential changes retain human approval.

8 · Improve

Feed observations back into the system. Repeated mistakes become tests, clearer skills, better architecture, new security checks, or tighter task templates.

The compact version

Human judgment creates direction. Skills make the process repeatable. Sandboxes contain execution. Queues create scalable coordination. Review produces evidence. Feedback improves the harness.

Strategic programming

AI changes which engineering skills create the most leverage

Pocock borrows the distinction between tactical and strategic programming. Tactical work is close to the code: editing syntax, following an implementation plan, fixing a localized defect, and preparing commits. Strategic work shapes the system over time: deciding the architecture, creating interfaces, making tasks separable, protecting quality with tests, and improving the team's ability to change the codebase.

His provocative formulation is that AI has “eaten” tactical programming. The useful underlying point is less absolute: tactical execution is becoming cheap and parallel, so weak strategic decisions can generate bad software faster than before. An engineer who can define the right task and recognize a correct result can multiply through agents; an operator without those skills may produce more code without producing more value.

Skill design

Three independent questions define an agent skill

The interview uses several overlapping labels, so it helps to separate them into independent axes. First is invocation: who decides to use the skill? Second is state: does the method rely on durable information from earlier sessions? Third is purpose: does the skill coordinate a procedure or supply reusable domain capability?

User-invoked procedure

The operator intentionally starts a known process such as adversarial interviewing, producing a PRD, or splitting a requirement into issues. Pocock prefers this mode because the human remains the workflow driver.

Model-invoked ability

The agent discovers and loads guidance when a task matches, such as React coding standards. This can be convenient, but descriptions must remain visible enough for discovery and therefore consume context.

Stateless skill

Every invocation can begin from the current request and workspace. The skill does not need a personal history to perform correctly.

Stateful skill

The skill keeps a learning record, mission, preferences, or past decisions. The Teach demonstration uses local files so lessons can build on what the learner has already understood.

Knowledge and technique

Reusable facts and practiced methods can be packaged and shared. They raise the team's floor by turning one expert's repeated method into a common workflow.

Contextual wisdom

Knowing when a method applies is harder to encode. Wisdom comes from operating in the real domain, seeing consequences, and making decisions under its actual constraints.

The key design warning is context load. If a platform exposes hundreds of automatically discoverable skills, each description competes for attention before any skill body is opened. A smaller, curated ability set plus explicit procedural workflows is often more predictable than a giant skill marketplace attached to every agent.

Teach skill demonstration

Personalized learning as a stateful agent workflow

Pocock demonstrates a Teach skill by role-playing a novice developer who wants to build a scheduling and practice application for singing students. The initial prompt communicates the mission rather than dictating a curriculum. The agent inspects the workspace, asks what “ship better software” means, records a concrete goal, and chooses Git as the first high-leverage concept because the learner needs a safe way to experiment.

The skill creates local artifacts: a mission document, reference material, a learning record, and an HTML lesson. The browser presentation supports explanations and exercises more naturally than a terminal stream. Short retrieval questions then reinforce concepts such as status, staging, commits, and restore. Progress is not inferred from exposure alone; the skill records what was taught and uses that state to choose the next reachable lesson.

This example reveals a broader pattern for cognitive skills. Good personalization is not merely inserting a user's name into a prompt. It needs a durable model of purpose, current capability, evidence of understanding, misconceptions, resources already used, and the next appropriate challenge.

Harness over hype

Improve the environment that receives the model

The hosts challenge Pocock's emphasis on the harness: if a new model is materially better, why not optimize the system and use the strongest model? He agrees model quality matters, but argues the attention split should be closer to 50/50. Builders cannot control frontier-model progress; they can control whether their repository is understandable, changes are localized, tests provide feedback, and an agent can recover from mistakes.

A well-structured codebase reduces token cost indirectly. The agent spends less time searching, encounters fewer accidental dependencies, and needs fewer attempts. The team may then use a less expensive model for bounded execution. A poor codebase has the opposite effect: it demands more intelligence merely to overcome preventable ambiguity.

Pocock acknowledges the “bitter lesson” counterargument that raw compute eventually beats hand-crafted optimizations. His response is pragmatic rather than predictive: build on software principles that have remained useful for decades, keep the workflow agent-agnostic, and benefit from new models when they arrive without redesigning the organization around every release.

AFK execution

Parallelism comes from independent work, isolation, and clear return artifacts

Pocock uses Claude Code locally for planning and some implementation, but much of his work runs AFK, meaning away from the keyboard. His Sandcastle project launches coding agents inside isolated sandbox providers such as Docker, Podman, or remote environments. Agents can work in parallel without sharing the developer's unrestricted host environment, then return commits to the real repository.

GitHub Actions provides the coordination surface. A pull request can trigger a review agent that checks the branch, runs tests and type checks, inspects the changes, and reports a verdict. The important architectural unit is not “an autonomous AI developer.” It is a scoped worker with defined input, a constrained environment, observable activity, and a concrete handoff artifact.

Why the sandbox matters

AFK autonomy without isolation turns productivity into host, credential, and data risk. The sandbox is not decoration; it is the boundary that makes parallel unattended execution operationally reasonable.

Queues, not infinite loops

Software work already has a scalable coordination model

Pocock pushes back on the fashion for endless agent loops. Human-in-the-loop sessions remain useful for planning, discovery, and unclear work. AFK agents are valuable when the work is sufficiently scoped. But repeatedly calling an agent forever is not the essence of an engineering organization.

He prefers the queue metaphor. Issues enter a backlog, receive triage, and move through exploration, implementation, review, and merge. Multiple human or agent workers can pick up eligible tasks. Labels can trigger automated stages. A task returns to the queue when more information or approval is needed and leaves when its completion condition is satisfied.

This model preserves human prioritization. Automation can enrich an incoming bug report with reproduction steps, codebase exploration, a candidate fix, tests, and a risk assessment before the person sees it. The human checkpoint moves to the right: instead of beginning with a raw report, the reviewer begins one informed decision away from resolution.

Review and self-improvement

The goal is not zero review; it is higher-value review

Review protects production from harmful changes, but it also teaches the team how well its engineering system works. Automatically merging trivial changes may be reasonable once risk is measurable, yet teams should still sample decisions and inspect whether the automation's classification remains trustworthy.

The review artifact itself can improve. For front-end work, an agent might attach screenshots or record a short walkthrough with generated narration. For infrastructure, it might attach test evidence, a risk summary, and an explicit rollback path. Rich evidence reduces the amount of code a human must reconstruct mentally.

When a stronger model uncovers a hidden security bug, the lesson is not only that the model is impressive. The team has discovered a missing system control. The durable response may be a regression test, scheduled security review, architecture change, or new review skill. This is how the harness becomes self-improving rather than permanently dependent on one exceptional model run.

Agent experience

Good developer experience and good agent experience overlap

Pocock distinguishes developer experience, or DX, from agent experience, or AX. A repository with clear names, small modules, explicit contracts, quick tests, reliable commands, useful errors, and focused documentation helps both people and agents. Senior developers often understand how to create good DX; AI-native juniors may be unusually comfortable experimenting with tools and harnesses. Strong teams need both perspectives.

This reframes the junior-versus-senior debate. Experience without experimentation may underuse the new leverage. Enthusiasm without software fundamentals may generate fragile systems. The valuable combination is curiosity about AI plus the discipline to improve the environment in which AI works.

Product fundamentals

Faster implementation does not discover what customers need

On the future of software businesses, Pocock is deliberately conservative. Teams must still talk to customers, identify a painful problem, test prototypes, and decide what not to build. AI makes implementation dramatically cheaper and can automate parts of research and delivery, but it does not eliminate the need for firsthand understanding or original product judgment.

The human should remain accountable for the vision and feature choices. A useful use of AI is often subtraction: simplify the product, improve the experience, and focus on the job customers actually value. Delegating the roadmap to a model risks building a larger but less coherent application.

Translation for an agentic AI platform

What this means for Master Agents, Sub-Agents, Skills, and MCP

Master Agent

Model it as a queue-aware coordinator, not an omniscient personality. It should preserve mission, priorities, task states, acceptance criteria, and escalation decisions while delegating bounded work.

Sub-Agent

Define workers by role and completion artifact: explorer returns findings, implementer returns commits, reviewer returns evidence and a verdict. Independence and failure containment matter more than elaborate personas.

Procedure Skill

User- or workflow-invoked orchestration such as clarify, plan, decompose, implement, or review. Give it explicit steps and checkpoints; keep it out of every context until invoked.

Ability Skill

Model-discoverable guidance such as coding standards or domain rules. Keep descriptions precise and the active catalog small enough that discovery does not overwhelm working context.

Stateful Skill

Store durable mission and progress separately from transient prompt context. Define ownership, update rules, provenance, and how stale memory is corrected.

Tool / MCP

Expose constrained capabilities with scoped credentials and structured results. Availability should follow the worker's role and task, rather than attaching every connector to every agent.

Sandbox

Make isolation a runtime policy for AFK execution. The worker receives only the repository, network access, secrets, and compute required for its task.

Business Flow

Represent work as a state machine or queue: entry criteria, allowed transitions, worker role, expected artifact, automated checks, human gate, retry policy, and terminal states.

Observability

Show not only model traces but workflow movement: why a task became eligible, who picked it up, what evidence was produced, which gate approved it, and what system improvement followed a failure.

For BA users, the creation experience should begin with mission, outcome, constraints, risk, evidence, and escalation. The platform can derive agent roles and tool access from those fields. Beginning with a long persona prompt asks the BA to design model behavior before defining the business contract.

Critical assessment

What is durable, what is opinion, and what needs caution

The strongest part

The interview's most durable contribution is the systems view. Agent performance is a property of the model plus the environment, task, tools, feedback, architecture, and reviewer. The queue model also fits real organizational behavior better than narratives about a single autonomous loop completing an entire product.

The claims to treat as provocation

Statements that tactical programming is “gone” or that hiring juniors no longer makes sense are intentionally forceful and should not be read as settled labor-market evidence. Tactical understanding remains necessary for debugging, security, review, maintenance, and learning. A junior with mentorship can develop strategic judgment; eliminating junior pathways can weaken the future senior pipeline.

The model-versus-harness tension is not either-or

A superior model can reveal problems a narrower process never asked about. A stronger harness can make those discoveries systematic, cheaper, and auditable. The practical strategy is to use capable models while continuously turning their surprising successes and failures into durable engineering controls.

Automation must remain risk-based

Moving human review later is sensible when changes are reversible, tests are strong, and the blast radius is small. Credentials, production deployment, customer communication, financial actions, and data access require independent policy enforcement. An agent deciding that its own action is safe is not a sufficient control.

My synthesis

The winning workflow is not “let the agent code everything.” It is a managed learning system in which humans choose direction, agents create parallel execution capacity, and every review improves the environment for the next run.
