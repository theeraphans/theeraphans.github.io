Go Together: Language Evolution, Agent Architecture, and 9x Cheaper Inference

Arise Tech Meetup #9 connects three engineering layers: how Go evolves without abandoning simplicity, how Google ADK composes code-first agent systems, and how LINE MAN Wongnai removed hidden concurrency waste from a production ranking service.

Executive summary

Good engineering removes accidental work at every layer

The meetup's three sessions appear separate, but they share one principle. Go 1.27 removes language friction while preserving compatibility. Google ADK provides reusable agent lifecycle and orchestration primitives so teams do not rebuild sessions, events, tools, and workflows. LINE MAN Wongnai's inference optimization eliminates concurrency the application never needed.

Session 1Go evolves carefully

Generic methods, stricter and faster JSON, SIMD, post-quantum signatures, UUIDs, and runtime diagnostics extend the language without turning it into another language.

Session 2Inference needs resource ownership

A ranking request accidentally created thousands of threads. Explicit worker and model ownership reduced resource usage by roughly 9x.

Session 3Agents become software architecture

ADK composes LLM, workflow, custom, and remote agents around shared event, session, tool, MCP, and A2A contracts.

The final Q&A supplies the most important qualification: cheaper generation does not remove software engineering. LLMs can write a large amount of code without understanding the business domain. The hard problem increasingly becomes how to verify and validate behavior, preserve maintainability, and know what “good” means.

The combined lesson

Use abstractions to eliminate incidental complexity, but keep ownership of scheduling, state, business meaning, and evidence explicit. Performance and correctness both collapse when hidden defaults multiply.

Session one · 00:00

Exploring What's New in Go 1.27

Jirapat “Nat” Klaokliang begins from Go's identity: readable syntax, a useful standard library, built-in testing, static binaries, concurrency, and a culture that values long-lived engineering over feature volume. His framing is that Go has not abandoned this identity; it has evolved in response to real ecosystem pressure.

Generic methods complete a previously awkward design

Go 1.18 introduced generic types and functions, but generic operations often had to live as package-level functions. Go 1.27 allows methods to declare their own type parameters. Operations such as map, filter, reduce, or typed random-number generation can now live in the namespace of a receiver and support more natural chaining.

This does not make every fluent abstraction idiomatic. Interface methods still cannot declare type parameters, and a generic method cannot satisfy an ordinary interface method through magical inference. The feature improves expression while retaining constraints that keep dispatch understandable.

JSON v2 separates syntax from semantics

The original encoding/json API accumulated compatibility constraints: ambiguous errors, permissive duplicate keys, invalid UTF-8 handling, type-dependent omitempty, and performance limitations around custom marshalers. Go 1.27 stabilizes encoding/json/v2 and the lower-level streaming encoding/json/jsontext.

Stricter inputReject invalid UTF-8 and duplicate names.

Inputs that v1 might silently accept can become explicit errors under v2 defaults.

Configurable semanticsOptions replace hidden behavior.

Callers can control unknown members, name matching, formatting, and migration compatibility.

Streaming coreTokens and values avoid unnecessary copies.

The syntax layer can process JSON incrementally without round-tripping whole byte slices.

MigrationCompatibility remains a product constraint.

V1 remains supported and is backed by the newer implementation; tests should reveal observable differences such as error text.

Runtime, security, and performance additions

  • SIMD: experimental portable and architecture-specific vector APIs expose data-parallel hardware while acknowledging that the interface is not yet stable.
  • Goroutine-leak profile: production diagnostics can identify goroutines blocked permanently instead of treating rising counts as a mystery.
  • Small allocations: size-specialized allocation can reduce cost for objects below roughly 80 bytes.
  • ML-DSA: the standard library adds a post-quantum signature scheme integrated with X.509 and TLS.
  • UUID: generation and parsing move into the standard library.
  • Modernizers: go fix can update patterns for atomic types, embedded literals, backward slice iteration, and unsafe functions.

Nat's takeaway is not a checklist of shiny features. Studying the release shows how tool designers balance performance, ergonomics, compatibility, and future direction. Language economics matter: evolution must make code easier to understand without imposing migration for its own sake.

Session two · 35:41

How LINE MAN Wongnai reduced ML inference resource usage by 9x

Korntewin Boonchuay presents a production ranking service. A user searching for “fried chicken” first passes through geographic and business filtering, leaving roughly 1,000–2,000 restaurants for a machine-learning model to rank. The public surface is an ordinary gRPC endpoint; behind it sits a large amount of numerical work using an ONNX model.

The failure was multiplicative concurrency

The service split candidates into roughly 40–50 batches. Each ONNX Runtime inference session could then create around 60 execution threads. One request therefore generated about 3,000 runnable threads; ten concurrent requests could imply tens of thousands. Much of the time was spent scheduling, copying, and moving data rather than computing scores.

Request1 search

Rank a candidate set for one user.

Partition40–50 batches

Split 1,000–2,000 restaurants.

Runtime~60 threads each

ONNX applies its own parallelism.

Explosion~3,000 threads

Nested concurrency overwhelms useful work.

ContentionCopy and schedule

CPU time shifts from inference to coordination.

Go's scheduler multiplexes goroutines onto operating-system threads. It can manage large numbers of goroutines, but it cannot make oversubscribed native threads free. Cgroup CPU limits and container quotas do not automatically teach every native library the correct parallelism level.

The fixes were architectural, not exotic

ONNX configurationLimit intra-op threads.

For the small tree-based model, forcing one thread per inference avoided pointless internal fan-out. Larger transformer models would need independent measurement.

Worker poolBound application concurrency.

A fixed queue and worker count make demand explicit and prevent each request from inventing a new scheduler.

Actor-style ownershipKeep mutable model state local.

A worker or actor owns its session and receives jobs, reducing locks, accidental sharing, and repeated initialization.

Faster support pathsOptimize serialization and math.

JSON implementation choices and SIMD can help, but only after removing the larger concurrency error.

The reported result is roughly a ninefold reduction in resource use for this workload. It should not be generalized to every ONNX service: model shape, operators, batch size, CPU topology, NUMA placement, latency SLO, and request mix determine the best configuration.

Performance lesson

Before changing models or buying more machines, draw the concurrency tree. Multiply request concurrency, application batches, model sessions, and library threads. Hidden parallelism is often more expensive than insufficient parallelism.

Session three · 64:57

Building AI Agents with Google ADK for Go

Pallat “Yod” Anchaleechamaikorn introduces ADK as a code-first toolkit rather than a low-code canvas. It supplies lifecycle and orchestration pieces around an LLM: tools, session state, events, callbacks, deployment hooks, evaluation surfaces, and communication with other systems.

Four agent forms share one contract

LLM agentThe model chooses and uses tools.

Descriptions of available functions enter context so the model can decide when and how to call them.

Workflow agentControl flow is deterministic.

Sequential, Parallel, and Loop agents compose known execution structures without asking an LLM to rediscover orchestration.

Custom agentGo code owns behavior.

Teams implement domain-specific control while conforming to the same agent and event interfaces.

A2A agentA remote agent becomes a node.

Agent-to-Agent communication lets separately deployed systems collaborate behind a common abstraction.

ADK's newer graph composition lets these forms become nodes in one directed workflow. An LLM agent can choose a path, a sequential agent can enforce order, a parallel agent can fan work out, a loop can retry until a condition is met, and a custom node can apply strict business rules.

Session and event are the runtime spine

A raw language model has no durable conversational memory. ADK's session holds state and event history; events communicate what happened and what should happen next. Callbacks intercept lifecycle moments for logging, policy, mutation, or observability.

This event-driven design is more important than the convenience API. It makes long-running work inspectable and gives state transitions a place to live. Teams should still define what state is authoritative, who can update it, how long it persists, and how it is recovered after failure.

MCP and A2A solve different boundaries

MCP connects an agent to tools and resources. A2A connects one agent service to another. A subagent does not need to be remote or use A2A; it can be an in-process LLM, workflow, or custom agent. Conflating these layers creates needless network complexity.

Agent testing

Agent outputs cannot be tested like fixed strings

In Q&A, the audience asks whether agent unit tests can lock an expected response pattern. The answer is largely no: generative outputs vary, and even semantically correct answers may differ in wording or trajectory. This does not mean agents are untestable.

  • Unit-test deterministic tools, validators, state transitions, and routing conditions normally.
  • Use fixed fixtures and fake models to test orchestration and error paths.
  • Evaluate outputs against semantic rubrics, required facts, prohibited actions, and evidence.
  • Record tool trajectories, cost, latency, retries, and termination behavior.
  • Run regression datasets across model and prompt versions.
  • Keep critical side-effect checks at the tool gateway rather than trusting model output.

The speaker jokes that teams may need an “AI test engineer.” Beneath the joke is a real role: generated behavior requires evaluation engineering, observability, simulation, and failure analysis—not only prompt writing.

Panel and Q&A · 96:00

AI makes generation cheap; software engineering defines what survives

The closing discussion challenges several common habits. Developers ask an LLM to rerun a deployment every time instead of having it write a reusable script. They generate tests without giving the agent a feedback loop. They accept controller-service-DAO scaffolds that contain no business language. They generate documentation that neither the author nor reader truly understands.

The panel argues that engineering knowledge remains necessary because neither the customer nor the AI begins with a complete specification. A model guesses from incomplete context; a human who does not understand the domain may merely agree with a plausible guess. The result can be structurally neat software that fails to express what the business does.

Go is presented as training for this judgment. Its design repeatedly asks whether code will remain understandable for ten years, work across cores and machines, compile across architectures, and omit syntax that does not earn its cost. AI changes implementation speed but not those questions.

The hardest SDLC problem

Generating software is becoming easier. Proving that it is the correct software remains difficult. Verification asks whether the implementation satisfies its specification; validation asks whether the system solves the real user problem. AI can help with both, but cannot invent a trustworthy oracle from missing business knowledge.

Synthesis

Three layers, one engineering discipline

LanguageMake correct code easier to express.

Go evolves APIs and runtime support while preserving compatibility and clarity.

RuntimeMake resource use explicit.

Bound concurrency and assign ownership instead of stacking invisible schedulers.

Agent systemSeparate reasoning from control flow.

Use LLMs where judgment is needed and deterministic workflows where order is known.

QualityMake evidence part of delivery.

Tests, evals, business language, traces, and validation convert generated output into trusted software.

All three sessions oppose accidental complexity. Generic methods remove awkward package functions. Worker pools remove thread explosions. ADK removes repeated orchestration code. But abstraction is safe only when its semantics and operating limits remain visible.

Practical playbook

Apply the meetup to production systems

  1. Run the full test suite before adopting Go 1.27 because JSON errors and edge semantics may change.
  2. Use JSON v2 strictness intentionally at trust boundaries; reject duplicates rather than silently choosing a value.
  3. Treat experimental SIMD APIs as measured optimizations, not default architecture.
  4. Monitor blocked goroutines and native threads separately.
  5. Map every concurrency layer from incoming request to model operator.
  6. Set ONNX Runtime thread counts from model benchmarks and container CPU limits.
  7. Use bounded worker pools for backpressure and predictable capacity.
  8. Reuse model sessions where safe and give mutable resources one clear owner.
  9. Choose LLM, workflow, custom, or A2A agents based on where uncertainty lives.
  10. Use MCP for tools and A2A for remote-agent boundaries; do not force all subagents over a network.
  11. Test deterministic agent infrastructure normally and evaluate probabilistic behavior with rubrics and datasets.
  12. Require business-domain concepts in architecture and documentation.
  13. Convert repeated agent work into scripts or tools when reasoning is no longer needed.
  14. Scale verification and validation faster than code generation.

Takeaways

Twelve ideas worth keeping

  1. Go evolves by reducing friction without abandoning compatibility.
  2. Generic methods improve composition but do not remove interface constraints.
  3. JSON v2 trades permissive ambiguity for configurable, stricter behavior.
  4. SIMD should follow profiling and remain isolated behind stable APIs.
  5. A goroutine and an operating-system thread are not the same resource.
  6. Nested parallelism can turn one request into thousands of threads.
  7. Explicit runtime configuration can outperform expensive infrastructure changes.
  8. Worker pools provide backpressure, bounded concurrency, and capacity clarity.
  9. ADK separates LLM reasoning from deterministic workflow structure.
  10. MCP connects tools; A2A connects independently deployed agents.
  11. Probabilistic output changes the test oracle, not the need for testing.
  12. Verification, validation, and business understanding become more valuable as generation gets cheaper.
