Synthesis

The shared lesson: production agents need flow control, not only smarter chat instructions

The LangGraph, MCP, OpenAI Agents SDK, Azure AI Foundry, Camunda, and human-in-the-loop videos all converge on the same point: real agents need state, tool boundaries, approvals, auditability, evaluations, and inspectable orchestration.

01

The Master Agent should be a router

Its job is to choose the flow, hold conversation state, route to specialists, and escalate when needed. It should not own every tool or execute every business action.

02

Sub-Agents are graph nodes

Think in LangGraph terms: an agent is a node, an edge is a routing condition, and state is the shared memory passed through the workflow.

03

A Skill is a contract, not a loose instruction

Each skill needs inputs, output schema, owner, risk level, allowed tools, eval cases, and failure modes so it can be reused and governed.

04

MCP is the tool and context layer

MCP reduces the N x M integration problem by letting agents connect to servers that expose tools, reusable context, and resources through a standard interface.

05

Human-in-the-loop belongs at the action boundary

Approval should be tied to risky tools or actionable skills such as refunds, payments, CRM updates, and outbound messages, not only to an agent persona.

06

BAs should author Flow Markdown

Business analysts should compose flows, policies, exceptions, and eval scenarios in a structured markdown format that the platform can compile.

The Recommended Framework

Workflow-first + Graph Orchestration + Router Master Agent + Specialist Sub-Agents + Skill Registry + MCP Tool Registry + HITL Gate + Simulation/Eval before release.

Patterns

Patterns that should become team standards

The research points to six recurring patterns that are useful for understanding how production agent systems are usually shaped.

Pattern Use when Platform rule
Graph-based orchestration The flow has multiple agents, branches, loops, or escalation paths. Every production flow should compile into a graph with nodes, edges, state, and checkpoints.
Router Master Agent The system must receive user intent and choose a flow or specialist. The Master Agent should not directly hold high-risk action tools except read-only or routing tools.
Skill Contract A capability should be reused across flows or agents. Every skill needs input/output schema, owner, risk level, allowed tools, and eval cases.
MCP Tool Registry The system connects to external services such as CRM, payments, databases, search, or ticketing. BAs choose tools through business-friendly cards; engineers publish schema, auth, policies, and audit fields.
HITL Tool Wrapper A tool has real-world impact such as moving money, changing records, or sending messages. Risky tools should be wrapped with approval objects that support accept, edit, respond, and reject.
Deterministic shell + agent task Most of the process is predictable, but some steps need reasoning. Keep the deterministic flow as the outer structure and place agent tasks only where interpretation is needed.

Decision Guide

How I would turn this research into platform decisions

These are the product and architecture ideas I would keep in mind after reading the research.

Let BAs build flows, not raw agent instructions

The BA surface should feel like a flow builder, markdown editor, and scenario editor, not a raw configuration playground.

Make agent behavior generated from governed flow artifacts

Runtime instructions should come from approved flow definitions, agent contracts, skill policies, and tool boundaries so governance can work.

Separate cognitive and actionable skills strictly

Cognitive skills reason and classify. Actionable skills require tool bindings, risk policies, approval gates, and audit logs.

Put tool approval at the wrapper level

Because MCP tools may come from many servers, governing them at the tool registry is safer than patching every agent instruction.

Use simulations as release gates

Every flow should include BA-authored scenarios and regression checks before release, especially for payments, identity, and compliance.

Avoid free-form swarm patterns first

Free-form multi-agent systems can look impressive in demos but are hard to debug. Start with graphs, state, handoffs, and escalation.

Final Recommendation

Build the platform around four registries: Flow Registry, Agent Registry, Skill Registry, and Tool/MCP Registry. Then force every release through one Simulation Registry and one Audit Trail.
