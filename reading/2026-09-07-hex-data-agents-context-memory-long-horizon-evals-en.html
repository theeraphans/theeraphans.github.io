How Hex Builds Data Agents That Learn Over Time

Izzy Miller explains why data analysis is harder to verify than coding, how Hex is unifying separate agents around capability bundles, and why honest evaluation must measure whether an agent improves across weeks of messy organizational work.

Izzy Miller with Harrison Chase LangChain · Max Agency 68m 20s Summary run September 7, 2026 · 14:46 ICT

This is an editorial paraphrase of the complete public English transcript. Product behavior and benchmark results are reported by Izzy Miller; the architecture recommendations and critical assessment are additional analysis.

Executive summary

A data agent must investigate, not merely translate a question into SQL

Hex began with single-shot text-to-SQL inside individual notebook cells. That was impressive in the GPT-3.5 era, but it constrained the model to a tiny part of the user's actual job. Real analysis is iterative: an intermediate answer changes the next question, a surprising segment suggests another cut, and an implausible metric should trigger an investigation rather than a polished chart.

The Notebook Agent expanded AI from one cell to the whole project. It can create and execute SQL or Python cells, build charts, investigate data, and produce a notebook that remains a usable artifact. Hex later built Threads for conversational self-service and an agent for semantic-model authoring. Those initially separate systems are now converging because users reasonably expect similar-looking assistants in one product to possess the same capabilities and context.

Underneath, the agent loop is comparatively simple: a model repeatedly calls tools. The hard engineering is the harness around it—context harvesting, capability selection, tool design, orchestration, termination, compaction, user experience, observability, and evaluation. Hex's toolkit had grown to nearly 100,000 tokens of tool definitions, forcing the team to add retrieval and consolidate overly granular operations.

The deepest problem is verification. Code can often be compiled and tested. A data query may run successfully while using the wrong metric definition, joining at the wrong grain, or producing a fantastical result that the model accepts. Hex therefore combines governed semantic context, post-run issue detection, human feedback, and deliberately difficult evals. Its experimental Metric City benchmark simulates 90 days of changing data, stakeholder requests, mistakes, and accumulated agent knowledge to test whether the system compounds rather than merely answering once.

Central thesis

A production data agent is not a text-to-SQL model. It is a governed learning system that turns organizational context into analysis, leaves inspectable artifacts, detects conflicts and implausible results, and improves through a measured feedback loop.

Product evolution

From cell completion to project-level agency

Stage 1Single-shot cells

A user opened a SQL cell, described a query, and received code inside that cell. The scope was explicit and controllable, but every broader analysis had to be broken into tiny prompts by the user.

Stage 2Notebook Agent

As models improved, Hex gave an agent access to the notebook's existing capabilities and project context. A user could request a complete feature-adoption report and let the agent work through subquestions for roughly twenty minutes.

Stage 3Threads

Threads offers a chat-like interface for people who want an answer without seeing SQL or Python. It still creates interactive data artifacts, but abstracts the implementation and prioritizes lower cognitive overhead.

Stage 4Semantic authoring

A specialized agent writes semantic-model YAML and harvests evidence from notebooks, conversations, warehouse metadata, and other workspace artifacts so institutional knowledge can move upstream into governed definitions.

Stage 5Unified capabilities

Rather than preserving arbitrary differences between agents, Hex is reorganizing tools, prompts, static context, and completion behavior into capability bundles that can be exposed in the appropriate interface.

The UI may remain different because notebook builders and self-service business users have different needs. Unification concerns what the agent can know and do, not necessarily forcing every user into one screen.

Domain difference

Why data agents are harder to verify than coding agents

DimensionCoding agentData agent
Typical pathPlan, implement, run tests, accept or rejectExplore, interpret, branch, revise the question, compare explanations
Executable proofCompilation and tests can verify many requirementsA successful query proves execution, not that the metric or interpretation is correct
Ground truthOften encoded in specifications and behaviorMay vary by team definition, time period, data freshness, and business context
Useful artifactA code change and test evidenceA reproducible notebook, query, chart, narrative, caveats, and follow-up path
Critical failureSoftware does not behave as requestedPlausible analysis confidently explains an invalid number

A strong analyst has a sense of when a result is strange. The agent must know when to distrust its own output, investigate the data-generating process, and ask a clarifying question. This “analytical instinct” is harder to reduce to a deterministic checker than a unit test.

Under the hood

The loop is simple; context and control are not

Hex describes its core agent as an LLM in a tool-calling loop, surrounded by an opinionated harness. Context is divided into static and dynamic sources. A capability bundle can include tools, prompts, static instructions, contextual access, and small but consequential policies such as what the system should do on its final turn.

02Harvest context
03Select capability
04Investigate

Context harvestingAssemble the relevant world

Potential sources include warehouse structure, semantic models, project cells, prior notebooks, Threads conversations, administrator guidance, and other artifacts. A context agent helps synthesize this graph rather than dumping everything into one prompt.

TerminationMake the final turn explicit

Hex enforces a hard iteration ceiling. If the agent is still working when it reaches the limit, the harness forces an appropriate wrap-up. As models handle longer work and compaction improves, old limits can become constraints that suppress useful behavior.

OrchestrationSupport durable tasks

Hex migrated from a single-shot, bulk-queue architecture to a Temporal-based system for long-running workflows. The transition required running old and new systems together, but enabled a wider family of agents.

Compensating machineryDelete it when models outgrow it

Older models confused long artifact IDs in projects with 50–60 cells, so Hex built a complex reference registry mapping short identifiers to real IDs. New evals indicate modern models no longer need it, turning a once-essential innovation into technical debt.

Harness components have a half-life. Every workaround should carry the eval that justified it—and a removal test for the day the model no longer needs it.

Tool architecture

Nearly 100K tokens of tools exposed the cost of capability sprawl

At the time of the interview, Hex had almost 100,000 tokens of tool definitions in its toolkit. Some of that represented genuine product complexity; some was accidental fragmentation, such as separate create-chart, update-chart, and delete-chart operations whose repeated descriptions consumed context.

Two responses helped. First, tool search or retrieval lets the model discover relevant operations without loading every definition at once. Second, evaluation showed that several normalized operations could be consolidated into a more general chart tool without degrading results.

Yet the answer is not to expose only arbitrary Python or shell execution. Specific tools encode behavioral policy: when an action is appropriate, what must be persisted, which outputs are visible, and what evidence returns to the user. The right boundary balances expressive power with predictable behavior.

Persistent operationsBuild the visible notebook

Most generated SQL and Python becomes a cell. The user can inspect it, rerun it, modify it, and turn the notebook into a report or application.

Ephemeral operationsInvestigate before committing

Small hidden SQL queries help inspect tables, data types, joins, and candidate sources. This can make the first visible query cleaner, but models may over-investigate or answer from hidden work without showing durable evidence.

RetrievalLoad capabilities progressively

Search over tools and guide-like skills reduces prompt pressure. The model sees enough metadata to select a capability, then loads the fuller instructions only when needed.

EvaluationProve consolidation is safe

Tool cleanup should be evaluated against representative trajectories. A smaller schema is valuable only if the agent still chooses the right operation and produces equivalent artifacts.

Agent experience

Transparency is a UX problem, not the same as correctness

Hex shows working activity while an agent runs and collapses it after completion. That helps users understand why a long task is taking time without leaving a wall of tool calls permanently open. But faster models and heavy parallelism may soon make turn-by-turn animation impossible to follow.

For technical notebook users, visible code supports inspection. For a business stakeholder who does not read SQL or Python, “show your work” can create the appearance of rigor without meaningful verification. Hex aims for the lowest cognitive-overhead answer appropriate to the request: a simple fact may need a concise response, while a complex question may require a reproducible report with charts and caveats.

The important distinction is:

  • Activity transparency explains what the agent is doing now.
  • Artifact transparency preserves queries, transformations, and results for inspection.
  • Verification establishes that definitions, data, joins, and conclusions are trustworthy.

Context governance

Semantic models create rails; memory can introduce conflict

A well-designed semantic model is Hex's strongest route to reliable self-service. Governed measures, dimensions, relationships, and approved assets constrain the agent to trusted organizational definitions. However, real analysis sometimes must go beyond the semantic layer, and even governed models can be incomplete or misused.

Hex's Context Studio gives data administrators a higher-level view of questions, answers, and suspicious outcomes. Separate model-based judges flag possible confusion or conflicts with the semantic model. The current loop is mostly post-action: a user may receive a wrong answer, the issue is surfaced to the data team, and the team improves a guide, model, or warehouse description so the failure is less likely to recur.

Personal memory complicates this hierarchy. A user may tell the agent that a metric has a particular meaning, but that claim could be wrong or stale. If user memory, team guidance, and admin-governed definitions disagree, models may spend dramatically longer reasoning and enter a collapse mode. In one Hex test, injecting contradictory context caused a normally efficient model to deliberate for about thirty minutes.

Evaluation

Most data evals test syntax or trivia, not analytical judgment

Miller argues that an eval set becomes weak when nobody actively maintains it. Common defects include incorrect ground truth, buggy deterministic graders, unrepresentative questions, and many near-duplicate cases built around one obscure rule. A benchmark may claim to measure data analysis while actually measuring SQL syntax, retrieval, or whether the model noticed a single sentence buried in documentation.

Hex prefers smaller aspirational suites whose failure modes the team can hold in its head. Difficult sets contain roughly 30–50 handcrafted cases and run multiple repetitions. A representative Notebook Agent eval may begin halfway through a complex project with the user's observation that a number looks wrong. The notebook contains a chain of three interacting bugs; fixing the visible one can obscure the other two. Success requires investigation, not direct translation.

The 900% quota trap

One eval starts from a real internal sales dashboard and introduces a fan-out join bug. Every account executive appears to achieve at least 900% of quota, with some above 1,200%. Asked how the top performers are doing, tested models celebrate an extraordinary quarter. Miller could raise the figures into the thousands before models expressed data-quality suspicion, and none independently found the join error. Yet after a human says “that does not seem right,” the model locates the bug within seconds.

This gap reveals a central weakness: models can debug effectively once doubt is supplied, but often fail to generate the doubt themselves. Human analytical instinct remains valuable not only for solving a problem, but for recognizing that a problem exists.

Two eval layers

Hex maintains ordinary cases with known answers to catch regressions and compare product changes. It also keeps aspirational cases that current systems perform poorly on. The first protects production quality; the second points research toward capabilities that do not yet exist.

Long-horizon evaluation

Metric City asks whether the agent compounds over 90 days

Point-in-time benchmarks ignore the proposed value of an organizational agent: it should learn the company's data, recurring problems, conventions, and history. Miller's experimental Metric City environment evaluates this longer arc.

Day 0Messy warehouse
DailyDBT updates
EventsProducts & fraud
TicketsStakeholder asks
LearningWiki & notes
Day 90Hard questions

The fictional company, Shoreline Commerce, has a realistically sized Snowflake warehouse with deliberately injected nulls, broken joins, confusing columns, partial semantic modeling, and other data-quality traps. Each simulated day advances the clock and reruns DBT models. New rows arrive, products launch, fraud occurs, systems break, and stakeholder tickets ask questions or provide information.

After replying to a ticket, the agent can end the turn or perform proactive knowledge work: follow a loose thread, document a discovery, or clean the wiki. By day 90, the benchmark questions are designed to be answerable if the agent accumulated and retrieved the right knowledge. In the reported experiment, Sonnet 4.6 rose from roughly 4% on day zero to 24% on day 90—evidence of learning, but far below the theoretical 100% target.

The project is still a research prototype. It currently evaluates model behavior in a simplified harness rather than the production Hex agent, costs a great deal to run, and is difficult to orchestrate and judge. Its contribution is conceptual: systems built to improve over time need evals that allow time, interaction, and state to change.

Models and technical debt

Measure every new model feature against the whole harness

Hex tries to adopt the strongest current models because data science benefits broadly from general intelligence. But “best” depends on quality, latency, effort settings, context behavior, and cost. More reasoning effort can help difficult cases while making a simple question unacceptably slow, and low effort can occasionally trigger a confused spiral.

New model APIs bring tool search, server-side compaction, stateful execution, and vendor agent SDKs. Hex adopts features à la carte when its evals show value. It remains cautious about migrating wholesale to a provider's stack merely to stay “in distribution” with how a model was trained, because custom data tools may already move the application away from that distribution while lock-in reduces control.

The practical question is what Hex's CEO calls sand versus stone. If models become twice as capable, which compensating harness features wash away, and which product assets remain durable? Miller's answer is that domain opinions, interaction quality, and especially the accumulated context from users' real work are more durable than many model-specific workarounds.

People and organization

Domain judgment is becoming more valuable, not less

Miller moved from marketing, community, and developer relations into AI engineering. Years of product knowledge and user empathy became leverage when coding models made implementation more accessible. He still reads, reviews, and edits code, but describes caring deeply about the problem and having a strong product opinion as an increasing share of the role.

Hex hires from diverse backgrounds, including data science, mathematics, marketing, and product users. One highly productive AI engineer began as a Hex customer whose detailed feedback demonstrated strong intuition for the product. Visualization experts contribute by encoding forceful opinions about good charts and analytical communication into the agents.

This does not eliminate senior engineering. Long-running workflows, context systems, privacy, evaluation infrastructure, and safe execution remain difficult engineering problems. The shift is that domain experts can now participate more directly in implementation—and their ability to recognize excellent or suspicious analytical behavior becomes a core system input.

For your agentic platform

Turn Hex's lessons into BA-composable controls

Capability bundlePackage more than tools

Bundle the agent role, static policy, retrievable guides, allowed tools, context sources, completion behavior, and evaluation suite. A persona prompt alone cannot define reliable behavior.

Context authorityModel precedence explicitly

Let BAs label context as enterprise-governed, team-scoped, user preference, observation, or inference. Define freshness, owner, conflict policy, and whether the agent may promote information to a higher level.

Cognitive skillInvestigate and interpret

A data-analysis skill should specify hypotheses, plausibility checks, expected grain, metric definitions, and escalation conditions—not merely “write SQL.”

Actionable skillCreate inspectable artifacts

Tools that run queries or publish reports need scoped credentials, row and cost limits, timeouts, side-effect declarations, durable outputs, lineage, and receipts.

Flow MarkdownDescribe learning loops

Represent Request → Retrieve context → Investigate → Build artifact → Validate → Publish → Observe feedback → Propose context update. Give every loop a budget and every context mutation an approval policy.

Eval portfolioCover normal, adversarial, and longitudinal behavior

Use regression cases for daily reliability, traps for missing analytical skepticism, conflict tests for context governance, and simulations for memory and compounding behavior.

Critical assessment

The interview is unusually honest about what remains unsolved

01Post-action detection is late

Context Studio may help prevent repetition, but a user can still receive a wrong answer first. High-stakes outputs need pre-delivery plausibility checks or explicit uncertainty gates.

02LLM judges are triage, not ground truth

Model-based clustering can preserve privacy and surface themes, but judges can share the agent's blind spots. Material metric failures need deterministic evidence or expert review.

03Long-horizon gains can hide accumulated error

A rising day-90 score is encouraging only if stored knowledge is correct, provenance is preserved, and mistakes can be repaired. Memory quality and memory quantity are different variables.

04Capability unification increases blast radius

A shared tool or context component improves consistency, but one defective update can affect every agent surface. Versioning, staged rollout, ownership, and per-capability evals become essential.

05Agent quality includes taste

Correctness alone cannot capture whether a report selected the right chart, caveat, explanation depth, or follow-up. Evaluation needs human preference and task-outcome evidence without reducing “good analysis” to superficial formatting.

My assessment

Hex's strongest insight is that the valuable moat is not a proprietary loop around an LLM. It is the governed context flywheel created by real work, plus domain opinions about how excellent analysis should proceed. Its hardest unsolved problem is preventing that same flywheel from accumulating conflicting or confidently wrong knowledge.

Takeaways

What to keep from the conversation

  1. Data analysis needs iterative exploration and judgment; single-shot text-to-SQL is only one primitive.
  2. Unify agent capabilities and context while preserving interfaces suited to different user groups.
  3. Treat tool schemas as scarce context and retrieve or consolidate them based on eval evidence.
  4. Keep hidden investigation separate from the durable artifact and require visible evidence for important claims.
  5. Give semantic models, admin guidance, team conventions, and user memory explicit authority and conflict rules.
  6. Maintain small, understood eval sets with repeated runs and realistic multi-step failure chains.
  7. Evaluate systems that learn over time with changing-state simulations, not only one-shot questions.
  8. Continuously retest harness workarounds so yesterday's advantage does not become tomorrow's constraint.
