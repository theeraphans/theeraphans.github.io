The System Behind 2,500 Agent-Written PRs

Lauren Tan's real lesson is not “run more agents.” High autonomy is the output of a deliberately engineered environment: observable work, executable verification, narrow conventions, external context loops, and a review process that fixes the system rather than correcting the same agent mistake forever.

Executive summary

Parallelism is the reward for trust, not the starting technique

Lauren Tan, known online as Poteto, describes how her work moved from micromanaging one coding agent to supervising many autonomous projects that can open and sometimes merge their own pull requests. The transition did not come from a clever orchestration prompt. It came from repeatedly removing the reasons an agent needed her: giving it tools to run and inspect the real application, encoding deterministic operations in scripts, constraining the codebase so the correct path is easier than the wrong path, and connecting external signals such as bug reports back into the development loop.

The viral “2,500 PRs in a month” claim needs context. Tan explicitly says those were not 2,500 product features. Much of the volume was gardening: maintenance, cleanup, pattern correction, performance work, bug triage, and improvements to the environment shared by agents and human engineers. PR count is therefore evidence of throughput, not proof of impact or quality. The interesting question is not how to reproduce the number. It is how to build a system in which high throughput does not multiply bad decisions.

  • Verification creates the agent loop. An agent cannot improve its own work if it cannot run the product, observe behaviour, collect traces, compare results, and decide whether the change satisfied the task.
  • Move mechanical work out of language. Stable operations belong in scripts, CLIs, type systems, linters, and repository structure. Reserve model judgment for work that actually requires interpretation.
  • The codebase is part of the harness. Conventional architecture and narrow legal paths reduce the search space for humans and agents alike.
  • Connect the outer loop to the inner loop. Agents need current context from users, issue trackers, Slack, email, telemetry, and product decisions rather than a stale snapshot of intent.
  • Review by sampling and system correction. At scale, inspect representative outputs, identify repeated failure patterns, then change constraints and verification so the whole fleet improves.
  • Autonomy must match reversibility. Auto-merge is more defensible for well-tested, reversible work. One-way doors and weakly verifiable domains require tighter human gates.

Evidence boundary. The operating details in this article come from Tan's interview and public pstack material. They are not an independent audit of SpaceXAI's production systems, PR quality, business impact, or security posture. Origin story

The trust ladder began with noticing the human bottleneck

Tan traces the approach to a side project after leaving Meta. She was already using AI to write code, but she was spending hours directing a single agent and could not tell whether a new skill actually improved the result. That pattern continued when she joined Cursor and worked on the agent interface and what the transcript calls “Grokbot.” During performance investigations, she became a manual bridge between the agent and Chrome DevTools: the agent changed code, but she had to inspect heap snapshots, traces, and runtime behaviour.

That is the first rung of the trust ladder: the model may generate code, yet the human still performs all observation and judgment. It feels faster than typing, but it does not scale because every feedback cycle waits for the same person. Tan's first major unlock was a verification skill that gave the agent “hands and eyes”—the ability to operate the application, inspect the result, and iterate without asking a person to relay every signal.

1. Assisted

The agent proposes code. A human runs it, interprets failures, and supplies the next instruction.

2. Self-verifying

The agent can launch the real product, interact with it, collect evidence, and repair observable defects.

3. Coordinated

Long-lived projects delegate work to multiple agents while preserving shared intent and dependencies.

4. Autonomous

Bounded work can be completed and merged under rigorous checks, with humans auditing results and improving the system.

The ladder is not a maturity badge for an entire company. A single repository can occupy several rungs at once. A reversible UI cleanup may run autonomously while a schema migration, payment change, or security policy remains human-gated. Trust attaches to a task, environment, and verification contract—not to “AI” in the abstract.

Operating metaphor

A Michelin kitchen preserves craft while scaling execution

Tan prefers “Michelin kitchen” to “software factory.” A factory suggests interchangeable output and volume for its own sake. A kitchen makes the relationship between craft and coordination visible. A home cook performs preparation, cooking, timing, plating, and cleanup. Adding more people without roles or shared conventions can make the kitchen slower. Scale appears only when tools, stations, recipes, quality standards, and responsibility are designed together.

The engineer becomes closer to the executive chef or technical lead. They may write less code directly, but remain accountable for what leaves the kitchen. Their work shifts toward arranging the environment: defining the menu, preparing ingredients, creating stations, teaching the process, choosing where judgment is required, tasting results, and improving the operation when quality drifts.

Human responsibilities

Choose outcomes, define acceptable risk, design architecture, create verification, sample quality, interpret ambiguous evidence, and own the consequence.

Agent responsibilities

Explore the code, execute bounded tasks, run tools, collect evidence, propose and test changes, document decisions, and escalate uncertainty.

This framing avoids a common mistake: multiplying agents before designing how work is divided. Parallelism only helps when tasks have clean boundaries, the environment makes correct choices discoverable, and the outputs can be verified independently. Otherwise, the team creates coordination debt faster than code.

Critical infrastructure

Verification is what turns a sequence into a loop

The interview's strongest technical claim is that verification should be the first serious skill a team builds. A prompt that says “check your work” is not enough. The agent needs a product-specific way to launch the system, navigate features, reproduce a report, inspect logs and traces, take screenshots or snapshots, measure performance, run focused tests, and compare the observed result against a finish condition.

Tan gives hill climbing as an example. If performance can be measured, an agent can propose a change, collect the same metric, retain an improvement, reject a regression, and repeat. The loop exists because there is an external signal that can disagree with the model. Without that signal, “iterate until good” becomes repeated generation judged by the same system that produced it.

Control allocation

Use models for judgment and software for invariants

Tan describes a gradient between work that genuinely requires judgment and work that is mechanical. A model is useful when it must integrate scattered evidence, interpret intent, generate alternatives, or reason about an unfamiliar failure. It is wasteful when every run must rediscover how to open DevTools, transform an AST, enumerate features, or apply a known migration.

Her response is to extract deterministic portions into a CLI or script and keep the skill as a thin workflow wrapper. That improves speed, reduces context consumption, and—more importantly—makes different agents execute the same operation the same way. The point is not that a CLI is sophisticated. The point is that the team retains a successful procedure instead of paying each agent to reinvent and debug it.

Design test. When a rule appears in a skill for the second time, ask whether it should become structure. If a bad state can be made impossible with a type, directory convention, lint rule, generated registry, or idempotent script, that is stronger than another paragraph asking the model to remember.

The codebase as harness

The new engineering work is shaping the environment

Low trust creates a trap. The engineer micromanages the agent because the environment provides weak guidance. Micromanagement consumes the time that could have improved the environment, so trust remains low. Tan compares this to cutting everything with a dull knife while deadlines leave no time to sharpen it.

Her alternative is to spend deliberate time making the repository easy to change correctly. In the interview she describes an internal framework called Dune, roughly an internal Next.js-like framework for Electron applications. Its value is not novelty. Restrictive lint rules and conventional feature directories create one obvious path. Early versions of the application had several enormous “god files”; the framework and conventions prevent agents from repeatedly extending that failure mode.

The general pattern is more important than Dune:

  1. Observe a recurring agent failure in real work.
  2. Find the environmental condition that allowed it.
  3. Encode the preferred path in architecture, types, tooling, or checks.
  4. Run the same class of work again and verify that the failure becomes rarer.
  5. Keep the constraint only if it improves the system without blocking legitimate variation.

This is fleet-level learning. Correcting one generated file fixes one output. Changing the environment alters the probability distribution of every future agent and every new human contributor.

System architecture

High throughput comes from connecting the outer and inner loops

A coding agent normally begins with a snapshot of intent: a task, repository state, and whatever context the operator supplied. That snapshot goes stale. New bug reports arrive in Slack or Linear, customers reveal related symptoms, infrastructure constraints surface, and product priorities change. If the agent cannot retrieve those signals, the human remains a “context courier” between the organisation and the coding loop.

Tan describes personal or connector agents monitoring services and sending relevant work to long-lived Cursor projects. A project acts like a chief of staff: it coordinates rather than performing every task itself. If thirty related performance reports arrive, the coordinator can preserve the thread between them, assign investigations, and search for one upstream cause instead of spawning thirty isolated fixes that duplicate work.

This is the architectural explanation for the large PR count. Tan is not manually opening thousands of chats. Persistent loops discover work, acquire context, group it, and feed coordinated projects that can delegate to subagents. The number of agents is downstream of that information architecture.

What the metric hides

2,500 PRs does not mean 2,500 features

At 46 minutes, Tan explicitly corrects the headline interpretation. A substantial share of the work is “gardening”: scanning for repeated bad patterns, improving maintainability, resolving bugs, tightening conventions, reducing performance problems, and preparing a better environment for the whole team. These changes can be small and atomic, which naturally increases PR count.

One routine searches for React footguns but does not immediately fix each occurrence. It appends findings to a document. After several days, a human or higher-level agent can inspect the buffer, recognise that many instances share one cause, and choose a systemic correction. The queue prevents a fleet of agents from executing locally plausible but globally repetitive work.

Metric warning. PR count has no denominator for scope, risk, acceptance, reverts, defects, review burden, or customer outcome. Use it to understand operating scale, not as a productivity target. A healthier dashboard would pair throughput with lead time, escaped defects, rollback rate, repeated failure classes, human intervention, and measurable product impact.

Quality at scale

Sample outputs, then repair the production system

No person can deeply review every line produced by thousands of PRs. Tan's answer is not to stop reviewing. It is to change the unit of review. She samples pull requests and code, looks rigorously for repeated shortcuts or workarounds, then modifies the environment—skills, types, lint rules, tests, and architecture—so the same class of defect becomes harder to produce.

Blocking review

Inspect each change before merge. Appropriate when verification is weak, consequences are high, or the change is difficult to reverse.

Sampling review

Allow bounded work through strong checks, then audit representative outputs and fleet-level trends. Appropriate only after trust has been earned.

Tan describes a “full autopilot” mode in which multiple verifier agents exercise the application, search for regressions, fix discovered problems, and repeat before a pull request lands. She also emphasises that reaching this point takes sustained effort. Installing pstack does not create a dark factory. The repository, verification loop, task boundaries, and risk controls must already support it.

The strongest insight is that post-merge review can still be active governance when the system is designed for reversibility. The human inspects history, samples results, reverts or modifies failures, and converts patterns into new constraints. But this model becomes irresponsible when rollback is incomplete, the verification signal is weak, or failures harm users before discovery.

Autonomy boundary

One-way doors expose the limit of the method

Matt Pocock asks about medical, legal, financial, and other changes that cannot be cheaply undone. Tan's answer is appropriately bounded: autonomy depends on verifiability. Software engineering often provides compilers, tests, runtime inspection, staged rollout, and version control. Other domains—or particular software changes—may not offer a signal strong enough to justify autonomous execution.

Formal methods may turn some apparent one-way doors into safer decisions, and Tan points to languages that combine programming with proofs. But she does not claim that every domain can reach the same autonomy. A passing test suite is not proof that a policy is fair, a medical recommendation is safe, a migration preserves every record, or a security boundary has no unseen path.

  • Reversible and observable: automate progressively, retain evidence, and sample.
  • Reversible but weakly observable: keep review until outcome signals improve.
  • Irreversible but strongly specified: require independent verification and explicit approval.
  • Irreversible and ambiguous: do not treat agent confidence as permission to act.

Skills as process memory

Your corrections are the raw material for your own skill library

The closing discussion rejects the idea that users must choose one person's skill collection wholesale. Skills are workflows expressed in language. They can be combined, shortened, forked, or replaced. What matters is whether the operator understands and trusts the process they encode.

Tan recommends mining prior agent transcripts for repeated interventions: moments when the user corrected an assumption, supplied missing context, rejected a shortcut, or explained how to verify a result. Those conversations are not merely logs. They are observed process. A repeated correction can become a skill; a mechanical instruction can become a script; a forbidden pattern can become a lint rule; a useful investigation path can become a recall workflow.

Her public pstack repository reflects this direction. Its current skills emphasise verification, investigation, review, reflection, and principles rather than giant collections of implementation trivia. Tan predicts that stronger models will make skills smaller: they will preserve the workflow and the decision boundary while leaving ordinary implementation details to the model.

Practical adoption

Climb one rung with one closed loop

A team should not begin by copying the final architecture or chasing thousands of PRs. Start where the human is visibly relaying information or repeating checks. Choose one narrow, frequent, reversible task and make its finish condition observable.

  1. Record the current loop. Capture the task request, human interventions, tools used, evidence inspected, and decision to accept or reject.
  2. Build real verification. Give the agent a repeatable path to run the actual system and observe the user-facing result.
  3. Extract determinism. Replace repeated language instructions with scripts, types, linters, fixtures, and repository conventions.
  4. Measure failure classes. Track why humans intervene, not only how many tasks complete.
  5. Increase authority narrowly. Let the agent perform one additional reversible action when evidence shows the loop is reliable.
  6. Add coordination last. Introduce more agents only when task boundaries and verification allow independent work without multiplying ambiguity.

For an agentic platform team. The reusable unit is not a persona prompt. It is a versioned work contract: intent, context sources, allowed actions, deterministic tools, verification procedure, escalation conditions, evidence output, and ownership. Master agents and subagents become useful after these contracts exist.

My take

The breakthrough is environmental learning

The interview is convincing when it treats trust as an engineering result rather than a feeling. The agent does not become trustworthy because a user becomes comfortable with it. Trust rises because the system exposes reality, rejects known bad states, preserves successful procedures, narrows the action space, and produces evidence that can falsify its own claim of completion.

The most transferable idea is the shift from session-level correction to environment-level learning. Most agent use today is amnesiac: a person catches an error, fixes the prompt, and repeats the same lesson next week. Tan's process asks where that lesson belongs permanently. This mirrors how mature engineering organisations improve—through tests, types, APIs, playbooks, architecture, and post-incident changes—not through heroic vigilance.

The headline number remains the least useful part. Thousands of PRs can still create thousands of tiny liabilities. What matters is whether the organisation can explain why work was initiated, how it was verified, which failures escaped, how the environment changed afterward, and whether customers received a better outcome. High autonomy without that evidence is not a trust ladder. It is invisible risk.
