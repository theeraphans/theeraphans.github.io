The Agent Does Not Need Another Essay. It Needs a Decision.

Microsoft-Decision-1 turns text or JSON state into bounded choices, ordered scores, and yes/no probabilities. The important idea is larger than one model: use language generation for open-ended work, but put a smaller decision layer between reasoning and action.

Microsoft Command Line articlePublished October 9, 2026By Achint SrivastavaSummary run: October 13, 2026 · 09:02 ICT

Executive summary

The useful innovation is a narrower contract between AI and software

A general-purpose LLM is excellent when the output should be language. Many production systems do not need language at the point where work branches. A ticket router needs one queue. A policy gate needs allow, block, or escalate. A model router needs one candidate from a known set. Asking a generative model to write prose and then parsing that prose back into a software value adds decoding time, cost, and another failure surface.

Microsoft-Decision-1 is built for that narrower boundary. The application sends text or JSON state plus one or more typed questions. The model returns a bounded answer and a probability distribution. Microsoft says the model is post-trained from Qwen3.5-9B for single-pass decision scoring and is available through Microsoft Foundry and OpenRouter.

  • The output is software-native. The API returns a boolean probability, a choice from named options, or an ordered score rather than free-form prose.
  • Confidence becomes part of the workflow contract. The application can act, defer, retry, or request human review according to thresholds defined from local error costs.
  • The model belongs inside the harness. It can route tasks, inspect proposed tool calls, grade an agent step, or decide whether the workflow should continue.
  • Microsoft's benchmark results are promising but vendor-reported. The announcement reports top accuracy across 36 benchmarks and large latency gains, but it does not publish enough per-task detail in the article to replace local evaluation.
  • Calibration is workload-specific. A probability-looking number is not automatically trustworthy on a new domain, distribution, language, or consequence level.
  • A fast classifier is not an authorization system. High-impact actions still need deterministic policy, scoped tools, payload verification, audit logs, and meaningful human review.

Evidence boundary. Accuracy, speed, cost, internal-use, robustness, and safety figures below are reported by Microsoft. The documentation exposes the API and operational cautions, but the announcement does not provide the complete benchmark datasets, prompts, hardware, latency distributions, or raw predictions needed for independent reproduction.

The interface mismatch

We keep paying a language model to produce text that software immediately throws away

Imagine a support agent that has read a customer message and must select the next team. A conventional LLM call might generate: “This appears to be a billing issue because the customer reports a duplicate charge.” The application then validates JSON, extracts billing, and discards the explanation. Generation did useful semantic work, but the final interface encouraged unnecessary tokens.

A decision model answers a different question: given this state and these valid options, what is the probability of each option? That output can flow directly into deterministic code. A low top probability can trigger abstention. A high probability can still pass through policy before any consequential tool executes.

The API contract

State in, bounded questions in, typed probabilities out

The Foundry endpoint accepts a state value as text or JSON and a questions object. Multiple questions can share the same state, so one ticket could be routed, severity-scored, and checked for repeat contact in a single request. This avoids repeating the full context while keeping related judgments aligned.

noul

A yes/no probability from 0 to 1. Useful for gates such as “does this action touch production data?”

choice

One selection plus a probability for every named option. Useful for intent, model, tool, team, or workflow routing.

score

A probability-weighted position over an ordered scale. Useful for severity, quality, relevance, and queue priority.

{
  "state": {
    "message": "Checkout fails for every EU customer",
    "customer_contact_count": 3
  },
  "questions": {
    "team": {
      "type": "choice",
      "instructions": "Which team should handle this incident?",
      "criteria": {
        "billing": "Charges, invoices, and refunds",
        "engineering": "Bugs, errors, and outages",
        "support": "Account and how-to questions",
        "cannot_tell": "Evidence is insufficient"
      }
    },
    "severity": {
      "type": "score",
      "criteria": ["Cosmetic", "Minor", "Major", "Critical"]
    }
  }
}

The explicit cannot_tell option matters. If the model must always choose among business actions, uncertainty is converted into false certainty. Abstention is part of the domain model, not a fallback added after launch.

The evaluation spans routing, ranking, long context, multilingual, out-of-distribution, reasoning, and safety tasks. Microsoft also perturbed requests in eight ways to test whether harmless changes altered the answer. The post reports an average 1.3% decision-flip rate and zero flips when options were paraphrased, reversed, or shuffled.

Those are useful tests because option order and wording are common production failure modes. Yet an average can hide the tasks that matter most. A 1.3% flip rate may be acceptable for content tagging and unacceptable for an authorization gate. The relevant metric is not the global average. It is the error distribution under your own paraphrases, languages, state formats, class imbalance, and consequences.

Internal pilots

The clearest wins appear where decisions repeat at high volume

Microsoft describes four internal use cases. Xbox Research used the model to label more than 10,000 open-ended feedback items into researcher-defined themes and reported quality competitive with GPT-6 Sol at more than 14 times the speed and 200 times lower cost. The Copilot team reports competitive quality with GPT5.6 Luna and 100 times the speed for response-quality measurement.

On-call engineers tested it for retrieving and routing incident knowledge. Microsoft Discovery used rubric grades inside an adaptive replanning loop and reports that the decision score was 46 times more consistent than an LLM-based score, with faster replanning overall. These examples share a structure: the state may be rich, but the next software action is bounded and repeated many times.

High-volume classification

Customer feedback, intent, document type, content policy, and data labels where each item maps to a known taxonomy.

Agent routing

Select a model, tool, skill, sub-agent, or human lane from a controlled registry.

Quality gates

Grade an answer or proposed action against a rubric before the workflow continues.

Prioritization

Score incidents, search results, hypotheses, or review queues on a defined ordinal scale.

Where it belongs

A decision model should advise the state machine, not become the state machine

Observed stateUser request, agent trace, tool proposal, policy facts
->
Decision layerTyped questions, options, probabilities, model version
->
Deterministic policyThresholds, abstention, allowlist, budget, consequence rules
->
Controlled executorScoped tool call, verified payload, audit event, human approval

The model may say that an action is probably safe. It should not grant itself permission. The harness owns valid transitions. A tool gateway checks the exact payload, credentials, destination, and user authorization. For customer-facing or irreversible egress, approval must bind to the payload that actually leaves the system.

This separation also makes evaluation legible. You can measure decision quality independently from policy quality and tool-execution correctness. When something fails, the trace can show whether the model chose the wrong option, the threshold was wrong, or the executor violated its contract.

Probability is a product feature

A 0.9 score is useful only when it means something locally

Microsoft emphasizes calibration: among representative cases assigned 90% confidence, roughly nine out of ten should be correct. This enables a three-lane workflow. High-confidence, low-consequence cases may auto-execute. Ambiguous cases go to review. High-risk or out-of-distribution cases fail closed.

Calibration can drift when the taxonomy changes, the state format changes, traffic shifts, or the question is reworded. A model can preserve ranking quality while its probabilities become unreliable. Teams therefore need reliability diagrams, expected calibration error, per-class precision and recall, abstention coverage, and cost-weighted decision metrics on a time-based holdout.

Threshold rule. Never choose 0.8 because it feels conservative. Derive thresholds from labeled production-like data and the asymmetric cost of false positives, false negatives, deferrals, and human review.

Known limits

The narrow interface removes some failure modes and exposes others

  • No explanation is returned. That reduces fluent rationalization but makes debugging, appeals, and regulated decision support harder.
  • Question design still matters. Ambiguous instructions, overlapping options, forced choices, or loaded wording produce bad decisions in a perfectly valid response shape.
  • Calibration is not universal. Microsoft says it is strongest on familiar task types. Domain shift can make confidence misleading.
  • Bias remains possible. The Foundry documentation warns against using model scores as the sole basis for consequential decisions about individuals.
  • Safety classification is imperfect. Subtle harmful requests may pass and harmless requests may be blocked. A probabilistic screen cannot replace deterministic controls.
  • The service can change behind a stable API. OpenRouter states that weights are updated continually. Pin, record, and monitor the served version wherever reproducibility matters.
  • Latency is deployment-dependent. Region, network, concurrency, context length, and provider routing affect end-to-end timing. Benchmark the whole request path, not a vendor P50.

Adoption playbook

Evaluate the decision contract before replacing the model

  1. Choose one bounded workflow. Start with a repeated routing, grading, or validation task whose options already exist in software.
  2. Freeze the contract. Define state fields, question wording, option criteria, abstention behavior, and the action that follows each result.
  3. Build a representative labeled set. Include paraphrases, reordered options, multilingual examples, rare classes, malformed state, prompt injection, and recent production edge cases.
  4. Keep the current baseline. Compare against existing rules, a cheap classifier, and the generative LLM already in use.
  5. Measure the full system. Track accuracy, macro F1, calibration, abstention coverage, P50/P95/P99 latency, cost per decision, and human-review volume.
  6. Test perturbation stability. Shuffle options, rename keys, vary formatting, and paraphrase equivalent instructions. Record whether the operational action changes.
  7. Shadow before acting. Run Decision-1 alongside production without controlling tools. Compare disagreements and investigate the expensive ones.
  8. Calibrate thresholds by consequence. Auto-route a low-risk ticket at a lower bar than a production write, refund, security block, or employment decision.
  9. Log the evidence. Persist model version, state hash, question contract, returned distribution, threshold, final action, reviewer override, and observed outcome.
  10. Re-evaluate every contract or model change. A stable endpoint does not guarantee stable behavior.

My take

Decision models are a missing middle layer, not a replacement for reasoning

The interesting part of Microsoft-Decision-1 is not that a smaller model can classify text cheaply. Software has had classifiers for decades. The advance is packaging semantic classification, ordinal judgment, and calibrated confidence behind one language-aware contract that can operate over rich state without generating an essay.

That makes it a natural component in an agent platform. A capable LLM can understand an open-ended objective, build a plan, and create candidate actions. A decision model can repeatedly handle the smaller questions inside that process: which specialist should receive this task, whether evidence satisfies a rubric, whether the result is uncertain, and whether the next step should continue, retry, or escalate.

The architecture becomes stronger when each model does less. Generative models reason and communicate. Decision models compress state into bounded uncertainty. Deterministic code owns permissions and side effects. Evals decide whether any of it deserves production traffic.
