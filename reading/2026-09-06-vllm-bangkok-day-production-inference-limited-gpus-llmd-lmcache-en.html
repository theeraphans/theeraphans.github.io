vLLM Bangkok Day 2026: A Field Guide to Production Inference

Five hours of practical lessons on making open models fast, affordable, governable, and useful: from one limited GPU to distributed llm-d clusters and reusable KV-cache infrastructure.

Creatorsgarten · vLLM Bangkok Special event recording 5h 18m Summary run September 6, 2026 · 20:57 ICT

This page is a detailed editorial paraphrase built from the full event audio, Facebook's partial captions, and the official agenda. Technical names have been normalized against the agenda. Benchmarks and forecasts remain speaker claims, not independent validation.

Executive summary

Inference is where a capable model becomes an economically usable product

The event's central argument is that model intelligence is only one layer of an AI system. A model creates business value when an inference stack can deliver its tokens at acceptable latency, concurrency, reliability, privacy, and cost. That shifts attention from model leaderboards toward serving mechanics: memory allocation, batching, KV-cache reuse, routing, prefill and decode separation, autoscaling, observability, and governance after deployment.

vLLM sits in the middle of this system. It turns open-weight models into production endpoints and brings together model integrations, hardware support, scheduling, PagedAttention, continuous batching, quantization, speculative decoding, and cache connectors. Around it, projects such as llm-d coordinate many replicas across Kubernetes, while LMCache extends reusable context beyond scarce GPU memory.

The Thailand-specific message is equally important. The country is unlikely to win by buying the most GPUs or reproducing frontier foundation models. The speakers repeatedly point toward local advantages: Thai-language tokenization, data residency, agriculture, SME workflows, enterprise integration, product taste, and engineers who understand both infrastructure and the problem being solved.

The shortest useful interpretation

Do not optimize “the LLM” in the abstract. Measure the workload, identify whether it is compute-bound, memory-bound, cache-friendly, latency-sensitive, or sovereignty-constrained, then assemble only the serving layers that change that workload's economics.

Mental model

The production inference path

The talks describe a stack in which each layer solves a different bottleneck. A gateway protects and accounts for access. A scheduler chooses the best replica. vLLM performs efficient model execution. Cache infrastructure preserves expensive context. Hardware supplies compute, memory bandwidth, and interconnect.

01Client or agentPrompt, history, tools, tenant, latency objective
02AI gatewayAuthentication, quotas, rate limits, token accounting
03Endpoint pickerModel route, queue load, prefix affinity, predicted latency
04vLLM workersBatching, PagedAttention, prefill, decode, parallelism
05Memory and GPUsHBM, CPU RAM, SSD, remote cache, accelerators

This makes the boundaries clearer. vLLM is the inference engine, not the entire platform. llm-d adds distributed orchestration and request-aware scheduling. LMCache adds a durable, shareable memory tier for computed context. An enterprise platform still needs identity, policy, observability, rollout controls, evaluation, and business ownership around those components.

Limited GPUs

Make memory a design variable, not a fixed wall

Tun Jian Tan begins with a practical distinction: Ollama is optimized for a convenient local experience, while vLLM is designed for production serving, although vLLM can also run on consumer hardware. A desktop GPU may be enough for one or a few users if the workload is understood and its memory budget is actively managed.

That budget contains more than model weights. It also includes activations, KV cache, CUDA graphs, and persistent buffers. Long-running agent workloads amplify the KV-cache component because hundreds of thousands of earlier tokens may remain relevant to every new token.

Weight quantization

Reduce model precision, such as BF16 to FP8 or lower-bit formats, to fit larger models or leave more memory for active sequences. Hardware support matters, and quality must be checked on the actual domain.

KV-cache quantization

Compress keys and values so more context can stay resident. This reduces memory traffic and can improve decode performance, but calibration or online scale calculation may be needed to control accuracy loss.

Prefix caching

Reuse KV blocks when requests share a stable prefix, such as a long system prompt. It is particularly valuable when many users or agents begin from the same instructions.

KV offloading

Move reusable context from GPU memory to CPU RAM, SSD, or remote storage. Fetching a saved cache can be faster than recomputing a 200K or 500K-token history.

Speculative decoding

Use a smaller draft mechanism to propose future tokens, then verify them with the main model. Techniques discussed include MTP, Eagle, and DFlash-style methods. Speed gains require extra memory for the draft components.

Sleep mode

Temporarily evict model weights and KV cache while preserving selected runtime metadata. This allows several models to time-share one GPU without paying the full cold-start and graph-capture cost each time.

The speaker's checklist

Choose the model, context length, input/output profile, concurrency, and task type before choosing an optimization. “Enable everything” is not a strategy: quantization may affect quality, speculative decoding consumes additional VRAM, and offloading adds transfer costs.

Enterprise adoption

The hard step is not demo to pilot; it is pilot to accountable production

The first panel connects infrastructure to organizational readiness. Dr Komes Chandavimol describes a staged system at KBTG: establish AI literacy, let knowledge workers create prototypes, evaluate whether an idea has measurable value, sponsor a smaller set of pilots, test internally, and require explicit exit criteria before customer-facing production.

His governance model continues after launch. Teams monitor quality, hallucination, loops, token consumption, and business impact, with a rollback or fallback plan for customer-facing failures. Governance therefore becomes a resource-allocation and learning system, not merely a list of prohibited actions.

01LiteracyPeople understand capabilities, limits, and responsibility
02PrototypeBroad access to tools and low-cost experimentation
03Value gateImpact hypothesis, budget, owner, success measure
04Internal pilotReal employees, bounded risk, defined exit criteria
05ProductionScale, monitor, govern, rollback, and learn

Dr Pin Siang Tan adds a different ROI lens. AI is not only about making each employee slightly faster. It can raise the quality and ambition of what a small team can build. That value may not appear in a short POC; it emerges when capable agents become part of real work for several weeks.

Tuan Luong calls out the productivity paradox: individuals often feel immediate gains while enterprises struggle to prove aggregate return. The missing link is usually workflow redesign, adoption, and measurement, not just access to a model.

Build or buy

Self-hosting is an economic and control decision, not an ideological one

The panel rejects one universal answer. Public APIs are the fastest route to frontier capability and early validation. Self-hosting becomes attractive when token volume is large and predictable, an open model meets the quality threshold, data must remain within a jurisdiction, latency benefits from local serving, or the team can exploit owned hardware.

Decision factorPrefer APIPrefer self-hosting

TeamNo inference operations capabilityEngineers can benchmark, tune, observe, and operate the stack

A hybrid policy is often strongest: route each project by sensitivity, quality, cost, and workload. This requires a gateway that can enforce quotas, guardrails, provider choice, and tenant boundaries. The operational headcount, on-call attention, upgrade risk, and idle capacity must be counted alongside GPU price.

Thailand strategy

Compete at the problem and application layers

CK from Fastwork argues that Thailand should begin with problems it is unusually positioned to solve rather than defaulting to a foundation-model race. Agriculture is his central example: a large share of the workforce and land is tied to farming, while its economic output remains disproportionately low. Precision farming, water management, crop rotation, and decision support offer places where globally available AI can be combined with local context.

He also predicts that the agent may become the primary interface while conventional SaaS products become backends. Instead of opening a CRM and navigating menus, a person states an outcome and the agent operates the systems. Whether that prediction arrives exactly as described is uncertain, but its product implication is useful: APIs, permissions, semantic actions, and trustworthy execution may become more strategic than another polished navigation layer.

The role of the engineer changes with it. When coding becomes faster, differentiation moves toward problem selection, product taste, systems thinking, and co-creation. His “new full stack” engineer can move between customer need, product decision, design, implementation, and business outcome rather than waiting for a perfectly complete requirement.

A stronger national KPI

Measure successful products and solved citizen problems, not only installed GPUs, consumed tokens, or cloud capacity. Compute is an input; useful outcomes are the point.

Inside vLLM

Production configuration begins with workload economics

Tiezhen Wang presents vLLM recipes as a starting point, then warns that defaults cannot know the service's latency and throughput objectives. Two configuration ideas receive special attention: maximum model length and maximum number of sequences.

Maximum model length

A model may support a million-token context, but reserving for that maximum can consume GPU memory that could otherwise serve concurrent users. A short chatbot and a long-horizon coding agent should not receive the same limit.

Maximum sequences

Batch size trades per-user interactivity against aggregate throughput. Serving one user extremely quickly may underutilize the GPU; maximizing total tokens can make every user feel slow. The correct point sits on a workload-specific curve.

The model-integration process is also instructive. For selected releases, the team works with a vendor before public launch, verifies model outputs against the vendor implementation, packages temporary dependencies and in-flight changes in a day-zero container, then upstreams the integration after review. Correctness comes first; kernel fusion, quantization, speculative decoding, and hardware-specific optimization follow.

The broader roadmap spans model performance, additional accelerators such as TPU and AMD, multimodal work, and reinforcement-learning infrastructure including weight synchronization and reducing the mismatch between training and inference. The architectural lesson is that a production engine is a moving compatibility layer across model architectures, hardware, kernels, and serving contracts.

Distributed inference

llm-d replaces blind round-robin with request-aware orchestration

Traditional web requests are often short, uniform, and cheap enough for simple load balancing. LLM requests are long, stateful, non-uniform, and expensive. A replica may already hold the right prefix, have almost no KV-cache headroom, or have a long queue. Round-robin cannot see any of this.

llm-d introduces an inference gateway and an Endpoint Picker, or EPP, that uses workload signals to choose a vLLM replica. It runs as a Kubernetes-native distributed inference framework and groups replicas into inference pools by base model.

Prefix-aware routing

Prefer a replica that already owns reusable KV blocks for the incoming request, reducing recomputation and preserving cache locality.

Load-aware routing

Consider queue depth and capacity rather than sending a large request to an already saturated worker.

Predicted latency

A lightweight predictor can learn from completed traffic and estimate latency for new requests, replacing fixed routing weights with continuously updated behavior.

KV-cache management

Keep useful context resident across GPU, CPU, and shared storage tiers, and route repeat traffic toward the replica where reuse is possible.

Prefill/decode disaggregation

Separate compute-heavy parallel prefill from sequential, memory-bound decode so each pool can use a configuration suited to its phase.

Expert parallelism

Distribute mixture-of-experts components across nodes and route work to the relevant experts rather than forcing a large model into one server.

Flow control

Apply tenant identity, priorities, queues, and fair scheduling when the cluster is saturated.

Proactive autoscaling

Use queue and cache pressure as leading indicators instead of waiting for GPU utilization and user latency to deteriorate.

The session reports substantial benchmark improvements for selected setups, including a large reduction in streaming latency with disaggregated prefill and decode. Those numbers demonstrate potential, not a portable guarantee. Network transfer, model shape, prompt distribution, cache hit rate, topology, and concurrency determine whether disaggregation helps a specific deployment.

Reusable context

LMCache treats computed context as a data asset

Dai Tran's session begins with the size of the problem. In his illustrative calculation for Llama 3.1 70B, KV cache occupies roughly 320 KB per token in the stated precision and architecture. A 120K-token context therefore approaches 40 GB, enough to consume a large share of one H100's memory. Keeping every conversation entirely in HBM is not viable at scale.

Request → find longest reusable span → load cached blocks → prefill only the missing span → decode → store asynchronously

LMCache extends the cache hierarchy from GPU HBM to CPU RAM, local disk, and remote shared storage. CacheGen compresses KV data before transfer to reduce bandwidth pressure. The point is not that slower storage beats GPU memory; it is that retrieving reusable context can beat paying the model to compute it again.

The talk identifies four ways expensive context “dies young”: GPU memory pressure evicts it, an engine process crash destroys locally attached cache, a request is routed to a replica that never saw the cache, or a tiny prompt change causes a prefix miss. CacheBlend addresses part of the last problem by dividing context into reusable blocks and recomputing only the portions needed to preserve attention accuracy.

Up to 6×better time to first token in the long-document QA setup described by the speaker
Up to 10×higher throughput in the same reported comparison
Up to 7.6×better reported P99 time to first token for that tested workload

Cache infrastructure is most promising for multi-turn chat, document QA, retrieval workflows, and coding agents where large spans recur. It is less useful for unique one-shot prompts or very short inputs. A valid rollout therefore starts with instrumentation: cache lookup and hit rates, tier latency, transferred bytes, TTFT, throughput, cost by model and tenant, and prompt-template stability.

At enterprise scale, performance alone is insufficient. The session calls for cluster-level cache services that survive engine replacement, tested version compatibility between vLLM and cache components, tenant-scoped cache keys, per-model and per-tenant metrics, air-gapped deployment, and operational service levels.

Thai inference engineering

Thailand's gap is also its opportunity

The final panel defines inference engineering as the work that makes model capability affordable and deliverable to many users. Sattaya Singkul highlights a concrete local issue: Thai text may consume more tokens than comparable English text under many tokenizers. That can increase prefill work, KV-cache demand, time to first token, and ultimately the cost assumptions used to size a service.

Pongsasit Thongpramoon recommends turning “the model is slow” into measurable questions. Is the complaint about time to first token, which is heavily influenced by prompt processing, or inter-token latency, which describes generation speed? Is the bottleneck scheduling, model execution, memory bandwidth, networking, interconnect, or hardware capacity?

Natthanan Bhukan describes research on distributing long context across GPUs while avoiding idle time and excessive communication. The broader lesson is to look beneath framework abstractions. Teams that can formulate a local workload problem precisely may find research and product opportunities that frontier labs are not incentivized to solve.

For policy makers

Fund engineers and operational knowledge alongside hardware. A GPU cluster without serving expertise is expensive idle capacity. Keep data-residency rules clear enough that companies can build locally.

For entrepreneurs

Do not default to another chatbot. Build the layer that lets Thai companies run an appropriate open model, under local constraints, at a price and service level they can approve.

For engineers

Serve a small model on available hardware, send realistic traffic, measure TTFT and inter-token latency, alter one parameter at a time, inspect why benchmarks differ, and connect the improvement to business value.

Platform blueprint

What this means for an agentic AI platform

For a platform team, the sessions suggest a workload-aware control plane rather than one universal model endpoint. Each agent or business flow should declare enough intent for the platform to choose a serving policy.

Data classificationDetermines provider, region, isolation, and logging policyAPI, private cloud, or on-prem route

Context patternStable prefixes and multi-turn history can be reusedEnable prefix affinity and cache tiers

This contract gives Business Analysts a meaningful role without asking them to tune kernels. They describe business criticality, user experience, sensitive data, expected repetition, volume, and failure policy. Platform engineers translate those requirements into model, gateway, scheduler, cache, and hardware configurations.

Critical assessment

The event is strongest when it connects a technique to a workload

What is convincing

The talks repeatedly reject infrastructure by fashion. Prefix caching only helps shared prefixes. LMCache needs enough reuse to justify another data layer. Self-hosting requires sustained demand and operating capability. Larger context limits and batches are not automatically better. This workload-first framing is the most transferable lesson.

What deserves caution

Several benchmark figures are “up to” results from selected configurations and should not become procurement assumptions. The recording also contains forward-looking claims about open models, agent interfaces, productivity, and national opportunity. They are useful hypotheses, but platform decisions still need task-specific evals, load tests, total-cost models, and security review.

What is missing

The event goes deep on serving but less deeply on output quality under optimization, evaluation design, incident response, model-risk ownership, energy cost, and the operational complexity introduced by distributed cache and routing. A complete production programme should test semantic quality and safety alongside latency, throughput, and cost.

Balanced conclusion

vLLM, llm-d, and LMCache form a compelling open serving stack, but architecture should be earned by observed traffic. Begin with a measured endpoint, add the layer that removes the current bottleneck, and verify that the business outcome improves after every addition.

Takeaways

What to remember after five hours

  1. Model quality is only the beginning; inference turns intelligence into a service.
  2. Measure TTFT, inter-token latency, throughput, concurrency, cost, and quality separately.
  3. Context length is a capacity decision. Do not reserve the model maximum by default.
  4. KV cache is both a memory cost and a reusable asset for long-running agents.
  5. Route requests with knowledge of load and cache locality, not blind round-robin.
  6. Separate prefill and decode only when tests show the added network and operational complexity pays back.
  7. Use APIs for speed and uncertainty; self-host when control, volume, residency, or owned capacity makes the economics real.
  8. Move ideas through explicit value, pilot, production, and post-launch governance gates.
  9. Thai tokenization, data residency, and local workflows are product and research opportunities.
  10. Buy expertise with the hardware. A serving platform is an operating capability, not a GPU purchase.
