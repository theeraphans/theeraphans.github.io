Agent Architecture

Domain-Specific Agents Are Composition

A summary of Justin Schroeder's talk on why small, specialized agents may become the next major layer in AI systems. The central argument: tools and skills add context to one big agent, while domain-specific agents compose many smaller agents with their own scope.

Video: The Future Is Domain-Specific Agents Creator: AI Engineer Transcript: 5,176 words

The Short Version

Businesses want custom agents because they need AI integrated with their data and workflows. But robust agents are hard to build, hard to observe, hard to move, and hard to compose. Schroeder argues that the next step is not adding more tools and markdown skills to one giant agent, but building small domain-specific agents that coordinate with each other.

  • Tools and skills mostly inflate context.
  • Specialized agents keep context small.
  • Multi-agent orchestration becomes the product layer.

Problem

Everyone is building custom agents because integration is still unsolved

The talk starts from a strange market observation: even though general-purpose AI tools are everywhere, companies still try to build their own agents. Schroeder's explanation is integration. Businesses need their own data, tools, policies, and workflows connected to AI in a way generic chat apps cannot fully satisfy.

Need

Business data integration

Companies want agents connected to internal systems, domain records, workflows, and proprietary knowledge.

Reality

Custom agents demo well

Many teams can build a demo, but the same system becomes difficult when it needs telemetry, reliability, portability, and scale.

Gap

No shared agent standard

Teams still make their own choices around loops, provider abstractions, durable execution, validation, stop conditions, and observability.

Context Inflation

MCP and skills help, but they do not solve the whole agent problem

Schroeder frames MCP as very useful, especially as a way to distribute tools into large general-purpose agents. But he argues tools alone do not create a complete system. Skills help as documentation, but many skills can also make the agent worse by adding too much context.

Inheritance-style agent

  • One big model or agent
  • More tools added through MCP
  • More skills added as markdown docs
  • More system behavior pushed into context
  • Diminishing returns as context grows

Composition-style system

  • Many small agents
  • Each agent has a narrow domain
  • Each agent owns its own tools and history
  • A coordinator delegates tasks
  • Only relevant context crosses boundaries

The key software-design analogy is composition over inheritance: stop adding more capabilities to one agent; compose specialized agents instead.

Core Idea

A domain-specific agent is a full agent, not just a tool server

In this model, a Figma agent is not merely a list of Figma tools. It has its own system prompt, toolset, message history, loop, rules, and domain assumptions. A coordinator can ask it for work in ordinary language, then receive a compact result back.

Benefits

Why specialized agents are attractive

The argument is not only architectural elegance. The talk claims practical benefits around token efficiency, model cost, capability control, and horizontal scaling.

Cost

Smaller context windows

The coordinator can ask a Gmail agent for one email instead of dragging the entire global conversation into every tool call.

Models

More small-model tasks

When the task is narrow and context is minimal, cheaper models can become viable for individual sub-tasks.

Safety

Strict capability limits

A small agent can only do the approved actions in its domain, which is easier to explain to security and IT teams.

Scale

Parallel execution

Small isolated agents can run in many instances and regions without one giant execution environment.

Portability

Reusable agent packages

A domain agent can be bundled, moved, and reused more easily than a giant custom agent with tangled environment assumptions.

UX

Specialist quality

A narrow agent can carry a deeper system prompt and better domain defaults without bloating every other workflow.

Ideal Agent

The talk's ideal agent has more primitives than a model plus tools

Schroeder sketches an ideal domain-specific agent as a package with its own model, prompt, tools, hooks, rules, file system, and sandboxed execution. This matters because a portable agent needs runtime boundaries, not just instructions.

Model and system prompt

The agent starts with a model and a domain-specific instruction set that defines its role and objective.

Tool layer

Tools can include functions, prompt-powered actions, or even other full agents exposed as callable capabilities.

Hooks

Hooks can inject time, mutate context, run side effects, or shape the message history without relying on the model to remember everything.

Agent rules

Rules define turn limits, validation requirements, tool-call behavior, and domain-specific constraints.

File system and sandbox

Each agent should have its own workspace and safe code execution environment so it can produce artifacts and run code without broad OS access.

Orchestration

Recursive sub-agents turn one giant context problem into many smaller domains

The talk's final architecture is recursive. A coordinator may call a Salesforce agent, which may call a Google Workspace agent, which may call an asset generator, while a legal agent or GDPR agent reviews specialized risk. The value is that deep domain context stays inside the sub-agent that actually needs it.

Platform Notes

What this means for your agentic AI platform

This talk reinforces the same direction as the earlier research digest: build a platform around composition, registries, contracts, and orchestration, not around one master prompt with every possible tool.

  • Treat each Sub-Agent as a deployable package with its own prompt, tools, rules, memory, filesystem, sandbox, and evals.
  • Keep the Master Agent as a coordinator and router, not as the place where every domain capability accumulates.
  • Model Skills as contracts inside a domain agent, but avoid attaching all skills to the global context.
  • Expose MCP tools through domain-specific agents where possible, so tool schemas stay close to the domain that understands them.
  • Let BA teams define Flow Markdown that composes domain agents rather than stuffing every business rule into one prompt.
  • Use orchestration traces to show which agent acted, what context it received, which tool it used, and why it handed off.
  • Measure token efficiency per domain agent, because small context windows are one of the main economic arguments for this pattern.

Strong opinion: domain-specific agents are the cleaner abstraction for BA-built multi-agent systems because they turn business capability into a composable runtime unit.
