Closed-Loop Evals For Multimodal Agents

A detailed reading guide to Soumya Gupta and Jai Chopra's Uber talk on building eval loops for a food-photo enhancement agent at marketplace scale: routing, QA, human labels, auto-tuning, diagnoser agents, pass@K, and production feedback.

Source: AI Engineer Speakers: Soumya Gupta and Jai Chopra, Uber Length: about 21 minutes Transcript: 605 caption rows, about 3,775 words

Executive Summary

The talk is a concrete production case study from Uber Eats: improve low-quality merchant food photos without making them look fake, generic, or unfaithful to the actual dish. The technical lesson is that a multimodal generation pipeline only becomes shippable when every stage has its own evals and every eval feeds a closed learning loop.

  • The agent system: understand the image, route it to skip or enhance, generate an image-specific edit prompt, run image editing, use QA feedback for retry loops, then run a final publish-ready QA gate.
  • The eval philosophy: every component needs its own metric. Router evals look like classifier evals. Editor evals use pairwise comparison and pass@K. Final QA uses redundant policy and quality checks.
  • The closed loop: sample production data, label it with objective guidelines, compare against agent outputs, diagnose which agent failed, auto-tune config, benchmark against golden data, then ship or rollback.
  • The platform lesson: logging and flat trace structure are not an afterthought. Without observability, there is nothing to optimize, no drift detection, and no safe self-improving loop.

Business Context

Uber Eats has a massive, global marketplace. The speakers describe a delivery marketplace operating across thousands of cities and adding millions of items every month. In that environment, visual content is not decoration. The photo is often the first signal a consumer gets about a merchant, and it can affect whether someone scrolls past, clicks, adds to cart, or completes an order.

The operational problem is that many smaller merchants do not have the time, know-how, or budget for professional food photography. But simply replacing their photos with obviously synthetic or heavily standardized AI images would damage trust. The agent must improve quality while preserving authenticity, merchant brand, dish faithfulness, and marketplace diversity.

Core tension: consumers want better photos, but they distrust images that look AI-generated or misrepresent the food. The system has to enhance, not invent.

System Goals

The goals create the shape of the eval architecture. This is not a generic image-generation agent. It has marketplace, trust, policy, safety, cost, and scale constraints.

Preserve authenticity

The output should look like a real merchant photo, not a generated stock image.

Improve selectively

Only enhance when there is real quality lift. Good images should often be skipped.

Optimize globally

The system should improve the marketplace without cannibalizing merchants or collapsing diversity.

Ship safely

Bad outputs should be blocked before publishing to menu pages.

Learn continuously

Production drift must feed back into diagnosis, tuning, and benchmark loops.

Control cost

Do not send already-good images through expensive generation paths.

Agent Architecture

The talk presents a simplified but representative production pipeline. It is a useful template for any multimodal agent that must decide whether to act, generate output, evaluate output, retry, and publish only when safe.

  1. 1UnderstandUse image, text description, dish metadata, and multimodal reasoning to produce structured output.
  2. 2RouteDecide whether to enhance the image or skip and keep the original.
  3. 3EditGenerate an image-specific prompt and run the image editing agent.
  4. 4QA LoopEvaluate plating, faithfulness, colors, naturalness, and other dimensions; retry up to K times.
  5. 5Publish GateRun final holistic policy and quality checks before publishing to the menu.

The final but essential layer is logging. The speakers emphasize that all agent stages are logged in a flat, readable JSON-like structure. This lets non-technical and technical stakeholders diagnose individual cases and aggregate metrics.

Start With Logging

One of the strongest lessons is that logging comes before optimization. If a team does not log each stage, decision, input, output, score, and failure reason, it cannot build a reliable learning loop. You cannot tune what you cannot inspect.

Trace field Why it matters Who uses it
Input metadata Dish name, merchant context, geo, image quality, and source modality affect expected behavior. Product, data science, policy, engineering.
Router decision Explains why an image was skipped or enhanced. ML engineers and operations reviewers.
Agent configs Allows diagnosis of which prompt, rubric, model, or version produced a result. Agent platform team.
QA feedback Feeds retry loops and auto-tuning. Prompt optimization and eval teams.
Publish status Shows whether output reached production or was rejected. Risk, support, and product teams.
Logging is not just observability. In closed-loop agents, logging is training material for future correction.

Router Agent

The router is the first major decision point. It receives multimodal inputs such as the image, text description, and metadata. It asks the LLM or vision model to describe what it sees, creates structured output, grades against a rubric, and decides whether the image should be enhanced or skipped.

Because the router makes a binary or multi-branch decision, its eval resembles a classifier eval. For a simple enhance/skip decision, a confusion matrix is enough. For a more complex router that sends images to different models, latency tiers, or policy branches, the matrix becomes n by n.

Router outcome Business meaning Risk
True positive Bad image is correctly sent for enhancement. Desired behavior.
True negative Good image is correctly skipped. Desired behavior and cost saving.
False positive Good image is unnecessarily enhanced. Compute waste and risk of degrading a good photo.
False negative Bad image is approved or skipped incorrectly. Quality issue or hallucination risk downstream.

Guardrail metric: for the routing use case, the talk names recall as the critical guardrail because they do not want bad images slipping through the system.

Human Labels And The Golden Dataset

The first version of the model is aligned to human labels. The team collects a representative dataset across geography, dish type, image quality type, and other marketplace cuts. Human labelers use objective guidelines to reduce subjective bias and noise.

The agent output is compared against this golden dataset. If the agent meets guardrail metrics, the team can ship. If not, they tune and repeat. This is classic eval-driven development, but applied to multimodal marketplace outputs where mistakes can affect trust, merchant quality, and cost.

Representative cuts

Geography, dish type, quality level, and long-tail marketplace examples.

Objective labels

Guidelines reduce ambiguity in what counts as good, bad, faithful, complete, or risky.

Golden benchmark

The system must pass the benchmark before new config or model versions ship.

Routing Failure Modes

The examples are practical. A high-quality cheeseburger photo can be mistakenly routed for enhancement, wasting compute and risking quality regression. A chicken-wing image can be approved even though the dish name says eight pieces while the image shows six. If such an image is enhanced, the model might hallucinate extra wings to match the description.

The second case reveals why multimodal evals are harder than text evals. The system must compare image content, dish metadata, and expected faithfulness. The right decision is not always "make it prettier." Sometimes the safest output is to reject, skip, or ask for better source material.

The Closed-Loop Learning System

Static offline evaluation is not enough because production traffic drifts. New geographies, dish categories, merchant behavior, model behavior, and image quality distributions create new failure modes. Uber's design samples production data at a regular cadence, labels it, compares it to agent output, and triggers diagnosis when there is a mismatch.

  1. 1SampleCollect production examples at a regular cadence.
  2. 2LabelHuman labelers apply the same objective guidelines.
  3. 3CompareFind mismatches between labeler output and agent output.
  4. 4DiagnoseA diagnoser agent localizes which component needs optimization.
  5. 5TuneAuto-tune config, benchmark against golden data, and ship if guardrails pass.

The speakers describe this as config-driven and able to run without a human directly editing every prompt. Human labels still provide the source of truth, but the diagnoser and optimizer can automate the tuning path.

Diagnoser And Prompt Optimizer

The diagnoser is a higher-level abstraction that receives feedback from multiple loops and decides which agent or agents need to change. This is important because in a multi-stage system, a bad final output might come from routing, prompt generation, image editing, QA scoring, post-processing, or a policy gate.

The talk describes a prompt optimizer with two sub-agents: a reflect agent and a synthesize agent. The reflect agent examines matches and mismatches, removes noise, and identifies systemic issues. The synthesize agent updates the target agent config from that feedback, then the new version is benchmarked. If it passes, it is registered in the agent store for future production runs.

Component Input Output
Diagnoser Feedback from labels, QA, dogfooding, production metrics, and failures. Which agent or config should be optimized.
Reflect agent Matches, mismatches, noisy labels, and failure patterns. Clean diagnosis and systemic issue summary.
Synthesize agent Diagnosis plus current agent config. Updated config or prompt proposal.
Benchmark gate Candidate config plus golden dataset. Ship, reject, or iterate.

Image Editing Loop

The enhancement step is not a single prompt. First, the system generates an image-specific prompt using the image description and directives from the routing agent. Then it edits the image. Then a QA gate evaluates multiple dimensions such as plating, faithfulness, colors, and realism. If QA fails, the feedback returns to prompt generation and the system tries again.

This creates two possible outcomes. The edited image passes QA within K iterations and is eligible for publishing, or the system takes a coverage hit and does not enhance that image. That coverage hit is intentional: it is better to leave an image unchanged than publish a misleading or low-quality generated edit.

Production principle: a good generation pipeline needs the courage to not generate. Skip and reject are product features, not failures.

Pass@K And Pairwise Comparison

The enhancement loop is measured with pass@K: the pass rate by the Kth iteration. In a well-designed feedback loop, pass rate should improve as the editor receives QA feedback. But pass@K must be grounded in good quality definitions, or the loop can reward meaningless changes.

The talk says Uber uses pairwise comparison for these evals: compare the input image and output image and judge whether the output is actually better. "Better" is defined through alignment with product, design, policy, and legal stakeholders. Quality includes faithfulness, completeness, naturalness, realism, and other proprietary dimensions.

Faithfulness

The output must not add food, ingredients, portions, or dish details that were not present.

Completeness

The edit should not remove important components, sauces, portions, or visual context.

Naturalness

The image should look like plausible food photography, not synthetic gloss.

Realism

Physics, object coherence, plating, and spatial relationships should make sense.

Editor Failure Modes

The examples reveal why image editing evals need to be multi-dimensional. One output adds shrimp that were not in the original photo, violating faithfulness. Another removes sauce from sushi, violating completeness. Another overcorrects after QA feedback and falls back to a generic bowl, which the speakers frame as reward hacking or a meaningless change.

Another failure shows the output plate covering the sauce, a physics and object-coherence problem. The team treats some of these frontier-model artifacts as issues to coordinate with model teams, because base model limitations can leak into applied production systems.

Failure What went wrong Eval needed
Ingredient addition The output adds food not present in the original. Faithfulness and dish-content comparison.
Ingredient removal The output removes sauce or components that should remain. Completeness and source-object preservation.
Over-conservative edit The model changes pixels without meaningful quality lift. Pairwise improvement and reward-hacking detection.
Object incoherence Plating or physics becomes implausible. Realism, object coherence, and physical plausibility.
Uncertain count The system cannot verify whether visual pieces match metadata. Unsure or reject path, not forced acceptance.

Publish-Ready QA

After the editing loop, Uber runs a final post-processing and publish-ready QA gate. This checks policy and holistic quality before anything goes live. The speakers describe this as a Swiss cheese model: multiple imperfect layers reduce the probability that a bad output reaches production.

This redundancy is deliberate. Some issues should have been caught upstream, but the final gate is allowed to catch them again. In high-volume agentic systems, duplicated safety checks are not waste when the downside of publishing a bad output is high.

Three Feedback Loops

The talk summarizes more than one loop. The model loop aligns with human-labeled data and handles drift. The dogfooding loop captures internal feedback from people testing the system before broad rollout. The production loop uses marketplace metrics such as conversion, add-to-cart, order completion, and segment-specific performance.

Loop Feedback source Optimization target
Model loop Human-labeled production samples and golden datasets. Agent config, routing rules, prompt generation, QA rubrics.
Dogfooding loop Internal thumbs up/down, free-form comments, merchant or design feedback. Known bad examples, qualitative issues, product fit.
Production loop Marketplace metrics sliced by geo, device, dish type, and other segments. Business outcomes and segment-specific tuning.

My Read

This is one of the best examples in your library for how production evals should work. It does not treat evals as a leaderboard number. It treats evals as control surfaces for a multi-agent system. Every stage has its own failure modes, metrics, and learning loop.

The most important lesson for your platform is the diagnoser abstraction. As soon as a workflow has multiple agents, feedback must be routed to the right component. Otherwise teams will keep tuning the visible prompt while the real problem sits in routing, QA, data labels, policy, or production drift.

I would directly borrow four things: flat readable traces, human-labeled golden datasets, component-level evals, and a config-driven auto-tuning loop that must pass benchmarks before deployment. That is the difference between "agent demo" and "agent system that can stay alive in production."

Bottom line

Closed-loop evals are not just a testing strategy. They are the operating model for multimodal agents at scale: observe everything, label drift, diagnose precisely, tune safely, benchmark before release, and use production outcomes to keep improving.
