Choosing the Right Multi-Agent Architecture

A decision guide from LangChain's short walkthrough on when to stay with one agent and when to choose supervisor, handoff, skills, or router-style multi-agent patterns.

Video: Choosing the Right Multi-Agent Architecture Channel: LangChain Transcript: English captions, 167 rows

The Short Version

LangChain presents multi-agent architecture as a tradeoff problem, not a default design choice. The first question is whether a single agent with good tools is enough. If the task becomes complex, choose a pattern based on four criteria: distributed development, parallelization, multihop conversational support, and direct user interaction.

  • Supervisor/sub-agents: strong for distributed development, parallel tool calls, and orchestrated multihop work, but weak for direct user-to-sub-agent interaction.
  • Handoffs: strongest when users need to move between specialized agents across a conversation.
  • Skills and routers: useful alternatives when you need progressive disclosure or parallel routing without full agent-to-agent handoff behavior.

Core Thesis

Multi-agent architecture is something you earn through complexity.

Sydney from LangChain opens with a caution: you may not need a multi-agent pattern. Many tasks are better handled by one capable agent with well-designed tools. Multi-agent design becomes useful when complexity rises enough that decomposition, ownership boundaries, parallel execution, or conversational handoff become important.

This is a healthy engineering framing. The question is not "Which multi-agent framework is coolest?" The question is "Which coordination structure matches the work?" That makes the architecture choice easier to explain to business analysts, product owners, and platform teams.

For a platform, the first workflow question should be: can this be one agent plus tools, or does the business process truly need multiple agent roles?
Selection Criteria

LangChain scores architectures across four practical dimensions.

The talk uses four criteria to compare patterns. They are useful because they separate organizational scaling from runtime behavior. A pattern can be great for distributed team ownership but weak for direct user interaction, or great for parallel work but poor for multihop conversations.

Criterion 1

Distributed development

Can different teams maintain agents, components, skills, or domains independently?

Criterion 2

Parallelization

Can the system invoke multiple agents or specialist capabilities at the same time?

Criterion 3

Multihop support

Can the architecture call multiple specialists in series while carrying forward context?

Criterion 4

Direct user interaction

Can a specialist agent talk directly with the user when the conversation requires it?

Pattern 1

Supervisor/sub-agents treat specialist agents as tools controlled by a main agent.

The first pattern is sub-agents, also called the supervisor pattern. A main supervisor agent coordinates specialist sub-agents as tools. All message routing passes through the supervisor, which decides when and how to invoke each sub-agent.

This is strong when multiple teams own different specialists or tools. It also works well with parallel tool calling: the supervisor can invoke multiple sub-agents in parallel. Multihop work is manageable because the supervisor can run multiple model-tool cycles. The weakness is direct user interaction: users do not naturally converse with each sub-agent.

User Request

User sends a goal to the main supervisor.

Main Supervisor

Classifies the task, decides specialists, and controls routing.

Tool Sub-agent A

Runs focused work as a callable capability.

Tool Sub-agent B

Can run in parallel or in a later cycle.

Output Final answer

Supervisor synthesizes and responds to the user.

Pattern 2

Handoffs let agents transfer control to one another during a conversation.

In the handoffs pattern, the entrypoint agent can hand control to another specialist agent, and agents can hand off to each other. Any of the agents may eventually generate the final response. This is less centralized than the supervisor pattern.

The tradeoff is ownership and coordination. It is harder to develop agents independently when each one needs to know how to hand off to others. It is also not ideal for parallelization. But it is excellent when the user needs a multihop conversation and direct interaction with whichever specialist is currently responsible.

Best fit

User-facing specialist transitions

Use handoffs when a conversation should visibly move between specialized agents, such as support, billing, technical triage, and escalation.

Watch out

Coupling between agents

Agents need clear handoff contracts, shared state rules, and failure behavior, otherwise the conversation can become brittle.

Pattern 3

Skills are a quasi multi-agent pattern built around progressive disclosure.

LangChain describes skills as specialized prompts and knowledge loaded on demand. One core agent stays in control, but it can load relevant skill context when needed. This is progressive disclosure: the system avoids loading every instruction, domain rule, and knowledge file up front.

Skills score well for distributed development because different teams can maintain different skills. They also support multihop workflows and direct user interaction because there is still one main conversational agent. Parallelization is possible but less direct because loading and using skills can become a two-step process.

Use skills when Why it works Platform design note
You need domain-specific SOPs or policies. The agent loads only the skill relevant to the task. Give each skill ownership, versioning, test cases, and required tools.
You want one user-facing agent. The conversation stays simple while capability changes behind the scenes. Use skills as BA-authored modules instead of giant persona prompts.
You need progressive disclosure. The context window is preserved for the current problem. Create skill indexes, activation conditions, and evidence contracts.
Pattern 4

Router architectures classify input, call one or more specialists, then synthesize results.

The router pattern begins with a routing step. The router classifies the input and directs work to one or more specialized agents. A synthesizer then combines the results into a response. The router and synthesizer can be agentic, but they can also be deterministic.

This pattern is strong for parallelization because a router can call multiple specialists at once. It is weaker for multihop conversations because the architecture is not naturally built around repeated specialist calls in series. LangChain suggests that if you need a stateful router, a practical option is to wrap the router in a tool.

Input User request

A request arrives and needs classification.

Route Classifier

Router chooses one or more specialists.

Fan out Specialists

One or many agents execute focused work.

Join Synthesizer

Results are merged and resolved.

Output Combined response

User receives one synthesized answer.

Platform Takeaways

For your agentic platform, make architecture selection an explicit BA-side decision.

This video is useful because it turns multi-agent design into a simple selection problem. A business analyst should not have to know LangGraph internals to decide whether a flow needs a supervisor, handoff, skill, or router. They should answer business questions that map to an architecture.

  • Start with the single-agent baseline. Require the flow author to explain why one agent plus tools is insufficient.
  • Use supervisor when ownership is modular. Master Agent plus sub-agents is best when teams own specialists and the platform needs central routing.
  • Use handoffs for user-facing role changes. Handoffs fit service journeys where the active specialist should speak directly to the user.
  • Use skills for progressive disclosure. Skills are ideal for SOPs, policies, domain knowledge, and cognitive/actionable capability modules.
  • Use routers for classification and fan-out. Routers are strong for independent specialists whose outputs can be synthesized.
  • Capture the four criteria in the flow spec. Distributed ownership, parallelism, multihop needs, and direct interaction should be first-class fields.
Flow Markdown

A reusable architecture-selection template.

Use this as the first page of a BA-authored agent flow. It forces the author to justify the multi-agent pattern before defining prompts, tools, skills, and handoff behavior. 

---
flow_id: customer_support_multi_agent_triage
architecture_decision:
  default_considered: single_agent_with_tools
  reason_single_agent_is_not_enough:
    - requires_specialist_user_handoffs
    - requires_parallel_policy_and_ticket_lookup
  selected_pattern: hybrid_supervisor_plus_handoffs
selection_criteria:
  distributed_development:
    score_needed: high
    rationale: support, billing, and technical teams own separate specialists
  parallelization:
    score_needed: medium
    rationale: policy lookup and ticket search can run together
  multihop_conversation:
    score_needed: high
    rationale: user may move from triage to specialist to escalation
  direct_user_interaction:
    score_needed: high
    rationale: specialist agent should ask follow-up questions directly
agents:
  supervisor:
    responsibility: classify_request_and_route
    tools: [customer_profile_lookup, agent_registry_search]
  support_specialist:
    pattern_role: handoff_target
    skills: [support_sop, refund_policy, ticket_summary]
  billing_specialist:
    pattern_role: handoff_target
    skills: [invoice_lookup, payment_policy]
  policy_checker:
    pattern_role: supervisor_tool
    skills: [risk_review, compliance_summary]
handoff_contract:
  required_fields:
    - reason_for_handoff
    - context_summary
    - unresolved_questions
    - allowed_actions
validation:
  success_metrics:
    - correct_route_rate
    - handoff_completion_rate
    - user_repetition_rate
    - escalation_accuracy
---
