Muon is Scalable for LLM Training

Scaled the Muon matrix optimizer to language-model training by orthogonalizing momentum updates, adding weight decay, and calibrating update scale.

The problem

What was missing before this work

AdamW treats coordinates largely independently and keeps two moment estimates per parameter. Muon proposed geometry-aware updates for 2D weight matrices but had not been validated at large language-model scale.

Scaling requires stable weight decay, comparable update magnitude across differently shaped tensors, and efficient distributed orthogonalization.

Core idea

The paper in one idea

Build momentum for each hidden weight matrix, then approximately orthogonalize that update with Newton-Schulz iterations. This gives singular directions more balanced update magnitude than raw momentum.

Use AdamW for embeddings, normalization, biases, and other non-matrix parameters. Add decoupled weight decay and a shape-aware scale so Muon works across model sizes.

Muon update ≈ NewtonSchulz( momentum_matrix ), scaled per parameter and combined with weight decay.

Mechanism

How the method works

Compute gradients and momentum. Normalize the matrix, run several Newton-Schulz polynomial iterations using matrix multiplications, rescale the result, apply weight decay, and update the weight.

Shard or communicate updates with an implementation designed to avoid storing unnecessary full optimizer state.

Technical deep dive

The machinery that matters

Orthogonalization is approximate and chosen because matrix multiplications map efficiently to accelerators. Update-scale calibration is critical: an orthogonal matrix’s entry and spectral statistics differ from Adam-normalized updates.

Muon reduces some optimizer-state requirements but adds matrix-multiplication work. Its cost depends on shape, parallelism, precision, and Newton-Schulz iteration count.

Evidence

What the experiments established

The paper’s scaling-law experiments reported about two-times compute efficiency versus AdamW under its compute-optimal setup and trained the Moonlight 3B/16B MoE model on 5.7T tokens.

Those results are substantial but come from one training stack and model family. Independent evidence across architectures and data regimes is still developing.

Why it mattered

How it changed the field

Muon reopened optimizer design as a major LLM scaling lever and demonstrated that matrix geometry can be exploited with accelerator-friendly operations.

It also encouraged teams to benchmark training loss per FLOP rather than compare optimizer steps or wall time without systems context.

Engineering use

What an AI engineer should do with it

Start with a small scaling sweep and match total tokens, FLOPs, and data order against AdamW. Monitor update RMS, spectral norms, loss spikes, and per-parameter category.

Keep an explicit parameter partition: matrix weights on Muon, vectors and special parameters on AdamW. Validate distributed numerical agreement and checkpoint resume.

Limits and later corrections

Where the result stops

Evidence is newer than AdamW’s broad deployment history. Orthogonalization assumptions fit matrix weights better than all parameter types, and kernel or communication overhead can erase gains.

Hyperparameter transfer, very small matrices, fine-tuning, multimodal models, and long-horizon stability need workload-specific validation.

Connections

Where this paper sits in the learning path

Muon complements scaling-law work by changing optimization efficiency rather than model/data allocation. It sits beside MoE methods that reduce active compute through architecture.

Takeaways

What to remember

  • Muon orthogonalizes momentum updates for matrix parameters.
  • Newton-Schulz uses accelerator-friendly matrix multiplications.
  • Weight decay and update scaling enabled larger runs.
  • Not every parameter should use Muon.
  • Compare loss per total FLOP under controlled data.
  • Current evidence is promising but still young.
