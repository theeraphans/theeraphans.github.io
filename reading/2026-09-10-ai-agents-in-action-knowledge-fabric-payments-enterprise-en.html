Arise Tech Meetup #10 follows enterprise agents from organizational knowledge and governed execution through AI-assisted work, persistent virtual teams, and the payment rails agents need when they can spend money.

Executive summary

An enterprise agent needs context, capability, control, continuity, and settlement

The meetup shows why a production agent is much more than a model with a prompt. It must understand how the organization works, retrieve current and traceable knowledge, invoke tools within policy, preserve work across sessions, expose uncertainty to humans, and—when commerce is involved—request and prove payment safely.

The through line

Autonomy amplifies whatever surrounds it. Good context creates useful judgment; weak governance creates invisible risk; durable workflow turns a chat into a coworker; payment turns a software bug into a financial incident.

Session one · 04:16

Build an AI Knowledge Fabric for Your Organization

Surasuk Oakkharaamonphong and Nitchakran Chaipojjana demonstrate a system that assembles fragmented enterprise knowledge into a connected map. The objective is not another document repository. It is to let people and agents trace how customer journeys, front-end screens, APIs, microservices, dependencies, and operational decisions relate.

From documents to connected evidence

The system scans service definitions and endpoints, extracts dependencies, and maps them into a graph. For front-end journeys, it uses a Figma MCP connection to interpret screens and relate them to application code and backend APIs. A person investigating a broken QR-scanning flow can move from the screen to the relevant endpoint and service rather than searching isolated systems manually.

SourcesCode, APIs, Figma, docs

Collect evidence from systems where work already lives.

NormalizeResolve entities

Identify screens, services, endpoints, journeys, and decisions.

RelateBuild the graph

Connect UI actions to code and downstream dependencies.

ServeExpose through MCP

Let assistants answer questions over the same governed context.

ImproveCapture feedback

Use uncertainty and corrections to refine knowledge.

The presenters describe maturity stages: foundational context, rule-based automation, semantic consolidation, agentic governance, and eventually enterprise knowledge that evolves through use. Provenance is central. If an answer comes from stale or conflicting material, users need to know which source produced it and how the system decided.

Human review is part of the data model

When the system cannot confidently map an entity or resolve a conflict, it raises a checklist for human review. Messy Figma organization is given as a concrete failure source: if design files are scattered and inconsistent, the generated journey map is also noisy. AI does not remove upstream information quality; it makes that quality visible.

Knowledge Fabric is not “put everything into a vector database”

The valuable layer contains identity, relationships, time, provenance, confidence, and ownership. Semantic retrieval helps discovery, but the enterprise still needs authoritative sources and a correction workflow.

Session two · 45:00

AI Agents Development and Application in Business

Panutat Tejasen argues that agents differ from RPA and chatbots. RPA follows a known script. A chatbot generally explains what a person should do. An agent chooses actions and performs them. That autonomy removes development friction but raises governance requirements.

His first management question is surprisingly operational: How many agents does your organization have? When employees can create agents with almost no barrier, central teams may not know what exists, who owns it, what credentials it holds, how much it spends, or whether it is still operating.

Teach work, not merely a static role

Traditional low-code systems often begin with fixed personas and dragged workflow boxes. Panutat expects stronger models to need less rigid control flow. The useful input becomes the expert's method: how an accountant reviews a transaction, how HR screens a resume, or how an administrator converts a purchase order into a contract.

This should not be read as “remove the workflow.” Business methods still contain mandatory controls, evidence requirements, and approvals. The agent can choose among allowed paths, but regulated transitions should remain explicit.

InventoryEvery agent needs an owner.

Register purpose, team, model, environment, data classes, tools, and lifecycle status.

IdentityAgents act as principals.

Use short-lived scoped credentials instead of sharing a human account or master key.

BudgetAutonomy needs economic limits.

Track token, tool, payment, and infrastructure cost with enforceable ceilings.

Audit trailReconstruct every consequential action.

Store intent, policy decision, tool call, result, approval, and resulting state.

GatewayTools enforce policy.

A smart gateway checks permissions, rate limits, sensitive targets, and approval requirements.

ReviewRisk determines oversight.

Low-risk reading may be autonomous; payments and production changes need stronger checkpoints.

The session emphasizes memory across sessions. If an invoice was rejected, the agent should learn the reason without turning one incident into an unsafe global rule. Durable memory therefore needs scope, provenance, confidence, update authority, and expiration—not simply a longer chat log.

Session three · 97:58

AI Agents at Work: How Agents Are Changing Business

Poramate Minsiri uses demonstrations from the WARROOM community to show agents performing research, content production, browser work, and multi-step execution. His larger claim is that AI should move from occasional chat to a persistent work surface that can accept goals, use tools, and continue while the person does something else.

The demos illustrate leverage but also the danger of evaluating by spectacle. A polished video, document, or completed browser sequence does not reveal hidden retries, cost, permission breadth, source quality, or how often the workflow fails. Production adoption needs repeatable evals and evidence beyond the best run shown on stage.

Do not pay LLM reasoning for deterministic repetition

A useful discussion emerges around skills and scripts. If a deployment procedure has become stable, ask the agent to write and invoke a script rather than repeatedly reason through the same steps. A skill can teach when and why to use the script; the script performs the deterministic action quickly and consistently.

The session also warns about downloaded skills. A Markdown file can contain instructions that invoke shell commands, exfiltrate data, or install dependencies. “It is only a skill file” is not a security argument. High-risk projects should review every imported skill and the tools it can reach.

Session four · 158:03

Virtual Assistant: Turn organizational work into a durable agent loop

Ohm Samkoses, Nanont Noparat, and the team present an approach for transforming roles such as business analyst, developer, and reviewer into reusable work protocols. Rather than hiding the system behind a chatbot, they store role instructions, artifacts, conventions, and workflow state as readable files alongside the workspace.

The spine is a staged operating procedure

The central loop is Assemble → Discuss → Plan → Execute. Each stage has a distinct purpose and can require human-in-the-loop review according to risk.

AssembleGather relevant context

Load prior requirements, architecture, standards, and related work.

DiscussResolve ambiguity

Surface gaps, alternatives, risks, and questions before commitment.

PlanDefine artifacts and checks

Translate intent into ordered work, acceptance evidence, and approval points.

ExecuteCreate and verify

Perform tasks, update artifacts, test results, and record decisions.

ResumeContinue from durable state

Read the saved stage and work products after a session closes.

A spine.md-style file describes the loop; role instruction files define what each participant needs to know; skill files encode reusable methods; and file-based state preserves work in progress. This makes the system inspectable by both humans and agents and avoids placing all continuity inside a vendor-specific conversation.

Risk appetite controls autonomy

Not every stage needs the same approval. A mature low-defect workflow may reduce human review, while sensitive payment or production work should keep close supervision. The team imagines adjusting human-in-the-loop checkpoints as evidence improves, rather than declaring an entire agent “autonomous.”

They also show a nontechnical interface using Obsidian mounted over the workspace. Business users can edit Markdown artifacts and interact through a side panel while technical users retain CLI and repository workflows. The important design decision is a shared artifact contract, not forcing every role into one interface.

Knowledge gaps do not disappear through orchestration

In Q&A, the team notes that highly specialized domains such as healthcare may not fit a generative model as the decision engine. Deterministic rules, traditional predictive models, and expert review should handle precise vertical judgments; the LLM can orchestrate, explain, gather context, or route work around them.

Session five · 205:13

Blockchain Agentic Payments: The payment layer for AI agents

Dome Charoenyos argues that once agents purchase APIs, data, content, or physical services, payments must become machine-readable and programmable. Human checkout flows, sessions, CAPTCHAs, cards, and manual login are poor interfaces for software acting at high frequency.

The session contrasts several emerging approaches. Coinbase's x402 revives HTTP status 402: a service returns payment instructions, the client signs a payment payload, and a facilitator verifies and settles it. Tempo exposes MPP for machine payments, including sessions and streaming payment patterns, on a payment-focused chain. Other ecosystems such as Circle's Arc are positioned around stablecoin settlement.

RequestAgent asks for service

An API or seller describes price and accepted payment method.

PolicyCheck delegated authority

Validate merchant, purpose, amount, currency, budget, and approval rule.

SignCreate bounded authorization

Use a scoped wallet or key without exposing unrestricted funds.

SettleVerify payment

The protocol or facilitator confirms transfer and prevents replay.

ReceiptBind money to outcome

Record settlement, purchased resource, delivery, and final state.

Fast settlement is not sufficient safety

The talk values low-cost, high-throughput settlement and stablecoins. For an enterprise, the decisive layer is the payment gateway above the protocol. It must enforce spending authority, vendor policy, sanctions and compliance requirements, approval thresholds, currency rules, replay protection, and reconciliation.

Never give an agent a general-purpose wallet and call it autonomy

Inject a trusted recipient and purchase context at the gateway, bind approval to the exact merchant, asset, amount, and expiry, then require a provider receipt. Recheck every field at execution because conversation state can change after approval.

The session includes strong predictions about which chains and payment companies will win. These are the speaker's market opinions. x402 and MPP documentation confirms the protocol mechanics, not the investment outcomes.

This architecture keeps business meaning outside the model. The agent reasons over a governed environment, but the environment decides what data is authoritative, which actions are possible, and what evidence is required before a result becomes real.

For business analysts

BA users should compose contracts, not write giant persona prompts

The meetup offers a practical answer to involving nontechnical domain experts. Give the BA editable artifacts with bounded responsibilities:

  • Role charter: goal, scope, decisions allowed, escalation conditions, and prohibited actions.
  • Inputs: authoritative systems, required fields, freshness, and data classification.
  • SOP stages: Assemble, Discuss, Plan, Execute, Verify, and Close with entry and exit criteria.
  • Skill contract: when to use the skill, inputs, output schema, examples, and failure behavior.
  • Tool contract: side effects, permissions, approval requirement, idempotency, and receipt.
  • Outcome rubric: factual checks, business rules, user-quality checks, and abstention threshold.
  • Test cases: normal, boundary, prohibited, missing-data, and recovery scenarios drawn from real work.

A platform can render these as forms and diagrams while storing them as versioned Markdown or structured data. That gives BA users an approachable interface and engineering teams diffable, testable specifications.

Critical assessment

The event is strongest on operating boundaries, weaker on measured outcomes

StrongKnowledge needs provenance and relationships.

The demos correctly move beyond isolated RAG toward traceable enterprise context.

StrongAgent inventory is an immediate governance need.

Organizations cannot secure or fund systems they cannot enumerate.

StrongDurable file state improves portability.

Readable roles, artifacts, and stages help humans inspect and resume work.

StrongPayment raises the security class.

Spending authority requires stronger controls than research or drafting.

Missing evidenceMost demos lack reliability metrics.

The event provides few task-success, error, latency, adoption, review-cost, or incident measurements.

RiskFlexible agents can obscure mandatory process.

Autonomy should not replace explicit compliance gates, authorization, and deterministic validation.

The most useful conclusion is not that every business needs more agents. It is that any agent allowed to act needs a named owner, bounded tools, inspectable state, evaluation evidence, and a reliable stop condition.

Implementation playbook

Turn the meetup into an enterprise rollout

  1. Inventory existing agents, scripts, copilots, credentials, models, owners, and costs.
  2. Choose one bounded workflow with observable value and reversible side effects.
  3. Map its authoritative knowledge sources, relationships, provenance, and freshness.
  4. Write the SOP as stages with explicit entry, exit, evidence, and escalation conditions.
  5. Separate cognitive skills from actionable skills that require tools.
  6. Give every actionable tool a typed contract, least privilege, idempotency strategy, and receipt.
  7. Store durable work artifacts outside transient model context.
  8. Add human review at risk transitions, not indiscriminately after every model call.
  9. Evaluate the full trajectory, including tool choice, state changes, cost, and recovery.
  10. Use deterministic systems for numerical, regulated, or safety-critical decisions where possible.
  11. Route all financial actions through a payment gateway that revalidates approved details.
  12. Review imported skills as executable supply-chain dependencies.
  13. Use audit trails for operations and learning, not merely compliance storage.
  14. Expand autonomy only when production evidence supports the next reduction in oversight.

Takeaways

Fifteen ideas worth keeping

  1. Enterprise agents need a knowledge graph with provenance, not documents alone.
  2. Source disorder propagates into agent confusion.
  3. Uncertain mappings should become explicit human-review work.
  4. An organization must maintain an agent inventory.
  5. Every agent needs identity, owner, budget, tools, and lifecycle state.
  6. Memory should preserve lessons without silently globalizing one incident.
  7. Stable repetition belongs in scripts; skills teach the agent when to use them.
  8. Imported skills are executable supply-chain risk.
  9. Durable files make virtual teams inspectable and resumable.
  10. Assemble, Discuss, Plan, and Execute separate context from commitment.
  11. Human-in-the-loop placement should follow risk transitions.
  12. Specialized deterministic systems should own precise vertical decisions.
  13. x402 and MPP make machine payment technically convenient, not automatically safe.
  14. Payment approval must bind exact recipient, amount, purpose, and expiry.
  15. Production success requires outcome metrics beyond an impressive demonstration.
