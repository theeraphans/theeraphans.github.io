Langfuse + AWS AgentOps summary

Continuous Agent Evaluation

A detailed reading guide to Langfuse and AWS on continuous evaluation, monitoring, and operations of AI agents with Amazon Bedrock AgentCore, Langfuse, OpenTelemetry, offline experiments, CI/CD quality gates, and production feedback loops.

Source: Langfuse Speakers: Marc Klingen and Aris Tsakpinis Length: about 82 minutes Transcript: 1,986 caption rows, about 13,772 words

Executive Summary

The session argues that agent development needs the same lifecycle discipline that DevOps brought to software, but adapted for probabilistic, tool-using AI systems. The speakers frame AgentOps as a combination of infrastructure, tooling, people, process, and culture. Their concrete blueprint uses Amazon Bedrock AgentCore as the runtime and operations layer, Langfuse as the tracing and evaluation layer, and OpenTelemetry as the common data transport.

  • AgentOps is an evolution of DevOps: overloaded mono-agents should be decomposed into smaller agent components that teams can own across the lifecycle.
  • AgentCore provides production primitives: runtime, memory, gateway, identity, browser, code interpreter, and observability can be combined or used independently.
  • Langfuse provides the tooling layer: tracing, monitoring, prompt management, datasets, experiments, annotation queues, and online or offline evaluations.
  • OpenTelemetry is the bridge: traces from AgentCore-hosted agents can flow into Langfuse so teams can inspect LLM calls, tool calls, MCP interactions, latency, cost, and errors.
  • Evaluation is a flywheel: production traces reveal failures, failures become dataset items, datasets power experiments, and passing variants move through CI/CD into production.
  • The practical lifecycle has three stages: experimentation and HPO, QA/testing with CI/CD gates, and production operations with continuous monitoring.

Core Thesis

The main thesis is that production agents cannot be managed as one-off demos. They need an operating model. The speakers compare the current agent moment to earlier software eras: teams first build one big thing, scope expands, maintenance gets hard, and eventually the system has to be decomposed into smaller parts with clear ownership, testing, deployment, monitoring, and incident learning.

For agents, the problem is harder because quality is not just uptime. A request can finish successfully at the infrastructure level while still being wrong, irrelevant, toxic, too expensive, too slow, or using the wrong tool. That is why tracing and evals must be continuous, not an afterthought at the end of development.

AgentOps means treating traces, evals, datasets, prompts, tools, and deployment gates as one continuous operating system.

From DevOps To AgentOps

The talk starts by showing how teams drift into overloaded mono-agents. A simple agent begins with one scope, then adds more tools, more subflows, more sub-agents, and more responsibilities. Eventually it becomes hard to reason about and hard to operate. The proposed response is similar to microservices: decompose the agent system into smaller agent components that a small team can own.

The DevOps analogy matters because the speakers do not define AgentOps as a dashboard. They define it as a system of ownership. The same team should be able to develop, deploy, evaluate, monitor, and improve the agent across its lifecycle.

Old agent pattern AgentOps pattern Why it matters
One overloaded mono-agent. Smaller agents and tools with clear ownership. Teams can test, trace, debug, and improve smaller responsibility boundaries.
Evaluation done manually after launch. Continuous offline and online evaluation. Regression and production failures feed the next development cycle.
Local notebooks and ad hoc demos. Cloud-hosted dev, test, and prod environments. Agents are tested in infrastructure close to the real target environment.
Debugging by reading final answers. Tracing reasoning, tool calls, costs, latency, errors, and outputs. Teams can see where an agent failed, not only that it failed.

AgentCore Production Primitives

Aris presents Amazon Bedrock AgentCore as a modular set of primitives for building, deploying, and operating agents. The runtime hosts agent implementations in a serverless, scalable, secure way. Memory provides managed context. Gateway wraps APIs, Lambda functions, or MCP servers as tools. Identity gives agents a security model. Browser and code interpreter provide managed tools. Observability gives the operational layer required for tracing and debugging.

The practical point is that AgentCore is not only an agent framework. It is a production substrate around agents. Teams can bring different frameworks or models, then rely on managed runtime, security, tool access, and observability primitives.

Runtime

Serverless, scalable hosting for agent implementations, regardless of chosen framework or model.

Memory

Managed short-term and long-term context for more stateful agent interactions.

Gateway

Turns APIs, Lambda functions, and MCP servers into governed tools agents can call.

Identity

Gives agents a secure identity and access-management boundary.

Built-In Tools

Managed browser and code interpreter capabilities for web and code execution tasks.

Observability

Trace, debug, and monitor workflow steps, tool usage, latency, tokens, errors, and production behavior.

Langfuse As The Tooling Layer

Marc describes Langfuse as the LLM engineering platform layer: observability, production monitoring, tracing, prompt management, datasets, experiments, annotation, and evaluations. The important point for enterprise platforms is API-first interoperability. Teams can use SDKs, framework integrations, OpenTelemetry clients, gateway-level instrumentation, or direct APIs.

The talk emphasizes that nontechnical domain experts often need to collaborate on prompts and evaluation. That matters for your BA-side platform: the people who understand domain quality should not be blocked by raw code. They need controlled interfaces for prompts, datasets, labels, scoring, and review.

Tracing

Inspect each execution: inputs, outputs, LLM calls, tool calls, errors, latency, token counts, and cost.

Prompt Management

Version and collaborate on prompts so changes are reviewable and deployable.

Evaluation

Run online and offline scores with human feedback, model-based evaluators, rule-based checks, and datasets.

OpenTelemetry Connects The Stack

The integration is powered by OpenTelemetry. AgentCore emits telemetry in an OTEL-compatible format, and Langfuse can receive OTEL traces through its ingestion endpoint. The demo shows configuring environment variables and adding a small amount of code so an AgentCore-hosted Strands agent sends traces to Langfuse.

This is a key architecture lesson: do not lock agent observability into one proprietary SDK if the platform needs to support multiple frameworks, teams, and languages. A common telemetry standard lets you plug in tracing, dashboards, quality evaluation, and data pipelines without rewriting every agent.

Platform rule: instrument once, then reuse traces across local experiments, CI, production debugging, cost analysis, and evaluation datasets.

Evaluation Taxonomy

Marc lays out a practical evaluation taxonomy. Online evaluation uses production behavior: explicit feedback such as thumbs up and thumbs down, implicit feedback such as whether a user accepts or edits a suggestion, manual annotation, model-based scoring, and rule-based checks. Offline evaluation uses datasets and experiments to test changes before deployment.

The most important advice is to start with final response evaluation because it can stay stable while the implementation changes. Then add agent-specific checks such as trajectory evaluation, tool usage quality, safety or toxicity checks, cost, and latency.

Evaluation method Where it fits What it catches
Explicit user feedback Production Direct user dissatisfaction, usefulness, or trust signals.
Implicit user feedback Production Edits, acceptance, reverts, retries, abandoned flows, or human corrections.
Manual annotation Online and offline Ground truth, evaluator alignment, and root-cause labels.
LLM-as-a-judge Online and offline Flexible qualitative checks such as relevance, factuality, helpfulness, and toxicity.
Rule-based checks Online and offline Deterministic requirements such as required fields, format, citations, or forbidden content.
Trajectory evaluation Agent-specific testing Whether the agent chose the right tools, sequence, and intermediate reasoning path.

The Continuous Evaluation Flywheel

The operating model is a closed loop. Offline, the team maintains datasets covering happy paths, edge cases, and adversarial inputs. They run experiments against those datasets, compare quality/cost/latency, and deploy the best candidates. Online, they trace real user behavior, monitor quality, sample traces into annotation queues, and add new production failures back into the dataset.

This prevents eval datasets from becoming stale. Without production feedback, test sets quickly stop matching real user behavior. The flywheel keeps the evaluation system honest because it continuously absorbs the mistakes users actually experience.

  1. 1Collect DataCapture traces, user feedback, errors, latency, cost, and tool behavior.
  2. 2AnnotateReview sampled traces and classify failures into reusable categories.
  3. 3Update DatasetTurn real production failures into test items, edge cases, and adversarial cases.
  4. 4ExperimentTry model, prompt, tool, logic, and hyperparameter variants against the dataset.
  5. 5GateUse CI/CD quality thresholds before production promotion.
  6. 6MonitorWatch production traces and online evaluators after deployment.

Multi-Environment Setup

Aris strongly recommends separate dev, test, and production environments. This is partly for engineering discipline and partly for data security. Teams should avoid experimenting in production and should avoid casually using production data for development when policy or privacy does not allow it.

He also argues for cloud-native development early, especially when the production target is a cloud environment with managed tools and remote dependencies. The goal is to avoid spending weeks building something that only works on a laptop and fails once deployed into the actual runtime.

Practical read: for enterprise agents, "works locally" is not enough. The agent must work where the tools, permissions, network paths, telemetry, and security controls actually live.

Experimentation And HPO

The timestamp in the user's link lands in this part of the talk. The speakers describe a cloud-based experimentation and hyperparameter optimization phase. Instead of guessing which model, prompt, and configuration is best, the team deploys a fleet of ephemeral agents, each with a different combination, evaluates them against a golden dataset, compares quality, latency, and cost, then tears down the temporary agents.

The sample repository implements this with an experimentation/hpo.py script and configuration files that define combinations such as models and system prompts. The important design pattern is the use of ephemeral infrastructure: create only what is needed for the experiment, collect the results, then clean up resources to control cost and reduce clutter.

Experiment variable Example Evaluation signal
Model Different foundation models or model sizes. Quality, cost, latency, tool success, and hallucination rate.
Prompt Different system prompts, language policies, or role instructions. Final response factuality, tone, relevance, and compliance.
Tool set Different MCP tools or APIs exposed to the agent. Tool selection accuracy, tool call success, and unwanted tool usage.
Runtime configuration Timeouts, memory, concurrency, retry strategy, and guardrail settings. Reliability, speed, cost, failure rate, and user experience.

QA And CI/CD Gates

After experimentation finds a promising configuration, the system moves into QA and testing. The example uses GitHub Actions, but the architecture is tool-agnostic. A pipeline deploys an ephemeral agent in the test environment, runs evaluation on a dataset, checks whether the score passes a threshold, cleans up the test agent, and only then deploys the persistent production agent.

This is where agent quality becomes operational, not subjective. A prompt change, model change, tool description change, or code change should not reach production just because it looks better in one manual run. It should pass the expected thresholds on a representative dataset.

  1. 1Push CodeA repository change triggers the pipeline.
  2. 2Deploy Test AgentCreate an ephemeral runtime in the test environment.
  3. 3Run EvalsExecute dataset cases with factuality, toxicity, trajectory, cost, and latency checks.
  4. 4Check ThresholdBlock promotion when scores fall below the required bar.
  5. 5Clean UpDelete ephemeral resources to manage cost and inventory.
  6. 6Deploy ProdPromote only passing versions into persistent production runtime.

Production Operations

Production operations close the loop. The demo includes simulated production users and online evaluation such as toxicity checks. The agent receives both regular prompts and harmful prompts, traces flow into the observability layer, and evaluators score incoming production behavior. Teams can inspect flagged traces and decide whether to add them to datasets, update prompts, change tools, or adjust guardrails.

The key cultural point is that production monitoring is not only for uptime. It is also for product quality. A live agent needs quality alerts, trace review, evaluator drift checks, user-feedback review, and a queue for turning real failures into future regression tests.

Production rule: every serious production incident should produce at least one reusable eval case or runbook update.

Annotation Queues And Human Review

Manual annotation is described as tedious but necessary. Teams often want to skip it, but without human labels it is difficult to trust automated evaluators or understand new failure categories. Annotation queues let humans review sampled traces, label errors, add comments, and feed better examples into datasets.

For a BA-facing platform, this is especially important. Business users can become reviewers of agent behavior without writing code. They can classify whether an answer is correct, whether a tool was appropriate, whether the output violated policy, or whether the agent missed domain context.

Translation For Your Agentic AI Platform

This video maps directly to the platform you are building. It gives a practical operating model for Master Agents, Sub-Agents, Skills, Tools, and MCP. The main lesson is that the platform should not only let BA users compose agents. It must also let them define eval datasets, review traces, approve promotion gates, and feed production failures back into workflows.

A good BA experience would let a non-engineer define the business flow, expected outputs, allowed tools, failure labels, golden examples, edge cases, and production review workflow. Engineering then provides the runtime, observability, tool integration, permissions, and deployment pipeline.

My Read

This is one of the more directly useful videos for your agentic AI platform. It gives you the missing operational half of Master Agent, Sub-Agent, Skill, and Tool/MCP design. Building the agent graph is only half the product. The other half is proving that the graph still works after prompts, tools, models, datasets, user behavior, and business rules change.

The strongest idea to borrow is the promotion model: every agent workflow should move from experiment to test to production through explicit datasets, eval scores, trace review, and human approval when needed. For BA users, the platform should hide the infrastructure complexity but expose the quality artifacts: test cases, failure labels, review queues, and promotion gates.
