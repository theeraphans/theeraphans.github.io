KV Cache Makes LLM Serving a Memory Problem

A practical summary of IBM Technology's explanation of why LLM latency and throughput often collapse at concurrency: not because the model changed, but because GPU memory, KV cache allocation, and attention paging decide how many requests can run efficiently.

The Short Version

The video says LLM serving bottlenecks often appear when concurrency rises. One user feels fast. Ten users start to show latency. A hundred users can spike GPU memory and crush throughput. The model is not always the problem. The serving system may be wasting memory while storing and retrieving context token by token.

  • KV cache: stores prior keys and values so the model does not recompute attention history for every new token.
  • Paged attention: stores KV cache in small non-contiguous pages, like virtual memory, instead of giant contiguous blocks.
  • Tuning: GPU memory utilization, prefix caching, chunked prefill, and speculative decoding can improve throughput or latency depending on workload.

LLM inference has two different bottlenecks

When you send a long prompt, there is a pause before the first token streams back. That is the prefill phase: the model runs the prompt through transformer layers to build representations before it can emit the first output token. Prefill is compute-bound.

After that, the model generates one token at a time. That is the decode phase. Decode repeatedly reaches into GPU memory to retrieve the context built so far. Decode is memory-bound, which is why fragmented or inefficient cache allocation becomes visible as latency.

Phase What happens Main pressure
Prefill Process the input prompt through transformer layers before the first output token. Compute
Decode Generate tokens one at a time while attending over the growing context. GPU memory bandwidth and cache layout

KV cache trades memory for compute

In transformer attention, each token produces query, key, and value representations. During autoregressive generation, a naive system would recompute keys and values for all previous tokens at every step. For a thousand-token response, the thousandth token would recompute information for the previous 999 tokens.

KV cache avoids that by storing the keys and values from previous steps. Each new token computes its own query, key, and value, then attends over cached history. The tradeoff is clear: use more memory to avoid repeated compute.

KV cache is worth it for long sequences, but it makes memory layout one of the central problems in LLM serving.

The problem is wasted KV memory

The video gives a simple memory picture: a 13B parameter model may take roughly 26 GB just for weights on a 40 GB GPU. That leaves the remaining memory for KV cache across active requests. Traditional systems pre-allocate a fixed contiguous block for each request based on the maximum possible output length. If most requests use far less than the maximum, much of that allocation sits empty.

Internal fragmentationReserved memory is unused because the request generated fewer tokens than the maximum block.
External fragmentationEnough total memory may exist, but no contiguous region is large enough for a new request.
Duplicate prefixesShared system prompts may be stored separately for many concurrent requests.

Paged attention fixes this by applying the virtual memory idea to KV cache. Instead of one huge contiguous block, it breaks cache into fixed-size pages that can live anywhere in GPU memory. A lightweight block table maps logical pages to physical VRAM pages, so allocation becomes on-demand and non-contiguous.

Production tuning depends on the workload

The practical section centers on VLLM tuning. The right knobs depend on whether the deployment is throughput-heavy, latency-sensitive, prefix-heavy, or prone to out-of-memory bursts.

Knob Use it for Watch out for
GPU memory utilization Control the fraction of remaining VRAM reserved for KV cache. Higher values pack more concurrent requests; lower values help when load bursts trigger OOM errors.
Prefix caching Reuse shared system prompts across RAG, chat, and coding-agent requests. It works best when many requests share the same prefix.
Chunked prefill Keep decode moving when long prompts arrive in throughput-heavy workloads. Benchmark max batch token settings for your model and traffic shape.
Speculative decoding Improve interactive latency by letting a small draft model propose tokens for the large model to verify. At very high concurrency, gains shrink because the GPU batch is already busy.

What this means for agent and AI platform builders

For agent platforms, the lesson is that model choice is only part of production performance. Long prompts, shared system instructions, RAG context, multi-turn history, and concurrent users all interact with KV cache behavior. A platform that hides those details may make cost and latency hard to explain.

  • Track time to first token and decode speed separately. They point to different bottlenecks.
  • Measure prefix reuse. Shared system prompts and agent instructions can benefit from prefix caching.
  • Expose memory pressure. GPU memory utilization, OOM events, fragmentation, and queueing should be visible in runtime dashboards.
  • Segment workloads. Interactive agents, batch summarization, RAG, and structured generation may need different serving settings.
  • Benchmark before changing knobs. The best settings depend on context length, concurrency, model size, and latency goals.
