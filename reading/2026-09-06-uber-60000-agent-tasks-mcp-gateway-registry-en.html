How Uber Runs 60,000 AI Agent Tasks per Week with MCP

Meghana Somasundara and Rush Tehrani explain how Uber turned thousands of existing service APIs into governed agent tools, centralized MCP discovery and security, and exposed the same control plane to no-code, code-first, and coding-agent experiences.

Executive summary

MCP becomes enterprise infrastructure when agents stop being experiments

Uber's talk begins after the pilot phase. The speakers report more than 5,000 engineers, over 90% monthly AI usage among them, more than 10,000 internal services, over 1,500 monthly active agents, and more than 60,000 agent executions each week. At that scale, allowing every team or agent to rediscover and integrate each service independently creates duplicated engineering, inconsistent security, poor discovery, and unpredictable tool quality.

Uber's answer is a centrally operated MCP Gateway and Registry. The platform mines the service definitions the company already owns, particularly Protobuf and Thrift IDLs, and converts selected endpoints into MCP tools. An orchestrator uses service names, messages, and comments to generate initial tool descriptions. Service owners remain responsible for deciding which endpoints are exposed and refining the descriptions agents will see.

The registry becomes the source of truth for available MCP servers and versions. The gateway becomes the enforcement and delivery plane. Changes are represented as code diffs, scanned before deployment, and distributed through object storage to the gateway service. Central authorization, PII redaction, periodic code scanning, blocking of dangerous mutable endpoints, metrics, logging, and tracing apply consistently across consumers.

Those consumers span three product surfaces: a no-code Agent Builder, a code-first Agent SDK, and coding agents such as Claude Code, Cursor, and Uber's Minions background agent. Reliability is improved by progressively reducing unnecessary model choice: builders can scope an MCP server, select only allowed tools, and override fixed parameters so the model cannot hallucinate values that the workflow already knows.

The next phase focuses on quality and discovery. Uber plans to add evaluation metrics and service-level tiers to the registry, load tools on demand through an “omni MCP” search capability, and treat skills as shareable recipes whose output quality, invocation correctness, and competing versions can be evaluated.

These numbers explain the design pressure. A protocol can standardize the shape of a tool call, but it does not automatically create ownership, lifecycle management, security review, discoverability, or a quality bar. Uber needed an organizational control plane around the protocol.

Three problem classes

The challenges were operational, not merely syntactic

Lifecycle fragmentation

Teams independently built custom integrations and solved the same deployment problems in silos. One-off playground environments were difficult to reuse, update, audit, or trust in production.

Security and governance

Agents can call systems faster and more broadly than people. Uber needed complete visibility into who accessed which data, protection against unauthorized service calls, and stricter treatment of third-party MCP servers and their data-handling behavior.

Discovery and quality

Finding a server is not enough. Builders and agents need to know whether its tools are reliable, performant, safe, and suitable for a given workflow. Poor tools degrade the entire agent, even when the underlying model is capable.

Important distinction

MCP standardizes connectivity. Uber's gateway and registry standardize how connectivity is created, approved, discovered, secured, measured, and consumed.

Architecture

From 10,000 service definitions to governed agent tools

Service layer

Existing Protobuf and Thrift IDLs describe Uber's internal service endpoints, message names, types, and comments.

Orchestrator

Crawl and generate. The gateway orchestrator discovers IDLs and asks an LLM to draft MCP tool descriptions from the service metadata.

Ownership

Service owners decide exposure. Domain experts select which endpoints may become tools and refine descriptions for the intended agents.

Registry

Versioned source of truth. Approved MCP definitions and metadata are stored centrally so teams do not depend on private one-off integrations.

Change gate

Updates become diffs. Definition changes produce pull-request-like diffs that pass Uber's unified security scanning. Scan reports are attached before commit and deployment.

Distribution

Object storage carries approved definitions. A configuration provider in the gateway service picks up the deployed versions.

Gateway

Serve and enforce. The gateway exposes tools while applying central authorization, redaction, endpoint controls, and observability.

Consumers

One plane, three experiences. Agent Builder, Agent SDK applications, and coding agents consume the same governed MCP inventory.

The architectural move

Uber converts existing API governance assets into agent infrastructure instead of asking every service team to hand-build and operate a separate MCP server.

Security and governance

Controls are placed at every stage of the tool lifecycle

Trust tiers

Third-party MCP servers receive more gating, scanning, and rigorous checks than trusted internal integrations. The distinction reflects different code, data, and operational ownership.

Central authorization

Tool access integrates with Uber's authorization service so availability does not imply universal permission to call the underlying data or endpoint.

PII redaction

A central redaction service removes sensitive information as part of the platform path rather than relying on every agent builder to implement privacy filtering correctly.

Code and metadata scanning

Changes are scanned at diff or commit time, and periodic scans look for risky patterns, accidental endpoint exposure, and problematic tool metadata.

Mutable endpoint blocking

The gateway can prevent agents from reaching operations capable of changing or disrupting critical services. Read and write capabilities are not treated as equivalent.

Observability

Logs, metrics, and traces provide visibility into calls and outcomes. This supports incident response, adoption analysis, performance management, and future tool evaluation.

The talk's broader lesson is that agent speed changes risk. A person might take several deliberate steps to cause damage, while an agent can repeat a mistaken call rapidly. The control plane must therefore enforce policy at the tool gateway, not merely describe expected behavior in a prompt.

The common platform does not force every user into the same interface. It standardizes tool ownership, security, and delivery, then offers a no-code configuration surface, a programmable SDK, and developer-native tooling.

Reliability pattern

Remove model decisions when the workflow already knows the answer

Tool calling often fails before execution: the model selects the wrong tool or invents an inappropriate parameter. Uber addresses this with three increasingly narrow controls.

  1. Scope the MCP server. The builder tells the agent which server is relevant to the workflow.
  2. Select the exact tools. The configuration can expose only the operations the agent needs, eliminating unnecessary tool-choice ambiguity.
  3. Override fixed parameters. Known values such as tenant, environment, region, or workflow mode can be supplied by configuration rather than generated by the model.

This is a strong enterprise pattern because it separates business configuration from probabilistic reasoning. The model should decide only what genuinely depends on context. Policy, identity, environment, and other predetermined values belong in trusted configuration.

Near-term roadmap

Uber wants the registry to become a quality and routing system

The speakers describe the following as work in progress or future direction, not as a fully completed system:

Evaluation metadata

Surface quality metrics in the registry so builders can compare tools using evidence rather than name recognition or internal popularity.

SLA tiers

Attach reliability and availability information to MCP servers, making production suitability visible during discovery and selection.

Omni MCP search

Give agents a tool-search capability that discovers and loads the relevant MCP tools on demand. This improves selection and reduces context bloat from loading every schema up front.

Shareable skills

Treat skills as reusable recipes that combine processes, conventions, and MCP use across teams.

Skill evaluation

Measure output quality, whether the skill was invoked correctly, and which version wins in an A/B test.

Translation for an agentic AI platform

Design implications for Master Agent, Sub-Agent, Skill, and MCP

MCP Registry

Store owner, version, trust tier, schemas, data classification, mutability, SLA, evaluation scores, approved consumers, and deprecation state. A name and description are not enough.

MCP Gateway

Enforce identity, authorization, rate limits, PII policy, immutable-versus-mutable restrictions, audit logs, tracing, and emergency disablement at execution time.

Master Agent

Discover a small eligible tool set based on business intent and policy. It should never receive the entire enterprise schema catalog in its working context.

Sub-Agent

Receive only the MCP tools and parameter range required for its delegated role. A researcher, approver, and transaction executor should have different capabilities.

Actionable Skill

Declare required tools, optional tools, fixed parameter bindings, runtime permissions, expected evidence, evaluation suite, and fallback or escalation behavior.

Cognitive Skill

Carry interpretation and reasoning guidance without inheriting unnecessary action permissions. Separate “how to assess” from “permission to execute.”

BA Builder

Offer controlled selectors for server, tool, fixed parameters, approval boundary, and output criteria. This is safer and easier to evaluate than asking a BA to encode everything in free-form system instructions.

Evaluation

Score tool selection, parameter correctness, authorization behavior, execution success, latency, result quality, and skill invocation. Registry ranking should use these signals.

The most useful platform rule

If the business already knows a value, bind it in trusted configuration. Do not spend model probability on rediscovering tenant, environment, permission, destination, or workflow mode.

Critical assessment

What Uber demonstrates and what the talk does not prove

Strongest evidence

The architecture is compelling because it reuses existing enterprise assets: IDLs, service ownership, code review, authorization, scanning, object storage, and observability. MCP is integrated into the engineering control system rather than operated as an isolated AI layer.

Throughput is not a quality metric

Sixty thousand executions and 1,800 code changes demonstrate adoption and operational volume, not correctness, cost efficiency, user value, or incident rate. Those outcomes require the evaluation and SLA work described in the roadmap.

Generated descriptions still need governance

An LLM can accelerate conversion from IDL to tool metadata, but message names and comments may be incomplete or written for human API consumers. Service-owner review, evaluation against realistic agent queries, and versioned rollback remain essential.

Internal does not mean harmless

Risk-based controls for third-party servers are reasonable, but internal tools can still expose sensitive data or damaging mutations. The same authorization, attribution, logging, and endpoint policy should remain mandatory; trust tier should change review depth, not erase runtime enforcement.

Static constraints trade flexibility for reliability

Tool selection and parameter overrides improve predictability when the workflow is known. They can also become brittle when context legitimately changes. The platform should make bindings explicit, test them across versions, and provide a safe escalation path rather than silently relaxing constraints.

My synthesis

Uber's key contribution is not a particular MCP implementation. It is the idea that enterprise tool use needs a product lifecycle: generate, own, review, publish, authorize, observe, evaluate, rank, and retire.
