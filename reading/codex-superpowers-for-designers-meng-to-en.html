Executive Summary

Meng To's main argument is that designers should stop thinking of AI as a prompt box and start treating it as an operating environment. In his current workflow, Codex is not only where code gets written. It is where ideas, Markdown files, local references, screenshots, image prompts, plugins, skills, agents, and memory come together into a personal product-building system.

  • Codex changes the design mindset: Meng describes it as an evolution from ChatGPT into a computer-aware environment where files, tools, threads, and integrations become part of the work.
  • Designers need their own tools: his local Notion-like system keeps content in Markdown, makes context available to agents, and generates article covers, YouTube covers, videos, and presentation assets from local knowledge.

Core Thesis

The episode is not only about Codex as a coding tool. It is about a shift from "designer using AI" to "designer operating a personal product studio." Meng's workflow combines local files, screenshots, reusable prompts, image generation, plugins, Markdown knowledge, and agent memory so that he can build, edit, publish, and organize work with far less handoff.

The deeper message is that AI does not remove taste. It raises the baseline. As soon as a visual pattern becomes easy for models to reproduce, it becomes generic. The designer's job is to stay ahead of the baseline by supplying better context, sharper references, stronger constraints, and a personal design language.

AI can make competent output cheap. The designer's advantage is knowing what should not look like everyone else's output.

Why Codex Changed Meng's Workflow

Meng says he used to use Cursor heavily, but Codex changed his mindset because it feels closer to an AI-native workspace than a code editor. It can work with files on the computer, chat, plan, build apps, create HTML, generate Markdown, produce charts, and connect to integrations. He also points to threads as a major change: the work becomes multiple parallel streams rather than one linear session.

He compares the current moment with his earlier Dream Cut attempt. With older models and tools, it was possible to build quickly, but some quality problems stayed unsolved. In the new workflow, he believes the same kind of work can move from weeks or months to a day, as long as the builder has enough domain knowledge to guide the system.

Important nuance: the productivity gain is not magic. Meng repeatedly says knowledge matters. If you do not know the product, the domain, the library, or the taste bar, the agent will not invent that expertise for you.

Meng's stack has several layers. Codex is the operating workspace. Local Markdown files are the knowledge substrate. Plugins connect external capabilities. Skills package taste and best practices. Screenshots and voice provide fast context. Memory and agents.md preserve project-specific decisions. Together, this becomes a loop for building and refining products.

The Local Notion Pattern

One of the most useful examples is Meng's local Notion-like tool. He built it because cloud tools trap context online, while Codex works well with local files. In his setup, Markdown files appear in a local web interface, and the agent can use those files to create images, article covers, presentation assets, and video variants.

The key idea is not that every designer should clone Notion. The key idea is that personal context should be computable. If your notes, references, prompts, version history, and assets are stored in a way an agent can read, then every workflow can use that context without asking you to re-explain yourself.

Old pattern Meng's pattern Why it matters
Content lives in a cloud app. Content lives as local Markdown. The agent can read, edit, and compose directly from project files.
Prompts are typed repeatedly. Presets and prompts are embedded in the tool. The designer spends less effort recreating context.
Design output is separate from notes. Images, articles, slides, and history share the same workspace. Artifacts can be generated from the same underlying context.
The tool defines the workflow. The designer builds the missing workflow. Custom software becomes a design advantage.

Plugins Vs Skills

Meng draws a practical distinction that maps directly to your agentic AI platform. Plugins are integrations built by startups, individuals, or tool providers. They connect to external capabilities, similar to how Figma plugins expand Figma. Skills are closer to large prompts or style guides. They encode best practices and taste so the model can act with better defaults.

For your platform, this distinction is important because "skill" should not mean every possible automation. A cognitive skill may only guide reasoning or style. An actionable skill may require a tool. A tool or MCP connector should define permissions, inputs, outputs, side effects, and failure modes.

Type Purpose Requires tool? BA-friendly example
Cognitive Skill Guide reasoning, writing, taste, analysis, or review. No. "Use our product-design critique checklist before proposing screens."
Actionable Skill Guide a workflow that may call one or more tools. Usually yes. "Create a Jira ticket, attach screenshots, and notify Slack after approval."
Tool / MCP Connector Perform a specific external action or read external state. It is the tool. Figma, Slack, Google Drive, database, browser, email, or internal API.
Agent Memory Preserve project-specific rules and repeated decisions. No, unless persistence is external. "For this product, modal animations should use the approved slow-ease pattern."

The Anti-Slop Strategy

Meng opens with a warning: if designers chase trends, they quickly become generic. He uses examples such as default fonts, purple gradients, predictable model-made animations, and soon other trends that will become recognizable as AI output. His solution is to stay ahead of the baseline.

The anti-slop strategy has three parts. First, preserve personal memory: past work, fonts, screenshots, Figma files, code, and design references. Second, put that memory into files and skills that AI can read. Third, spend the last 10 percent on taste, iteration, and precise direction. The first draft is not the work. The edited version is the work.

Reference Yourself

Use your own past work as a starting point so the output inherits your taste rather than generic internet style.

Package Taste

Put fonts, colors, spacing, motion, composition, and anti-patterns into reusable design.md or skill files.

Edit Hard

Use screenshots, voice, annotations, and repeated tests to guide the final details.

Screenshots, Voice, And Annotation As Prompting

Meng says his workflow starts with screenshots over and over. The reason is simple: screenshots carry visual context faster than typing. If he wants to fix a bug or adjust a UI detail, he can send the current window to Codex, point to the problem, and explain what should change.

Voice matters for the same reason. Designers often leave out details when typing because describing a visual issue is tedious. Speaking lets them explain three to five times more detail. Annotation adds another layer: instead of saying where the problem is, the designer can point to the exact area and then give an instruction.

  1. 1CaptureSend the current screen, broken state, target reference, or inspiration into the agent.
  2. 2PointAnnotate or name the region: header, timeline, modal, padding, transition, or button.
  3. 3ExplainUse voice or short text to say what is wrong and what success should feel like.
  4. 4PatchLet the agent implement, then inspect the actual product, not just the diff.
  5. 5RememberSave reusable design terms, rules, and patterns when the fix becomes a convention.

0 Percent Code Does Not Mean 0 Percent Work

Meng says he has moved from writing most of his own code to writing none of it manually. The important point is what replaced the coding. He is still testing, inspecting, bug-reporting, searching for libraries, evaluating edge cases, and using precise language to make the AI understand what has to happen.

That is why this workflow is better described as "designer as director" than "designer as passenger." The work becomes choosing the right library, knowing what the product should do, recognizing wrong output, reporting bugs well, and controlling the last 10 percent of quality.

Platform lesson: when BA users build multi-agent systems, do not promise that they can ignore domain knowledge. Give them better artifacts for expressing knowledge, checking output, and approving changes.

Image, HTML, And Motion Exploration

Meng describes using GPT Image 2 to create UI concepts, then converting screenshots into HTML. He also uses image generation for article covers, YouTube covers, slides, wireframes, 3D versions of logos, glass effects, and perspective mockups. The pattern is content first, concept second, artifact third.

For animation, he shares a tactic that is easy to reuse: give the AI a video of the motion and ask it how to prompt that animation. This is powerful because interaction design often fails at the language layer. Designers know what they want when they see it, but may not know the animation terms, easing vocabulary, shader terms, or implementation language.

What Design.md Really Is

Meng's explanation of design.md is one of the most useful parts of the episode. A design.md file is not a random prompt. It is the designer's accumulated style guide, taste, visual principles, typography decisions, spacing logic, color behavior, accessibility rules, composition patterns, and anti-patterns in a form that an AI can read.

He says designers used to carry this inside their training and experience. The AI cannot see that internal taste unless the designer makes it explicit. A strong design.md lets a stronger model use the designer's language and constraints. A weak model may ignore it, but a capable model can use it to produce more distinctive results.

Design.md Sections

Product personality, visual principles, typography, color, layout, components, motion, accessibility, content voice, anti-patterns, and examples.

Agents.md, Runbook.md, Workflow.md, And Memory

Meng is careful about agents.md. He says it can be useful because it is read for prompts, threads, or tasks inside a project, but it can also become dangerous if it contains too much global instruction. His preference is to keep it focused and use memory for specific decisions that should repeat.

He sometimes calls workflow instructions runbook.md or workflow.md. The distinction is useful: design.md describes taste, agents.md describes project behavior, and runbook.md describes a repeatable workflow. For your platform, this suggests a clean separation between persona prompt, skill spec, tool contract, memory policy, and workflow SOP.

File Primary job What to avoid
design.md Encode taste, visual language, product feel, and UI constraints. Do not put operational secrets or unrelated process rules here.
agents.md Tell the agent how to behave inside this project. Do not overload it with rules for every possible future project.
runbook.md Describe a repeatable workflow, checks, approvals, and done criteria. Do not mix it with brand taste unless the workflow depends on taste.
memory Persist decisions that should apply again later. Do not save vague preferences that will pollute unrelated work.

Model Choice And Context Size

Meng distinguishes between fast, cheaper models and more capable higher-effort models. His point is not that the most expensive model should be used for everything. For simple tasks, a very strong model may produce output similar to a weaker one because the task does not use its intelligence. To use a powerful model well, you need rich context: design.md, screenshots, references, HTML previews, URLs, sections, and pre-prompts.

This is an excellent operational rule: model power only matters when the task is hard enough and the context is rich enough. Otherwise the user may be paying for unused capability. In a BA-facing platform, this should become a routing policy.

Routing policy: use cheaper models for drafts, summaries, simple edits, and fast iteration. Use stronger models when the task requires large context, multiple constraints, design reasoning, architecture decisions, or high-impact output.

Translation For Your Agentic AI Platform

This video maps cleanly to your Master Agent, Sub-Agent, Skill, Tool, and MCP problem. Meng's workflow suggests that a BA should not be forced to write raw prompts. Instead, the platform should offer structured artifacts: design.md for taste, skill.md for reusable cognition, actionable-skill specs for tool workflows, runbook.md for SOPs, and agents.md for project-specific agent behavior.

The platform should make the difference between "knowledge", "behavior", and "capability" visible. Knowledge is what the agent should know. Behavior is how it should act. Capability is what it is allowed to do through tools. Most multi-agent confusion happens when those three are mixed into one giant persona prompt.

  1. 1Business GoalBA defines the workflow outcome, user role, inputs, and done criteria.
  2. 2Knowledge FilesAttach policy, examples, design.md, product docs, and domain references.
  3. 3SkillsSelect cognitive and actionable skills with clear trigger rules.
  4. 4ToolsBind MCP/API capabilities with permissions, scopes, and approval gates.
  5. 5AgentsCompose Master Agent routing plus Sub-Agent responsibilities.
  6. 6RunbookTurn the business flow into steps, checks, outputs, and escalation rules.
  7. 7EvaluateRun traces, eval cases, human review, and regression checks.
  8. 8RememberPersist only reusable decisions and successful patterns.

My Read

Meng is directionally right about the next designer workflow, especially for solo builders and design engineers. The strongest insight is not "designers should stop using Figma." It is that designers need a personal context system that the AI can read. If your taste, references, design language, and workflow live only in your head, the model will fall back to generic taste.

For your agentic AI platform, the most useful takeaway is separation of concerns. Persona prompts should not hold everything. BA users need structured building blocks: role, business flow, cognitive skill, actionable skill, tool contract, design/taste guide, runbook, evals, memory policy, and approval rules. That is how non-engineers can compose a multi-agent system without turning every workflow into one giant brittle prompt.

Strong recommendation: build your BA experience around editable Markdown artifacts plus guided forms. Let the form keep users safe, but let Markdown preserve power, portability, reviewability, and version history.
