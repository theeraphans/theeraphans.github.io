Agents That Keep Getting Better

The Short Version

Long-running agents are now useful enough that the hard questions have become economic: reliability, cost, latency, and product experience. The speaker's answer is to train models on the actual harness, traces, tools, and feedback loops of the agent system, rather than hoping that a larger context window will solve orchestration.

  • Large context windows still suffer from context rot, especially for reasoning across very long histories.
  • Agents should pass references and variables, then explore context programmatically instead of swallowing everything at once.
  • Continual learning means harvesting trajectories, scoring them, and training the model to use the harness better over time.

Why It Matters

Agent work moved from short autocomplete to long-running workflows

The talk opens by contrasting 2024 with 2026. In 2024, most people still thought of coding LLMs as autocomplete. Cursor Agent changed that mental model by showing that users could describe a task in English and let an agent modify code. By 2026, the speaker says agents can run for far longer, spend millions of tokens, and become part of enterprise workflows.

2024 Mental Model

LLMs complete code, fill boilerplate, or answer short questions. If an agent ran more than a few minutes, users expected it to drift.

2026 Reality

Developers run multiple agent terminal sessions, let agents work overnight, and expect them to solve longer tasks.

Enterprise Pressure

Businesses ask how to make agents more reliable, cheaper, and fast enough for product-grade user experiences.

Context Rot

A million-token context window is not the same as a million-token reasoning ability

The first technical problem is long-context degradation. Many modern models advertise very large context windows, but accepting a long prompt is not the same as retrieving and reasoning reliably across all of it. The speaker points to benchmark patterns where performance drops as context grows.

MRCR

Retrieval gets worse

Needle-in-the-haystack style tasks test whether the model can find specific information in long generated text.

GraphWalks

Reasoning gets worse

Graph tasks test whether the model can reason across nodes and edges, not just recall an isolated fact.

Agent Runs

Compaction creates drift

Long tool-call histories and repeated summarization can cause the agent to forget what it already did.

The key warning: do not design long-running agents by dumping the whole world into context and trusting the model to stay coherent.

References

Pass references and variables, then let the agent inspect context as needed

The proposed fix is to stop passing every detail into the prompt at once. Instead, pass handles, references, or variables that the agent can open, filter, inspect, and query. The speaker compares this to data science: a data scientist does not paste an entire CSV into code; they load a dataframe and inspect it incrementally.

ContextDocuments, traces, files, videos, or data tables exist outside the prompt.
HandleThe agent receives a reference, variable, path, or object ID.
InspectIt reads slices, filters rows, or asks subqueries.
ReasonOnly relevant results enter the working context.
ActThe agent calls tools with stable variables rather than retyping huge text.
  • Context chunking becomes natural. Chunks can be passed around as variables instead of copied into every prompt.
  • Tool calls become less brittle. The model can pass a reference to a tool instead of trying to regenerate thousands of tokens correctly.
  • Sub-agent delegation becomes easier. The main agent can send focused references to sub-agents and collect their results.
  • Batch processing becomes possible. A programmatic loop can process many documents without forcing the agent to remember every prior step in prose.
Recursive Language Models

The next harness pattern is to let agents write code to orchestrate their own work

The speaker calls this pattern recursive language models. Rather than performing 10,000 sequential tool calls in natural language, the agent can write a loop, delegate subtasks, and process context programmatically. A main orchestration agent stays clean, while messy document processing or search is pushed into sub-agents.

Old pattern Recursive pattern Why it helps
Paste a giant context into the prompt. Pass a reference and inspect slices. Reduces context overload and keeps reasoning focused.
Ask the model to make thousands of sequential calls. Let the model write a loop or batched subqueries. Tracks progress deterministically and avoids repeated compaction.
One agent carries all intermediate work. Main agent delegates messy work to sub-agents. Preserves orchestration state while workers handle detailed context.
Tool calls depend on regenerating long arguments. Tool calls pass object handles or variables. Less chance of malformed calls and lost information.

The talk frames recursive orchestration as the next version of “thinking”: first models learned to spend tokens reasoning; next they may learn to spend code orchestrating.

Harness Training

Models are specific to the harness they were trained on

A major point is that recursive language model prompts do not automatically work well out of the box. The speaker argues that models become good at the agentic patterns they are trained to use. Prompt engineering can help, but training on the actual harness should help more.

Continual Learning

The deployed agent becomes the data engine for the next model

Continual learning is the loop from deployed behavior back into training. Once an agent is in production, the platform can harvest traces and trajectories, attach feedback signals, train or fine-tune models, evaluate the new model, and deploy improvements back into the harness.

DeployThe agent runs in real workflows.
HarvestCollect model calls, tool calls, user messages, memory access, and outcomes.
ScoreUse ratings, rule checks, task completion, frustration signals, or LLM judges.
TrainUpdate a model on successful, efficient, harness-specific trajectories.
EvaluateRun benchmark tasks, rollout viewers, and environment tests.
ShipDeploy a model that performs the same workflow faster, cheaper, or more reliably.
  • Quality improves through traces. The agent's own behavior becomes training data when the platform captures enough detail.
  • Efficiency is part of the reward. The system can score not only correctness, but also tool count, latency, tokens, and unnecessary retrieval.
  • The harness and model co-evolve. Better prompts, references, tools, and training examples reinforce each other.
  • Eval must be consistent. You need repeatable evaluation environments before trusting a continually improved model in production.

Platform Takeaways

What this means for your agentic AI platform

For your Master Agent, Sub-Agent, Skill, Tool MCP, memory, and Flow Markdown work, this talk adds a strong point: the platform should not only execute agents. It should collect trajectories that make future agents better.

  • Use references as a core runtime primitive. Flow Markdown should pass files, cases, tickets, traces, and datasets as handles that agents inspect on demand.
  • Separate orchestrator state from worker context. The Master Agent should preserve the plan, while Sub-Agents process heavy context and return compact structured outputs.
  • Avoid blind compaction. Store task state, processed items, pending items, decisions, and stop reasons as structured state, not only as prose summaries.
  • Make every run a training candidate. Capture user prompt, context handles, memory retrieval, tool calls, outputs, approvals, failures, cost, and latency.
  • Design feedback signals early. BA-authored flows should include pass criteria, success events, failure events, user satisfaction signals, and escalation outcomes.
  • Train for the harness you actually use. If your platform has MCP tools, Skill Cards, Flow Markdown, and approval gates, the model should see those patterns in training data.
  • Build a rollout viewer for business users and engineers. A BA needs to inspect what happened; engineers need the same trace to debug retrieval, tools, and model behavior.
  • Evaluate smaller specialized models. A domain-trained smaller model may beat a larger generic model on a narrow business workflow while reducing latency and cost.
