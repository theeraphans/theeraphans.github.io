Hermes Architecture

Memory, Context, Gateways, and Cron Jobs

A readable architecture summary of Hugging Face's Hermes Agent walkthrough. The talk explains how Hermes is built: a simple agent loop, markdown-based persona and memory files, SQLite session history, optional external memory, messaging gateways, context compression, and a built-in scheduler.

The Short Version

Hermes is described as a straightforward but well-composed agent runtime. Users can reach the same agent through CLI, API, or messaging gateways. Each user message triggers a loop: build context, call the LLM, execute tools if needed, return a final answer, then update memory.

  • The agent's identity and long-term notes are mostly markdown files such as soul.md, user.md, and memory.md.
  • Gateway conversations reconstruct message history from SQLite so Telegram, Slack, email, and similar channels can feel continuous.
  • Cron jobs are stored as JSON and run through Hermes' own minute-by-minute scheduler loop.

Agent Loop

The runtime loop is deliberately simple

The loop runs every time the user sends a message. Hermes builds context from system prompts, markdown files, tool and skill descriptions, message history, and optionally external memory. Then the model can call tools until it is ready to answer.

MessageUser sends a message through CLI, gateway, or API.
ContextHermes assembles prompts, files, tools, memory, and messages.
LLMThe full context is sent to the selected model.
ToolsThe model may call tools repeatedly and receive results.
AnswerThe model returns a final response to the user.
RememberHermes analyzes whether anything should be written to memory.

The self-improving feel comes from the final memory-update pass, not from magic inside the LLM call itself.

Context Stack

Hermes treats context as a stack of files, history, tools, skills, and summaries

The speaker spends significant time on context because it is the main programming surface of this architecture. Hermes uses a small set of markdown files plus generated runtime context rather than one giant hidden prompt.

Context item What it contains How it behaves
System prompt Baseline runtime instructions for Hermes. Always included when context is built.
soul.md The agent's personality, tone, goals, and operating style. Usually empty after install unless the user writes or asks Hermes to write it.
user.md Information about the user, learned from conversation. Hermes can update it automatically when it learns user facts.
memory.md Arbitrary useful facts, workflows, notes, and tool-use lessons. Can be updated by Hermes or manually by the user.

Tools and skills Descriptions of available capabilities and how to call them. Included so the LLM knows what it can do.
Message history Recent conversation turns or a compressed summary if the context is too large. Summarized after a threshold or on context-window errors.
Compression

Context compression keeps long conversations inside the model window

Hermes checks whether the conversation needs compression before each turn and when a context-window error occurs. The default threshold is described as 50% of the model's context window, though it can be adjusted during setup.

Trigger

Before every turn

Before calling the model, Hermes estimates context size and decides whether to compress previous messages.

Fallback

On context error

If the provider returns a context-window error, Hermes checks context and summarizes aggressively.

Estimate

Characters divided by four

Before the first call, it uses a cheap token estimate rather than a full tokenizer. Later it can use provider usage data.

  • The compressor prompt creates sections such as goal, constraints, completed actions, active state, historical progress, blockers, decisions, resolved questions, relevant files, and critical context.
  • Previous messages are replaced by a summary, then that summary becomes part of future context.
  • The approach is richer than minimal summarize-history prompts, because Hermes tries to preserve operational state for tool-using work.
Gateway

The gateway is what makes Hermes feel always reachable

The gateway is an always-running service that listens to messaging providers, normalizes incoming messages, reconstructs the relevant conversation history, builds context, and sends it into the agent loop. The speaker argues this is one reason Hermes became popular.

Memory Layers

Hermes memory is not one thing; it is markdown, SQLite, and optional external recall

The video clarifies a useful distinction. Markdown files are always attached to context. SQLite stores session transcripts. External memory providers, when configured, retrieve relevant older memories and feed them into future turns.

Memory layer Storage Purpose Platform lesson
Profile memory soul.md, user.md, memory.md Identity, user facts, reusable notes, and learned workflow details. Keep high-value operating context human-readable and editable.
Session memory Local SQLite database Full transcripts and message history across conversations and gateways. Every channel needs a durable session ID and trace store.
Searchable text Bare-text SQLite table Simplifies similarity search over conversation text. Separate raw trace storage from retrieval-optimized indexes.
External memory Providers such as Mem0, Supermemory, Honcho, or similar systems Retrieve relevant prior context after the first message of a topic. External recall improves continuity, but should be explicit and observable.

Important behavior: external memory is queried after Hermes has enough topic context, so the first message may orient the system and the follow-up may benefit from recall.

Cron Jobs

Hermes has its own scheduler loop, not just operating-system cron

Cron jobs let Hermes run scheduled work such as daily briefings, weekly reports, or recurring community updates. The talk notes that Hermes cron is its own loop that ticks every minute, checks jobs, executes due work, and stores output.

Tick

Runs every minute

The scheduler loop calls a tick function every minute and checks whether any job is due.

jobs.json

Plain JSON job store

The speaker says jobs are stored in a file such as .hermes/cron/jobs.json, not pulled from SQLite in his analysis.

Run Output

Markdown per job run

Job outputs are stored under cron output directories, with markdown records for individual runs.

Home Channel

Notification target

Cron results go to the configured home messaging integration rather than the agent calling a send-message tool manually.

Plain English

User-friendly scheduling

The user can ask Hermes to perform recurring work, and the system turns it into scheduled agent activity.

Audit

The output files create a place to inspect what each scheduled task actually did.

Platform Takeaways

What this means for your agentic AI platform

This is one of the most directly useful videos for your Master Agent, Sub-Agent, Skill, Tool MCP, memory, gateway, and Flow Markdown design. Hermes shows a concrete runtime architecture you can translate into BA-facing concepts.

  • Make the context builder explicit. A BA-authored flow should compile into system prompt, agent card, memory policy, tools, skills, recent messages, retrieved memory, and current task state.
  • Separate agent identity from user memory. Use different artifacts for persona/role, user profile, workflow notes, and business facts.
  • Keep important memory human-readable. Markdown-like memory is valuable because BAs and SMEs can inspect, edit, and approve it.
  • Store full session traces separately. SQLite-style transcript storage should feed audit, replay, debugging, evaluation, and retrieval indexes.
  • Design gateway sessions as first-class objects. Telegram, Line, Slack, webchat, and email should each map messages into a durable session with channel, user ID, permissions, and history.
  • Add session controls. Interrupt, steer, queue, stop, retry, and escalate should be platform primitives, not hidden chat tricks.
  • Expose context compression policy. Let advanced users configure when to summarize, what summary schema to use, and which artifacts must never be summarized away.
  • Treat external memory as a provider layer. Memory providers should be swappable, observable, and evaluated for precision, recall, privacy, and cost.
  • Use a deterministic scheduler for business flows. Recurring tasks should live in a job store with next run, owner, prompt, channel, output, approval rules, and run history.
  • Build the dashboard around runtime truth. Show context stack, messages, tool calls, memory writes, gateway events, scheduled jobs, model usage, and errors in one trace view.
