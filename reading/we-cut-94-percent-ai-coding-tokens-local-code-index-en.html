AI Coding Cost

Cut Context Before You Cut Output

A practical summary of Rajkumar Sakthivel's talk on reducing AI coding token usage with a local code index. The core idea is simple: most cost comes from the context you send, not the answer the model writes back.

The Short Version

The talk argues that AI coding tools often waste money by sending too much irrelevant code as context. Shorter prompts and compressed answers help only a little because the major cost sits in input tokens. The proposed fix is a local code index that retrieves only the code slices the model needs.

  • Local retrieval beats dumping whole files.
  • Hybrid search works better than one search type.

Problem

The bill did not explode because the model thought harder. It exploded because the tool sent too much.

Raj describes a familiar pattern: the team used the same AI coding tools on the same project, but the bill jumped. Their investigation found that most of the spend came from unnecessary context, not from the model's final code output.

Wrong Fix

Make the prompt shorter

The prompt is read after the context has already been sent, so this does not prevent input-token spend.

Wrong Fix

Tune model settings

Settings like max tokens and temperature shape the response, but they do not shrink the context payload.

Partial Fix

Compress the output

Short answers can reduce output cost, but output is only a small part of total spend in this example.

The practical lesson: fix the input first. That is where most AI coding cost is hiding.

Cost Math

Why output compression is not enough

The talk frames the cost split as roughly 90% input and 10% output. That means even aggressive output compression has limited impact if the tool is still sending large, irrelevant context to the model.

Architecture

The local code index sits between the codebase and the AI coding tool

Instead of sending whole files, the tool searches a local index and returns only the relevant functions, classes, methods, or connected snippets. Everything runs locally, so the search layer does not need to send the codebase to a cloud indexing service.

Parse code into meaningful units

Split code into functions, classes, and methods rather than arbitrary chunks. The retrieval unit should match how developers reason about code.

Run two searches in parallel

Use semantic search for meaning and keyword search for exact names. Each search type covers the other's weakness.

Compress retrieved results

Represent large functions with names, summaries, and the smallest useful slice instead of sending every line.

Track code connections

Record which functions call which other functions so the index can pull related code when one relevant piece is found.

Score and filter results

If relevance is too low, send nothing rather than poisoning the model with bad context.

Search Quality

Hybrid search works because semantic and keyword search fail differently

Semantic search can find related ideas but miss exact identifiers. Keyword search can find exact names but miss synonyms such as login versus sign in. The talk claims each approach misses about one in four results alone, while the combined approach misses about one in ten.

Semantic

Good for related meaning

It can find conceptually related code, but may return the wrong auth function when the exact function name matters.

Keyword

Good for exact names

It finds specific identifiers, but may miss related vocabulary or renamed flows.

The scoring formula they landed on

50% semantic score + 30% keyword score + 20% recency, with an adaptive threshold. The talk says this runs in 0.4 milliseconds and avoids extra AI calls.

Caveats

The 94% number is a worst-case baseline, not a universal promise

The speaker is explicit about the limits. The 94% result is measured against a full-file baseline. Modern AI coding tools are already smarter than blindly sending every file, so real-world savings may be lower.

Mixed large codebases are harder

When files each do one thing, retrieval works well. When files do many unrelated things, recall can drop badly.

Speed was chosen over perfection

They used a small fast model for search. Bigger models could find more, but would add cost and latency.

The benchmark baseline matters

Compare against your current tools, not against the full-file worst case, before expecting the same percentage.

Platform Takeaways

What this means for an AI coding or agentic platform

The deeper lesson is not only about coding cost. It is about context governance. A platform should decide what context is useful, measurable, shareable, and safe before it sends anything to a model.

  • Build a shared local project index instead of making every AI tool rediscover the codebase independently.
  • Treat context retrieval as a first-class product surface, not hidden plumbing.
  • Measure tokens saved per query and show the user what would have been sent versus what was sent.
  • Use hybrid retrieval: semantic search, keyword search, graph/call relationships, and adaptive filtering.
  • Do not send low-confidence context. Bad context can make the model confidently wrong.
  • Keep memory at the project/index layer so Cursor, Copilot, Claude Code, Codex, or internal agents can share the same learned context.
  • For agentic platforms, apply the same principle to business tools: retrieve the smallest sufficient policy, record, workflow, and code context.

Fix the input, and the model choice matters less than you think.
