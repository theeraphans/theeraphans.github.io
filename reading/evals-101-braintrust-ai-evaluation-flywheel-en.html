Braintrust Evals 101

The Evaluation Flywheel for AI Products

A practical summary of Doug Guthrie's Braintrust talk on evals: how to test AI systems with tasks, datasets, and scores; how to iterate before launch; how to trace production behavior; and how human review plus user feedback turns logs into better future evals.

Video: Evals 101 Speaker: Doug Guthrie, Braintrust Transcript: 9,125 words

The Short Version

Evals are structured tests that measure how well an AI system performs. They answer practical questions: did a model change help or hurt, did a prompt edit create a regression, and can this AI feature be trusted enough for production? The talk's deeper lesson is that evals should not be a one-time pre-launch checklist. They should be a flywheel: offline tests guide development, production traces reveal real failures, humans review those failures, and selected logs become new dataset rows.

  • An eval needs a task, a dataset, and at least one score.
  • Offline evals create pre-production rigor; online scoring watches live traffic.
  • Human review and user feedback close the loop by turning production failures into better tests.

Why Evals

Evals make AI development measurable instead of vibe-based.

Large language model systems are non-deterministic, so normal "it looks better to me" iteration is not enough. Evals let a team compare versions of a model, prompt, retrieval step, tool call, or workflow and see whether quality, correctness, reliability, cost, or latency improved or regressed.

Model changes

Did switching models improve the product?

Run the same task and dataset against multiple model choices and compare scores instead of guessing.

Prompt changes

Did the new prompt help or hurt?

Use the eval results to validate edits before shipping them into user-facing traffic.

Regression control

Did a feature update break behavior?

Use evals as an offensive development tool, not only a defensive safety net.

The talk compares evals to unit tests, but then pushes further: evals help teams build AI products faster because they provide a repeatable way to decide what to improve next.

Evaluation Flywheel

The strongest pattern is offline tests connected to production reality.

Braintrust frames the work as a loop across prompt iteration, evals, observability, human review, and user feedback. Offline evals help the team improve before launch. Online traces and scores show what happens in production. Human review and user feedback select the most useful logs, and those logs become future eval dataset rows.

Prototype Change prompts, models, tools, or agent steps in a playground or local codebase.
Evaluate offline Run the task against a dataset and score the outputs before release.
Trace online Log live inputs, outputs, intermediate steps, tool calls, cost, latency, and token usage.
Review and feed back Use humans and user feedback to identify important failures and add them to datasets.

The eval system is not a report. It is the operating loop that tells the team what to change next.

Core Ingredients

Every eval needs a task, a dataset, and at least one score.

Doug breaks an eval into three components. The task is what you want to test. The dataset is the set of examples you run the task against. The score is the logic that decides whether the output is good.

Ingredient What It Means Examples From The Talk
Task The prompt, code, tool call, RAG chain, or full agentic workflow being tested. A changelog generator that reads GitHub commits and produces release notes.
Dataset Real or representative examples, optionally with expected outputs and metadata. Inputs for the changelog task, production spans, or curated rows from human review.
Score Code-based or LLM-as-a-judge logic that measures specific quality dimensions. Accuracy, completeness, formatting, correctness, relevance, or binary contract checks.
  • Start small. You do not need a perfect golden dataset on day one. Establish a baseline and improve it.
  • Use focused scores. Separate accuracy, formatting, and completeness instead of asking one overloaded score to judge everything.
  • Use stronger models for scoring when useful. A production task may run on a cheaper model while scoring uses a higher-quality judge.
  • Test your judge prompts. LLM-as-judge scores need their own validation, rubrics, and iteration.
Offline Evals

Offline evals are the pre-production loop for changing prompts, models, and workflows.

Offline evals are run before deployment. They help identify and resolve issues while the team is still developing. In Braintrust, this can happen through the UI playground or from code through the SDK.

Load task Bring in a prompt, agent workflow, tool-enabled chain, or code function.
Add dataset Run the task across representative examples with inputs, expected values, and metadata.
Add scores Measure targeted criteria such as accuracy, formatting, completeness, and correctness.
Compare variants Duplicate the task, swap the model or prompt, and compare score changes.
Save experiment Keep snapshots over time so the team sees whether quality is trending up or down.

The talk highlights a useful mental model: if the output is good but the score is low, improve the eval. If the output is bad but the score is high, improve the score. If both are bad, improve the task.

SDK and CI

Teams can manage eval assets in code, not only in a UI.

Braintrust supports defining prompts, datasets, scores, and evals through SDKs such as Python and TypeScript. This matters because AI product teams often want version control, local development, repeatable runs, and CI/CD checks before a change ships.

Assets in code

Prompts, datasets, and scores can be pushed to the platform

This lets developers source-control eval components while still allowing PMs, reviewers, or domain experts to inspect results.

CI/CD gates

Eval runs can become release checks

Teams can run evals automatically and block or warn when score thresholds regress.

For agent platforms, this is the bridge between product-facing eval definitions and engineering deployment discipline: the same eval contract should exist in the UI, SDK, and CI pipeline.

Online Scoring

Production traces turn real traffic into measurable evidence.

Moving to production means instrumenting the application. The talk describes initializing a logger, wrapping the LLM client, tracing functions or tool calls, and creating custom spans with structured inputs, outputs, and metadata. Online scores can then run against sampled production logs or specific spans.

Root trace

Capture the full request

Log user input, final output, model usage, latency, cost, token counts, and overall success.

Span-level scoring

Evaluate important substeps

Score RAG retrieval, query rewriting, intent detection, tool calls, or sub-agent handoffs independently.

Alerts

Catch regressions early

Create automation when a score drops below a threshold or a production pattern deserves review.

The transcript gives a strong example: in a conversational analytics app, if the model rephrases the user's question badly, every downstream step can fail. Span-level evals let the team detect that exact step instead of only judging the final answer.

Human Review

Human review and user feedback turn production logs into better future evals.

The production loop needs humans. Reviewers can filter logs, inspect simplified review views, apply custom human scores, add notes, and push selected examples into datasets. Users can also provide thumbs-up, thumbs-down, and comments inside the product.

Feedback Source What It Adds How It Improves Evals
Human review Domain judgment, score labels, comments, and selected failure cases. Reviewed logs become high-value dataset rows for future offline evals.
User feedback Real product satisfaction signals such as thumbs down, comments, or complaints. Filtered negative feedback becomes a review queue and regression test source.
Rubrics Shared scoring criteria for multiple human reviewers. Reduces inconsistent labels and makes human review more reliable.

One audience question asks about multiple humans scoring differently. The answer is important for platform design: define a rubric before comparing reviewers.

Platform Takeaways

What this means for your Master Agent, Sub-Agent, Skill, and MCP platform

This video is a strong blueprint for making evaluation a first-class platform primitive. Your BA-facing builder should not only create agents and flows. It should create eval contracts, run offline gates, trace online behavior, and route production failures back into datasets.

  • Create an Eval Spec in Flow Markdown. Every flow should declare task, dataset, scores, thresholds, owner, and release gate.
  • Evaluate sub-agent handoffs, not only final answers. Score routing, memory retrieval, tool choice, output schema, and handoff quality as individual spans.
  • Use different score types by risk. Code-based scores fit schemas, citations, permissions, and exact outputs; LLM judges fit tone, relevance, completeness, and reasoning quality.
  • Start with baseline datasets. BAs can seed a small set of representative cases, then production logs should expand it over time.
  • Make CI gates configurable. Engineers should be able to block deploys when critical scores regress or cost and latency exceed budgets.
  • Build online scoring into the runtime. Production traces should include root requests, sub-agent spans, tool calls, MCP calls, cost, latency, tokens, and score results.
  • Create human review queues. Low-score runs, user-downvoted runs, low-confidence agent decisions, and risky tool calls should route to reviewers.
  • Define reviewer rubrics. Human review should be guided by scoring criteria, not ad hoc taste.
  • Close the eval flywheel. One-click "add to dataset" from a trace should become a core product feature.
  • Expose evals to BAs in business language. Instead of raw logs, show "routing failed," "citation missing," "handoff incomplete," "tool output irrelevant," or "human override needed."
