How to Plan, Build, and Run Loops with Claude Code

Thariq Shihipar from the Claude Code team walks through /goal, /loop, workflows, skills, artifacts, Slack-based collaboration, and why planning is really about removing unknowns before asking an agent to work for a long time.

Source: Peter Yang Guest: Thariq Shihipar Length: 41 minutes Transcript: 8.8k words

Executive Summary

The episode's main lesson is that longer-running agents need better operating structures, not just bigger prompts. /goal gives the agent an exit condition, /loop helps it repeat work, workflows split work across sub-agents and verifiers, and skills package reusable patterns once the user actually understands what they want.

  • Planning is an iterative process of exploration: discover unknowns, understand constraints, build prototypes, and refine the spec.
  • /goal is useful when the agent should power through complications and stop only when a clear done condition is met.
  • Workflows are strongest when the task benefits from parallelism, clean context, rubrics, adversarial verification, or separate workers.
  • Skills should come after repeated experimentation; package the workflow only after edge cases and desired outputs become clear.
  • As models get smarter, shorter instructions often work better because excessive constraints and examples can overfit the model's behavior.

1. The Central Thesis

Thariq frames loops as ways to let an agent work for longer periods while still receiving feedback and staying attached to the desired outcome. The tools differ by purpose. /goal prevents premature stopping. /loop supports repeated work. Workflows create custom harnesses with sub-agents, verification, and coordination.

The deeper point is that long-running AI work is not mainly about saying "do the thing." It is about creating the right harness for the task: the right context, exit condition, artifact, rubric, worker boundaries, and verifier behavior.

My read: this interview is a practical bridge between prompt engineering and agent operations. The user becomes a loop designer, not just a prompt writer.

2. The Loop Stack

The conversation separates three related mechanisms. They are not interchangeable. Each one solves a different failure mode in agent work.

  1. 1 Explore Use the agent to learn constraints, edge cases, references, and unknowns.
  2. 2 /goal Set a hard exit condition so the agent does not stop at partial progress.
  3. 3 /loop Repeat triage, research, checks, or maintenance until a stop condition is met.
  4. 4 Workflow Spin up sub-agents with clean context, roles, rubrics, and coordination logic.
  5. 5 Skill Package the reliable pattern so it can be reused by people and agents.

Platform implication: in your agentic AI platform, do not model "agent" as one flat prompt. Model work as a stack: exploration, goal, loop, workflow, skill, validator, and reusable artifact.

3. /goal: Give the Agent an Exit Condition

/goal is for tasks where stopping early is the failure mode. Thariq describes it as a way to remind the agent what completion means and to allow exit only when that condition is met. This is useful when the user has already done enough specification and exploration and wants execution to continue through obstacles.

The key product idea is that /goal changes the agent's relationship to ambiguity. Instead of stopping whenever it sees something imperfect, the agent receives a signal that it should fill gaps, power through reasonable complications, and keep checking against the target.

Use /goal When Avoid /goal When Good Done Condition
The outcome is clear and the agent may otherwise stop too soon. The problem is still vague or the user has not explored constraints. Rendered video exists, tests pass, design matches reference, report has citations.
There is a measurable signal like latency, build success, rendered output, or acceptance criteria. The task requires taste decisions that the user has not expressed. All acceptance checks pass or a clear escalation note explains why not.

4. Planning Means Removing Unknowns

One of the strongest parts of the interview is Thariq's definition of planning. It is not a single document written before implementation. It is an iterative process of exploration, investigation, learning, mockups, implementation notes, and re-specification.

In the video editing demo, he asks Claude to explain how Whisper transcription works and where it fails: silence hallucinations, word chunking, missing speaker recognition, and other edge cases. That research helps him avoid building a complicated workflow around a tool he does not understand.

Learning

Ask the agent to explain the domain, tools, limits, edge cases, and alternatives.

Mockups

Generate HTML artifacts or visual prototypes before doing expensive production implementation.

Implementation Notes

Ask the agent to record surprises and constraints discovered while building.

Re-spec

Use discoveries to revise the spec instead of forcing the first plan to survive reality.

This maps cleanly to BA workflows: a Business Flow Markdown should not be one-and-done. It should evolve as agents discover exceptions, missing rules, tool limits, and real data constraints.

5. The Video Editing Demo

Thariq records a quick video, gives Claude Code a prompt to transcribe it with Whisper, create a Remotion UI, highlight words, add overlays, and render the final video. He uses /goal so the agent does not stop until the render exists. The result is not perfect, but it proves that non-technical creative work can be handled through a coding-agent harness.

The important part is not only the demo output. It is the workflow behind it: speak instructions in the video, transcribe, inspect edge cases, generate design variations, review HTML artifacts, and only then move toward more expensive React or rendering changes.

One-Shot Prompt

Good for proving a workflow can exist: transcribe, caption, overlay, render.

Exploration Artifact

HTML variants help humans choose style before committing to production implementation.

Future Skill

After edge cases are known, package the repeated video workflow into a reusable skill.

6. HTML Artifacts as Shared Plans

The interview repeatedly returns to HTML artifacts. Plans, PR walkthroughs, incident reports, status reports, design explorations, and implementation notes become easier to review when Claude renders them as readable artifacts rather than long markdown walls.

Thariq is clear that beauty is not the point by itself. The artifact must be something humans actually read. A common failure mode is glazing over AI-generated plans because they are too long. A visual artifact can make planning feel inspectable and collaborative.

For your summary-library project, this validates the direction you are already taking: not only transcript to markdown, but transcript to readable web artifact with tables, diagrams, templates, and source links.

7. Claude Tag and Multiplayer Agents

Thariq describes a split between focused local work and parallel remote work. He tends to keep one main Claude Code session for the thing he is actively focused on, while background explorations, PR babysitting, review handoffs, and multi-Claude work happen through Claude Tag in Slack.

The Slack framing matters because coding agents move from single-player threads to multiplayer channels. A reviewer can be tagged in the same channel where the agent is fixing tests. A project team can interact with the agent in shared context. This makes the agent closer to a proactive collaborator, but Thariq cautions that human metaphors can also be limiting.

Mode Best For Risk
Local Claude Code Focused interactive building, debugging, and tight feedback loops. Too many parallel local threads create attention overload.
Claude Tag in Slack Background work, PR babysitting, team collaboration, shared channels. Identity, memory, and channel context need careful design.
Artifacts Status reports, plans, PR walkthroughs, design options, incident summaries. Long or decorative artifacts still fail if no one reads them.

8. Skills: Package Only After You Know the Shape

Peter shows a podcast production skill that generates posts, takeaways, thumbnails, and clip ideas from a transcript. Thariq's feedback is useful for any skill platform: sometimes the best shape is not one giant skill. It may be a persistent repo or workspace with scripts, examples, assets, output folders, and smaller skills that create or operate inside that workspace.

The more scripts and artifacts a workspace accumulates, the less the agent has to recreate from scratch. A skill can include instructions for how to create or use the workspace, while the workspace itself becomes the durable harness.

Cognitive Skill

Reasoning recipe, rubric, exploration plan, or taste framework.

Actionable Skill

Tool-backed procedure with permissions, inputs, outputs, and verification.

Workspace Harness

Persistent repo with scripts, examples, generated assets, and repeatable commands.

9. Workflows: Sub-Agents, Rubrics, and Clean Context

Workflows are presented as the most powerful pattern when a task benefits from parallelism and verification. In the video-shorts example, a main agent can choose five clip candidates, spawn one sub-agent per clip, give each a rubric, and then use verifier agents to judge output quality.

This addresses two recurring problems: single-agent context overload and self-referential bias. If the same agent creates and verifies its own work, it may be too lenient. Separate worker and verifier agents create a cleaner structure.

Workflow Role Responsibility Why It Helps
Main Agent Chooses candidates, creates the workflow, coordinates outputs. Keeps strategy separate from execution.
Worker Agent Builds one clip, prototype, fix, report section, or candidate output. Gets clean context and enough compute for one bounded task.
Verifier Agent Reads the rubric and evaluates the worker's output. Reduces self-preferential bias and lazy acceptance.
Synthesizer Merges results, selects winners, reports tradeoffs. Turns parallel work into one usable decision.

10. Context Should Get Shorter as Models Get Smarter

One of the most important tactical points: the Claude Code team cut the system prompt by 80%. Thariq says that as models get smarter, they need fewer directions, fewer constraints, and fewer examples. Excessive examples can constrain the model into imitating the example instead of solving flexibly.

The better pattern is often to give the reason behind a preference rather than hard "never" rules. Some constraints are real, like a character limit. But many "never" instructions really mean "usually avoid this because..." A model with the reason can adapt more intelligently.

Platform implication: BA-authored persona prompts should stay compact. Put procedures in skills, tool actions in MCP tools, business rules in policies, and validation in rubrics. Do not turn every agent into a giant prompt document.

11. Productivity Without Attention Collapse

Peter asks about the exhaustion of running many agent threads at once. Thariq's answer is refreshingly human: his personal goal is to be more productive while working less. The practical routine is to keep one main focus project and let background work happen elsewhere.

Lazy prompts create downstream attention debt. If five threads are running from vague prompts, the user pays later in review, correction, confusion, or rework. The optimal amount of "multi-Claude" work depends on the person and task, but prioritization still matters.

One Focus Thread

Keep the high-judgment work in one place where you can actively steer it.

Background Agents

Move PR babysitting, exploration, and queued work to shared or remote channels.

Attention Budget

Measure not only token cost, but review cost and cognitive switching cost.

12. Becoming More Technical Means Knowing Unknown Unknowns

Near the end, Peter asks how someone becomes more technical in an agent-driven world. Thariq's answer is not about memorizing syntax. The goal is to learn the constraints of systems: what is possible, how it works, what alternatives exist, and where the limits are.

Claude can teach and brainstorm, but the learner has to push. It is easy to keep prompting until the output looks good without learning anything. Real learning should feel like work. The path from good output to best output requires understanding the domain, the technical concepts, and the production constraints.

  • Ask the agent to explain tradeoffs, not only produce the final artifact.
  • Read the generated plan, report, or HTML artifact instead of skipping straight to execution.
  • Ask what could go wrong before building the workflow.
  • Learn enough domain vocabulary to ask sharper follow-up questions.
  • Use AI to accelerate learning, not replace it.

13. What This Means for Your Agentic AI Platform

This interview is highly relevant to your Master Agent, Sub-Agent, Skill, Tool, MCP, and Flow Markdown design. It suggests that a BA-friendly platform should separate exploration, execution, verification, and packaging. Business users should not be forced to write giant prompts. They should create structured artifacts that the platform compiles into agent runtime behavior.

Platform Object From the Interview Recommended Implementation
Flow Markdown Planning as iterative unknown removal. Allow versions, implementation notes, edge cases, and re-spec cycles.
Master Agent Main agent coordinates candidates, workers, and verifiers. Own decomposition, routing, synthesis, and escalation.
Sub-Agent Worker agents run with clean context on bounded tasks. Give role, input slice, output contract, and budget.
Validator Separate verifier reduces self-preferential bias. Use rubric agents, deterministic tests, and human approval gates.
Skill Package repeatable procedures after experimentation. Version skills separately from personas; include examples and failure modes.
MCP Tool Agent uses tools like Figma MCP, Whisper, image APIs, and video tooling. Declare permissions, side effects, required evidence, and rollback behavior.
