The Memory Problem Is a Context Compression Problem

A readable summary of Cursor's Compile 26 talk with Baseten researchers. The talk is not about product memory like notes or databases. It is about how long-horizon agents might keep useful context inside the model's KV cache without paying the full cost of every token forever.

Video: The Memory Problem, Baseten | Compile 26 Creator: Cursor Transcript: 2,164 words

The Short Version

The speakers frame agent memory as the problem of retrieving the right context at inference time. Full KV cache is accurate but grows linearly with context length. RAG, fine-tuning, and natural-language summaries are compact, but they lose detail. Their research explores an intermediate layer: learned KV-cache compaction that can be reused in a loop.

  • Long-horizon agents need compressed memory, repeated memory use, and a path from experience to durable knowledge.
  • The method learns queries that attend over the full KV cache and output a smaller compressed KV cache.
  • The deeper idea: compressed KV cache can behave like generated weights, not just stored text.

Problem

The hard part is not storing everything; it is keeping the right information usable

The talk starts with the ambition of near-lossless retrieval of relevant context during inference. For long-running agents, every extra observation, tool result, decision, and conversation turn creates memory pressure. If the agent keeps the full KV cache, memory and compute scale badly. If it over-compresses, the agent forgets details.

Bottleneck

Full KV cache is faithful but expensive

The full cache preserves token-level context, but it grows linearly and becomes a bottleneck for long-horizon agent work.

Tradeoff

Summaries and RAG are compact but lossy

Fine-tuning, retrieval systems, and markdown-style summaries can help, but they do not preserve every useful internal representation.

Gap

The missing layer is between raw cache and durable knowledge

The speakers argue that a middle memory layer is needed for agents that keep working across long tasks.

Memory Layer

They describe three ingredients for reliable long-horizon agents

This is the most useful framing for product builders. The talk separates memory into three jobs: compress the working state, use that memory repeatedly in the loop, and eventually turn important experiences into durable knowledge.

1. Compressed Working Memory Keep enough of the KV-cache information to continue a task without carrying the full context forever.
2. Memory in the Loop Reuse the compacted state across many steps, because long-horizon agents repeatedly plan, act, observe, and continue.
3. Durable Knowledge Find a mechanism that projects useful experience back into weights, preferences, or stable reusable state.

For agent systems, memory should be treated as an active runtime component, not as a passive transcript archive.

Compression Map

The talk places memory methods on a 2x2 map: selection versus synthesis, per-context versus amortized

The speakers classify memory-compression approaches by what they keep and when they pay the cost. Selection keeps a subset of the original cache. Synthesis creates a learned representation. Per-context methods spend work at inference time, while amortized methods pay training cost up front and reuse the learned compressor later.

Method

Their proposed compressor learns to ask questions of the KV cache

The method is inspired by amortized optimization. Instead of running an expensive optimizer for every new input, train a general function that learns to produce the compressed representation. In this talk, that function receives a variable-length KV cache and outputs a smaller KV cache.

Training Signal

Match the full-cache model

The loss compares the model using full KV cache with the model using compressed KV cache, so the compressed version learns to preserve behavior.

Product Intuition

It is a learned context distiller

For platform thinking, imagine a memory service that distills working state while preserving enough behavior to continue the task.

Loop

Single-pass compaction is not enough; the memory must survive repeated use

The researchers want this to support very long or effectively infinite context. A naive loop compresses a block, generates more content, compresses again, and repeats. They report that a compressor trained only for one pass starts to collapse after a few iterations.

Long context The practical goal is to keep extending the working context without paying full KV-cache cost every time. Use a compaction policy that is trained and measured as part of the agent runtime.
Meaning

The bold idea: a compacted KV cache behaves like a small generated network

Near the end, the speaker compares a compacted KV cache to an MLP. A query interacts with keys, applies a softmax-like nonlinearity, then combines values. In that view, compaction is not merely shrinking text; it is producing a functional object from context.

Representation

Context becomes a computation

The compressed cache can be understood as a structure that transforms future queries, similar to how weights transform activations.

Learning

In-context learning is sample efficient

The model can learn from something said once in context, while gradient descent usually needs many examples.

Future Work

Compaction plus gradient descent

The researchers are interested in combining direct compaction with gradient descent into the same memory-like block.

My read: this is research-level infrastructure, but it points toward agent memory that is more than a vector store or a summary file.

Platform Takeaways

What this means for your agentic AI platform

For a BA-facing multi-agent builder, this talk should not become a confusing KV-cache configuration screen. It should become a clean memory framework that hides the low-level machinery while helping BA users choose the right kind of memory for each workflow.

  • Separate business memory from model runtime memory. BA users should design facts, policies, SOPs, evidence, and audit trails; engineers can decide whether the runtime uses RAG, summaries, cache compaction, or fine-tuning.
  • Create memory types in your SOP: working memory, episodic memory, semantic knowledge, procedural SOP, user preference, tool result cache, and audit memory.
  • For each Master Agent and Sub-Agent, define memory permissions: what it can read, what it can write, what must be summarized, what must be retained losslessly, and what requires human approval.
  • For Skills, distinguish cognitive skills that transform understanding from actionable skills that call tools. Actionable skills should always declare required tools, input schema, output schema, guardrails, and audit fields.
  • For Flow Markdown, add explicit memory checkpoints: capture, retrieve, compact, verify, escalate, and persist. This makes memory part of the workflow instead of hidden prompt magic.
  • Evaluate long workflows with memory degradation tests. Run the same business process across many steps and check whether the agent still remembers constraints, facts, tool outputs, and prior decisions.
  • Keep the BA UI simple: let users choose memory intent such as "remember exact evidence", "summarize interaction", "retrieve policy clause", or "persist approved decision" rather than exposing model internals.
  • For regulated workflows, never let compressed memory replace the audit log. Compression can support reasoning, but the source records and decisions must remain inspectable.
