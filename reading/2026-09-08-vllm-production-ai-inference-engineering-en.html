vLLM and Production AI Inference Engineering

A model produces one token at a time. A production inference system must turn thousands of differently shaped requests into an efficient, observable, and reliable GPU workload.

Primary-source research15–20 min readUpdated September 8, 2026Research run 22:38 ICT

This guide synthesizes the vLLM paper and current official documentation with Orca, DistServe, llm-d, and LMCache sources. Feature support and defaults evolve quickly; production configuration should be checked against the deployed vLLM version.

Executive summary

vLLM is the execution engine, not the whole inference platform

vLLM turns an open-weight model into a high-throughput inference engine and OpenAI-compatible server. Its central contribution was to manage the rapidly changing key-value cache with PagedAttention, then combine that memory model with iteration-level scheduling and continuous batching. Modern vLLM adds chunked prefill, prefix caching, quantization, speculative decoding, optimized kernels, and several forms of parallelism.

Those mechanisms solve the single-engine problem: how to keep accelerators useful while requests arrive, grow, finish, and compete for memory. A production platform still needs authentication, quotas, model routing, overload policy, autoscaling, rollout safety, tracing, cost accounting, and evaluation. At larger scale, llm-d can add cache-aware routing and disaggregated serving, while LMCache can extend reusable KV state beyond one engine's GPU memory.

The governing idea

Do not optimize “tokens per second” in isolation. Optimize goodput: requests completed while meeting the latency, quality, reliability, and cost constraints of a real product.

Mental model

One request has two very different computational phases

PrefillRead and encode the prompt.

The model processes many input tokens in parallel, builds attention state, and writes each layer's keys and values into the KV cache. Large matrix operations tend to make this phase compute-heavy.

DecodeGenerate one new token per iteration.

Each step reads model weights and the accumulated KV cache, samples a token, appends new KV entries, then repeats. The small amount of work per step often makes decode memory-bandwidth-heavy.

ConflictPrefill can interrupt smooth generation.

A very long incoming prompt consumes substantial compute and can create inter-token latency spikes for requests already decoding.

OpportunityThe phases use hardware differently.

Schedulers can mix or separate them, tune token budgets, and allocate different parallelism according to product SLOs.

Prefill is compute-heavy; decode is memory-bandwidth-heavy. This distinction explains much of inference engineering. Chat feels slow before the first token when queueing or prefill dominates. It feels choppy after generation starts when decode scheduling, memory bandwidth, or interference dominates.

Measurement

Latency is not one number

TTFTTime to first token

Client send to first streamed token. Includes queueing, tokenization, and prefill.

ITLInter-token latency

The gap between consecutive streamed outputs. It exposes jitter and interruptions.

TPOTTime per output token

Per-request average generation interval after the first token.

E2ELEnd-to-end latency

Total time until the final output arrives, including queue and all generation.

TPOT = (end-to-end latency − TTFT) / (output tokens − 1)

Throughput measures tokens or requests processed per unit time. It can look excellent while interactive users experience unacceptable tails. Goodput counts only work completed inside explicit SLOs, such as P99 TTFT below two seconds and P99 TPOT below 60 milliseconds. Capacity planning should therefore use percentile metrics under realistic arrival rates, prompt lengths, output lengths, sampling parameters, and cache-hit patterns.

Benchmark terminology differs across tools, so compare measurement points and formulas rather than labels. Warm prefix caches can also inflate repeated benchmark results. vLLM's benchmark documentation recommends resetting caches or varying reproducible inputs when reuse is not part of the intended workload.

Core contribution

PagedAttention makes KV cache allocatable

Autoregressive generation avoids recomputing the full prefix by storing each layer's attention keys and values. That KV cache grows with sequence length, model depth, KV-head count, head dimension, concurrency, and bytes per element. Long contexts can make this runtime state consume more GPU memory than expected.

Approximate KV bytes per request = 2 × layers × KV heads × head dimension × cached tokens × bytes per element

Earlier serving designs often reserved contiguous memory for a request's maximum possible sequence. Variable lengths produced internal fragmentation; changing requests made external fragmentation difficult; beam search duplicated shared prefixes. Memory waste reduced the number of sequences that could be batched together.

PagedAttention borrows the operating-system idea of virtual memory. A request sees logical KV blocks, while a block table maps them to non-contiguous physical blocks in GPU memory. Blocks are allocated as needed and returned when requests finish. Copy-on-write permits generated branches to share blocks until they diverge. The vLLM paper reported roughly two-to-four-times throughput over its tested FasterTransformer and Orca-style baselines at comparable latency, especially with long, variable sequences and complex decoding.

This does not make memory infinite. When the working set exceeds available KV blocks, requests can queue or be preempted and later recompute state. Frequent preemption is usually a capacity signal: reduce maximum context, reduce concurrent sequences, use lower-precision KV cache where supported, add memory, or change the workload policy.

Scheduling

Continuous batching follows token iterations, not whole requests

Static batching waits for a fixed group and holds its shape until every request completes. Generation lengths vary, so short requests waste capacity while waiting for the longest. Orca introduced iteration-level scheduling: reconsider the batch after each model iteration, remove completed sequences, and admit new work.

Continuous batching applies this idea in production engines. The active batch changes as requests arrive and finish. vLLM V1 uses a unified scheduler with a fixed token budget per iteration rather than treating prefill and decode as entirely separate request types. This supports prefix hits, speculative tokens, and chunked prefills through the same accounting model.

Chunked prefill divides a long prompt so decode requests do not wait behind one huge prefill operation. Current vLLM V1 documentation says it is enabled whenever possible and prioritizes pending decodes before using the remaining token budget for prefill. Smaller token budgets generally favor smoother ITL; larger budgets can improve prefill efficiency and TTFT or throughput, depending on workload and hardware. There is no universal best value.

Scaling inside an engine

Fit first, then optimize communication

vLLM supports tensor, pipeline, data, expert, and context parallel strategies, but they solve different constraints. Tensor parallelism shards matrix operations and usually performs best within a node with fast GPU interconnects. Pipeline parallelism partitions model layers into stages and can cross nodes, but bubbles and uneven partitions affect utilization. Data parallelism duplicates the model so replicas serve independent traffic. Expert parallelism distributes experts in mixture-of-experts models.

The official guidance commonly starts with tensor-parallel size equal to GPUs per node and pipeline-parallel size equal to node count when a model spans nodes. That is a starting topology, not a guaranteed optimum. Measure collective communication, uneven memory, queue depth, request shape, and failure behavior.

A model that fits on one GPU is often easier to scale with independent replicas. Sharding should be earned by model size or a demonstrated latency need because every collective operation creates synchronization and networking sensitivity.

A generic round-robin load balancer ignores the most valuable runtime facts. One replica may already hold a long shared prefix, another may have a deep waiting queue, and another may be close to KV saturation. llm-d separates a Router, an InferencePool, and model servers such as vLLM. Its Endpoint Picker can score pods using real-time signals and cache affinity; precise routing can consume KV events emitted by engines.

LMCache extends the cache boundary. It can move KV state into CPU memory, local SSD, or remote backends; share it across engine instances; and keep cache state alive independently from a vLLM process. This can reduce repeated prefill for long-context agent and RAG workloads, but only when hit rate, transfer bandwidth, serialization overhead, and reuse distance justify the added layer.

Advanced architecture

Disaggregated prefill and decode trades interference for transfer

Aggregated serving runs both phases on the same workers. It is simpler and avoids moving KV tensors between pools, but long prefills can interfere with active decode and the two phases must share one scaling ratio. DistServe assigns them to different GPUs, optimizes each pool for its own SLO, and places workers according to network bandwidth.

The concept is compelling when traffic is large enough to keep specialized pools utilized and when TTFT and TPOT require different resource plans. The cost is substantial: the scheduler must select both workers, transfer KV state, handle partial failure, adapt the prefill-to-decode ratio, and avoid turning the network into the new bottleneck. Start aggregated. Disaggregate only after traces show phase interference or coupled scaling is limiting goodput.

Operating model

Production failures usually appear at the boundaries

  1. Admission: unbounded queues hide overload and convert it into extreme tail latency. Set explicit concurrency, queue, prompt, and output limits.
  2. Memory: monitor KV utilization and preemption together. High GPU utilization is not success if requests repeatedly recompute evicted context.
  3. Streaming: detect disconnected clients and cancel work promptly; otherwise the GPU generates tokens nobody will consume.
  4. Routing: include model revision, adapter, structured-output mode, multimodal capability, and cache affinity in placement decisions.
  5. Autoscaling: GPU utilization alone reacts late. Combine queue depth, waiting tokens, active sequences, arrival rate, and SLO headroom.
  6. Rollouts: warm model weights and kernels before traffic, then canary both quality and latency distributions. Engine upgrades can change defaults.
  7. Security: authenticate the public gateway, isolate tenants in cache keys and logs, restrict model repositories and remote code, and protect distributed worker networks.
  8. Evaluation: performance changes can alter precision, decoding, or output behavior. Run correctness and product evals alongside load tests.

Practical adoption

A conservative path from one GPU to a serving platform

  1. Define product SLOs for TTFT, TPOT, E2EL, availability, output quality, and cost per useful request.
  2. Capture representative traces: prompt length, output length, arrival pattern, shared prefixes, cancellations, and multimodal inputs.
  3. Serve one fixed model revision on one engine and establish correctness plus latency percentiles.
  4. Tune maximum context, batched token budget, concurrent sequences, memory utilization, and overload limits.
  5. Add prefix caching, quantization, or speculative decoding only when the trace predicts a benefit.
  6. Scale with replicas when the model fits; add tensor or pipeline parallelism when size or step latency requires it.
  7. Introduce cache-aware routing, external KV storage, or P/D disaggregation only after measuring the bottleneck they solve.
  8. Automate canary evaluation and rollback for model, engine, driver, kernel, and configuration changes.

Takeaways

Twelve ideas worth keeping

  1. Prefill and decode have different compute profiles and user-visible latency metrics.
  2. KV cache, not only model weights, determines concurrency and serving cost.
  3. PagedAttention reduces fragmentation by mapping logical cache blocks to physical blocks.
  4. Continuous batching changes the active batch at token-iteration boundaries.
  5. Chunked prefill trades prompt efficiency against smooth decode and tail latency.
  6. Measure TTFT, ITL, TPOT, E2EL, throughput, and goodput at percentiles.
  7. Prefix caching only helps when prompts share exact token prefixes and routing preserves locality.
  8. Speculative decoding is workload-dependent, not a universal throughput switch.
  9. Scale with replicas before sharding when the model comfortably fits one accelerator.
  10. Disaggregation is an advanced answer to measured phase interference.
  11. vLLM is the model execution layer; the product still needs a control and operations plane.
  12. The correct optimization is the one that improves SLO-compliant useful work.
