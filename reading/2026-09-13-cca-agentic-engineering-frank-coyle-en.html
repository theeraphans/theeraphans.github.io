The CCA Exam as a Field Guide to Agentic Engineering

Frank Coyle uses production scenarios to explain what an agent engineer must control: loops, tools, instruction scope, context boundaries, and unattended workflows.

Executive summary

Learn failure modes, not just vocabulary

Coyle opens with a practical teaching problem: how to prepare students for agentic AI when a computer science background alone no longer feels like a straightforward route to employment. He treats the Claude Certified Architect exam as a map of engineering concerns, rather than presenting certification as a guaranteed job credential.

His central learning strategy is experimentation. Build things, observe where they fail, and learn the anti-patterns. The talk moves through customer support, code generation, multi-agent research, developer productivity, and continuous integration. Structured extraction is introduced as another scenario, but time runs out before a substantive walkthrough.

The transferable lesson

An agent system is not just a clever prompt. Its runtime must distinguish requests from completed actions, manage termination, limit context growth, and fit the operational environment in which it runs.

01 · The learning map

Use the domains as engineering topics

The speaker describes a scenario-based, timed, proctored exam and lists five topic areas: agentic architecture, Claude Code configuration and workflows, prompt engineering and structured outputs, tool design and MCP integration, and context management and reliability.

He also describes six production scenarios, with a subset selected for the exam. Those mechanics are not essential to the talk's engineering value. Even without taking an exam, the topic list highlights capabilities that a production engineer needs to understand.

His six scenarios are customer support resolution, code generation, multi-agent research, developer productivity, Claude Code in CI, and structured data extraction. This article does not invent a missing extraction lesson or a complete MCP tutorial merely because those topics appear in the introduction.

Certification details are time-sensitive

The presentation mentions a March release, a $99 individual fee, and a six-month retake interval. Treat these as speaker-reported details, not verified enrollment instructions. The official access-request page could not be retrieved during this summary run.

02 · Control flow

The loop is a runtime responsibility

Coyle connects agent loops with classical control flow: sequence, conditionals, and repetition. His historical analogy invokes the structured-programming work of Böhm and Jacopini. The useful point is that repeated observation and action give an agent workflow more flexibility than a single prompt-and-response interaction.

The analogy should not be stretched into a proof that adding a loop alone makes an LLM system correct, autonomous, or computationally universal. Computation also depends on the underlying machine and data operations. Loops create opportunities for recovery and progress, but also for repeated mistakes.

As an engineering implication, production loops need explicit limits: maximum steps, deadlines, cost budgets, retry rules, cancellation, and escalation. The presentation's simplified loop illustrates control flow, not a complete safety design.

03 · Customer support

A model proposes a tool call; the runtime performs it

The customer-support example illustrates a distinction that is easy to miss. For a client-side tool, the model returns a structured request containing the tool identity and arguments. Application code executes the tool, then sends the result back so the model can continue.

1. Request

Send the conversation and tool definitions to the model.

2. Inspect

Read the stop reason and structured tool-use blocks.

3. Execute

Validate authority and arguments, run the client tool, and return its result.

4. Continue or finish

Let the model use the result; handle completion and failure explicitly.

Coyle warns against taking a single response as the final answer without checking why generation stopped. A tool request is not a finished action, and a truncated response is not a complete answer.

Different stop reasons imply different next steps

tool_use signals requested tool work. end_turn signals that the assistant turn ended. max_tokens means output generation hit its configured limit and may be incomplete. Other stop reasons also require handling. Claude's stop-reason documentation is the primary reference for these distinctions.

Two important clarifications

max_tokens is not automatically evidence that the entire input context window was exhausted. Also, the statement that “the LLM cannot execute tools” describes client-tool execution responsibility: hosted server tools may be executed by the provider's infrastructure. In either case, execution happens outside token generation.

Coyle mentions human review or escalation when an answer is uncertain. In a production support system, a model's stated confidence alone should not authorize a refund, account change, or customer delivery. Policy, validation, and evidence must govern those actions.

04 · Code generation

Instructions should match their scope

The talk introduces hierarchical CLAUDE.md instructions: broad guidance and more specific project or directory rules. The purpose is to avoid making every task carry every rule at the same level.

A useful interpretation is to separate generally applicable practices from repository conventions and local exceptions. Coyle's verbal description of the levels is brief and somewhat ambiguous, so it is better treated as the concept of scoped instructions than as an exact filesystem recipe.

Claude Code's memory documentation explains the supported instruction locations and loading behavior. A Markdown instruction file guides the model; it is not a security boundary that can enforce permissions or guarantee compliance by itself.

05 · Multi-agent research

Specialize the work and minimize the return context

Coyle's anti-pattern is one agent overloaded with unrelated tools and responsibilities. He argues for specialized workers with only the capabilities needed for their tasks. The carpenter analogy makes the point: a role should have a clear purpose rather than claim to do everything.

The exact suggestion of one or two tools is illustrative, not a universal optimum. A coherent research task may legitimately need several tools. The design criterion is relevance and manageable responsibility, not the smallest possible tool count.

Give a critic the claim and evidence

The critic example receives a proposed claim and supporting evidence, without inheriting the full reasoning narrative that produced the claim. Coyle argues that this reduces the chance of agents simply converging on the same position through shared context.

Research worker → claim + evidence → critic

The critic evaluates the result using task-relevant material, rather than absorbing all exploratory conversation.

This is a plausible independence strategy, not a guarantee against groupthink. Agents can share model biases even when contexts are isolated. Reliable criticism also needs enough evidence to reconstruct the issue; aggressive context trimming can make the critic less informed.

06 · Developer productivity

Return findings, not every log line

The next anti-pattern is letting each subtask dump its complete output into the primary conversation. Logs and exploratory messages consume tokens and can obscure the information needed for the next decision.

Coyle gives a log-analysis example: run the investigation in a separate context, produce a useful summary, and bring that summary back. The important boundary is between the working material needed for investigation and the decision material needed by the coordinator.

He also proposes monitoring token count and compacting long sessions. His 150,000-token example is a demonstration threshold, not a generally recommended setting for every model. Context capacity, cost, task sensitivity, and the quality of the compacted result all matter.

What a summary must preserve

As editorial interpretation, useful compression keeps findings, source references, unresolved uncertainty, current state, and constraints that would change the next action. A shorter context that loses an approval condition or a critical error is not an improvement.

The talk briefly mentions custom compression logic in a book handed out at the event. It does not provide enough implementation detail to establish a specific compression framework or reproduce its API here.

07 · Continuous integration

Unattended execution still needs bounded authority

Coyle warns that an interactive session is a poor fit for CI: a job can stall while waiting for someone to answer a prompt or approve an operation. Automated pipelines should use supported non-interactive execution with an environment configured for the task.

Non-interactive does not mean unrestricted

As an implementation implication, predefine allowed tools, credentials, network access, write targets, and failure behavior. Removing prompts should not mean granting an agent arbitrary production access. Required approvals can remain separate workflow gates.

Batch processing trades immediacy for lower cost

The speaker recommends batch processing for work that can wait. The Message Batches documentation describes asynchronous requests priced at 50% of standard API usage. Requests are processed independently, and unfinished processing expires after 24 hours.

This corrects the caption's “at least 24 hours” wording: the documentation does not say every job requires a minimum 24-hour wait. Batch processing is also an API mechanism, not automatically the same thing as running Claude Code non-interactively in CI. A dependent client-tool loop still needs orchestration around successive requests.

Editorial assessment

A useful checklist, not a complete architecture

The talk is strongest as an anti-pattern tour. It encourages engineers to look past a plausible answer and examine the runtime around it: what stopped, what executed, what context returned, and whether the workflow can operate in its actual environment.

Its short format leaves gaps. MCP tool-contract design, structured extraction, validation, evaluation, retries, idempotency, and permission enforcement are not developed in depth. The example loop should not be copied as a production implementation without those concerns.

For an agentic platform, the transferable message is to make control visible. Each worker needs a bounded task; each tool call needs an execution owner; each returned summary needs a useful contract; each stopping condition needs a defined outcome. A certification topic list can motivate these decisions, but cannot make them for the system.

Takeaways

What to remember

  1. Learn by building and inspecting failure modes.
  2. Use exam domains as a learning map, not a promise of employment.
  3. A tool request is not a completed action.
  4. Inspect stop reasons before declaring an answer complete.
  5. Keep scoped instructions clear and relevant.
  6. Specialize responsibilities without assuming a fixed tool-count rule.
  7. Give critics evidence without unnecessary anchoring context.
  8. Return concise findings from isolated investigations.
  9. Compaction must preserve critical state and constraints.
  10. CI needs non-interactive execution with bounded permissions.
  11. Batch API processing is asynchronous, not a 24-hour minimum wait.
  12. Simple agent loops still require production controls.
