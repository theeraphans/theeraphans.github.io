Opening Signal

The event frames agents as an engineering discipline.

The opening positions the day around harness engineering: the code, controls, protocols, and practices that turn model capability into reliable systems. The captions emphasize that standardization is happening around tools and platforms, not around any single model provider.

Cost becomes an SLA-like metric Teams are watching spend just below quality, because agentic workflows can multiply calls quickly.
Agents leave demo mode The event survey points to broad agent usage and much more willingness to give agents write access.
Experimentation accelerates Cheaper prototypes and trials let teams make more bets, but they also increase review burden.
Technical understanding is at risk The benefit of speed comes with the danger that teams lose deep codebase and system knowledge.

The lesson for platform teams: do not measure only automation success. Measure review load, cost per outcome, escalation rate, and whether humans still understand the system they are shipping.

Harness Engineering

The harness is the product boundary around model intelligence.

Across the recording, "harness" means the operational wrapper that gives an AI system shape: prompts, tools, runtime loops, graders, context retrieval, memories, permissions, traces, tests, and human checkpoints. A strong harness lets the same task become reusable, inspectable, and improvable.

Intent Capture the business goal, user role, constraints, and definition of done.
Context Select documents, memories, examples, schema, policies, and current state.
Action Route work through tools, MCP servers, APIs, CLIs, or human approvals.
Verification Use evals, graders, validators, tests, traces, and review gates.
Learning Turn successful work into skills, memories, datasets, and reusable flows.

The agent is not the model call. The agent is the loop, the tools, the judgment, and the memory around it.

DSPy

DSPy treats AI programs like composable, testable functions.

The DSPy segment is useful because it gives a programming-language lens for prompts. Instead of baking everything into one prompt, the system separates the task from the model, harness, and implementation details. Natural-language signatures express inputs and outputs, while code enforces constraints.

Idea Meaning Platform Translation
Signature A clear contract for what goes in and what must come out. Let BAs define Flow Markdown input and output shapes before agent design begins.
Module A reusable AI program block such as predict, reason, retry, or extract. Represent Sub-Agent and Skill blocks as composable units with typed responsibilities.
Optimizer A way to improve prompts and examples against an evaluation target. Connect skills to golden examples, rubrics, and automated eval runs.

The practical takeaway is not "use DSPy everywhere." It is that prompt behavior should be packaged as reusable programs with contracts, tests, and measurable improvement loops.

Token Roles

Tokens are not fungible; assign them jobs.

One of the strongest system-design ideas in the recording is that tokens have roles. A token used by an executor is different from a token used by a grader, dreamer, planner, critic, memory writer, or advisor. Reliability often improves when the harness deliberately spends tokens on verification and reflection, not only direct execution.

Executor Uses tools and changes system state. Needs permissions, rollback, and exact task boundaries.
Grader Checks work against rubrics, examples, policies, tests, or expected outputs.
Dreamer Inspects transcripts or traces after a run and writes findings back to memory.
Advisor Surfaces risks, tradeoffs, and next questions before the execution loop proceeds.

This maps cleanly to Master Agent design: the Master should not simply delegate work. It should decide which token job is needed at each phase and whether the next step is execution, critique, learning, or escalation.

Tools, MCP, Skills

Security belongs in the infrastructure around the loop.

Several segments converge on the same warning: a capable agent will pursue its goal through whatever context and tools are available. That means credentials, tenant boundaries, tool permissions, identity, and approval gates must be enforced outside the model, not merely requested in a prompt.

Layer Use When Main Failure Mode
CLI One agent needs a transparent, reproducible command for a narrow task. Wrong command, hidden environment assumptions, or missing audit trail.
MCP Multiple agents need shared access to a service, database, registry, or tool provider. Weak validation, poor tenant isolation, broad credentials, or vague tool schemas.
Skill Multiple workflows share a repeatable procedure, policy, method, or playbook. Outdated instructions, missing verification, or too much hidden persona logic.
  • Do not share raw credentials with agents. Give scoped tool access through infrastructure gates.
  • Enforce tenant isolation below the model. The model should not be trusted to remember boundaries perfectly.
  • Track agent identity and human accountability. A human owner must remain attributable for consequential actions.
  • Treat registration as its own problem. MCP gives tool access, but agent-native onboarding and legitimacy need additional patterns.
Loops

Do not automate the whole company first. Build small loops that compound.

The panel content repeatedly argues for incremental loops. Instead of handing an entire business process to an autonomous system, teams should automate a bounded loop, verify it, give it a clear owner, and expand only after the evals, traces, and permission model are trustworthy.

Assist Agent drafts, searches, summarizes, or proposes work while humans execute.
Act Agent performs low-risk actions inside clear boundaries with approval gates.
Review Humans inspect diffs, traces, logs, cost, and quality before promotion.
Learn Successful work becomes examples, skill files, flow changes, or memory updates.
Scale Only then does the loop expand to broader tasks or more users.

This is especially relevant for BA-created flows. The BA should define the business loop and escalation points, while the platform turns that into an executable agent graph with approval and attribution built in.

System Patterns

The talks keep returning to context, specs, and tool routing.

The middle of the recording spans many system talks. The unifying pattern is that agent quality depends on what the agent sees, which tools it can call, how concrete the spec is, and whether the runtime can inspect or improve the work afterward.

Fat agent risk

Too many tools create routing confusion

Giving every tool definition to every request works at small scale, but prompt size and tool ambiguity become real failure modes.

Concrete specs

Abstract goals need implementation detail

Agents struggle when an abstract product spec hides database, consistency, store, and runtime assumptions.

Frameworks

Boilerplate should be abstracted

Agent frameworks can handle generation loops, function calling, retries, routing, state, and error handling.

Polygraph-style context

Make many repos feel readable

Meta-harnesses can analyze dependency graphs and code relationships so agents do not act like every repo is isolated.

Provider abstraction

Keep the app above model churn

SDK and runtime layers let teams switch providers or models without rewriting the agent product surface.

Persona Evals

Persona performance can look good while being historically wrong.

One later talk gives a useful warning for role-based agents. A model may pass a persona-style evaluation while still blending modern culture, fictional representations, and training data artifacts into the output. The issue is not only tone. It is source separation and temporal correctness.

Persona prompt

Defines role and behavior

Useful for style and scope, but not enough to guarantee factual grounding.

Knowledge source

Defines what the agent may know

Domain agents need explicit allowed sources, time windows, and retrieval rules.

Eval

Defines what correctness means

Persona evals should check source grounding, contradictions, and historical or policy boundaries.

For your platform, persona should be just one field in the Agent Spec. It should not swallow business rules, skill instructions, knowledge boundaries, or tool permissions.

Platform Takeaways

How this maps to a Master Agent, Sub-Agent, Skill, and MCP platform

For your BA-facing agentic AI platform, this video is valuable because it argues for separating business intent from execution mechanics. The BA should describe the business flow, policy, exception path, and success criteria. The platform should assemble the agent graph, tools, skills, evals, and permissions.

  • Make Flow Markdown the contract. Business Flow should become a structured spec with actors, triggers, states, data, risks, decisions, and definition of done.
  • Keep persona small. Persona should describe role, communication style, and responsibility boundary, not hide all business logic.
  • Separate cognitive and actionable skills. Cognitive skills guide reasoning and judgment. Actionable skills require tools, inputs, permissions, and verification gates.
  • Attach MCP tools through capability policies. A tool should be available only when the flow, user, tenant, and agent role allow it.
  • Represent Master Agent as orchestrator. It routes token jobs, delegates Sub-Agents, asks for human approval, and writes learning back to memory.
  • Represent Sub-Agent as bounded worker. Each Sub-Agent should have input contract, output contract, allowed tools, stop conditions, and escalation rules.
  • Make evals first-class. Every important flow needs examples, rubrics, cost targets, trace checks, and regression tests.
  • Capture successful work into the company brain. Good prompts, decisions, exception handling, and tool recipes should become versioned skills or memory assets.
Flow Markdown

A BA-friendly Flow Markdown can turn business process into agent harness.

The artifact below is the shape I would give BAs. It keeps business language at the top, then lets the platform compile that into Master Agent orchestration, Sub-Agent scopes, skills, MCP tools, and verification gates. 

# Agentic Flow: Business Process to Harness

goal: Convert a business flow into a governed multi-agent workflow.
owner: Business Analyst
runtime_owner: Master Agent
flow_type: governed_multi_agent_harness

business_context:
  domain: claims_processing
  target_user: operations_specialist
  trigger: new_claim_received
  desired_outcome: claim_ready_for_human_decision
  risk_level: high

master_agent:
  persona:
    role: claims_workflow_orchestrator
    tone: concise_clear_audit_friendly
  responsibilities:
    - understand_business_goal
    - select_sub_agents
    - route_token_jobs
    - enforce_policy_and_escalation
    - write_lessons_to_memory

sub_agents:
  - id: intake_reader
    job: extract_claim_facts
    allowed_skills: [document_extraction, policy_grounding]
    allowed_tools: [ocr_mcp, document_store_mcp]
    output_contract: structured_claim_facts
  - id: policy_checker
    job: compare_facts_to_policy
    allowed_skills: [policy_reasoning, exception_detection]
    allowed_tools: [policy_mcp]
    output_contract: coverage_assessment
  - id: risk_reviewer
    job: identify_uncertainty_and_escalation
    allowed_skills: [risk_rubric, evidence_gap_analysis]
    allowed_tools: []
    output_contract: review_recommendation

skills:
  cognitive:
    - policy_reasoning
    - exception_detection
    - evidence_gap_analysis
  actionable:
    - document_extraction:
        required_tools: [ocr_mcp, document_store_mcp]
        verification: extraction_confidence_check
    - policy_lookup:
        required_tools: [policy_mcp]
        verification: source_citation_required

permissions:
  tenant_isolation: required
  write_access: disabled_until_human_approval
  secret_access: never_exposed_to_model
  human_owner_required: true

evals:
  examples:
    - approved_claim_with_complete_documents
    - claim_with_missing_evidence
    - exception_case_requiring_escalation
  graders:
    - factual_extraction_accuracy
    - policy_source_grounding
    - escalation_correctness
    - cost_per_completed_review

loop:
  steps:
    - receive_input
    - retrieve_context
    - delegate_to_sub_agents
    - synthesize_result
    - grade_and_validate
    - request_human_approval
    - write_reusable_learning
  stop_conditions:
    - missing_required_document
    - policy_conflict
    - confidence_below_threshold
    - human_rejects_recommendation

memory:
  write_when:
    - human_approves_result
    - reviewer_corrects_agent
    - new_exception_pattern_found
  assets:
    - examples
    - decision_rationales
    - tool_recipes
    - updated_skill_instructions
