Agents Can Improve Agents When the Harness Is Strong

A practical summary of Alfonso Graziano's talk on using coding agents, spec-driven development, golden datasets, live traces, and human review to make AI agents more reliable and secure over time.

Video: Agents Building Agents - Alfonso Graziano, Nearform Creator: AI Engineer Transcript: 4,742 words

The Short Version

The talk argues that AI agents should be improved like software systems, not tuned by guesswork. Build a golden dataset, define scorers, run evals, let a coding agent propose changes, measure the result, roll back regressions, and convert production failures into future tests.

  • Agents fail because of missing tools, weak prompts, poor retrieval, and messy live data.
  • A coding agent can optimize another agent when evals, traces, and constraints are explicit.
  • The real unlock is harness engineering: specs, quality gates, context, observability, and governance.

Problem

Everyone wants agents, but agents create a new reliability problem

Alfonso starts with the obvious market demand: agents for workflow automation, search, and business use cases. But agents are non-deterministic, can hallucinate, can be slow, can be expensive, and can behave differently on live user data than they do in controlled tests.

Failure

Missing tools

If an agent is expected to fetch a page, update a record, or search a system, the tool must exist and be described clearly.

Failure

Weak system prompt

The system prompt carries domain instructions, boundaries, and expected behavior. Small gaps can create large eval failures.

Failure

Poor context retrieval

The agent may know it needs information, but not where to look or which secure retrieval tool to call.

Failure

Non-determinism

Traditional unit-test thinking is not enough because outputs, tool choices, and reasoning paths can vary.

Failure

Live data messiness

Real users produce wider, noisier, and less predictable cases than the team initially includes in evals.

Failure

Blind production

Without traces, feedback, and observability, the team cannot tell why an agent failed or how to fix it.

Evals

A golden dataset is the test suite for a non-deterministic system

The talk defines a golden dataset as a file or set of files created with subject matter experts. Each case records the input and the expected behavior. The expected output can be a final answer, a number, a tool call, a tool call with specific parameters, or a chain of tool calls.

AutoAgent

The core pattern is an optimization loop around a target agent

Alfonso describes AutoAgent: a coding agent that changes another agent, runs evals, reads reports and traces, proposes hypotheses, and keeps or rolls back changes based on measured results. In the demo-style example, a naive agent improves from 18% to 83% pass rate in about 10 iterations.

Create an optimization job

Use a markdown file to describe objective, target repository, metric, constraints, relevant files, and what the coding agent must not change.

Run the baseline

Run evals once, generate a baseline report, and identify what currently works and what fails.

Generate a hypothesis

The coding agent tackles one class of failures at a time: missing tool, prompt gap, retrieval problem, or tool logic bug.

Change the agent

The system updates prompts, tool descriptions, tool logic, or agent code to test the hypothesis.

Run evals and write reports

Each iteration produces a report, updates shared memory, and records whether the branch improved, regressed, or stayed flat.

Keep, rollback, or steer

If metrics improve, continue from the branch. If they regress, roll back. If the idea is promising, a human can guide the next iteration.

The important point is not that an agent edits code. The important point is that it edits code inside a measurable loop.

Live Data

Production feedback becomes the raw material for the next eval suite

The second failure mode is bad performance on live data. The talk proposes collecting traces, user feedback, and subject matter expert annotations, then clustering failure modes and converting validated failures into future golden dataset cases.

User Feedback

Thumbs plus notes are enough to start

The example uses a simple "was this helpful" signal plus a comment that describes what went wrong or what was expected.

SME Feedback

Experts annotate traces when users do not

Subject matter experts can review the input, output, tool usage, and behavior, then provide a richer correction.

Failure Reports

The report is the bridge between messy traces and actionable engineering work

After enough traces are collected, a coding-agent skill analyzes the JSON traces, clusters failure modes, runs root cause analysis against the code and traces, and generates a markdown report. The report can include positives, negatives, negative rate, trace IDs, root causes, and proposed fixes.

Report section Purpose Decision it supports
Executive summary Shows overall feedback, quality direction, and major risks. Whether the issue pattern deserves immediate attention.
Failure clusters Groups related problems instead of treating every trace as unique. Which recurring failure modes to fix first.
Trace links Connects the cluster back to concrete examples and trace IDs. Whether SMEs and engineers trust the diagnosis.
Root cause analysis Explains whether the issue comes from prompt, tool, retrieval, formatting, or code logic. Which part of the agent system should change.
Fix proposal Suggests implementation direction and expected behavior. Whether to fix now, fix later, discard, or turn into a spec.

The talk's operational rhythm is strong: generate a report about once per sprint, or whenever you have enough meaningful feedback volume.

Harness Engineering

Agents building agents only works when the surrounding environment is engineered

Alfonso names the discipline "Harness Engineering": build the environment around a coding agent so it can work reliably. The harness gives the coding agent constraints, tasks, feedback loops, governance, tests, evals, context, and observability.

Spec

Every failure mode becomes a spec

Expected behavior is written down before implementation, so the coding agent has a clear target.

Quality

Quality gates are mandatory

Linting, unit tests, evals, LLM code review, and regression traces keep the loop grounded.

Context

Context engineering matters

The coding agent needs the right repository files, reports, traces, constraints, and product goals.

Observability

Production cannot be blind

Teams need traces, tool calls, token cost, latency, outputs, and user feedback to understand failures.

Governance

Humans define the boundaries

The coding agent should not modify golden datasets or scorers just to make evals pass.

Change Log

Every hypothesis is preserved

Branches, reports, memory files, and metrics create a history of what was tried and why.

Platform Takeaways

What this means for your agentic AI platform

This video is very relevant to your Master Agent, Sub-Agent, Skill, Tool MCP, SOP, and Flow Markdown challenge. The key lesson: do not make BA users "prompt engineers." Give them structured artifacts that become specs, evals, traces, and improvement loops.

  • Agent Card: define purpose, scope, allowed tools, forbidden actions, inputs, outputs, memory permissions, escalation rules, and eval metric.
  • Skill Card: separate cognitive skills from actionable skills. Cognitive skills transform understanding. Actionable skills must declare required tools, input schema, output schema, preconditions, side effects, and audit fields.
  • Tool MCP Contract: every tool should expose permission level, schema, deterministic behavior, failure modes, retries, logging, and data sensitivity.
  • Flow Markdown: let BA users describe business steps, decision points, required evidence, responsible agent, tools, memory checkpoints, and human approval gates.
  • Golden Dataset Builder: every flow should generate test cases from SME examples: input, expected answer, expected tool call, expected handoff, and unacceptable behavior.
  • Scorer Library: provide reusable scorers for exact answer, semantic answer, tool-called, tool-parameter, no-unsafe-action, citation-present, policy-compliant, and human-escalated.
  • Trace Review Workspace: give SMEs a screen to annotate real runs, cluster failures, mark false positives, and promote validated failures into regression tests.
  • Optimization Job: convert a BA-approved failure cluster into a markdown job that a coding agent can run against a target repository with constraints.
  • Human Governance: forbid coding agents from weakening evals, deleting traces, changing scorers to cheat, or expanding tool permissions without review.
  • Release Gate: require eval improvement, regression stability, trace evidence, and approval before shipping a new agent version.
