A Simple Framework for AI Native Businesses

A practical summary of Devin Kearns' framework for building AI-native operations: do not start by scattering agents across the company. Start by capturing business events, syncing clean context into the source of truth, auditing work against SOP checklists, and only then building workflows or agents on top.

The Short Version

Devin argues that most companies should stop beginning AI transformation with a list of agents. The first layer is an operating system for business context: capture the events where work actually happens, clean and deduplicate them, match them to source-of-truth records, update those records, monitor work against checklists, and then build automations or agents once the foundation is trustworthy.

  • The real blocker is often not model capability. It is incomplete, stale, or unstructured business context.
  • Events from meetings, emails, and internal chat are the raw material for an AI-native operation.
  • Agents come later, after source-of-truth data, workflow state, confidence scoring, and audit loops exist.

The Problem

Business leaders ask for agents, but the operating environment is often not ready.

The talk starts with a pattern the speaker sees often: teams show up with a list of agents they want to build, such as proposal generators, claims follow-up agents, CRM assistants, or project coordinators. The problem is that the source-of-truth systems those agents need to rely on are usually incomplete, stale, or too thin to support autonomous work.

False start

A list of agents is not a strategy

Building scattered agents in different environments creates fragmentation instead of an AI-native operation.

Real blocker

Data readiness is a human workflow issue

Humans compensate for missing CRM, project, case, or ATS context by asking each other and filling gaps manually.

Core risk

Agents cannot take over from incomplete records

If a human cannot confidently continue work from the source-of-truth record, an agent will struggle too.

The speaker's practical reframing is useful: the foundation is not "AI readiness" in the abstract. It is whether the business captures enough real context for a person or agent to continue work without reconstructing history.

Foundation First

The Agentic OS starts by keeping the source of truth alive.

The source of truth might be a CRM for sales, project management software for delivery, case management software for legal, or an applicant tracking system for recruiting. The first job of the AI system is not to run a fancy workflow. It is to keep those records complete, current, and contextualized for both humans and future agents.

Capture Listen where business context originates: meetings, email, and internal messages.
Contextualize Clean the event and determine which deal, case, project, candidate, or task it belongs to.
Sync Write the useful context back to the source-of-truth platform.
Monitor Audit work against checklists and workflow state before automating more of the work.

Do not build agents on top of messy records. Build the context layer that makes records usable first.

Event Sources

Meetings, emails, and internal chat are the main origination points for work context.

Devin narrows the starting inputs to three practical channels. Documents, files, and calendar events matter too, but in many organizations they are created, shared, or announced through meetings, email, or chat. That makes these channels the best first surface for event-driven capture.

Meetings

Transcripts capture decisions and nuance

Call transcripts can preserve why a deal moved, what a client asked for, and what next steps were agreed.

Email

Threads carry external commitments

Email is where proposals, approvals, requests, documents, notifications, and scheduling messages often arrive.

Internal chat

Team messages reveal work in motion

Slack, Discord, Teams, or Google Chat often contain operational decisions that never reach a formal record.

This is also a behavior change. Once people know meetings and messages feed downstream systems, they tend to become clearer, more explicit, and more generous with useful context.

Event Pipeline

The event pipeline turns raw communication into trusted operational state.

The talk describes a repeatable high-level flow. An event happens, the system deduplicates it, cleans it, matches it to a work item, checks confidence, escalates when uncertain, updates or creates records, and then decides whether any workflow should run.

1. Event happens Email, meeting transcript, chat message, document notification, or signed document event arrives.
2. Ingest and dedup Prevent duplicate events when several teammates receive the same thread or notification.
3. Fetch and clean Remove messy HTML, signatures, images, and noise so the content is usable.
4. Match work item Connect the event to a deal, case, project, candidate, job role, ticket, or other record.
5. Confidence gate High confidence writes automatically. Low confidence routes to a human for help.
6. Workflow match If the event advances a workflow state, the correct automation or agent can run.
Decision Point System Behavior Why It Matters
Low match confidence Escalate to a human to confirm the correct record. Prevents the source-of-truth system from being polluted by wrong updates.
High match confidence Update the existing source-of-truth record automatically. Keeps humans and future agents working from current context.
No existing match Create a new record when the business rules allow it, often with human review. Lets the system capture new work without silently dropping context.
Workflow match Run a workflow, deterministic automation, LLM step, or agent only after the context is matched. Ensures the agent is acting on the right case, deal, project, or task state.
Workflow State

Agents should run after the system knows what work item and workflow state the event belongs to.

A key insight is that the visible "agent" is only one part of the system. Around it sits a state machine that tracks scheduling, communications, pending states, back-and-forth messages, and confidence for whether the event should advance a workflow.

State machine

The workflow knows what it is waiting for

A response like "here are my available times" means something different depending on which case, stage, and communication workflow it belongs to.

Execution layer

The workflow can be many different things

It may be a deterministic automation, an LLM step, a two-step draft-and-review flow, or an agent with tools and instructions.

This distinction matters for platform design. The "agent" should not be the whole product object. The durable object is the event, the work item, the workflow state, the confidence gate, and the execution policy.

Audit Layer

Checklist monitoring tells you what to automate next.

Once records are being updated reliably, Devin adds a monitoring or audit workflow. Every case, deal, project, or work item usually has a checklist, pipeline, or SOP even if it lives in people's heads. Extracting that checklist lets the system monitor whether humans are doing the work, whether anything is falling through the cracks, and which steps are good candidates for automation.

Extract checklist Turn implicit SOPs into explicit steps for deals, projects, cases, or roles.
Audit current work Compare source-of-truth records against what should have happened by now.
Reveal bottlenecks Find missed emails, missing updates, inefficient handoffs, and repeated manual work.
Build targeted workflows Automate the specific checklist items that are measurable, repetitive, and well-contextualized.
  • It helps managers see work state. Leaders get better operational visibility without asking people for updates.
  • It helps operators forget fewer things. The system becomes a lightweight managerial layer around real work.
  • It clarifies the agent roadmap. The team can see what humans are doing to complete each checklist item before replacing pieces of that work.
  • It reduces brittle automation. Workflows are built after the data and process are visible, not from guesses.
Platform Takeaways

What this means for your BA-facing agentic AI platform

This video maps directly to your Master Agent, Sub-Agent, Skill, Tool MCP, and Flow Markdown problem. It suggests that the platform should start with event capture and operational state, not with persona prompts alone. BAs should be able to define source-of-truth systems, work items, matching rules, confidence gates, SOP checklists, and workflow triggers before composing agents.

  • Create an Event Source object. Meetings, email, and internal chat should each have connectors, normalization rules, deduplication rules, and privacy scopes.
  • Create a Work Item object. Deal, case, project, ticket, candidate, claim, or task should be the unit that events attach to.
  • Make Source of Truth explicit. Every flow should name where truth lives, such as CRM, case management, project management, ATS, or database.
  • Add confidence gates to Flow Markdown. Matching, record creation, workflow routing, and tool execution should each have thresholds and human escalation paths.
  • Separate sync workflows from action workflows. First keep records clean and contextualized; then run agents that act on that context.
  • Represent workflow state machines directly. The platform should track pending states, waiting-for states, incoming response states, and next-action states.
  • Turn SOPs into audit checklists. BA-authored SOPs should compile into monitoring rules before they compile into automation.
  • Use audits to prioritize agents. Build agents where checklists show frequent, measurable, repetitive work and where source context is reliable.
  • Allow multiple execution types. A step might be deterministic code, an LLM transformation, a human review, a tool call, or a full agent.
  • Design for human behavior change. When teams know conversations feed downstream work, the platform should encourage clearer notes, decisions, and next-step language.
