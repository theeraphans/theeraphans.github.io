OKF Turns Karpathy-Style LLM Wikis Into Portable Agent Knowledge

A detailed summary of Cole Medin's video on Google's Open Knowledge Format: why LLM wikis need a standard, how OKF structures markdown knowledge bundles, and why this matters for second brains, team knowledge, and agent memory platforms.

The Short Version

Cole's core point is simple: Karpathy's LLM wiki pattern is powerful because agents can build and maintain linked markdown knowledge bases, but every person structures those wikis differently. OKF adds a small, shared contract so one agent can understand another person's or team's knowledge bundle.

  • Karpathy-style LLM wikis turn raw sources into linked, persistent, agent-readable knowledge pages.
  • The fragmentation problem is metadata and structure: tags, categories, links, folders, and indexes differ across every wiki.
  • OKF standardizes the minimum needed surface: bundle structure, concept documents, frontmatter fields, index files, and markdown links.

Core Thesis

OKF is trying to make agent memory portable.

Cole opens with Andrej Karpathy's LLM wiki idea: instead of dumping documents into a RAG index, use an LLM to incrementally build a persistent wiki made of structured, interlinked markdown files. The agent reads new sources, extracts important knowledge, updates entity pages, links related concepts, and maintains a knowledge graph over time.

The problem is that this works well locally but breaks down socially. If everyone asks their coding agent to build an LLM wiki from the same gist, each wiki may still end up with different folders, metadata fields, link conventions, index files, and page types. An agent can probably figure it out eventually, but it loses the efficiency and reliability that made the wiki valuable in the first place.

The real value of OKF is not that it invents a new knowledge system. It gives agents a shared reading and writing contract for simple knowledge bundles.
Why a Standard Matters

Without a standard, every LLM wiki becomes a private dialect.

Cole's main practical complaint is interoperability. A personal second brain is more useful when it can share knowledge with team members, other agents, and other tools. But if each wiki uses a different metadata vocabulary, the receiving agent does not know how to search it optimally.

Even tiny differences matter. One wiki might use `tags`; another might use `categories`. One might link related concepts at the bottom of each page; another might store relationships in frontmatter. One might have a top-level index only; another might use index files in every folder. These small differences compound when an agent needs to traverse knowledge quickly.

Problem What happens without OKF Why agents suffer
Different metadata Fields like tags, category, type, title, and resource vary by author. The agent must inspect conventions before it can search or filter confidently.
Different folder shapes Pages, concepts, transcripts, logs, and indexes are organized differently. The agent has to rediscover the bundle map instead of using a known traversal pattern.
Different link rules Relationships may be markdown links, lists, IDs, headings, or ad hoc text. The knowledge graph is harder to follow and easier to miss.
No producer/consumer contract One agent can write knowledge that another agent does not know how to consume. Shared memory becomes brittle, bespoke, and expensive to integrate.
Karpathy Wiki Anatomy

A basic LLM wiki already has progressive disclosure and graph traversal.

Cole shows one of his earlier Karpathy-style wikis. At the top is an index file. The agent reads that first to see what documents exist and which pages might be relevant. The index acts like a map, giving short summaries so the agent can decide whether to drill deeper.

Each page can then include metadata, a title, tags, the main content, and links to related concepts. This creates a knowledge graph that agents can traverse. The important design pattern is progressive disclosure: show the agent the high-level map first, then let it open full pages only when the task calls for them.

Start Read index

The agent loads the top-level map and summaries.

Filter Use metadata

Type, title, tags, and resource fields narrow the search space.

Drill Open concept page

The agent reads a specific file when the index says it is relevant.

Traverse Follow links

Related concepts connect pages into a navigable graph.

Update Maintain wiki

New sources can revise pages, links, and indexes over time.

What OKF Does

OKF standardizes organization and frontmatter, not the whole knowledge model.

Cole says OKF standardizes two main things: how information is organized and what metadata fields appear at the top of documents. The official Google Cloud post describes OKF v0.1 as a directory of markdown files with YAML frontmatter and a small set of conventions so different producers and consumers can interoperate.

The official spec is intentionally minimal. A bundle is a directory tree of markdown concept documents. A concept is one unit of knowledge. Frontmatter gives agents a structured entry point. Markdown links express relationships beyond parent-child folders. Optional `index.md` files support progressive disclosure, and optional `log.md` files can track update history.

Bundle

Unit of distribution

A self-contained directory of knowledge documents that can be shared as a repo, archive, or subdirectory.

Concept

One knowledge unit

A single markdown file that can describe a table, API, process, metric, video, idea, or any other useful entity.

Frontmatter

Structured agent hints

YAML metadata lets agents filter, route, search, cite, and understand the page before reading everything.

Spec as Skill

The OKF spec can be used like an instruction file for your coding agent.

Cole emphasizes the practicality of the `SPEC.md` file. Like Karpathy's gist, the OKF spec can be copied into a coding agent and used as a skill. You can ask the agent to build a new OKF wiki or refactor an existing wiki into the format.

The reason this works is that the standard is small. The agent only needs to understand bundle structure, terminology, frontmatter, required and optional fields, links, indexes, and logs. For a large existing second brain, Cole suggests using sub-agents to refactor different sections in parallel.

  • For new wikis: give the agent the OKF spec, a memory brief, and the raw sources to transform into concept pages.
  • For existing wikis: ask the agent to map old metadata and folder conventions into OKF bundle structure.
  • For large wikis: split folders across sub-agents, then run a final validator to check frontmatter, links, and indexes.
  • For teams: keep the spec and bundle conventions in version control so producers and consumers share the same contract.
Example Bundle

Cole's AI coding bundle shows why portable knowledge matters.

Cole then demonstrates his own OKF bundle for selected AI coding videos. The idea is that a creator can package transcripts, concepts, and relationships into a bundle that viewers can import into their own second brain.

This is more valuable than sharing raw transcripts. The bundle can contain video pages, concept pages, indexes, and links between repeated ideas such as context engineering, sub-agents, or the PIV loop. The consumer's agent can ask questions against the bundle and use the standardized structure to find the right concept without being told exactly where to look.

Creator value

Package knowledge, not just content

Creators can turn videos, articles, talks, and templates into a portable agent-readable knowledge product.

Consumer value

Ask questions over curated memory

Users can mount the bundle in Obsidian, Notion, a repo, or a local agent workspace and query it directly.

Agent Navigation

The demo shows OKF working through layered indexes and concept IDs.

Cole adds a small CLI on top of his bundles. It lets the agent list bundles, view an index, and read a file by bundle and concept ID. This is not required by OKF, but it shows the useful separation between the storage format and the agent-facing retrieval tools.

In the demo, he asks his agent what bundles are available, then asks a question about his biggest idea for reliable AI coding. The agent reads the AI coding bundle index, identifies relevant concepts, drills into the concept page, and answers from the curated knowledge. That is the progressive disclosure pattern in action.

Layer What the agent sees Why it matters
Bundle index A list of available knowledge bundles and their purposes. The agent can choose the right knowledge source before reading details.
Folder index Sections such as videos, concepts, metrics, tables, or runbooks. The agent can traverse a large corpus without loading everything.
Concept page Frontmatter, structured markdown, references, and links. The agent gets the actual curated knowledge with enough metadata to cite and connect it.
Retrieval tool CLI, MCP server, file search, or app-specific consumer. The format stays portable while each runtime can expose the best interface.
Critique

The best criticism of OKF is also its design strength: it is very small.

Cole acknowledges a valid critique: OKF does not add a huge amount on top of a Karpathy wiki. It mainly standardizes organization and metadata. The required field is minimal, and many fields are optional.

His response is that minimalism is the point. A knowledge standard should avoid becoming a platform, schema registry, SDK, or cloud dependency. It should define just enough so agents can produce and consume bundles consistently. Google Cloud's own post frames OKF the same way: format, not platform.

Risk

Too little structure

Teams may still invent incompatible type systems, body templates, and quality rules on top of OKF.

Benefit

Easy adoption

Because OKF is simple markdown and YAML, agents, tools, creators, and teams can adopt it without a new runtime.

Platform Takeaways

What this means for your agentic AI platform.

This video pairs well with the LangChain LLM Wikis panel. That panel argued that wikis are agent memory infrastructure. This video adds a concrete portability layer: OKF can be the exchange format for memory bundles across agents, teams, and tools.

  • Use OKF as the memory artifact format. Store BA-authored and agent-generated knowledge as bundles, concepts, frontmatter, indexes, and logs.
  • Keep memory separate from persona prompts. Persona defines behavior. OKF bundles define inspectable domain knowledge that agents can read and update.
  • Let BAs define bundle types. A business flow can create bundles for SOPs, customer journeys, product knowledge, compliance rules, and operational runbooks.
  • Expose OKF through MCP tools. Agents should list bundles, search frontmatter, read concepts, write proposed updates, validate links, and open review requests.
  • Add a validator agent. Check required `type`, broken links, missing indexes, stale logs, duplicate concepts, access rules, and source citations.
  • Use bundles as reusable skills context. A skill can declare which OKF bundle it needs before running, making domain context composable.
  • Track producer and consumer metrics. Measure bundle creation cost, retrieval success, token savings, stale-entry corrections, and answer quality.
Flow Markdown

A practical OKF bundle spec for platform builders.

This template turns the video into a reusable platform artifact. It defines how a BA, Knowledge Agent, and runtime can produce and consume an OKF bundle for a business domain. 

# OKF Knowledge Bundle Flow

goal: Produce a portable, agent-readable knowledge bundle for one business domain.
owner: Knowledge Domain Owner
runtime_owner: Agent Platform Team
format: Open Knowledge Format v0.1
flow_type: okf_bundle_production

bundle:
  id: claims-processing-knowledge
  description: Shared agent knowledge for claims intake, evidence review, coverage checks, fraud signals, and escalation rules.
  distribution:
    - git_repository
    - zip_archive
    - mcp_read_interface
  required_files:
    - index.md
  optional_files:
    - log.md

concept_types:
  - sop
  - policy
  - workflow
  - role
  - tool
  - metric
  - exception
  - customer_case_pattern

frontmatter_contract:
  required:
    - type
  recommended:
    - title
    - description
    - resource
    - tags
    - timestamp
    - owner
    - confidence
    - source_system
    - access_level

producer_agent:
  role: knowledge_librarian
  inputs:
    - existing_sop_docs
    - workshop_notes
    - tickets
    - policy_documents
    - data_dictionary
  responsibilities:
    - create_concept_pages
    - write_frontmatter
    - maintain_index_files
    - create_markdown_links
    - cite_sources
    - append_log_updates

consumer_agent:
  role: domain_task_agent
  tools:
    - list_okf_bundles
    - read_okf_index
    - search_okf_frontmatter
    - read_okf_concept
    - follow_okf_links
  retrieval_policy:
    - read_bundle_index_first
    - prefer_concept_pages_over_raw_sources
    - follow_links_when_context_is_incomplete
    - cite_concept_ids_in_final_answer

mcp_tools:
  - okf.list_bundles
  - okf.read_index
  - okf.search
  - okf.read_concept
  - okf.validate_bundle
  - okf.propose_update
  - okf.open_review

validation:
  checks:
    - every_concept_has_type
    - markdown_links_resolve
    - index_files_match_children
    - restricted_concepts_have_access_level
    - concepts_have_source_or_owner
    - log_updated_for_material_changes
  human_review_required_for:
    - policy_changes
    - compliance_content
    - customer_sensitive_content
    - high_confidence_claims_without_sources

metrics:
  - bundle_reuse_count
  - retrieval_success_rate
  - broken_link_count
  - stale_concept_count
  - token_savings_per_task
  - human_review_acceptance_rate
  - answer_quality_with_bundle_vs_without_bundle
