Building an Agentic Analytics Harness

A blog-style summary of Chris Merrick's session on Omni's Blobby analytics agent: how a semantic layer gives Claude business context, why the architecture moved away from split-brain sub-agents, and how error recovery, SQL, observability, and evals make the harness production-worthy.

The Short Version

Omni's lesson is that an analytics agent cannot be a generic chat wrapper over a database. It needs a domain harness: curated data access, business definitions near the data, tool design that matches model strengths, recovery paths when queries fail, raw traces for debugging, and evals that turn confusing failures into fixable engineering work.

  • Put business context near data definitions, not only in one giant global prompt.
  • Avoid split-brain designs where one agent knows the plan and another isolated agent owns execution.
  • Use evals and traces as an improvement system, not just a scoreboard.

The Problem

Business analytics agents fail when they do not understand the business.

A user can ask a simple-looking question such as "how were online sales last quarter?" but every word hides business-specific ambiguity. Which business unit is "our"? Does "online" include mobile app purchases or buy-online-pickup-in-store orders? Does "sales" include returns, cancellations, discounts, or only booked revenue? Does "last quarter" mean calendar quarter or fiscal quarter?

Data sprawl

Warehouses contain too many possible tables

An agent needs curation so it chooses the trusted business model instead of grabbing a misleading table with a familiar name.

Business terms

Natural language is not self-defining

The platform needs definitions for fiscal periods, regions, sales concepts, ownership, permissions, and field usage.

Executive trust

Analytics has a low tolerance for plausible wrongness

The output must be explainable and recoverable because users make business decisions from the answer.

The key product lesson: analytics agents are domain-specific systems. The real product is not only the model call. It is the harness that binds the model to trusted definitions, tools, permissions, and observability.

Semantic Layer

Omni uses the semantic layer as the agent's business memory.

The semantic layer is described as more than a translation layer from natural language to SQL. It curates which data matters, supplies business context, enforces permissions, and creates a feedback surface for improving how the agent understands company-specific data.

Function What It Does Agent Design Lesson
Curation Guides the agent toward approved tables, metrics, and topics instead of every raw warehouse object. BA builders need a "use this, ignore that" layer for data and tools.
Context Stores field definitions, business terms, example usage, and model-facing guidance close to the data. Context should be local to the object it explains, not only buried in a global persona prompt.
Permissions Prevents users and agents from seeing data they are not allowed to access. Tool permissioning belongs in the harness, not in model goodwill.
Feedback loop Lets definitions and behavior improve as real user questions expose gaps. The platform should treat failures as updates to context, rules, evals, or tools.

Blobby

Blobby evolved from Q&A into an agentic analytics worker.

Omni's agent, Blobby, started as a simple question-answering experience and matured over roughly 18 months into an agentic system that can plan, select data, generate queries, recover from errors, create visualizations, and summarize the result.

User question A user asks a business question in natural language, often with domain-specific ambiguity.
Semantic grounding The harness maps the question to topics, fields, definitions, values, and permissions.
Query and validation The agent generates SQL, executes tools, checks results, and retries with useful error context.
Workbook output The product returns charts, summaries, and UI artifacts that users can inspect and refine.

Architecture

The strongest design move was consolidating the agent brain.

One early architecture separated an outer planning agent from a query-generation sub-agent. That sounded modular, but it created a "split brain": the planner knew what data was relevant, while the executor knew what one query could actually retrieve. The mismatch caused back-and-forth failures.

Initial Q&A Answer simple questions with labels and descriptions in the semantic layer.
Agentic loop Add task planning, retry budgets, tool execution, checkpoints, and error recovery.
Split-brain issue Outer planning and inner query generation did not share enough operational context.
Brain consolidation Move query, dashboard, validation, visualization, and modeling tools into one harness.
Two-loop system Use an outer durable loop and inner parallel tool loop with observability across spans.

This does not mean sub-agents are bad. It means sub-agents are dangerous when they separate planning knowledge from execution knowledge. If the task requires tight reasoning over data availability, query feasibility, and presentation, a unified harness can be more reliable than role decomposition.

SQL Shift

Omni leaned into what Claude already knows: SQL and CTEs.

Another major design decision was moving away from a proprietary JSON query format toward SQL generation. The reason is strategic: Claude already has broad training-time familiarity with SQL, especially common table expressions. A custom JSON query language requires prompt budget and repeated instruction, while SQL lets the model use a format it already handles well.

Before After Why It Matters
Custom JSON query format SQL generation with parsing Lower prompt overhead and better fit with model priors.
Multiple chained attempts More one-pass query construction Reduces retry loops, latency, and unpredictable intermediate states.
Model must learn Omni's format Harness adapts to model strengths Good harness engineering designs tools around what the model is naturally good at.

Good agent tooling is not just exposing tools. It is shaping the tool interface so the model can use it reliably.

Evals and Observability

Omni treats evals as a debugging system for product quality.

The talk's eval lesson is especially relevant for production agents. Omni uses benchmark questions, LLM-as-judge style assessment, daily review of real sessions, and raw traces of tool spans so failures can be diagnosed instead of dismissed as "LLM unpredictability."

Benchmarks

Run regular quality checks

Use curated questions that cover realistic, difficult, and semantically ambiguous analytics scenarios.

Trace review

Inspect the raw path

Read tool inputs, outputs, errors, retries, and validation signals to find the actual failure point.

Daily triage

Turn user sessions into fixes

Use real failed sessions to improve semantic definitions, prompts, tools, and eval questions.

  • Evaluate answer quality. Does the final output answer the user's business question?
  • Evaluate data choice. Did the agent pick the correct table, topic, field, and filter?
  • Evaluate ambiguity handling. Did it resolve or ask about fiscal periods, region terms, and metric definitions?
  • Evaluate tool behavior. Did the loop recover from errors with bounded retries and clear state?
  • Evaluate UI validation. Can users inspect, troubleshoot, and refine the generated workbook?
Platform Takeaways

What this means for your Master Agent, Sub-Agent, Skill, and MCP platform

This video is a very strong case study for your BA-facing agentic platform. It shows that high-performing agents need domain-specific harnesses, not generic persona prompts. The builder should guide BAs to define business semantics, tool boundaries, validation criteria, and feedback loops in the same place where they define business flow.

  • Create a semantic layer object. Let BAs define terms, metrics, examples, allowed values, data owners, and permission rules close to the data or tool they affect.
  • Make context local and inspectable. Context should attach to fields, APIs, documents, SOP steps, and business policies instead of living only in one master prompt.
  • Prefer unified brains for tightly coupled work. If planning and execution require the same context, expose tools directly to one agent rather than splitting into sub-agents too early.
  • Use sub-agents for bounded probes. Sub-agents are still useful when they explore, validate, or review a slice and return compact evidence.
  • Design tool interfaces around model strengths. If the model is already strong in SQL, Markdown, JSON Schema, or a domain DSL, use that advantage instead of inventing unnecessary formats.
  • Invest in recoverable errors. Every MCP tool should return errors that explain what happened, what can be retried, and what information is missing.
  • Build traces into every span. Log inputs, outputs, retries, costs, latency, permission checks, and eval scores at both root-flow and sub-step level.
  • Use evals to improve the harness. Failed sessions should update semantic definitions, benchmark questions, tool contracts, or BA review rules.
Flow Markdown

A BA-friendly Flow Markdown spec should include semantic context and evals.

For your platform, the practical artifact is a reusable flow template. It should make BAs declare the meaning of business terms, not just the sequence of tasks. 

# Agent Flow: Agentic Analytics Request

goal: Answer a business analytics question with trusted data, explainable logic, and a reviewable workbook.
owner: Analytics Master Agent
domain: revenue_analytics
loop_type: durable_agentic_harness

semantic_context:
  terms:
    - name: online_sales
      definition: Includes web and mobile app orders, excludes store pickup unless specified.
    - name: last_quarter
      definition: Use fiscal quarter for Sales users, calendar quarter for Product users.
  fields:
    - name: revenue
      ai_context: Net revenue after returns and discounts.
      allowed_values: [gross, net, booked]
    - name: region
      allowed_values: [NAM, EMEA, APAC]

permissions:
  enforce_row_level_security: true
  restricted_metrics:
    - executive_compensation
    - unreleased_forecast

agent_harness:
  outer_loop:
    max_iterations: 50
    checkpoint_each_step: true
  inner_loop:
    allow_parallel_tools: true
    tools:
      - semantic_model_lookup
      - sql_generator
      - sql_executor
      - visualization_builder
      - workbook_validator

error_recovery:
  on_sql_error: return_fixable_error_context
  on_ambiguous_term: ask_clarifying_question_or_use_role_default
  on_permission_denied: explain_safe_alternative

evals:
  benchmark_questions:
    - covers_ambiguous_time_periods
    - covers_metric_definition_conflicts
    - covers_multi_table_questions
  scoring:
    - answer_correctness
    - data_source_choice
    - ambiguity_resolution
    - visualization_usefulness
    - trace_completeness

human_review:
  required_when:
    - low_confidence
    - executive_metric
    - new_semantic_definition_needed
