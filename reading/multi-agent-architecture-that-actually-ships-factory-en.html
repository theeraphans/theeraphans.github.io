The Short Version

Factory's claim is that the bottleneck in software engineering is now human attention. Models can attempt many tasks, but humans cannot supervise all of them at once. Missions is Factory's answer: a multi-agent workflow where a human scopes the goal, approves the plan, and then an ecosystem of agents executes, validates, writes handoffs, corrects failures, and reports progress over hours or days.

  • Missions combine delegation, creator-verifier, broadcast, and negotiation into one production workflow.
  • The validation contract is written before coding, so correctness is defined independently from implementation.
  • Factory favors serial feature execution with targeted internal parallelism because correctness compounds over multi-day runs.

Attention Bottleneck

The talk starts from a product thesis: humans can choose goals, but agents should carry execution

Luke's opening claim is that software engineering is no longer limited only by model intelligence. The hard limit is human attention. A strong engineer may have a backlog of 50 useful tasks, but can only drive a few forward per day. The question is: what if the human decides what to build and a system figures out how to do it?

Human Role

Scope the goal, make strategic decisions, approve the plan, and inspect outcomes when the system needs judgment.

Agent Role

Break work into features, implement, validate, write handoffs, catch problems, and keep moving across milestones.

System Role

Maintain shared state, enforce validation, preserve context, block progress on unresolved issues, and expose mission status.

Taxonomy

Factory frames multi-agent systems as five reusable communication patterns

The speaker says the multi-agent field has too much inconsistent terminology, so he proposes a simple taxonomy. These patterns are the building blocks, but the talk's key move is that Missions compose several of them into a durable workflow.

Pattern What it means Risk or value
Delegation One agent spawns another agent to perform focused work and return a result. Simple and common, especially for coding sub-agents.
Creator-verifier One agent builds; another fresh agent checks the work. Separates implementation bias from review, similar to human code review.
Direct communication Agents communicate without a central coordinator. Flexible but can fragment state because there is no single source of truth.
Negotiation Agents coordinate over shared resources such as APIs, code areas, or plan scope. Best when there is a positive-sum trade, not only adversarial conflict.
Broadcast One agent sends updates, constraints, or shared context to many agents. Less flashy, but critical for coherence in long-running tasks.

Validation Contract

The validation contract is the part that keeps a multi-day agent run honest

The speaker warns that tests written after implementation often confirm the agent's decisions instead of checking the real goal. Missions avoid this by writing a validation contract during planning, before coding. The contract defines what "done" means independently of the implementation.

ScopeUser and orchestrator clarify the intended outcome.
ContractThe orchestrator writes correctness assertions before work starts.
AssignEach feature receives one or more assertions it must satisfy.
ValidateScrutiny and user testing validators check the milestone.
RepairFailures create follow-up features or rescoping work.
  • Correctness comes before code. The contract prevents implementation-shaped tests from becoming the definition of success.
  • Behavior matters. Missions do not stop at lint, typecheck, tests, or review; user testing validators interact with the live app.
  • Validation is adversarial. A fresh validator with separate context is more likely to catch mistakes than the agent that wrote the code.
Structured Handoffs

Long-running agent systems do not trust memory; they force agents to write state down

When a worker finishes, it does not simply say "done." It fills out a structured handoff. This handoff explains what was completed, what was left undone, what commands ran, what the exit codes were, which issues appeared, and whether the worker followed the procedures defined by the orchestrator.

The system self-heals by catching issues at milestone boundaries, scoping corrective work, and pulling the mission back on track.

Execution Strategy

Factory chooses serial execution with targeted internal parallelism

The obvious answer is to run many agents in parallel, but Factory found that broad parallelism creates conflicts: agents step on each other's changes, duplicate work, and make inconsistent architectural decisions. Missions run features serially, while parallelizing read-only work such as search, research, and code review.

Choice Why it matters Tradeoff
One active worker or validator Reduces conflicts, duplicate work, and inconsistent architecture. Looks slower on paper, but has lower error compounding.
Parallel read-only operations Search, API research, and code review can fan out safely. Requires clear boundaries between read-only and mutating work.
Mission Control UI Shows active worker, progress, budget burn, handoff summaries, and validator findings. Long-running agents need a project-management surface, not only chat.
Model Routing

The right model belongs in the right seat

The talk calls this skill "droid whispering": mentally modeling how different LLMs behave, where they fail, and how those failures compound over a multi-day run. Planning, implementation, and validation benefit from different model traits, so a model-agnostic architecture becomes an advantage.

Planning

Slow careful reasoning

The orchestrator benefits from strategic questioning, ambiguity handling, and plan decomposition.

Implementation

Fast code fluency

Workers need strong coding ability, creativity, and speed inside focused feature scopes.

Validation

Precise instruction following

Validators may even use a different provider to reduce shared blind spots from the implementation model.

  • Model diversity reduces weak links. Locking into one provider means the system inherits that provider's weakest capability.
  • Structure can compensate for weaker models. Validation contracts and milestone checkpoints can make open-weight models more usable.
  • The architecture should improve with model releases. Factory keeps most orchestration logic in prompts and skills rather than a hard-coded state machine.
Platform Takeaways

What this means for your agentic AI platform

This is one of the most directly useful videos for a BA-facing Master Agent, Sub-Agent, Skill, Tool MCP, and Flow Markdown platform. The main lesson is that multi-agent architecture needs contracts, handoffs, validators, model routing, and a mission dashboard, not just many agents talking.

  • Make "Mission" a platform object. A mission should have goal, scope, owner, plan, milestones, validation contract, budget, agents, state, and final report.
  • Compile Flow Markdown into contracts. BA-authored flows should produce acceptance assertions before any agent starts implementation.
  • Separate builder and verifier personas. Creator-verifier should be a default architecture for risky work, not an optional prompt trick.
  • Use structured handoffs between every agent step. Handoffs should capture completed work, evidence, commands, failures, open questions, and next state.
  • Add milestone gates. Progress should pause when validator findings, handoff issues, or unaddressed contract failures exist.
  • Make user testing a first-class validator. For software workflows, the platform should test behavior through browser or computer use, not only code inspection.
  • Prefer controlled serial mutation. Let agents parallelize research and review, but serialize code-changing work unless conflict management is explicit.
  • Route models by role. BAs can choose autonomy level, while engineers configure planner, worker, validator, and reviewer model defaults.
  • Expose mission control. Users need progress, budget burn, current agent activity, handoff summaries, validator findings, and follow-up features in one dashboard.
  • Keep orchestration prompt-native where possible. Thin deterministic infrastructure plus prompts, skills, and agent-readable docs lets the system improve as models improve.
