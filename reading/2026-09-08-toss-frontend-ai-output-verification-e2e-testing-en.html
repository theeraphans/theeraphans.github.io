How Toss Makes AI-Generated Frontend Work Trustworthy

AI multiplied frontend output. Toss discovered that trust, not generation, had become the bottleneck, then built a real-device verification loop that people can teach and agents can repair.

Toss Challengers 19m 10s Published September 7, 2026 Summary run September 8, 2026 · 21:18 ICT

YouTube provided no public captions for this Korean talk. The full audio was transcribed locally, reviewed chronologically, translated into English, and reorganized as an editorial article. Names and a few internal tool terms may contain speech-recognition uncertainty.

Executive summary

Generation got cheaper; confidence got more expensive

Toss's two-person Front AI team helps frontend engineers adopt AI throughout product development. The company was producing at least four times as much output, according to the speaker, but engineers were spending more time understanding code they had not written and deciding whether an agent's work could be trusted.

The team's answer is not another coding prompt. It is a verification environment centered on real-device end-to-end tests. A person demonstrates the intended user journey, an agent observes both natural-language instructions and manual actions, then generates a durable test using Toss's internal device and setup tools. When that test later fails, a replay package gives the agent enough evidence to diagnose whether the product changed and repair the test.

ProductivityAt least 4x more output

AI participates in planning, implementation, review, and deployment.

BottleneckTime to trust rises

Unfamiliar generated code still needs understanding and behavioral proof.

ResponseVerification becomes infrastructure

Real devices, test APIs, logs, replay, and agents form one closed loop.

The core lesson

Reliable AI engineering is not achieved by asking the model to be more careful. It comes from making intent observable, environments controllable, failures reproducible, and corrective action available through tools.

The problem · 01:22

AI accelerated almost every stage except verification

The speaker maps a familiar frontend workflow: discuss specifications, analyze designs, plan, build logic and UI, self-check, deploy to an alpha environment, run QA or acceptance testing, release, and respond to bugs or customer feedback. AI can assist in nearly every stage. It can draft requirements, apply designs, generate code, review changes, and support deployment.

Verification remained stubbornly manual. Teams with dedicated QA relied on testers; teams without it gathered people from the product silo and compared whether each flow worked. This was not evidence that E2E testing was unnecessary. Interviews revealed the opposite: teams wanted it, but the cost of building and maintaining it had been too high.

This creates a structural mismatch. If generation speed grows fourfold while the final confidence check remains human and sequential, verification becomes the system constraint. More output simply produces a longer queue of things nobody yet trusts.

First attempt · 03:54

The codebase contained everything except what mattered most

The team's first design treated the codebase as the source of truth. An agent would infer screen flows, derive test scenarios, and generate E2E tests automatically. The premise sounded reasonable: the implementation contains the product, business rules, and accumulated decisions.

It failed because the code contained too much information without revealing priority. The intent that determines a valuable test often lives in the heads of product managers, designers, developers, and QA staff. Code can show that several branches exist; it cannot reliably tell an agent which promise to the customer is critical, which transition carries financial risk, or which failure the team most fears.

Code-first assumptionWhat the team learned
The implementation is the complete specification.Implementation records possibility, not necessarily business importance or testing intent.
An agent can infer the right user journey.People must identify the journey whose failure would matter.
Automatic generation removes the hard work.The hard work is creating a deterministic environment and useful tools.
More context will solve ambiguity.Direct observation and demonstration can communicate intent more precisely than a larger context dump.

The team returned to its actual customers, Toss service developers, and worked inside teams with urgent verification needs. Face payment and Toss Shopping are cited as examples: areas where a single mistake can have enough impact that a maintained E2E test becomes a valuable asset.

Design principles · 06:03

Test the visible product, remove randomness, use AI for cost

Surface fidelityExercise what the user actually experiences.

The tests interact with the real app and external surfaces instead of proving only mocked internals.

DeterminismThe same run should produce the same answer.

Unstable dependencies, delayed indexing, authentication state, and test data must be controlled.

AI leverageReduce creation and maintenance cost.

Agents generate tests, operate devices, inspect evidence, and update broken selectors or steps.

Compounding valueTreat tests as durable product assets.

A growing suite creates an AI-friendly environment and preserves confidence as delivery accelerates.

The phrase “unbreakable E2E” does not mean tests never fail. It means failures are evidence-rich and repairable, so a test does not become abandoned legacy code after the first product change.

Building the environment · 07:40

The expensive part was making the business testable

The team first wrote tests itself, learning the workflow from practitioners rather than attempting instant platform automation. This exposed missing foundations across authentication, native-app behavior, admin operations, test accounts, and domain data.

A shopping test, for example, might create a product in an admin system but fail because the new item is not searchable before the test ends. An AI model cannot prompt its way around eventual consistency. The platform needs APIs or controls that create the required state, wait for readiness, and clean up afterward.

Toss's internal device-farm team became a key partner. The Front AI team contributed requirements, created setup and control utilities, and exposed device operations so agents could use them. They also connected internal logs through MCP-like tooling. During one broad QA migration, they pulled the actions associated with QA users from the Elastic/Kibana logging system and experimented with generating code from those observed journeys.

Human-agent workflow · 10:49

A developer teaches the journey by doing it

To create a test, a developer can describe the goal in natural language and ask the agent to prepare a device with a fresh authenticated user. The agent navigates the app while streaming its actions and logs. The person can then correct it verbally or click an element directly. Those manual actions are observed as part of the same trajectory.

Once the desired outcome is reached, such as returning from an external browser and receiving points, the developer asks the agent to turn everything demonstrated so far into E2E code. The agent combines the observed path with the team's purpose-built device and environment tools.

01State the outcome
02Agent prepares device
03Agent explores
04Human redirects or clicks
05Confirm success
06Generate durable test

This is more practical than demanding one-shot autonomy. The human contributes intent and judgment at the moment ambiguity appears; the agent contributes patient execution, trace collection, and code generation. The workflow was not magically smooth on day one. The team repeatedly added tools until common obstacles became routine agent actions.

Failure loop · 12:26

Replay turns a broken test into a solvable incident

Generated tests face the same maintenance problem as human-written tests. When ownership is unclear and a failure is hard to reproduce, teams skip the test, delete it, or let it decay. Toss therefore records a replay artifact whenever an E2E test fails locally or in CI.

The replay combines the real device recording, screen state, the element the test tried to find, and structured logs from every device-farm API call. In the example, the test searched for a button labeled “Go do the mission,” but the product had changed it to “Go take a look.” The video and UI evidence made the cause visible.

Giving that package to an agent allowed it to infer that the primary call to action had changed while the intended next action remained the same, then update the test. The replay tool was initially built for humans investigating CI failures. Its structured evidence also made the agent far more capable.

A reusable pattern

Design observability for the person who must debug the system. When the evidence is structured, complete, and easy to retrieve, it often becomes exactly the context an agent needs as well.

Agent engineering lesson · 15:08

Tools multiply capability more than another context dump

The speakers describe a recurring realization: instead of only supplying more context, build tools that are genuinely useful to people and expose those tools to the agent. Device control, deterministic account setup, searchable operational logs, screen dumps, and replay artifacts let the model act on the environment and verify what happened.

This changes the role of the agent from text generator to participant in an operational loop. The model does not need to contain Toss's entire world in its prompt. It needs clear objectives, bounded interfaces, observable results, and evidence when reality differs from expectation.

For teams designing agent platforms, this suggests a useful division:

  1. Cognitive skill: interpret the user's intended journey, compare expected and observed behavior, and choose a repair.
  2. Action skill: provision a user, manipulate a device, query logs, save replay artifacts, modify test code, and rerun the test.
  3. Verification contract: declare the expected visible outcome and collect evidence that proves or disproves it.
  4. Recovery contract: distinguish a product regression, test drift, unstable environment, and missing prerequisite before changing anything.

Product discipline · 15:42

Do not fall in love with the platform

The team is candid about a common platform-engineering risk: once developers build powerful tools, they can become absorbed in the technology and lose contact with user value. Cheaper code does not make an unwanted product useful.

Different teams had different constraints, so the goal shifted away from a universal tool that weakly covers everyone. A better starting point was a narrow system that fully solves the problem for a few teams with strong needs. Continuous work alongside those users prevents the platform and real workflows from drifting apart.

The approach also depended on Toss's organizational infrastructure. Internal logging was treated as a product, a device-farm group already existed, framework teams were available, and colleagues challenged requests that lacked a clear reason. The two-person Front AI team could assemble these capabilities because many other teams owned strong pieces of the environment.

Critical assessment

What is strong, and what remains unresolved

StrongThe bottleneck diagnosis is convincing.

As generation accelerates, behavioral verification and comprehension naturally become limiting work.

StrongHuman demonstration is an efficient intent interface.

It resolves ambiguity at the exact point where static code and written requirements are incomplete.

StrongReplay creates grounded repair.

Video, UI state, target elements, and logs give the agent evidence instead of inviting speculative fixes.

Trade-offReal-device fidelity costs time and infrastructure.

The speakers acknowledge that some tests take longer than their value may justify; the next step is reducing execution time without losing trust.

ConstraintThe system relies on organizational maturity.

Teams without device farms, productized logging, controllable test data, and cross-team support will need to build those foundations first.

Open questionSelf-repair needs policy boundaries.

An agent should not silently rewrite assertions when the product is actually broken. Repair requires classification, review rules, and preserved evidence.

My conclusion

Toss's most transferable idea is not its specific E2E stack. It is the sequence: begin with a costly business workflow, observe people performing it, expose the missing controls, make failure legible, and only then automate. The agent becomes reliable because the surrounding system was redesigned for verifiability.

Takeaways

Ten ideas worth keeping

  1. When AI multiplies output, verification can become the dominant delivery cost.
  2. A codebase describes implementation more clearly than it describes business intent.
  3. Start with teams for whom one failure is expensive enough to justify durable E2E coverage.
  4. Realistic tests require deterministic accounts, data, dependencies, and environment controls.
  5. Human demonstration can communicate the critical path better than one-shot autonomous inference.
  6. Let people intervene during agent execution and preserve those interventions as training context for the task.
  7. A replay should combine video, screen state, target elements, actions, and backend logs.
  8. Build debugging tools for humans first; their evidence often becomes excellent agent context.
  9. Self-repair must distinguish test drift from a genuine product regression.
  10. The real agent product is the environment, tools, evidence, and feedback loop surrounding the model.
