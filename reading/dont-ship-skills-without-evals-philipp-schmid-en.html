AI Engineer x Google DeepMind summary

Don't Ship Skills Without Evals

Philipp Schmid argues that agent skills should be treated like production code. A skill can improve performance, waste tokens, over-trigger, under-trigger, or become obsolete as models improve. Without evals, you cannot know which one happened.

Source: AI Engineer Speaker: Philipp Schmid, Google DeepMind Length: 21 minutes Transcript: 4.0k words

Executive Summary

The talk's core idea is that skills are not harmless prompt snippets. They are behavior-changing runtime assets. They affect triggering, context cost, task quality, model portability, and customer experience. Therefore, every serious skill needs a small eval suite, ablation tests, regression gates, and a retirement plan.

  • Distinguish agents you use from agents you build. Customer-facing agents cannot rely on users knowing skill names.
  • Skill descriptions are the critical trigger surface: weak descriptions cause over-triggering, under-triggering, or silent non-use.
  • Capability skills are temporary; preference skills are more durable. Evals tell you which type you are dealing with.
  • Start with 10 to 20 eval prompts: happy paths, negative cases, and production traces when available.
  • Always run ablations: with the skill loaded and without the skill loaded. That is how you know whether it helps.

1. The Central Thesis

Philipp opens with a quick poll: many people use coding agents, many use skills, but far fewer have evals for those skills. That gap is dangerous because agent behavior is non-deterministic. When a task fails, you may not know whether the model was too weak, the skill was bad, the skill never triggered, or the skill made things worse.

This is especially important when moving from internal coding assistants to customer-facing agents. A developer using Claude Code, Cursor, Gemini CLI, or Antigravity can notice when a skill is missing and reprompt. A customer using your app does not know that a refund skill, support skill, or policy skill exists.

My read: this talk turns "skills" from a prompt convenience into a production quality problem. If a skill can change behavior, it deserves tests.

2. What a Skill Is

A skill is a lightweight package of procedural context. In many ecosystems it looks like a folder with a skill manifest or SKILL.md file plus optional assets, examples, scripts, docs, or reference files. The important mechanism is progressive disclosure.

  1. 1 Name Human and system-readable identity for the skill.
  2. 2 Description Always-visible trigger surface that tells the model when to use it.
  3. 3 Body More detailed instructions, constraints, examples, and output expectations.
  4. 4 References Deep docs, cloud-specific instructions, examples, scripts, or schemas.
  5. 5 Evals Prompt cases, expected outcomes, trigger checks, and regression gates.

Platform implication: your BA-facing platform should treat a skill as a versioned artifact with metadata, trigger policy, references, tool permissions, and evals. Do not store it as only a blob of prompt text.

3. Capability Skills vs Preference Skills

The talk separates two skill types with different lifecycles. Capability skills teach the model something it cannot yet do consistently. Preference skills encode company-specific taste, policy, workflow, style, or domain expectations that foundation models are unlikely to learn generically.

Skill Type Purpose Lifecycle Eval Question
Capability Skill Close a model knowledge or reliability gap, such as a new SDK, log tracing workflow, or API migration. Temporary. Newer models may make it unnecessary. Does the model still need this skill to pass the task?
Preference Skill Encode team-specific workflow, writing style, support policy, design system, or domain language. More durable. It represents your organization, not only model weakness. Does this protect the behavior our business wants?

This matters because capability skills should be retired aggressively when models improve, while preference skills should be guarded against regressions when you change model, harness, or prompt stack.

4. Model-Invoked vs User-Invoked Skills

User-invoked skills are explicitly requested by a human or command. They are powerful for internal development workflows such as creating pull requests, staging documentation, or running a known script-like process. The user knows the skill exists and can ask for it.

Model-invoked skills are harder. The model must infer from the user prompt whether a skill should be used. This is the customer-facing agent problem: the customer does not say "use the refund skill." They just say what they need. The skill description becomes the product interface.

User-Invoked

Best for slash commands, internal workflows, known dev tasks, and repeatable scripts.

Model-Invoked

Best for customer agents and ambient assistance, but requires strong trigger evals.

Script Instead

If the path is always step one, step two, step three, write a script and let the agent call it.

5. What the Data Suggests

Philipp references Skill Bench and related analysis of large public skill collections. The high-level finding: skills can help, but most skills are not evaluated, many are AI-written, and some can degrade performance. Human-written skills tend to be stronger because they encode actual domain judgment and reduce vague filler.

He also warns against bloated skills. Long descriptions and long skill bodies cost tokens and can confuse the model. The description is paid on every model call. The body is paid whenever the skill is loaded. References should be layered so the model only reads deep material when necessary.

Practical rule: keep the always-loaded surface tiny, keep the skill body directive, and move long cloud, domain, or language-specific detail into reference files.

6. How to Write Better Skills

The talk gives a clear writing style: directive, lean, layered, and testable. A skill is not an essay. It is a behavioral contract for an agent.

Rule Why It Matters Example Pattern
Explain why, how, and when The model needs a trigger reason and a use pattern. Use this skill when building a React component with Tailwind CSS.
Write directives, not essays Passive background text is easier to ignore. Use the Interactions API for chat apps; avoid old SDK patterns.
Layer references Deep docs should not be loaded for every task. Put AWS, Google Cloud, and Azure deploy details in separate references.
Define goals and constraints Rigid fixed paths may belong in scripts instead. Tell the model what success means, not every keystroke.
Add negative cases Over-triggering is as harmful as under-triggering. Do not use the React skill for generic web or Angular tasks.
Remove no-ops Instructions that do not change behavior waste tokens. Delete filler like "write clear, high-quality code" unless it changes something specific.

7. A Minimal Skill Eval Harness

The suggested starting point is simple: create 10 to 20 prompts. Include happy paths where the skill should trigger, negative cases where it should not trigger, and real production traces when available. Then run the same cases with and without the skill.

  1. 1 Prompts User-like tasks, language, expected trigger behavior, and expected outputs.
  2. 2 Runner Script that launches the agent in a clean workspace and captures traces.
  3. 3 Checks Regex, AST, command traces, file assertions, or LLM-as-judge rubrics.
  4. 4 Trials Run multiple attempts per case to measure reliability, not one lucky pass.
  5. 5 Ablation Compare skill-loaded performance against no-skill performance.

For many coding skills, regex and script checks are enough. In the Gemini Interactions API example, checks can inspect whether generated code uses the correct SDK, model ID, method names, and avoids old patterns. LLM-as-judge is better reserved for more subjective or trace-level behaviors.

8. Gemini Interactions API Case Study

Google DeepMind created a skill to help coding agents use the newer Gemini Interactions API. The reason is a classic capability-skill problem: the API shipped after model training, so models may not know current SDK patterns, model names, or migration guidance.

The team built an eval harness with 117 prompts across Python and TypeScript. Each test case included prompt, language, whether the skill should trigger, and expected checks. A simple runner invoked the coding agent, collected output, and scored whether the generated code used valid current patterns.

Input

Prompts drawn from real users, synthetic cases, feedback, and known failure patterns.

Languages

Python and TypeScript, because both SDK patterns needed validation.

Checks

Correct SDK, current model, correct methods, no legacy API patterns.

Outcome

The talk reports large performance gains for valid Interactions API code when the skill was used.

9. Put Evals Next to Skills

Internally, Philipp says skills are paired with evals. When a skill changes, the eval runs. If the change does not improve the test cases or add new coverage, it should not merge. This is the same engineering discipline teams already expect from code.

A useful pattern is to keep the skill, eval cases, workspace fixtures, startup commands, script checks, and LLM-judge rubrics together. That makes the skill reviewable, measurable, and portable across model updates.

Governance rule for agent platforms: no production skill should be promoted without an eval artifact, and no skill diff should be approved without eval results.

10. Eval Best Practices

Test Triggering

Evaluate whether the model uses the skill when needed and avoids it when irrelevant.

Test Outcomes

Do not only check that the skill loaded. Check whether the task succeeded.

Isolate Runs

Use clean workspaces so agents cannot leak answers from prior attempts.

Run Trials

Non-deterministic systems need repeated runs to estimate reliability.

Cross Harnesses

Test the actual model and harness combinations your users rely on.

Keep Evals

Even after retiring a skill, keep the eval to detect future regressions.

Ablate

Run with skill and without skill. Otherwise you cannot prove lift.

Retire Skills

If the model passes without the skill, remove token cost and maintenance burden.

11. What This Means for Your Agentic AI Platform

For your Master Agent, Sub-Agent, Skill, Tool, and MCP platform, this talk is almost directly an SOP. Skills should be owned, versioned, evaluated, promoted, monitored, and retired. BA users can author business intent, but the platform should require testable cases before that skill becomes production behavior.

Platform Object Eval Requirement Promotion Gate
Cognitive Skill Prompt cases, expected reasoning output, negative cases, rubric. Improves decision quality without over-triggering.
Actionable Skill Tool-call traces, side-effect checks, rollback checks, permission checks. Performs the action safely and attaches evidence.
MCP Tool Schema validation, permission policy, successful/failed tool-call fixtures. Agent calls it only when allowed and with valid arguments.
Master Agent Routing cases across multiple skills and sub-agents. Chooses the right skill, tool, or escalation path.
Business Flow Markdown Business scenarios, happy paths, exception paths, and customer language. Customer prompts map to the correct policy, skill, or human gate.
