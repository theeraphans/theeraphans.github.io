Harness Engineering with Codex

A structured field guide to OpenAI's article about building a real internal product with Codex agents, zero manually written code, repository-native knowledge, mechanical architecture, and feedback loops that let agents work reliably.

Article: Harness engineering: leveraging Codex in an agent-first world Author: Ryan Lopopolo, OpenAI Published: February 11, 2026

The Short Version

Harness engineering is the discipline of designing the environment around coding agents so they can produce, test, review, and maintain software with far less human handholding. The key move is not "write better prompts." It is to make the repository, application, tools, observability, architecture rules, and cleanup loops legible and enforceable for agents.

  • Humans steer, agents execute: engineers specify goals, acceptance criteria, constraints, and feedback loops.
  • Repository knowledge becomes the system of record: `AGENTS.md` is a map, while structured docs and plans carry the real context.
  • Autonomy requires guardrails: architecture, taste, logs, tests, browser validation, reviews, and garbage collection are encoded into the harness.

Core Thesis

Harness engineering moves human effort from writing code to designing the system that lets agents write code safely.

The article describes a shift in the software engineer's job. When Codex can write application logic, tests, CI, documentation, observability, and tools, the bottleneck moves to the surrounding environment: how the agent gets context, how it validates output, how it receives feedback, how architecture is enforced, and how the codebase resists entropy.

The most useful framing is that the agent is not the whole product-development system. The harness is the system: prompts, repo knowledge, plans, tooling, tests, browser automation, logs, metrics, traces, linters, architecture rules, review loops, and recurring cleanup tasks. Better models help, but the compounding advantage comes from an environment that makes correct work easy and incorrect work mechanically visible.

For an agentic platform, this is the same pattern as Master Agent plus Sub-Agent plus Skills plus Tools: the value is in the operating loop around the model.
The Experiment

OpenAI built an internal beta from an empty repository with Codex writing every line.

The team began with an empty repository in late August 2025. Codex CLI using GPT-5 generated the initial scaffold: repository structure, CI, formatting, package manager setup, application framework, and even the first `AGENTS.md`.

Five months later, the repository was around a million lines across product code, infrastructure, tooling, docs, observability, and internal developer utilities. Roughly 1,500 pull requests were opened and merged. The early team was three engineers driving Codex, with reported throughput around 3.5 PRs per engineer per day, and the product had hundreds of internal users plus external alpha testers.

Constraint

No manually written code

The team kept the constraint intentionally so every missing capability had to become part of the agent environment.

Scale

Agent-generated repo

Application code, tests, CI, docs, observability, internal tooling, and dashboards were all generated by Codex.

Outcome

Software that ships

The product deployed, broke, got fixed, and served real internal users, which kept the experiment grounded in reality.

Engineer Role

The engineer becomes a harness designer, not a code typist.

The article says early work felt slower than expected because the environment was underspecified. Codex was not blocked by raw intelligence as much as by missing tools, missing abstractions, weak feedback loops, and unclear internal structure. So the engineer's job became finding the missing capability and making it legible and enforceable for the agent.

In practice, engineers break large goals into smaller building blocks, prompt Codex to create them, and then use the created artifacts to unlock more complex work. A pull request can go through local self-review, additional agent reviews, human feedback when needed, response loops, and repeated iteration until reviewers are satisfied.

Old center of gravity New center of gravity What the platform must support
Write implementation code. Specify intent, constraints, and acceptance criteria. Structured task specs, planning artifacts, and measurable done definitions.
Manually inspect most behavior. Give agents direct access to UI, logs, traces, tests, and reviews. Tool access, sandboxed runs, browser inspection, observability APIs, and screenshots.
Fix bad output by rewriting it. Ask what capability, rule, or feedback path was missing. Reusable skills, custom lint messages, validation loops, and doc updates.
Application Legibility

Codex needs to see and operate the app, not only edit files.

As code throughput rose, human QA became the bottleneck. OpenAI responded by making the running application directly legible to Codex. Each git worktree could boot its own isolated app instance. Browser state became accessible through Chrome DevTools Protocol. The agent could use DOM snapshots, screenshots, navigation, runtime events, and console state to reproduce bugs and validate fixes.

The same pattern applied to observability. Logs, metrics, and traces were exposed through a local ephemeral stack for each worktree. Codex could query logs and metrics, correlate failures, restart the app, run journeys, and loop until the observed behavior matched the target.

Repository Knowledge

`AGENTS.md` should be a map, not a 1,000-page manual.

The team tried a giant instruction file and found the predictable failure modes: it consumed context, made everything feel equally important, rotted quickly, and was hard to verify. The better approach was a short `AGENTS.md` that points to a structured `docs/` directory treated as the system of record.

This is progressive disclosure for agents. The initial file gives the agent a stable map. Deeper docs carry architecture, design docs, product specs, execution plans, generated schema references, quality scores, reliability rules, security notes, and technical debt. Dedicated linters and CI jobs validate that the knowledge base is current, cross-linked, and structured. A recurring doc-gardening agent opens fix-up PRs when docs drift from code behavior.

Architecture and Taste

Agents move fast only when boundaries are strict and mechanically checked.

Documentation alone does not keep an agent-generated codebase coherent. OpenAI enforced architecture through custom linters and structural tests. Business domains had fixed layers and validated dependency directions. Cross-cutting concerns entered through explicit provider interfaces instead of arbitrary edges.

The article's practical lesson is to enforce invariants, not micromanage every implementation. The team cared deeply about boundaries, correctness, reproducibility, structured logging, naming conventions, file sizes, schema/type rules, and reliability requirements. Inside those constraints, agents had room to choose the local implementation.

Merge Philosophy

When correction is cheap and waiting is expensive, merge gates change.

The article notes that high agent throughput makes some traditional engineering norms counterproductive. Pull requests are short-lived. Merge gates are lighter. Test flakes may be addressed in follow-up runs instead of blocking indefinitely.

This is not a universal recommendation for every team. The article explicitly frames it as a tradeoff that depends on throughput and environment quality. In a low-throughput or weakly validated system, it would be risky. In a harnessed system where agents can cheaply detect and remediate issues, waiting can become the bigger cost.

Risky without harness

Fast merges amplify chaos

If tests, docs, architecture checks, observability, and cleanup loops are weak, agent speed can compound drift quickly.

Useful with harness

Fast correction enables flow

If the system can detect, validate, review, and repair cheaply, shorter PR cycles can preserve momentum.

Autonomy Levels

End-to-end autonomy emerged only after the loop was encoded into the repository.

OpenAI says Codex can now drive a new feature end to end in that repository: validate current state, reproduce a bug, record failure evidence, implement a fix, validate the fix, record resolution evidence, open a PR, respond to feedback, detect build failures, remediate them, escalate when judgment is required, and merge.

The important caveat is that this behavior depends heavily on the repository's specific tooling and structure. It should not be assumed to generalize to a random codebase without similar investment. That caveat is the heart of harness engineering: agent autonomy is not just a model property; it is a system property.

Observe Validate current state

Run tests, inspect UI, query logs, gather existing behavior, and reproduce the issue.

Change Implement fix

Edit code, docs, tests, and tooling while respecting architecture and repo conventions.

Prove Record evidence

Capture screenshots, videos, traces, and test output showing failure and resolution.

Review Loop on feedback

Use agent reviewers, human feedback, CI failures, and local checks to iterate.

Ship Merge or escalate

Merge when the loop is satisfied, or ask a human where judgment is required.

Entropy and Garbage Collection

Agent-generated systems need continuous cleanup, not occasional heroic cleanup sprints.

Full agent autonomy creates a new maintenance problem: Codex replicates patterns already present in the repository, including uneven or suboptimal ones. At first, the team spent a weekly cleanup block on this. That did not scale.

The better answer was to encode "golden principles" into the repository and run background cleanup tasks. These tasks scan for deviations, update quality grades, open targeted refactoring PRs, and keep technical debt from compounding. This makes human taste reusable: encode it once, enforce it continuously.

Entropy source Harness response Platform implication
Bad pattern copied repeatedly Promote the correction into a lint, test, doc, or skill. Every review finding should ask whether it belongs in policy or automation.
Stale documentation Run doc-gardening agents and CI checks for freshness and links. Knowledge memory needs lifecycle management, not just storage.
Technical debt accumulation Open small recurring refactor PRs instead of large cleanup bursts. Background maintenance agents are part of the production system.
Agentic Platform Takeaways

This article is almost a blueprint for Master Agent, Sub-Agent, Skill, Tool, SOP, and Flow Markdown design.

For your platform, the most important lesson is to avoid putting the whole business process into a giant persona prompt. Instead, treat the agent prompt as a map to structured, versioned, testable, permissioned knowledge and workflows.

BA-side users should author flow specs, domain docs, SOPs, acceptance criteria, and business rules in a format agents can progressively discover. Engineers should provide the harness: runtime isolation, tool contracts, permission checks, logging, evaluation, review, cleanup, and escalation. The model sits inside that system; it does not replace it.

  • Master Agent: routes events, chooses flow specs, assembles context, spawns sub-agents, and owns escalation.
  • Sub-Agent: performs bounded cognitive or actionable work with a clear memory contract and output schema.
  • Cognitive Skill: reads, classifies, compares, summarizes, plans, critiques, or extracts evidence without side effects.
  • Actionable Skill: uses tools and must declare permissions, inputs, write-back behavior, rollback, and audit evidence.
  • Tool/MCP Contract: exposes capabilities in a small, typed, observable interface that agents can call directly.
  • Flow Markdown: stores SOP, entity model, task steps, required context, validation, review, and abstention rules.
  • Garbage Collection: turns recurring mistakes into rules, docs, evals, or cleanup agents.
Harness Spec Template

A reusable Flow Markdown skeleton for harness engineering.

This template adapts the OpenAI article into a platform artifact. It gives BA users a place to define the business flow while giving engineers the mechanical hooks needed for validation, observability, review, and cleanup. 

---
harness_id: customer_follow_up_agent_harness
owner: customer_operations_platform
entrypoint:
  master_agent: customer_ops_router
  trigger_events:
    - email.received
    - ticket.updated
    - meeting.completed
repo_knowledge:
  agent_map: AGENTS.md
  system_of_record:
    - docs/product-specs/customer-follow-up.md
    - docs/domain/customer-account.md
    - docs/policies/customer-risk.md
    - docs/quality/customer-ops-score.md
progressive_disclosure:
  load_first:
    - AGENTS.md
    - docs/domain/index.md
    - docs/product-specs/index.md
  load_on_demand:
    - active_execution_plan
    - account_summary
    - policy_exception_register
sub_agents:
  context_researcher:
    skill_type: cognitive
    output_schema: evidence_pack
  response_drafter:
    skill_type: actionable
    required_tools: [email_draft_tool]
    output_schema: draft_response
  policy_reviewer:
    skill_type: cognitive
    output_schema: risk_decision
tool_contracts:
  email_draft_tool:
    side_effect: draft_only
    audit_required: true
    human_approval_required_if:
      - legal_topic
      - price_change
      - high_risk_customer
validation_loop:
  preflight:
    - verify_context_freshness
    - run_policy_checks
  execution:
    - produce_plan
    - run_agent_review
    - run_human_review_if_required
  evidence:
    - cite_sources
    - log_tool_calls
    - store_before_after_state
garbage_collection:
  recurring_tasks:
    - stale_doc_scan
    - repeated_failure_pattern_scan
    - flow_quality_grade_update
  promote_to_rule_when:
    - same_review_comment_count_gte: 3
    - unsafe_action_attempt_count_gte: 1
---
