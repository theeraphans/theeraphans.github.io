No Vibes Allowed in Complex Codebases

A practical summary of Dex Horthy's talk on why coding agents struggle in brownfield systems, how context engineering keeps them out of low-quality trajectories, and why research, planning, compaction, and human review matter more than bigger prompts.

The Short Version

The talk argues that AI coding works well in small greenfield demos but breaks down in complex brownfield codebases when teams rely on vibes, giant prompts, and unbounded tool output. The alternative is a disciplined workflow: keep the context window small, compact only the truth that matters, use sub-agents to gather narrow evidence, turn research into a reviewed plan, and let implementation execute against that plan.

  • Context quality drives output quality: correctness, completeness, size, and trajectory all matter.
  • Sub-agents are for context control, not for role-play org charts like frontend, backend, and QA personas.
  • Human thinking moves earlier in the pipeline: review research and plans before they become large code changes.

The Problem

AI coding gains can become a technical debt factory.

Dex starts from a familiar split: AI coding can be impressive in greenfield demos, but it often creates rework, churn, and low-quality changes in old production codebases. The failure mode is not simply that models are weak. It is that teams give them weak operating conditions: too little truth, too much noise, unclear plans, and no disciplined review of the high-leverage decisions.

Greenfield

Small demos hide the hard parts

Fresh apps and isolated dashboards let the agent work without decades of architecture, hidden constraints, and team norms.

Brownfield

Large systems require accurate context

The agent must know where the real behavior lives, what not to touch, and how the team expects changes to be made.

Slop

More code is not automatically progress

Shipping faster can mean cleaning up last week's AI-generated mistakes unless the workflow changes.

The practical takeaway is blunt: advanced agent adoption is less about finding one magic prompt and more about redesigning how engineering work moves from problem discovery to reviewed implementation.

Context Window

The agent only has the tokens you give it.

The talk's most important technical frame is that LLMs are stateless between turns. The next action is influenced by what is inside the conversation. So the team's job is to optimize the context window for correctness, completeness, size, and trajectory.

Dimension Meaning Failure Mode
Correctness The context must describe the codebase as it actually is. One wrong assumption can send the implementation into the wrong subsystem.
Completeness The agent needs enough relevant facts to act safely. Missing constraints make the output look plausible while breaking real behavior.
Size The context should stay compact enough to leave room for reasoning and tool use. Huge logs, broad file dumps, or noisy MCP payloads push the agent into low-quality work.
Trajectory The conversation should carry a productive path, not repeated correction loops. After several bad turns, it may be better to compact truth and restart with a clean window.

Dex calls the low-quality region the "dumb zone": once too much of the context window is filled, the model has less room to make good next-step decisions. The exact threshold varies, but the operating lesson is stable: large context is not the same as useful context.

Sub-Agents

Sub-agents should control context, not mimic job titles.

A sharp point in the talk: sub-agents are not mainly for anthropomorphizing roles. Their highest-value use is isolating exploration. A sub-agent can search, inspect files, understand a slice of the system, and return a small, accurate summary to the parent agent.

Parent agent asks Find how a specific feature, integration, schema, or workflow works.
Sub-agent explores Spend tokens reading files, traces, tests, and docs inside an isolated context.
Sub-agent compresses Return only the files, line references, constraints, and relevant findings.
Parent acts Use the small result to plan or implement without polluting the main context.
Good use

Vertical slices through a codebase

Ask sub-agents to investigate the exact areas relevant to the task and report compressed truth.

Weak use

Persona sprawl

Creating frontend, backend, QA, data, and manager agents without a context-control reason just adds orchestration noise.

Research, Plan, Implement

The workflow is really repeated compaction.

Dex describes a practical three-phase workflow: research how the system works, plan exact steps with file names and test strategy, then implement against the plan. The important part is not the acronym. The important part is frequent intentional compaction: every phase compresses messy exploration into a smaller artifact that can be reviewed and reused.

Research Understand the relevant code paths, files, dependencies, tests, and constraints.
Compact truth Write a concise research document with exact references and verified findings.
Plan Outline steps, code snippets, change order, risk points, and validation method.
Review Human or peer review catches wrong assumptions before they become code churn.
Implement Execute the plan in a clean context with enough evidence to verify completion.

The talk includes both wins and limits. Dex describes successful work in a large Rust codebase and a very large code shipping session, but also a failed attempt to remove Hadoop dependencies from Parquet Java that required going back to the whiteboard. That is the right lesson: context engineering amplifies thinking, it does not replace it.

Mental Alignment

Plans are not just for the agent. They keep the team aligned.

The talk reframes code review. Yes, review checks correctness, but it also keeps the team mentally aligned: everyone can understand how the system is changing and why. As AI increases code volume, teams need artifacts that make the path to the code legible.

Research docs

Show what the agent learned

Reviewing research catches wrong system understanding before it turns into a broad implementation.

Plan files

Show intent and order

A good plan includes file names, snippets, steps, tests, and the reasoning behind the path.

PR narratives

Show the journey

Teams should see prompts, steps, test runs, and manual checks, not only a wall of final diff text.

Do not outsource the thinking. Move human review to the parts of the pipeline with the highest leverage.

Spec-Driven Dev

The phrase is too fuzzy; the useful practice is still real.

Dex is skeptical of the term "spec-driven development" because it has started to mean too many things: a longer prompt, a PRD, markdown files, verifiable feedback loops, or even library documentation. The useful part is not the label. It is the discipline of compressing intent, evidence, constraints, and tests into artifacts that make work executable and reviewable.

Artifact What Good Looks Like What To Avoid
Onboarding docs Progressively disclosed context near the part of the codebase being changed. Huge static documents that become outdated and consume the smart zone.
Research On-demand compressed context based on the current task and current code. Generic summaries that feel impressive but are not tied to files and behavior.
Plan Specific change order, code snippets, test plan, and known risks. A vague checklist that cannot be reviewed before implementation.
Prompt A routing and execution instruction backed by evidence. A giant wish list that asks the model to invent the missing thinking.
Platform Takeaways

What this means for your Master Agent, Sub-Agent, Skill, and MCP platform

This talk is directly relevant to a BA-facing agentic platform because it explains why persona prompts are not enough. The platform should help BAs and engineers build operating loops that preserve truth, compress intent, manage context budgets, and create reviewable artifacts before tools mutate the system.

  • Make context budget a first-class field. Every agent and skill should declare what it can read, what it should summarize, and what it must avoid dumping into the parent context.
  • Use sub-agents as context probes. Let them investigate slices of systems, policies, APIs, and workflows, then return compact evidence rather than long transcripts.
  • Separate research skills from action skills. Research skills gather truth. Planning skills compress intent. Action skills mutate systems and require gates, permissions, and audit logs.
  • Require plan review for high-risk flows. Before an agent changes production data, code, policy, or customer-facing communication, a human or verifier should approve the plan.
  • Make MCP output controlled. Tools should return structured, filtered, task-relevant payloads. Raw JSON dumps can sabotage the context window.
  • Store compaction artifacts. Research docs, plan docs, review notes, test evidence, and final diffs should become traceable artifacts in the platform.
  • Expose mental alignment as a product feature. Show BAs and reviewers why the agent chose a path, what it read, what it ignored, and how it validated the result.
  • Scale process by complexity. Simple tasks can go direct. Medium cross-system work needs research and a plan. Hard brownfield work needs full context engineering and review.
Flow Markdown

A BA-friendly Flow Markdown template should encode context engineering.

Instead of asking BAs to write a giant prompt, let them define the business problem, context sources, research questions, plan review rules, tools, gates, and escalation policy. Engineering can then bind each section to actual repositories, MCP tools, permissions, and eval checks. 

# Agent Flow: Brownfield Feature Change

goal: Add or fix a feature inside an existing production codebase without creating AI slop.
owner: Master Agent
complexity: high
workflow: research_plan_implement

context_budget:
  target_zone: smart
  max_parent_context_tokens: 60000
  raw_tool_output_policy: summarize_before_returning

research:
  purpose: Compress truth from the current codebase.
  sub_agents:
    - name: Code Path Researcher
      task: Find the files, functions, tests, and integration points that matter.
    - name: Risk Researcher
      task: Identify constraints, side effects, migrations, and backward compatibility risks.
  output_required:
    - relevant_files_with_line_refs
    - current_behavior_summary
    - constraints_and_unknowns

plan:
  purpose: Compress intent before implementation.
  required_sections:
    - change_sequence
    - expected_code_snippets
    - validation_steps
    - rollback_or_escalation_plan
  review_required: true

implementation:
  tools_required:
    - repo_search
    - file_edit
    - test_runner
    - git
  gates:
    - plan_approved
    - tests_pass
    - no_unreviewed_scope_expansion
    - summary_attached_to_pr

failure_policy:
  on_bad_research: restart_research_with_narrower_scope
  on_bad_plan: revise_before_code_changes
  on_repeated_test_failure: escalate_to_human
  on_context_growth: compact_and_restart
