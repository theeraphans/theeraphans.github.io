Peter Steinberger on Attention as the New Agent Bottleneck

A practical summary of Peter Steinberger's short talk on OpenClaw-era agent workflows: why attention matters more than tokens, how transcript context improves PR review, how auto-review should return to the original coding session, and why fresh-machine verification is becoming a core primitive for agentic software work.

The Short Version

Peter's core point is that the bottleneck has moved. Earlier agentic coding was constrained by tokens, then by local CPU, but once those constraints loosen, the real scarce resource is human attention. The best agent workflow is therefore the one that lets the agent do more of the boring context gathering, review, testing, setup, and visual verification before the human has to look.

  • Attach sanitized agent transcripts to PRs and issues so reviewers can see how the work happened, not only the final diff.
  • Run auto-review inside the active coding session, because the original session has the most context to accept, reject, or document feedback.
  • Use fresh remote boxes with screenshots and clicking so agents can verify setup and UI behavior without burning local CPU or relying on a polluted dev machine.

Core Thesis

Attention, not raw model capability, is becoming the scarce resource.

Peter opens by describing a sequence of bottlenecks. First he felt constrained by tokens. Then, after joining OpenAI, that constraint loosened. Next he felt constrained by compute and local CPU. Once remote execution becomes available, the remaining bottleneck is attention: how often the human must stop, inspect, decide, and unblock the agent.

The practical objective is to expand the range of work an agent can do between human checkpoints. A valuable coding agent should not only write code from a prompt. It should gather context, preserve its reasoning trail, review its own output through another model, run tests remotely, set up a fresh system, produce visual evidence, and package the result so the human can make a faster final decision.

Token bottleneck Early workflows were limited by context windows, token budget, and how much state an agent could carry.
CPU bottleneck Parallel agent sessions, tests, installs, and builds can make the local machine slow or unusable.
Attention bottleneck The human still has to decide what is worth reviewing, merging, or rejecting.
Workflow bottleneck The next gains come from better loops, evidence, review routing, and verification primitives.

The talk is useful because it moves past "agent writes code" and asks a sharper question: how do you reduce the number of times a human must babysit the agent while still keeping quality and intent intact?

OpenClaw Context

OpenClaw's PR volume forced Peter to redesign the review workflow.

Peter says OpenClaw receives a lot of pull requests. Some are serious, but some are created with almost no human effort: someone tells a coding agent to fix an issue number, the agent generates a large diff, and the maintainer receives a massive PR with little sense of whether the contributor understood the change.

This creates a trust problem. A 4,000-line PR might be valuable, but it also might be low-effort agent output that consumes reviewer time. The maintainer needs more than the final diff. They need context about how the work was done, what the agent tried, where the human intervened, and whether the contributor cared enough to inspect the result.

New artifact

Primitive 1

Transcript context turns PRs into inspectable work sessions.

Peter's first workflow improvement is an agent transcript skill. After a PR is created, the agent asks whether the contributor wants to upload a sanitized version of the coding-session transcript. The explicit incentive is simple: PRs with useful transcripts are more likely to get reviewed.

The value is not that transcript length proves correctness. The value is that the reviewer gets another signal. A longer, richer transcript can show that the contributor explored the problem, asked the agent to revise, noticed issues, and understood some of the constraints. A tiny transcript can reveal a near-zero-effort change.

Peter says he initially overthought the implementation, wondering whether he needed hooks or a more complicated system. The final solution was just a skill. The skill explains to the agent how to find the transcript, load the underlying JSON, sanitize it as best it can, and attach the useful context to the PR or issue. Because he controls the repository defaults, he made this skill load automatically when someone creates a PR or issue.

Transcript Signal What It Helps With Remaining Risk
Prompt trail Shows what the human asked, corrected, and accepted. It can still be incomplete, sanitized poorly, or edited dishonestly.
Agent exploration Shows attempted fixes, failures, tests, and reasoning paths. Transcript volume does not guarantee quality.
Reviewer triage Helps maintainers decide whether a PR deserves attention. Reviewers still need diffs, tests, and product judgment.

For enterprise agent platforms, this is a strong pattern: every agentic change should carry a process artifact, not only an output artifact.

Primitive 2

Auto-review is most useful when feedback returns to the original coding session.

Peter's second workflow improvement is an auto-review skill. When an agent creates a PR or commit, the skill calls whatever review CLI is available in the environment, such as Codex, Claude, or other coding tools. It asks that reviewer to inspect the current work and return feedback.

The key design decision is where the review feedback goes. Peter argues it should go back into the original coding session, because that session has the most task context. A detached reviewer can find plausible issues but may not understand the product constraints or why a weird-looking choice was intentional. If the feedback returns to the active coding session, the original agent can decide whether the feedback is valid, reject it with explanation, or update the PR description so the next human reviewer does not repeat the same naive critique.

Agent changes code The active session has the task history, constraints, and decisions.
Skill invokes reviewer A review CLI inspects the diff and returns concerns or suggestions.
Feedback returns The original session receives the critique instead of leaving it detached.
Session decides The agent fixes true issues and documents intentional tradeoffs.
PR improves The human reviewer sees both the diff and the recorded review decisions.

This is a subtle but important pattern: review is not just another model call. Review must be routed to the place that has enough context to act on it intelligently.

Primitive 3

A fresh remote box gives agents a clean place to build, test, and verify.

Peter's third workflow improvement is remote execution in a fresh box. The problem starts locally: if you run many long coding sessions, test suites, builds, and installs at once, your laptop becomes the bottleneck. He tried using multiple machines, but that was awkward. The better primitive is a disposable or remote environment that can sync repo changes and run expensive work elsewhere.

The fresh-box idea matters for more than performance. Local machines are polluted with hidden state: installed packages, old config, cached credentials, working-directory leftovers, system preferences, and environment quirks. If a feature only works on the developer's machine, that is not reliable verification. A clean machine gives more confidence that the install instructions, tests, setup, and UI behavior actually work.

Peter describes adding Linux, macOS, and Windows support so the agent can install and verify OpenClaw across real operating-system conditions. This is especially useful for platform bugs, setup flows, launch issues, and anything that depends on the operating system rather than only application logic.

Eyes For Agents

Visual verification lets the agent prove UI work instead of merely claiming it.

Peter then adds a visual layer: screenshots and clicking. The agent can open a browser inside the fresh box, set up the system, click through UI, capture screens, and show the result. This is like a lightweight computer-use loop without fighting the user's real mouse focus or desktop state.

This creates a powerful review artifact. Instead of asking the human to read a diff and imagine whether the UI is fixed, the agent can produce before-and-after evidence. For visual bugs, setup flows, and product demos, that can compress review time dramatically.

Peter also points out that these sessions can be shareable. Someone in a feedback channel can ask for a feature, an agent can implement a rough version, and the requester can click through a live remote session to discover whether the idea is good, bad, or needs adjustment. That reduces the number of low-value ideas that maintainers or engineers must personally inspect.

The best agent output is not just a patch. It is a patch plus enough evidence that a human can decide faster.

Loops

Peter treats loops as workflows that reduce human babysitting.

In the Q&A, Peter says "loops" is a fancy name for workflow. His example is an open-source issue pipeline: when someone creates an issue, an agent checks whether it fits the project's direction, using a vision document. If the agent thinks the idea is worth pursuing, it can create a PR. Another agent reviews the PR, another repairs it, and the final result is prepared for the maintainer.

The purpose is not to remove the maintainer. The purpose is to turn a raw stream of issues and agent diffs into a smaller queue of higher-quality candidates. When Peter has time to look at the project, more work is already bundled with context, review, repair, and evidence.

Loop Stage Agent Job Human Job
Issue intake Compare the request against the project vision and decide whether it is promising. Maintain the vision document and reject bad direction when needed.
PR creation Implement a candidate change with transcript context. Judge whether the candidate is strategically worth merging.
Auto-review Find issues, return feedback to the original session, repair, and document decisions. Check whether the final reasoning and evidence are convincing.
Visual proof Run in a clean box, capture before and after states, and share an interactive session. Use the evidence to make a faster yes, no, or revise decision.
Limits And Risks

The workflow helps, but it does not remove product judgment.

Peter is clear that attention is not fully solved. Agents need less babysitting when they have better tools, but they still struggle with whether a change fits the big picture. They can focus intensely on the local task and miss how it affects architecture, product feel, project direction, or long-term maintainability.

  • Transcript artifacts can be gamed. Peter notes that people can manually edit PR descriptions or scores, so process evidence still needs trust and verification.
  • Auto-review can go too far. Review agents may optimize for worst-case concerns unless project invariants and assumptions are defined clearly.
  • Fresh boxes do not prove product fit. They prove setup, tests, and UI behavior. They do not decide whether the feature belongs.
  • More code creates more coordination. Agents can produce more work, which means humans must think harder about system coherence.

The final bottleneck is not whether the agent can make a change. It is whether the change is the right one for the project.

Platform Takeaways

What this means for your agentic AI platform

This talk maps directly to a platform for Master Agents, Sub-Agents, Skills, and MCP tools. Peter is essentially describing the missing workflow layer around coding agents: context capture, review routing, remote verification, visual evidence, and human attention management.

  • Make attention a first-class metric. Track how often a human must intervene, how long review takes, and how many agent outputs are worth reviewing.
  • Require process artifacts for agent work. Attach sanitized transcripts, decision logs, test output, screenshots, and review responses to PRs or business-flow outputs.
  • Route review feedback into the owning session. A detached reviewer is useful, but the session with context should decide how to apply or document the feedback.
  • Give agents clean execution environments. Fresh boxes should be a standard primitive for install, test, cross-platform, and UI verification.
  • Separate verification from product judgment. Agents can prove behavior, but humans still own whether the idea fits the project vision.
  • Use vision documents as routing policy. A `vision.md`-style artifact can help agents triage issues and reject work that does not fit strategy.
  • Make evidence shareable to non-coders. Remote UI sessions and before-after GIFs let PMs, BAs, and users validate ideas before engineers spend attention.
