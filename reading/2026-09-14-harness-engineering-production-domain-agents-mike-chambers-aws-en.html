Executive summary

The model is not the whole agent

Mike Chambers defines a harness by subtraction: remove the model from an agent, and the surrounding machinery is its harness. That includes the loop, tools, memory, runtime, identity, context handling, and the mechanisms that let engineers observe and evaluate behavior.

His main distinction is between agents people use directly, such as coding assistants, and agents engineers build for other users. Both need a harness, but a production service must also account for scale, isolation, operating costs, and reliability.

The live demonstration progresses from a small Strands agent, to persistent local state, to an AgentCore deployment with managed infrastructure. It ends with a configuration-based managed harness that removes the need to write the agent loop yourself.

The central lesson

A system prompt and tools may express the agent's task. They do not eliminate the engineering needed to operate it safely and reliably for an audience.

02:45 · Two audiences

Agents we use versus agents we build

The assistant on your own machine

For a coding or productivity assistant, the harness includes instructions, relevant skills, memory, tools, and MCP connections. An engineering organization can distribute these conventions across its team, much as it distributes coding standards.

The user remains close to the work: inspecting changes, supplying context, and deciding whether an output is useful. Chambers names familiar coding products to illustrate this category, rather than compare their quality.

The service other people depend on

When building an agent for customers or many employees, the audience becomes part of the design problem. A developer's preferred way of consuming tokens is not automatically appropriate for a product's users.

The two categories can connect: someone builds the coding assistant that another engineer uses. The distinction is about responsibility and perspective, not an absolute boundary between products.

04:24–08:20 · Production responsibilities

Everything around reasoning must work too

Chambers first describes a relatively familiar harness: memory, skills, tools, and MCP servers. He then expands the picture for an agent deployed at cloud scale.

The production concerns he names include loop management, scaling, payments, memory, identity, skills, runtime, context management, observability, and evaluation. Observability and evaluation appear last on his list, but he explicitly says they should be considered first.

Reasoning and execution

Model interaction, the agent loop, tools, skills, and context management.

State and access

Session history, longer-lived memory, identity, and access to external systems.

Operating the service

Runtime, scaling, spending, traces, and evaluation.

This grouping is an editorial map of the talk, not a formal framework named by Chambers.

Do not confuse deployment with architecture

Putting all responsibilities into one container and increasing the container count is not his preferred answer for thousands of users. Different components have different scaling and operational needs. He argues for considering them individually rather than treating the harness as one undifferentiated process.

This is a cloud-scale design argument, not a claim that every prototype requires microservices. A small local example is still useful; it simply demonstrates less than a complete production platform.

06:07 · Infrastructure ownership

Generate infrastructure as code, not untracked cloud changes

Chambers warns against what he calls slop ops: asking an agent to create cloud resources directly in the same ad hoc spirit as manually clicking around a console.

His alternative is to have the assistant produce infrastructure as code that engineers continue to own. Exploring the console can help someone understand a service. Production deployment should instead leave a durable definition of what was created and how it can be reproduced.

He mentions the AWS agent toolkit as a way to guide assistants working with AWS. The important point is the deployment pattern, not that a toolkit by itself guarantees correctness.

Interpretation

Infrastructure as code makes review and reproducibility possible. It still needs validation, permissions, and an appropriate deployment process; generated configuration is not automatically safe.

08:38–12:30 · Local examples

From a basic loop to persistent conversation

First example: a minimal Strands agent

The first example uses the Strands Agents SDK, a system prompt, a calculator tool, and a custom time tool. The framework manages the loop. Chambers calls this a harness of sorts, but it has relatively few responsibilities and runs on his laptop.

The point is that an agent can be very simple at the code level. That simplicity should not be mistaken for evidence that scale, memory, security, or operating requirements are already addressed.

Second example: session state and remembered facts

The second example adds a session manager that maintains state across invocations and rehydrates conversation history when a user returns. It also includes a remember tool and files for longer-lived facts.

The demonstration asks who will win the World Cup. The response recognizes his preference for Australia from earlier interactions while acknowledging uncertainty about the outcome. The example demonstrates persistence and personalization, not a sports prediction system.

History and memory are related, but not identical

Restoring a conversation gives an agent access to prior turns. Storing selected facts provides a different kind of persistence. Chambers describes both in the example, making it useful to distinguish session continuity from information intended to survive across sessions.

Neither mechanism automatically establishes that a remembered fact is correct, fresh, or appropriate to use. Those quality questions remain outside the small demonstration.

12:50–18:00 · Managed deployment

Separate the agent from the infrastructure it depends on

Chambers then uses Amazon Bedrock AgentCore to move toward cloud-scale deployment. A CLI guides him through choices including generating code or bringing existing code, Python or TypeScript, a framework, a model, an interface, and memory options.

He chooses an HTTP interface for the example, while mentioning MCP and AG-UI as other interaction options. These examples illustrate interface choices rather than a complete integration walkthrough.

Memory becomes managed infrastructure

The memory selection creates infrastructure connected to the agent but managed separately from its running process. Chambers emphasizes the ability to scale pieces independently and add further capabilities without embedding every responsibility inside the agent.

The generated code still resembles a recognizable Strands agent, with additional connections to the runtime, memory/session management, and MCP. The demonstration presents runtime isolation as reducing the amount of multi-tenant execution code a developer needs to write.

Isolation is not every authorization rule.

This is an architectural clarification: isolated execution does not by itself define which business records a user may access. Applications still need correct identities, tool permissions, and data-scoping behavior.

Develop locally, then inspect the deployed system

He demonstrates agentcore dev for local interaction through a browser, and describes agentcore deploy as using infrastructure as code to deploy the system. The interface can also be used to inspect traces and stored memory.

These command names summarize what was shown. This article is not an installation guide, and CLI behavior can depend on the version in use.

18:40 · The managed harness option

Sometimes configuration can replace custom loop code

Chambers returns to an option he deliberately skipped earlier: choosing a managed harness instead of generating an agent implementation. The example is a simple JSON configuration specifying a model and system prompt, with the managed system supplying the execution machinery.

He suggests that a large fraction of use cases may need little more than a prompt connected to suitable tools. His approximate 80% framing is an argument for simplicity, not a measured result or a guarantee that most enterprise workflows are solved.

Less custom code does not mean less product responsibility

The distinction is between writing the loop and specifying the product. A managed loop can remove implementation work while leaving decisions about task scope, tool design, memory use, quality criteria, and acceptable behavior with the team building the service.

The talk concludes with composability: an existing agent can adopt one managed capability, such as long-term memory, without adopting the entire stack. Chambers also highlights Strands as the open-source framework used in his demonstrations.

AWS's AgentCore overview corroborates the modular service approach and its managed harness capability. That documentation check is supporting context, not additional material presented in the video.

Key takeaways

The durable ideas behind the AWS demo

  • Design for the audience: your own assistant and a service for thousands of people carry different responsibilities.
  • The harness is the surrounding system: tools and prompts are only part of it.
  • State has multiple forms: restoring history and remembering selected facts solve different needs.
  • Keep deployment reproducible: prefer owned infrastructure definitions over ad hoc resource creation.
  • Observe and evaluate early: a running agent is not proof of a dependable agent.
  • Use managed components selectively: adopting one service does not require rebuilding everything around the same vendor.
  • Do not overread the demo: minimal code, runtime isolation, and managed loops do not automatically solve domain authorization or workflow correctness.
