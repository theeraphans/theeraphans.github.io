Synthesis

แก่นเดียวกันจากทุกคลิป: agent ต้องถูกควบคุมด้วย flow ไม่ใช่ปล่อยให้ prompt คิดเองทั้งหมด

คลิปจาก LangGraph, MCP, OpenAI Agents SDK, Azure AI Foundry, Camunda และ human-in-the-loop examples ชี้ไปทางเดียวกัน: production agent ต้องมี state, tool boundary, approval, audit, eval และ orchestration ที่ตรวจสอบได้

01

Master Agent ควรเป็น router

หน้าที่หลักคือเลือก flow, ถือ conversation state, route ไป specialist และตัดสินใจ escalate ไม่ใช่ถือ tool ทุกตัวแล้วทำเองทั้งหมด

02

Sub-Agent คือ node ใน graph

ให้คิดแบบ LangGraph: agent เป็น node, edge คือเงื่อนไขการส่งต่อ, state คือข้อมูลที่ทุก node ใช้อ้างอิงร่วมกัน

03

Skill คือ contract ไม่ใช่ prompt ก้อนหนึ่ง

Skill ต้องมี input, output schema, owner, risk level, allowed tools, eval cases และ failure mode เพื่อให้ reuse และ govern ได้

04

MCP เป็น tool/context layer

MCP ช่วยลดปัญหา N x M integration โดยให้ client/agent ต่อกับ server ที่ expose tools, prompts และ resources ผ่าน standard interface

05

Human-in-the-loop ต้องอยู่ที่ action boundary

อย่าผูก approval แค่กับ agent ให้ผูกกับ risky tool หรือ actionable skill เช่น refund, payment, update CRM, send email

06

BA ต้องเขียน Flow Markdown

BA ไม่ควรแก้ raw system prompt แต่ควรประกอบ flow, policy, exception และ eval scenario ในรูปแบบ markdown ที่ platform compile ได้

Framework ที่ควรใช้

Workflow-first + Graph Orchestration + Router Master Agent + Specialist Sub-Agents + Skill Registry + MCP Tool Registry + HITL Gate + Simulation/Eval ก่อน release

BA SOP

SOP สำหรับให้ BA สร้างและประกอบ multi-agent system

เป้าหมายคือให้ BA ทำงานในภาษาของ business flow แต่ผลลัพธ์ยังถูก compile เป็น agent graph ที่ engineer ตรวจสอบและ release ได้

เขียน Flow Markdown ก่อนเสมอ

ระบุ trigger, goal, inputs, happy path, exception, policy, success metric และ eval scenarios อย่าเริ่มจาก prompt

แตก step เป็น skill candidates

ทุก step ต้องถูก classify เป็น cognitive skill หรือ actionable skill เพื่อแยก reasoning ออกจาก action ที่กระทบระบบจริง

เลือก skill จาก registry

ถ้ามี skill อยู่แล้วให้ reuse ถ้าไม่มีให้ request new skill พร้อม input/output และ eval cases

bind skill เข้ากับ specialist agent

Agent หนึ่งตัวควรมี scope ชัด เช่น identity, eligibility, payment, ticketing, knowledge ไม่ควรรวมทุกอย่างไว้ใน agent เดียว

bind actionable skill เข้ากับ approved tools

Tool/MCP ต้องมี risk level, auth scope, approval policy, audit fields และ failure handling ก่อนให้ agent เรียกใช้

compile เป็น graph แล้ว run simulation

ใช้ eval scenarios จาก BA เพื่อทดสอบ happy path, edge case, policy conflict, missing data และ risky action ก่อน release

release แบบมี monitoring loop

ทุก conversation ต้องเก็บ outcome, tool call, approval, handoff และ failure reason เพื่อย้อนกลับมา update flow/skill/eval

# Refund Request Flow

## Goal
Help the customer request a refund while following company policy.

## Steps

### 1. Understand Request
agent: cx_master_agent
skill: classify_customer_intent
type: cognitive
output: refund_request | non_refund_request | unclear

### 2. Verify Customer
agent: identity_agent
skill: verify_customer_identity
type: actionable
required_tools:
  - crm.customer.lookup
human_approval: none

### 3. Check Refund Eligibility
agent: refund_eligibility_agent
skill: refund_eligibility_check
type: cognitive
required_resources:
  - refund_policy_v3

### 4. Issue Refund
condition: eligibility = true
agent: payment_action_agent
skill: issue_refund
type: actionable
required_tools:
  - payments.refund.create
human_approval:
  - amount > 5000
  - confidence < 0.85

## Exceptions
- If identity fails, ask customer to verify.
- If policy is unclear, escalate to human.
- If payment tool fails, create support ticket.

## Eval Scenarios
- eligible refund within policy
- ineligible refund outside policy
- missing order ID
- angry customer
- high-value refund requiring approval

Decision Guide

ถ้าจะเอาไปทำ platform จริง ให้ตัดสินใจแบบนี้

นี่คือ recommendation ที่ผมจะใช้เป็น north star ให้ทีมตอนออกแบบ SOP และ product surface

ให้ BA สร้าง flow ไม่ใช่ agent prompt

UI ของ BA ควรเหมือน flow builder + markdown editor + scenario editor มากกว่า prompt playground

ให้ prompt เป็น compile target

persona/system prompt ควรถูกสร้างจาก Agent Contract, Skill Card และ Flow Markdown เพื่อให้ governance ทำงานได้

แยก cognitive/actionable skill ให้เด็ดขาด

cognitive skill ใช้คิดและจัดประเภทได้ ส่วน actionable skill ต้องมี tool binding, risk policy และ audit

ทำ tool approval ที่ wrapper level

เพราะ MCP tools อาจมาจากหลาย server การ wrap ที่ tool registry จะควบคุมความเสี่ยงได้ดีกว่าแก้ agent prompt ทีละตัว

ใช้ simulation เป็น release gate

ทุก flow ต้องมี scenario set จาก BA และ regression run ก่อน release โดยเฉพาะ flow ที่มี payment, identity, compliance

อย่าทำ swarm ก่อนมี governance

free-form multi-agent ดูฉลาดตอน demo แต่ debug ยาก ให้เริ่มจาก graph ที่มี state, edge, handoff และ escalation ชัดก่อน

คำแนะนำสุดท้าย

สร้าง platform surface เป็น 4 registries: Flow Registry, Agent Registry, Skill Registry, Tool/MCP Registry. จากนั้นให้ release ทุกครั้งผ่าน Simulation Registry และ Audit Trail เดียวกัน
