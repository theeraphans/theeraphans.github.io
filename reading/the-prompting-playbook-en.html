The Prompting Playbook

A concise summary of how to make prompts work in production: use evals as your compass, cleanly structure the prompt, add tools when the model lacks capability, and split complex work into loops that can check and repair themselves.

Source: Claude / Anthropic Length: 33:41 Format: fast-reading summary

The Short Version

The core message is: do not debug prompts by guessing. Start with evals, use them to identify the actual failure modes, clean up the prompt structure, fix one failure mode at a time, and recognize when prompting is the wrong tool. If a task needs exact calculation or rule enforcement, give the model a tool or split the workflow into generate, evaluate, and repair steps instead of cramming every responsibility into one giant prompt.

  • Measure first. A prompt change without evals is just a guess.
  • Prompt for behavior, but use tools for capability.
  • For hard tasks, split the work into draft, check, and repair.

Key Takeaways

Core Lessons From the Video

These are the points worth remembering if you want to apply the talk directly to real AI systems.

  1. Start with evals before editing the prompt Without a test suite, you cannot tell whether a prompt change improved the system or merely felt better.
  2. Separate failure modes clearly A model may be capable but behaving differently, or it may simply lack the capability required. Those two cases need different fixes.
  3. Prompt hygiene creates immediate lift Remove stale content and separate role, policy, guidelines, tone, data, and output format so the model can understand each part.
  4. Avoid long ban lists as patches Prompts full of narrow prohibitions often cause overfitting and new regressions elsewhere.
  5. Instructions do not add capability Telling a model to calculate accurately does not make it better at math. If exactness matters, provide a tool.
  6. State both sides of trade-offs If you only say escalation is expensive, the model may avoid escalation too aggressively. Include the cost of being wrong too.
  7. Split complex tasks into multiple stages Instead of one prompt doing everything, use generate, evaluate, and repair loops so the system can inspect and improve its own output.
Concrete Example

Before and After: Turning a Messy Prompt Into a Testable Prompt

The talk's practical advice becomes clearer when you see it as a rewrite pattern: vague blocks of instructions become structured sections that are easier for the model, and easier for engineers, to reason about.

Before: one blended instruction blob

You are a helpful support agent. Be friendly and answer customer questions.
Use the plan information below. Do not escalate unless absolutely necessary.
Never mention internal policy. Always calculate bills correctly.
If the customer is confused, explain the plan.

After: separated responsibilities

<role>You are Meridian Mobile's support assistant.</role>
<policy>Use customer_account as the source of truth.</policy>
<tools>For prorated bills, call calculate_proration.</tools>
<handoff>Escalate billing conflicts to a human specialist.</handoff>
<output>Answer briefly, cite the relevant plan, then ask if the customer needs anything else.</output>
Case Study 1

When an Existing Prompt Breaks After a Model Change

The first example is a customer support bot for a fictional telecom company, Meridian Mobile. The old prompt handles easy cases, but starts failing edge cases after moving to a different model.

Step 1

Measure with an eval suite

Include control cases, edge cases, and cases where the model should know when to refuse or hand off to a human.

Step 2

Restructure the prompt

Separate role, guidelines, policy, tone, and customer context with clear structure such as XML tags.

Step 3

Remove stale defensive patches

Many prompts contain fixes for old model behavior. After a model change, those patches can become the source of new failures.

Step 4

Add tools when the model needs calculation

For prorated billing, the model should not do mental math. It should call a dedicated proration calculator tool.

Step 5

Balance the objective

If the model must decide whether to escalate, it needs both the cost of escalation and the cost of giving the wrong answer.

Failure Likely Cause Fix Result You Want
Model mixes policy, tone, and customer data. The prompt is one long undifferentiated block. Separate sections with explicit labels or XML tags. The model knows which text is instruction, context, and data.
Model gives wrong prorated billing math. The prompt asks the model to do a task it is not reliable at. Add a calculator tool and instruct the model when to call it. The system computes the answer rather than hoping the model does.
Model refuses to escalate billing conflicts. The objective only says escalation is expensive. State both costs: escalation cost and cost of giving the wrong answer. The model escalates when the risk of being wrong is higher.

The lesson: a good prompt does not merely tell the model what to do. It gives the model the right information, tools, and objective.

Case Study 2

When Building a New Agent From Scratch

The second example is an agent that creates a weekly retail staff schedule. The task has hard rules: employee availability, shift coverage, and specific constraints, so it can be evaluated programmatically.

What was limited

A simple prompt with a smaller model fails many cases. A larger model reduces errors but still does not fully solve the problem. Adaptive thinking improves reliability, but increases token use and latency.

What worked better

Splitting the work into a generate, evaluate, repair loop lets the model draft a schedule, identify violations, and repair only the broken parts. This improves control and supports soft constraints that change case by case.

Generate

Create the first complete answer without forcing one prompt to carry every rule and responsibility.

Evaluate

Check the answer against the required rules and report violations with clear evidence.

Repair

Fix the specific violations found, rather than asking the model to start over from scratch.

Decision Guide

Should You Fix It With a Prompt, a Tool, or a Workflow?

This is the missing decision layer: once an eval fails, decide what kind of fix the failure deserves. Not every problem belongs in the prompt.

Use a prompt change when...

The model has the capability, but it is choosing the wrong behavior, tone, priority, or format.

Use a tool when...

The task requires exact calculation, retrieval, validation, data mutation, or a system action outside the model.

Use a workflow when...

The task is too large for one pass and benefits from drafting, checking, repairing, or handing off between specialized steps.

Playbook

The Practical Sequence to Use

This is the video's core workflow translated into steps you can apply to AI products or internal tools.

01

Define evals

Create cases that must pass, including normal cases, previous failures, refusals, and human handoff scenarios.

02

Run the baseline

Find out where the current prompt fails before making changes.

03

Apply prompt hygiene

Remove clutter, separate prompt sections, and make the output format easy to parse and test.

04

Fix one failure mode at a time

Avoid broad prompt rewrites. Change one thing, then rerun the evals.

05

Add tools or workflows

If the task needs precision, calculation, checking, or rule enforcement, use tools or multi-step loops.

Checklist

Checklist for a Production-Ready Prompt

  • There is an eval suite covering control cases, edge cases, and boundary cases.
  • Role, policy, guidelines, data, tone, and output format are clearly separated.
  • Old instructions that patched previous model behavior have been reviewed and removed when obsolete.
  • The prompt is not a long ban list that solves one narrow issue while creating regressions elsewhere.
  • Tasks requiring calculation or rule enforcement use tools or programmatic checks.
  • Important objectives are written as balanced trade-offs, not one-sided incentives.
  • Complex work is split into stages that can be evaluated and repaired.

Tomorrow's move: pick one failing behavior, write three eval cases for it, run the current prompt, make one targeted change, and rerun the same evals before touching anything else.
