Advanced Ontology: Model the Business, Not the Tables

Landon Carter explains how interfaces, structured values, derived properties, and security turn an ontology into reusable operational software rather than a thin copy of upstream datasets.

Executive summary

An ontology is the software model of an organization

The presentation's central claim is that a useful ontology should mirror the meaningful entities and workflows of the business, not the accidental structure of its source tables. A restaurant, an office, a staffing assignment, or an address has semantic meaning. A collection of columns copied from a pipeline may not express that meaning clearly.

Carter connects advanced product features to familiar software design principles. Interfaces make workflows reusable across object types. Structs keep related values and metadata together. Reducers and main fields simplify how rich values are consumed. Derived properties expose business meaning without duplicating facts. Security and object-backed links let those patterns remain useful when observations have different permissions or relationships have their own history.

The key takeaway

Advanced ontology design is not about adding more object types. It is about giving people and agents a coherent, reusable, permission-aware model of what exists and what can be done.

FoundationIntegrated facts

Bring disparate sources into reliable data foundations.

OperationsObjects, actions, logic

Represent entities and the decisions that affect them.

AI-firstAutomation over the model

Let LLMs use existing operational semantics rather than invent them from scratch.

01 · The evolution

From golden tables to operational decisions to AI

Carter describes three stages. The first is integrating disparate sources into usable “golden tables.” The second is operational decision-making: capturing an organization's behavior through actions, functions, logic, and models. Data enters the system, computation and decisions happen inside it, and effects return to the real world.

The third stage layers LLMs and automation over those existing capabilities. AI therefore does not sit above a passive document collection alone. It operates over a model that already describes entities, relationships, and operational behavior.

The talk traces this approach back to Gotham's work with unstructured reports and documents, then through Foundry and AIP. Carter argues that this history provides depth that an AI lab cannot simply reproduce instantly. That is a vendor's competitive argument, not something this summary independently proves.

02 · Four principles

Borrow software engineering discipline

1. Domain-driven design

Represent real-world concepts directly. An ontology is intended as a virtual representation of the business world, not a virtual representation of dataset layouts. Names, properties, and links should make sense to the people doing the work. Carter also argues that this makes the model more intuitive for agents.

He criticizes automatically mapping every upstream column as a final design strategy. It can be a starting point, but it skips the important step of thinking about workflows from first principles.

2. Don't repeat yourself, using the rule of three

If the same workflow or model has been built three times, look for a shared abstraction. Carter links duplication to context-management problems: people and agents must otherwise distinguish many nearly identical object types and decide which is canonical.

The rule is a heuristic, not a requirement to merge every similar concept. An abstraction should capture shared meaning, not merely shared column names.

3. Open for extension, closed for modification

Protect a stable core while allowing new teams to add workflows and object types. A refined interface should not be casually changed in ways that break existing consumers. Builders should be able to extend the model around that contract.

As interpretation, this requires governance and versioning as well as good modeling. The principle itself is not an automatic permission control or a promise that interfaces will never need to evolve.

4. Producer extends, consumer super

Carter borrows Java's PECS terminology to explain flexible consumption of compatible types. A workflow reading events can accept more specific event types; an operation capable of handling a general event can handle a particular event instance. The talk uses NBA games and DevCon keynotes to make this concrete.

The point is reusable contracts. This explanation is not a claim that Foundry literally implements every Java wildcard or generic variance rule.

03 · Interfaces

Build one workflow over a common capability

The example introduces a Building interface implemented by Restaurants, Office Buildings, and Arenas. A building-oriented workflow can operate across all three types or allow the user to select just one. The organization does not need three copies of the application merely because the source entities differ.

Building workflow

Building interface → Restaurant, Office Building, Arena

Scheduling workflow

Schedulable Resource interface → Arena and other schedulable entities

The Arena participates in both contracts without forcing every building to become schedulable.

Carter says interfaces support multiple inheritance and multiple levels. An object type can participate in more than one interface, and interfaces can extend other interfaces. The Arena therefore supports building workflows and resource-scheduling workflows independently.

He relates this to favoring composition over a contrived hierarchy. Rather than inventing a “Schedulable Building” abstraction solely to combine two concerns, the model can express those capabilities separately.

This feature supports all four principles: domain meaning, reduced workflow duplication, stable extensible contracts, and flexible use of compatible types. Its success still depends on choosing the right shared properties and links.

04 · Structs

Keep a meaningful value and its context together

An address consists of several fields but is conceptually one value. Carter first shows a historical Gotham example, then a Foundry address with street, city, state, and postal code. Structs let these fields be grouped as one property rather than scattered across unrelated properties.

Metadata can live alongside the value: who created it, when it was modified, and whether it was manually entered or sourced from another system. The advantage is proximity. Consumers can understand the value and its provenance together rather than locating a separate sidecar object or hidden field.

The LLM example: an ontology help bot

A Slack helper produces a response together with related information: a relevant prior Slack message, a documentation URL, and a model-generated explanation described in the talk as reasoning. Capturing these in structured output makes downstream processing possible.

Explanation is not proof

A stored model explanation is an output artifact, not a guaranteed faithful record of internal computation. Its presence does not validate the answer. Source links and independently checked evidence remain important.

Palantir's struct documentation describes grouped fields and notes that support varies across applications. A struct should not be assumed to behave identically in every product surface.

05 · Reducers and main fields

Preserve richness without making every consumer handle it

Rich structured values introduce a usability problem: a workflow may need the business value, not the entire bundle of metadata and history. Carter presents two complementary mechanisms.

Reducers: choose a representative value from many

A person may have multiple addresses over time. Instead of discarding that history, the model can keep an array of address structs with timestamps. A reducer can select the struct with the most recent modification timestamp as the default address displayed in relevant interfaces.

The remaining addresses still exist and can be inspected when necessary. The reduction changes the representation presented to a consumer; it does not mean the history is deleted. Nor does “latest modified” necessarily mean “currently valid” in every business domain. The selection rule must match the intended semantics.

The property-reducer documentation confirms reducing an array of structs to one struct using a configured field.

Main fields: expose the semantic value inside a struct

A geolocation struct may contain a point, its creator, and timestamps. Marking the point as the main field allows supported workflows to treat the property like the meaningful geospatial value while retaining metadata for inspection.

ReducerWhich value?

Select a representative struct from an array, such as the latest address.

Main fieldWhich part of the value?

Expose the point or other core field inside that struct.

Combined, these mechanisms let an internally rich representation satisfy a simpler consumer-facing contract. The main-field documentation explicitly describes their combination with reducers. Availability and interface-action constraints should be checked before designing around the feature.

06 · Derived properties

Expose business facts without copying them everywhere

The example is an organizational chart. A lead has links to workers who report to them. The application wants the workers' names and a count. One option is to copy names and counts onto the lead object, but those copies become brittle when a worker changes their name or a reporting relationship changes.

Derived properties instead express how to obtain the value from existing facts. Follow the reporting links, collect the worker names, and count the linked workers. The information remains normalized while consumers receive convenient, meaningful properties.

Authoritative facts

Worker names + lead-to-worker relationships

Derived values

Report names = collect linked worker names

Report count = count linked workers

The design benefit is reducing independently maintained copies. Business logic becomes part of the model rather than a repeated convention in every application. The talk does not supply detailed performance measurements or consistency guarantees, so the summary does not assume these calculations are free, instant, or suitable for every high-volume query.

07 · Granular security

Permissions must follow the meaningful unit of information

The final examples intentionally layer several features. Carter uses fictional patient records to explain increasingly precise security. Dataset-level security applies the same access boundary to a collection. Row-wise security restricts a particular patient. Combining row and column controls allows cells to have different visibility.

He then describes sub-cell security: individual elements in an array of patient notes have their own access levels. A user may be allowed to see ordinary notes without being allowed to see a particularly sensitive observation.

BroadDataset or row

Restrict a collection or a specific object's information.

More preciseCell

Protect selected fields differently for different objects.

Finest exampleArray element

Preserve distinct permissions for individual observations.

The talk references Object Security Policies, restricted views, multi-dataset objects, and derived properties as parts of these designs. The layered examples are not evidence that creating a derived property alone grants a complete security system.

For AI consumers

As an architectural implication, enforce authorization before information reaches model context. Asking an agent not to reveal restricted content is not equivalent to preventing retrieval of that content. Derived and resolved views also need to preserve the original access boundaries.

08 · Entity resolution

A unified view should not erase source permissions

Two records may turn out to describe one person. Carter uses similarly named patient objects to explain entity resolution: when either object is opened, consumers can see the combined properties while each property's original security is retained.

He then sketches a more complicated model with equipment and equipment observations, resolution links, and a multi-step derived-property chain. Adding another resolved equipment record extends the unified view with its observations.

The transferable distinction is between identity and observation. Determining that two records refer to the same entity does not imply that all their observations have the same provenance, confidence, or visibility. Those attributes need to survive the unified presentation.

The speaker explicitly says the audience does not need to understand the complete underlying model in this short session. Accordingly, this summary treats it as an illustration of compositional depth, not a complete implementation recipe or a guarantee about arbitrary merge operations.

09 · Object-backed links

Sometimes a relationship deserves its own object

Employees work on ventures or teams. A staffing assignment connects the two and records metadata, such as when the employee worked on the venture. In some workflows, users only want the set of teams an employee has worked on. In others, they need the assignment object and its dates to determine the current team.

Detailed view

Employee → Venture Staffing assignment → Venture

Simple view

Employee → Venture, backed by that same assignment object

Object-backed link types support the two views. The relationship can appear as a direct link when the intermediate object is not useful to the task, while remaining traversable as an object when its semantics matter.

The ontology therefore avoids a false choice between “everything is an object” and “everything is a bare edge.” The same relationship can carry rich meaning internally and offer a simple navigation surface externally. Palantir's link overview provides the underlying distinction between object and relationship definitions.

Editorial synthesis

Why this matters for an agentic platform

The talk's relevance to agents is not a new persona-prompt framework. It is the environment in which agents reason and act. Canonical objects reduce ambiguity. Interfaces reduce repeated workflow definitions. Structs attach context to values. Derived properties make domain logic reusable. Security decides which observations can be seen.

For a BA designing business flows, the first questions are therefore semantic: What entities exist? Which relationships have dates or state? What is authoritative? Which value is a summary of other facts? Who can view or change each part? Only after those decisions should the platform expose readable tool contracts or workflow steps.

This does not mean buying Palantir is required to apply the ideas. The design principles are portable. The exact primitives, security behavior, and application integrations described in the presentation are product-specific.

Useful separation

The ontology describes the business and its available operations. An agent decides how to use that model for a task. A prompt alone should not become the authority for identity, data freshness, permissions, or irreversible actions.

Takeaways

Ten ideas worth keeping

  1. Model real business concepts, not source-table quirks.
  2. Operational semantics should exist before AI automates them.
  3. Use common interfaces when workflows share meaningful capabilities.
  4. Protect stable contracts while allowing extensions.
  5. Keep compound values and their metadata together.
  6. Reducers select representative values; main fields expose their semantic core.
  7. Derived properties reduce brittle duplication of related facts.
  8. Security may need to operate below the object or property level.
  9. Entity resolution should preserve provenance and original permissions.
  10. A relationship can be both a navigable link and a first-class object.
