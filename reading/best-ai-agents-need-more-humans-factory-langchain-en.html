The Best AI Agents Need More Humans Than You Think

Eno Reyes of Factory argues that production AI agents are not just better chatbots. They are workflow systems: signal pipelines, product judgment, model-independent harnesses, deterministic feedback, validators, and humans who keep tightening the loop.

Source: LangChain Guest: Eno Reyes, Factory Length: 77 minutes Transcript: 15.9k words

Executive Summary

The conversation's strongest point is that autonomy only becomes useful when it is wrapped in a system that can absorb business signals, translate them into verifiable work, route the right model, and keep humans in the parts where taste, prioritization, risk, and accountability still matter.

  • A "software factory" is best understood as a signal-to-deployed-code operating loop, not a fully hands-off robot team.
  • Humans remain central because they decide which changes are worth making, refine product opinions, and design the deterministic feedback that lets agents continue.
  • The durable advantage is the harness: workflow opinions, tools, validation, memory structures, routing, observability, and evals that work across models.
  • Long-running agent work needs structured outcomes and validators. Without explicit verification, agents can appear busy while drifting away from the real target.
  • For enterprise platforms, model routing and cache-aware cost control are platform primitives, not afterthoughts.

1. The Central Thesis

The episode pushes back against the fantasy that the best agents remove people from the process. Factory's view is more practical: agents can perform large amounts of software work, but the most valuable systems still need humans to define the work, judge whether it should happen, shape the operating rules, and improve the harness after every failure.

The important shift is not "humans stop coding." It is "humans move higher in the loop." People become product stewards, architecture stewards, process engineers, context curators, and validation designers. The agent does more execution, but the human becomes more responsible for the system of execution.

My read: the video is not anti-agent. It is anti-magic. The real product is the loop around the model.

2. Software Factory: Signal to Deployed Code

Factory describes its long-term product vision as a "software factory" that runs continuously and produces desired software. The less sci-fi version is more useful: create a structured path from business signals to shipped changes. Signals come from customers, Slack, support threads, GitHub issues, bug reports, telemetry, error systems, internal conversations, and public feedback.

The hard part is not collecting signals. The hard part is deciding which signals matter, translating them into a product opinion, and creating work objects that agents can execute without losing intent.

  1. 1 Signals Customer Slack, issues, bugs, telemetry, sales calls, support, docs gaps.
  2. 2 Priorities Humans and agents consolidate patterns into product-level guidance.
  3. 3 Specs Desired outcomes become scoped plans, tasks, constraints, and acceptance criteria.
  4. 4 Agents Workers use tools, code context, skills, and tests to implement changes.
  5. 5 Validation Tests, review, security, browser checks, metrics, and policy gates verify outcomes.
  6. 6 Learning Failures update rules, docs, workflows, skills, model routing, and future specs.

Platform implication: do not start by asking BA users to "make an agent." Start by asking them to capture signal, business intent, decision rules, acceptance criteria, and exceptions. The platform can then compile that into agent instructions, tools, and validation plans.

3. Why More Humans Are Needed

The video argues that as agents become more capable, the bottleneck moves from typing code to knowing what should be built and how the system should behave. Humans still matter because product taste, architectural judgment, organization policy, and risk appetite are not automatically available to the model.

Product Steward

Owns customer pain, priority, user experience, scope, and what should not be changed. This is a more technical version of product work because the person must reason about agent-executable specs.

Architecture Steward

Defines constraints, service boundaries, ownership rules, performance goals, and codebase standards so the agent does not solve locally while damaging the system.

Loop Engineer

Improves lint rules, type rules, tests, evals, traces, prompts, tools, and policies after each agent mistake. This role turns failures into better future execution.

Factory gives an example of a human engineer spending significant time building static checks, lint rules, and type checks so agents cannot repeat complex mistakes. That is the pattern: instead of fixing every mistake by hand, humans create feedback systems that make entire classes of mistakes harder.

4. Harness Is the Product Layer

A model-independent harness is one of the strongest themes. In the transcript, the guest argues that the harness captures workflows, tool use, validation patterns, and model-specific handling in a way that can be reused across frontier models, open models, and cheaper specialized models.

This matters because enterprises pay real inference costs. A consumer product might subsidize expensive usage, but a company deploying agents across thousands of employees needs quality, cost, routing, visibility, and governance. The harness becomes the control plane.

Layer What It Does Why It Matters
Prompt and persona Defines role, scope, tone, operating rules, and decision boundaries. Prevents "generic helper" behavior when the agent needs domain-specific judgment.
Tools and MCP Expose systems of action: repos, browsers, tickets, docs, databases, APIs, and internal services. Turns the agent from advisor into operator, while keeping permissions explicit.
Skills Package reusable procedures, examples, checklists, templates, and tool usage recipes. Lets non-engineers compose repeatable capabilities without rewriting prompts every time.
Validation Runs deterministic checks, tests, policy gates, rubrics, and human approvals. Creates trust by forcing the agent to prove outcomes instead of only narrating progress.
Routing Chooses models based on task type, context state, cache, budget, and quality target. Controls enterprise cost without asking every user to understand the model landscape.

A useful design principle for your platform: keep persona prompts small and stable, put changing procedures into skills, put external actions behind tools, and put acceptance criteria into validators.

5. Signals, Product Opinion, and the 2,000-Line Rule

The conversation describes a product-level prioritization document that is short enough to fit into context. It starts with agent-written material, but humans consolidate and refine it. This is important because agents can gather scattered information, but humans must decide which patterns represent product truth.

For an enterprise agentic platform, this suggests a design pattern: separate raw evidence from curated policy. Raw evidence can be long, messy, and constantly updated. The curated policy should be compact, opinionated, versioned, and easy for agents to load.

Raw Signal Store

Slack threads, tickets, CRM notes, bug reports, calls, user feedback, analytics, and logs.

Curated Product Memory

Priorities, target users, anti-goals, standards, examples, escalation rules, and release policy.

Work Object

One specific desired outcome with scope, constraints, dependencies, owner, and validation plan.

Feedback Update

When work fails or surprises users, update the curated policy and skill library.

6. Workflows Beat Prompt Tricks

The guest repeatedly frames application-layer value as encoding workflow opinions deeper and deeper. This is a mature view: the advantage is not one perfect mega-prompt, but an evolving system of steps, tools, checks, examples, and learned operating rules.

The video also notes that model differences now feel less like tiny comma-sensitive prompt quirks and more like workflow/tool preference differences. One model may prefer a patch-style edit tool. Another may perform better with a different tool schema, tool description, or context shape. The harness should observe those differences and adapt.

Pattern to copy

  • Define the workflow as steps and artifacts, not just a paragraph of instructions.
  • Attach required tools to the workflow, not to the agent identity only.
  • Version skills independently so BA users can improve a process without editing the master agent.
  • Record examples of good and bad runs so the harness can learn from operational reality.

7. Memory, Auto Wiki, and Knowledge Structures

The discussion separates several things that are often called "memory." Some memory is learned behavior from training or fine-tuning. Some is durable system-of-record context, such as files, wikis, knowledge graphs, and style guides. Some is user preference. Some is a reusable procedure, which is better named a skill.

Factory's Auto Wiki is framed as especially useful for humans. It can explain a codebase, show history or "lore," and help new hires understand how a system works. The surprising point is that wikis may help people more than agents, because agents are already good at searching code, while humans need compressed narratives and canonical structure.

System Memory

Architecture docs, canonical workflows, business rules, service ownership, and domain models.

Preference Memory

Style, tone, review preferences, product taste, and company-specific definitions of quality.

Skill Memory

Reusable how-to procedures with examples, tool requirements, failure modes, and validation rules.

Run Memory

Traces, corrections, failed validations, routing choices, and lessons from completed tasks.

For your BA-facing platform, this suggests avoiding the vague label "memory" in the UI. Use concrete names: Business Rules, SOP, Skill, Product Policy, Persona, Tool Permission, Run History, and Validation Evidence.

8. Missions: Long-Running Agents Need Validators

"Missions" are Factory's approach for larger, verifiable work. The system decomposes a big objective into structured work, defines skills, runs workers with fresh context, validates their outputs, and then consolidates progress across milestones.

Orchestrator

Turns the goal into structured outcomes, hypotheses, task units, skills, dependencies, and validation plans.

Workers

Start with fresh context, receive a task and skill set, perform the work, and avoid cross-run contamination.

Validators

Check deterministic evidence, write tests, use browser actions, apply rubrics, and decide whether work is complete.

The best line of thinking here is that an agent should not be allowed to finish just because it says it is done. It should finish when each important validation has passed or when a clear human escalation is triggered.

Agent readiness means deterministic feedback

  • Unit, integration, end-to-end, fuzzy, and coverage tests.
  • Reproducible dev environments and flakiness detection.
  • Logging, metrics, naming, AST, ownership, and file-structure checks.
  • Browser or computer-control checks for flows that cannot be tested only through code.
  • Human approval for product risk, legal risk, security risk, or ambiguous user experience judgment.

9. Tokenomics and Model Routing

The episode treats tokenomics as one of the biggest enterprise issues. Long missions can be expensive, but the bigger waste may come from broad enablement: thousands of people using expensive frontier models for work that a cheaper or open model could handle.

Factory's answer is auto model routing. The admin chooses a quality/cost tradeoff, and the harness learns which model to use for which task distribution. The guest says this can produce large savings, and argues that model names should often be hidden from users because visible names create bias toward frontier models.

Routing Decision What the Harness Must Know Good Behavior
Start cheap or strong Task type, risk, complexity, historical success, expected cost. Use cheaper models for routine work, stronger models for ambiguous or high-risk work.
Upgrade mid-run Progress state, failures, distance to completion, cache state, validation results. Upgrade early when the agent is clearly stuck, not after burning tokens.
Finish before switching Whether the agent is near completion and whether switching would break useful context. Finish cheaply when close to done; avoid needless compaction or cache loss.
Parallelize Cost tolerance, uncertainty, need for diversity, synthesis quality. Use parallel agents selectively because gains can be unclear and cost can jump quickly.

Key design call: model routing belongs inside the agent harness, not only in a generic LLM gateway. The gateway sees requests. The harness sees task progress, validation state, tool history, cache state, and budget.

10. Evals Are a Living Product System

Factory describes an eval-driven culture with many small regression suites, not only large public benchmarks. Some evals check prompt caching. Some check compaction. Some check model routing. Some are larger benchmarks for code migration or code review.

The most practical insight is that benchmarks expire. The guest gives a rough shelf life of three to six months before a benchmark becomes less useful as a product-improvement signal and more useful as a regression test. Public benchmarks can also shape products in unhealthy ways if every vendor optimizes around the same narrow tasks.

Regression Evals

Small, fast suites that protect prompt caching, compaction, routing, and tool behavior.

Workflow Evals

Longer tasks that test whether the agent can complete multi-step work with tools and validators.

Rubric Evals

Graded quality checks when binary pass/fail does not capture usefulness.

Benchmark Evals

Industry or internal benchmarks, useful but perishable. Harbor is mentioned as a strong format.

11. What This Means for Your Agentic AI Platform

For the BA-side platform you have been describing, the video supports a component model where business users create structured operating objects, not raw prompts. The platform should compile those objects into agent behavior, tool permissions, validation plans, and execution flows.

BA Artifact Platform Compilation Runtime Output
Business Flow Markdown Steps, decision points, required evidence, exception paths, and approvals. Orchestrator plan plus worker tasks and validation checkpoints.
Persona Prompt Role, boundaries, tone, escalation rules, and forbidden actions. Stable agent identity that does not carry too much procedure.
Cognitive Skill Reasoning recipe, examples, classification rules, rubrics, and output format. Reusable thinking pattern for analysis, planning, triage, or explanation.
Actionable Skill Tool requirements, permissions, preconditions, side effects, rollback, and verification. Safe operator capability through MCP tools or internal APIs.
Validation Policy Tests, deterministic checks, evidence requirements, LLM-as-judge rubrics, human gates. Completion criteria that agents must satisfy before the task is accepted.

Recommended framework

  • Master Agent: owns goal intake, planning, routing, delegation, memory selection, and escalation.
  • Sub-Agent: owns a bounded task type with its own persona, skills, tools, and validators.
  • Skill: reusable procedure. Cognitive skills reason. Actionable skills operate tools.
  • Tool/MCP: external capability with permission, schema, audit log, and failure handling.
  • Flow Markdown: business-readable source of truth that compiles into agent runtime instructions.
