Key Takeaways

บทเรียนหลักจากวิดีโอ

นี่คือสาระที่ควรจำจากวิดีโอ ถ้าต้องเอาไปใช้กับงานจริงทันที

  1. เริ่มจาก evals ก่อนแก้ prompt ถ้าไม่มีชุดทดสอบ คุณจะไม่รู้ว่าการแก้ prompt ดีขึ้นจริงหรือแค่รู้สึกว่าดีขึ้น
  2. แยก failure mode ให้ชัด ปัญหาอาจเกิดจากโมเดล “ทำต่างจากเดิม” หรือโมเดล “ไม่มีความสามารถพอ” สองกรณีนี้แก้คนละแบบ
  3. prompt hygiene ช่วยได้ทันที ลบข้อมูลเก่า, แยก role, policy, guideline, tone และ data ออกจากกัน เพื่อให้โมเดลรู้ว่าข้อมูลไหนคืออะไร
  4. อย่าใช้ ban list ยาวเพื่ออุดรู prompt ที่เต็มไปด้วยข้อห้ามเฉพาะจุดมักทำให้โมเดล overfit และเกิด regression ในสถานการณ์อื่น
  5. instruction ไม่ได้เพิ่ม capability บอกโมเดลว่า “คำนวณให้ถูก” ไม่ได้ทำให้โมเดลคำนวณเก่งขึ้น ถ้างานต้องแม่น ควรให้ tool
  6. ให้ trade-off ครบทั้งสองด้าน ถ้าบอกแค่ “อย่า escalate เพราะแพง” โมเดลจะเลี่ยง escalation เกินไป ต้องบอก cost ของการตอบผิดด้วย
  7. งานซับซ้อนควรแยกเป็นหลายขั้น แทนที่จะให้ prompt เดียวทำทุกอย่าง ให้แยกเป็น generate, evaluate, repair เพื่อให้ตรวจและปรับงานได้เป็นระบบ
Case Study 1

เมื่อ prompt เดิมเริ่มพังหลังเปลี่ยนโมเดล

ตัวอย่างแรกคือบอท customer support ของบริษัทโทรคมนาคมสมมติชื่อ Meridian Mobile prompt เดิมผ่านเคสง่าย แต่เริ่มพลาดใน edge cases หลังย้ายโมเดล

Step 1

วัดด้วย eval suite

ใช้ test cases ที่มีทั้ง control case, edge case และเคสที่โมเดลควรรู้ว่าเมื่อไรต้องส่งต่อมนุษย์

Step 2

จัด prompt ใหม่

แยก role, guideline, policy, tone และ customer context ด้วยโครงสร้างที่ชัด เช่น XML tags

Step 3

ลบ patch เก่าที่ไม่จำเป็น

หลาย prompt มีคำสั่งป้องกันปัญหาจากโมเดลรุ่นก่อน เมื่อเปลี่ยนโมเดลแล้ว patch เหล่านี้อาจกลายเป็นตัวทำให้พลาด

Step 4

เพิ่ม tool เมื่อโมเดลต้องคำนวณ

ในเคส proration bill โมเดลไม่ควรคิดเลขเอง แต่ควรเรียก calculate proration tool ที่ระบบเตรียมไว้

Step 5

ทำให้ objective สมดุล

ถ้าจะให้โมเดลตัดสินใจเรื่อง escalation ต้องบอกทั้งต้นทุนของการ escalate และต้นทุนของการตอบผิด

บทเรียนสำคัญ: prompt ที่ดีไม่ได้แค่ “สั่งให้โมเดลทำ” แต่ต้องออกแบบสภาพแวดล้อมให้โมเดลมีข้อมูล เครื่องมือ และเป้าหมายที่ถูกต้อง

Case Study 2

เมื่อสร้าง agent ใหม่จากศูนย์

ตัวอย่างที่สองคือ agent สำหรับจัดตารางพนักงานร้านค้าปลีก งานนี้มีกฎแข็ง เช่น availability, จำนวนคนต่อ shift, และข้อจำกัดเฉพาะ จึงเหมาะกับการวัดผลแบบ programmatic

วิธีที่ลองแล้วมีข้อจำกัด

prompt ง่ายกับโมเดลเล็กทำพลาดหลายเคส ส่วนโมเดลใหญ่ช่วยลดข้อผิดพลาดแต่ยังไม่พอ การเปิด reasoning/adaptive thinking ทำให้ผ่านมากขึ้น แต่แลกกับ token และ latency สูง

วิธีที่เวิร์กกว่า

แยกงานเป็น generate, evaluate, repair loop ให้โมเดลสร้าง draft ก่อน จากนั้นตรวจ violation แล้วค่อยซ่อมเฉพาะจุด วิธีนี้คุมคุณภาพได้ดีและยืดหยุ่นกับ soft constraints ที่เปลี่ยนตามเคส

Generate

สร้างคำตอบหรือแผนแรกให้ครบก่อน โดยไม่พยายามยัดทุกกฎไว้ใน prompt เดียวจนหนักเกินไป

Evaluate

ตรวจผลลัพธ์กับกฎที่ต้องผ่าน และรายงาน violation พร้อม evidence ให้ชัด

Repair

แก้เฉพาะ violation ที่พบ แทนการให้โมเดลเริ่มคิดใหม่ทั้งหมดทุกครั้ง

Playbook

ถ้าจะเอาไปใช้จริง ให้ทำตามลำดับนี้

ลำดับนี้คือแกนของวิดีโอในรูปแบบที่นำไปใช้กับงาน AI product หรือ internal tools ได้ทันที

01

นิยาม evals

กำหนดเคสที่ต้องผ่าน ทั้งเคสปกติ เคสที่เคยพัง และเคสที่ต้อง refuse หรือ hand off

02

รัน baseline

ดูว่า prompt ปัจจุบันพลาดตรงไหน อย่าเพิ่งแก้ก่อนรู้ failure mode

03

ทำ prompt hygiene

ลบของรก แยกส่วนของ prompt ให้ชัด และทำให้ output format ตรวจได้ง่าย

04

แก้ทีละ failure mode

อย่าแก้กว้างเกินไป ให้เปลี่ยนทีละจุดแล้วกลับไปวัด evals ใหม่

05

เพิ่ม tools หรือ workflow

ถ้างานต้องการความแม่นยำเชิงระบบ เช่น คำนวณ ตรวจตาราง หรือ enforce กฎ ให้ใช้ tool หรือ loop

Checklist

Checklist สำหรับ prompt ที่พร้อมใช้งานจริง

  • มี eval suite ที่ครอบคลุม control case, edge case และ boundary case
  • แยก role, policy, guideline, data, tone และ output format อย่างชัดเจน
  • ลบ instruction เก่าที่เป็น patch ของโมเดลรุ่นก่อน หากไม่มีเหตุผลแล้ว
  • ไม่มี ban list ยาวที่แก้ปัญหาเฉพาะจุดแต่สร้าง regression ใหม่
  • งานที่ต้องคำนวณหรือ enforce กฎใช้ tool หรือ programmatic checker
  • objective สำคัญถูกเขียนแบบสมดุล ไม่บอก trade-off ด้านเดียว
  • งานซับซ้อนถูกแยกเป็นหลายขั้นที่ตรวจและซ่อมได้
