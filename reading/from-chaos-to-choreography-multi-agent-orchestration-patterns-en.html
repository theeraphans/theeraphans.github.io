Production War Story

The bug was not in the model. It was in the architecture.

The talk starts with a credit-decisioning system. The first credit-score agent worked fine in production. Then the team added income verification, risk assessment, fraud detection, and final approval agents. Within days, about 20% of decisions had incorrect risk ratings.

What happened

One agent wrote the latest score

The credit-score agent wrote a score of 750 to PostgreSQL for a customer.

What went wrong

Another agent read stale cache

The risk agent read 680 from a cache that had not been invalidated after the database write.

Business impact

The system made wrong approvals

Customers who should have been flagged were approved because state coordination was broken.

This is the most important lesson for platform builders: multi-agent failure often looks like an AI issue, but the root cause is usually coordination, state, or infrastructure.

Complexity Curve

Five agents are not five times harder. They create many relationships.

One agent has no coordination problem. Two agents create at least one relationship. Five agents create many possible dependencies, handoffs, race conditions, and failure paths. Every connection becomes a possible stale read, duplicate event, missing event, contract mismatch, retry storm, or partial failure.

One agent Prompt, tools, retrieval, and output are mostly local to one runtime.
Five agents Agents now depend on each other for data, timing, and state transitions.
Shared resources Databases, caches, APIs, queues, and memory become coordination surfaces.
Failure modes Timeouts, retries, stale data, and crashes can cascade across the workflow.
System design Reliability comes from architecture, not from adding more agent prompts.

When you add agents, you are building a distributed system. You need distributed-system thinking.

Coordination Patterns

Choreography gives autonomy. Orchestration gives control.

The first major architecture decision is how agents coordinate. Choreography is decentralized and event-driven. Orchestration uses a central coordinator as the single source of truth. Neither is universally better; the right choice depends on workflow complexity, autonomy needs, debugging requirements, and rollback needs.

Pattern How it works Use when Main risk
Choreography Agents publish and subscribe to events through a message bus. No central coordinator owns the full flow. The workflow is naturally event-driven, agents need autonomy, and new agents are added frequently. Debugging can become detective work unless event tracing and delivery guarantees are strong.
Orchestration A workflow orchestrator calls agents directly, manages parallelism, stores state, retries, and logs every step. The workflow has complex dependencies, rollback requirements, audit needs, or low tolerance for autonomy. The orchestrator can become a bottleneck if it is not designed and scaled carefully.
Hybrid Critical flow is orchestrated, while some independent activities use events and saga-style compensation. The workflow is complex but some agents still need autonomy or asynchronous collaboration. Requires clear boundaries between event-driven behavior and orchestrated checkpoints.

The talk recommends orchestration for regulated domains like financial services because auditability, rollback, and exact execution order matter more than maximum agent autonomy.

State Management

Shared mutable state is where multi-agent systems quietly break.

The speaker warns against multiple agents reading and writing the same records directly. Defaults are dangerous: databases have locks and isolation levels, but teams must use them correctly. The recommended pattern is immutable state snapshots with versioning and schema validation at each handoff.

Agent A Produces state version 1 and seals it as immutable.
Contract check Validates that output matches the next agent's input schema.
Agent B Receives version 1, cannot mutate it, and produces version 2.
Append-only log Stores each state version as a new row rather than updating the old one.
Replay and debug Trace bad output back through versions to find where it entered the system.
  • Never treat shared state as casual scratch space. Race conditions and lost updates appear quickly.
  • Make every handoff versioned. Each agent should know exactly which state version it received.
  • Enforce data contracts at the boundary. Catch low-confidence or malformed outputs before they move downstream.
  • Prefer append-only state history. It gives auditability, replay, rollback, and root-cause analysis.
Failure Recovery

Agents will fail. Design the recovery path before they do.

Timeouts, rate limits, crashes, and flaky models are guaranteed. The talk highlights two production patterns from distributed systems: circuit breakers for failing fast and preventing cascading failures, and compensation or saga patterns for undoing partial work.

Circuit breaker

Protect the workflow from repeated agent failure

If an agent fails repeatedly, open the circuit and stop sending traffic for a timeout window. Then test one request in half-open mode before returning to normal.

Compensation

Undo already-completed steps when a later step fails

Each agent exposes execute and compensate methods. If Agent C fails, the orchestrator walks backward and compensates Agent B, then Agent A.

This is unglamorous infrastructure, but it is what separates demos from systems that survive 2:00 a.m. failures.

Reference Architecture

The production shape is orchestrator, governed agents, versioned data, and traces.

The Databricks example places a workflow orchestrator at the center. Agents do not call each other directly. The orchestrator stores state versions, calls agents, manages parallelism, logs observability data, triggers compensation, and becomes the single source of truth for the workflow.

Orchestration LangGraph with Mosaic AI Agent Framework manages the workflow graph, order, state, retries, and compensation.
Agent registry Unity Catalog functions, models, and schemas make agents discoverable, governed, versioned, and auditable.
Serving controls Model Serving, Function Serving, and AI Gateway enforce timeouts, retries, rate limits, and circuit breaker policies.
Data and telemetry Delta Lake stores immutable state versions, while MLflow traces calls, latency, inputs, outputs, token usage, and evals.
  • The orchestrator owns coordination. Agents focus on their task and return structured outputs.
  • State versions are rows, not overwrites. Every step can be replayed and audited.
  • Every call is traceable. Inputs, outputs, latency, token usage, failures, and circuit transitions are visible.
  • Agent assets are governed. Models, functions, schemas, access control, lineage, and audit trails live in a central catalog.
Platform Takeaways

What this means for your Master Agent, Sub-Agent, Skill, and MCP platform

This talk is extremely relevant to a BA-buildable agentic AI platform. It argues that the platform should not only help users create agents and prompts. It should help them design reliable distributed workflows with typed contracts, versioned state, visible traces, recovery policies, and governance.

  • Make coordination pattern a first-class choice. A Flow Markdown should declare choreography, orchestration, or hybrid, not hide it in prose.
  • Represent every Sub-Agent handoff as a contract. Include input schema, output schema, quality gates, confidence thresholds, and rejection behavior.
  • Use immutable mission state. Each agent should append a new state version instead of mutating shared state.
  • Add circuit breaker policy to every actionable skill. Timeouts, retry limits, rate limits, fallback behavior, and human escalation should be configurable.
  • Require compensation for side-effecting tools. If a tool writes, sends, updates, or approves, the platform should ask how to undo or reconcile it.
  • Expose trace views to BA users. Show which agent ran, why it was chosen, what state version it used, which tools it called, and what it produced.
  • Separate cognitive skills from actionable skills. Cognitive skills transform information; actionable skills need tool contracts, permissions, circuit breakers, and compensation.
  • Govern agents like production assets. Persona prompts, schemas, tools, MCP servers, versions, owners, permissions, and evaluation results should be cataloged.
  • Prefer the simplest reliable architecture. A single agent is fine for one job. Multi-agent only pays off when role separation reduces overload more than coordination increases risk.
