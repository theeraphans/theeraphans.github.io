Build Durable Agents With Eve

A detailed guide to Andrew and Casey's Vercel workshop on Eve, the open agent framework: filesystem-first agents, channels, tools, connections, approvals, evals, observability, sandboxes, workflows, and what this architecture means for enterprise agent platforms.

Source: Vercel Video: Ship 26 NYC - Workshop - Build an Agent with Eve Length: about 40 minutes Transcript: 403 caption rows, about 6,956 words Framework status: beta, per official docs

Executive Summary

Eve is Vercel's filesystem-first framework for durable backend AI agents. The pitch is that an agent should be inspectable as a directory of files, but still run with production primitives such as durable sessions, sandboxed compute, channels, approvals, observability, evals, and deployment to Vercel.

  • Authoring model: put instructions, tools, skills, channels, connections, subagents, schedules, and sandbox files under an agent/ directory.
  • Runtime model: Eve compiles that filesystem contract into a deployable app that runs on Vercel Functions and uses Vercel Workflows for durable session state.
  • Interaction model: the same agent can be reached through HTTP, Slack, web UI, WebSocket, or other channels, while sessions and streams stay channel agnostic.
  • Enterprise model: approvals, scoped tools, observability, evals, sandbox isolation, user identity, and code-first extensibility make Eve closer to an agent platform substrate than a single prebuilt assistant.

Central Thesis

The workshop is not only a product demo. It presents a design philosophy for agent platforms: make the agent readable as files, make the runtime durable by default, and hide the generic harness plumbing that every serious agent needs.

Andrew describes the simplest Eve agent as just an instructions file and runtime configuration, then progressively adds channels, a Slack deployment, OpenAPI connections, custom tools, approvals, evals, channel permissions, multi-tenant memory, hooks, sandbox execution, and long-running workflow semantics.

The interesting thing about Eve is not that it can call an LLM. It is that the boring production pieces become first-class framework concepts instead of one-off glue code.

Why Eve Exists

Most agent demos start with a model call and then slowly accumulate infrastructure: a web route, a Slack integration, a tool registry, a sandbox, trace logging, retries, persistence, approvals, evals, and deployment. Eve reverses that. It assumes those pieces are part of the agent platform, not extra work for every team.

The official docs describe Eve as a filesystem-first framework for durable backend AI agents. You define files under agent/, Eve discovers and validates them, compiles a manifest, and serves the runtime as a deployable app. The docs also note that Eve is currently beta, so APIs and behavior may change before general availability.

Practical interpretation: Eve is trying to be the agent equivalent of a full-stack web framework: conventions over custom wiring, but still code-first when teams need control.

The Filesystem Is The Agent Interface

The main authoring surface is a folder. The workshop shows that by default an Eve app has an agent/ directory, and an agent can be just an instructions file. The official docs expand the structure into a conventional set of folders.

Path What it means Platform value
agent/instructions.md The always-on prompt or persona. BA and domain owners can read the standing rules.
agent/agent.ts Runtime config such as model and options. Engineering controls the model and runtime choices.
agent/tools/*.ts Typed functions the model can call. Tools become inspectable, testable, and permissionable.
agent/skills/* On-demand procedures or domain knowledge. Longer instructions stay outside the always-on prompt.
agent/subagents/* Child agents for focused tasks. Delegation becomes explicit rather than hidden inside prompts.
agent/channels/* Entry points such as Slack or HTTP. The same core agent can live in multiple business surfaces.
agent/connections/* Typed integrations with external services. Credential handling and provider configuration stay outside model context.

Workshop Walkthrough

The live demo begins by scaffolding a new Eve app with the CLI. After authentication with a Vercel project and AI Gateway, the agent can be used from the command line. It is initially a generic assistant, but already has framework-level features such as web search and tool-call presentation.

Then the demo adds Slack as a channel. Eve uses Vercel Connect to connect the Slack workspace, deploys the agent, and lets the audience interact with it by mentioning the Slack bot. When a tool call fails during the live demo, Andrew jumps to Vercel's Agent Runs view to inspect the session, showing the observability story in practice.

Channels Are Runtime Entry Points

Eve's channel concept is one of the strongest parts of the model. A channel is how users talk to the same agent runtime: terminal, HTTP, Slack, web UI, WebSocket, and potentially other surfaces. The channel owns authentication, routing, and platform-specific presentation.

In Slack, Eve can show thinking indicators, tool calls, and native interaction elements in a Slack-appropriate way. The workshop also clarifies that adding a Slack channel does not automatically give the agent permission to post anywhere in Slack. The channel contract defines how agent events render into Slack; Slack write actions are separate tools and permissions.

Design lesson: channels should not be confused with tools. A channel is where the conversation happens. A tool is an action the agent can choose to execute.

Tools And Connections

The demo then adds an OpenAPI connection for weather data. A coding agent reads the bundled Eve docs inside node_modules/eve/docs, adds a weather connection file, and the Eve agent immediately uses the connection to answer weather questions.

The Q&A distinguishes tools from connections. A normal tool is a one-to-one function. A connection is a typed integration with an external service, intended to keep provider details and credential access outside the prompt and tool internals. For delegated user or team credentials, the docs point to pairing Eve tools with Vercel Connect.

Primitive Use it for Example from workshop
Connection Structured external API integration with provider-specific setup. OpenAPI weather connection.
Read tool Low-risk retrieval from a data source. MongoDB query tool.
Write tool Mutations that may require human approval. MongoDB mutate tool with approval required.
Framework tools Standard harness operations like file reads, writes, web fetch, web search, glob, and grep. Default tools that can be disabled or replaced.

Human Approval Is A First-Class Control

When Andrew shows the MongoDB example, he separates query from mutate. The mutation tool requires approval, so it will not run until a human approves the action. This is a small detail, but it is the shape of production agent design: reads and writes should not share the same trust boundary.

Approvals also flow through channels. In the terminal, a question or approval can appear as a TUI prompt; in Slack, the same interaction can be presented as a native Slack experience. The framework owns the channel-specific presentation so every team does not have to rebuild approval UI from scratch.

Enterprise rule: any tool that mutates data, sends messages, changes configuration, spends budget, or exposes sensitive information should have an explicit approval policy.

Evals Close The Feedback Loop

When asked how Eve improves agents over time, Andrew points to evals as the starting point. If a business will iterate seriously on an agent, it needs to know the current state, then compare new behavior as instructions, tools, skills, and models change.

The demo asks a coding agent to write an eval for weather behavior. Eve's eval API lets developers interact with the agent similarly to manual CLI testing, but automate the assertions. It supports deterministic checks such as "does the output include NYC" and semantic checks through LLM-as-judge. Andrew also mentions sending evals to providers such as Braintrust.

Regression

Does a new instruction or tool break previous behavior?

Tool use

Does the agent choose the correct connection or tool?

Policy

Does it ask for approval before risky operations?

Semantics

Does the answer mean the right thing, not merely match a string?

Observability Out Of The Box

The workshop's failed Slack demo is useful because it shows the debugging surface. A run can be opened in Vercel, then inspected for messages, tool calls, reasoning, timings, and token usage. The official docs call Agent Runs the primary observability surface and say every Eve project gets it automatically without a separate instrumentation file.

This matters because agent failures are often not normal request failures. They can be tool failures, poor skill selection, bad context, invalid arguments, permission problems, or model behavior. A production platform needs turn-level inspection, not only application logs.

Observation target Why it matters Platform implication
Sessions and turns Shows what interaction triggered the agent and how the conversation progressed. Support teams can reproduce user-visible behavior.
Tool calls Shows what the agent attempted and what failed. Tool owners can debug contracts and permissions.
Reasoning and traces Shows why the agent selected an action or skill. Reviewers can detect policy or prompt drift.
Token usage Shows input, output, cached token, and cost patterns. Platform teams can manage budget and optimize context.

Sessions, Streams, And Persistence

The Q&A explores message persistence and channel ownership. Eve has sessions and streams. A session is channel agnostic, and channels decide how to present it. Andrew describes Vercel's internal data agent, where most invocations happen in Slack but a button can open the same session in a web view.

Official docs define a session as the durable conversation or task started by a channel or HTTP request. Each user message or external event creates a turn. During a turn, the agent can call tools, load skills, read and write sandbox files, delegate to subagents, and stream lifecycle events back to the client.

Design lesson: persistence should belong to the task/session, not to any one UI channel. That lets Slack, web, HTTP, and future channels resume the same work safely.

Determinism Where It Matters

A question asks how Eve handles less deterministic use cases that cross-reference multiple connections. Andrew's answer is pragmatic. He believes frontier models are good at following plain-English instructions, so teams should try that first, then add evals. But Eve also offers ways to regain determinism when needed.

The workshop mentions output schemas, TypeScript SDK surfaces, subagents, and possible workflow primitives that mix agent calls with predetermined output. The broader lesson is not to force every agent into a rigid workflow, but to make deterministic boundaries available where the business needs them.

Plain English first

Use instructions and skills when the model can reasonably follow the procedure.

Output schema

Ask the agent to return typed data when downstream systems need structure.

Workflow steps

Use predetermined steps when compliance, approvals, or deterministic outcomes matter.

Skills And Subagents

Eve separates skills from subagents. A skill is larger procedural or domain context loaded into the running agent only when relevant. A subagent is a child agent with separate conversation history and state, useful for narrower tools, specialist identity, or parallel delegation.

This distinction is useful for your platform. A skill changes what the current agent knows or how it should behave. A subagent creates a separate worker with its own role, tools, memory boundary, and outputs. Mixing those concepts creates vague agent architecture.

Concept Use when Do not use when
Skill The same agent needs a repeatable procedure or domain guide. You need isolated context, separate tools, or parallel work.
Subagent A focused task deserves its own identity, state, or tool boundary. A short instruction would be enough.
Tool The agent needs a typed action with inputs and outputs. You are only adding knowledge or process instructions.

Multi-Tenant Memory

When asked how Eve differs from Claude Tag-like Slack agents, Andrew says Eve is code-first and intended for building an agent for your business. He contrasts a single deployed assistant with a programmable framework that can support multi-tenant APIs, per-user skills, and custom memory behavior.

The workshop references a guide for multi-tenant memory where skills could be defined per invoking user and stored in a database. That is a high-leverage idea: memory should not be a single global blob. It needs tenant, user, channel, permission, and data-retention boundaries.

Platform lesson: for enterprise agents, memory must be scoped by who is asking, which workspace they are in, what data they are allowed to access, and whether the memory is personal, team, or global.

Harness Extensibility And Hooks

Eve owns the default harness, but it exposes extension points. The workshop mentions default harness features such as read file, write file, web fetch, web search, glob, and grep. Teams can disable or replace default implementations, but Andrew recommends leaning heavily on evals when doing so.

Hooks let developers plug into harness events such as compaction, pre-tool calls, and post-tool calls. That gives teams a way to build around the harness without replacing it wholesale. Andrew notes that owning the harness enables dynamic step boundaries, workflows, stateless serverless execution, and cross-function continuation.

Sandbox And Durable Workflows

Every Eve agent has a sandbox. Locally, the workshop says it uses Docker; on Vercel, it uses Vercel Sandbox. The official docs describe the sandbox as an isolated bash-style compute environment with its own filesystem, targeted by framework tools and authored tools. On Vercel, the sandbox can run in ephemeral microVMs for untrusted or model-generated commands.

For long-running tasks, Eve relies on Vercel Workflows under the hood. Andrew explains that because the harness is stateless, a turn can dispatch to a new serverless function at tool-call boundaries and pick up where it left off. This is how Eve can avoid thinking in terms of one long-running process stuck inside a single function timeout.

Sandbox

Isolated filesystem and command execution for model-generated work.

Workflows

Durable progress, replay, retries, and long-running session semantics.

Functions

Serverless routes, tool execution, channels, and streaming surfaces.

AI SDK Versus Eve

One audience question asks when to use Eve versus the Vercel AI SDK. Andrew answers that Eve is built on top of AI SDK. If you want low-level primitives and want to build your own harness, AI SDK makes sense. If you want durable agents, channels, tools, evals, sandboxes, workflows, and production runtime conventions, Eve is the higher-level framework.

This is a useful mental model for platform teams. AI SDK is the model interaction layer. Eve is the agent runtime and authoring layer. A business can still drop down to lower-level primitives when it needs a different authoring model.

Cost Model

The workshop says deployment itself is serverless, so an idle Eve agent should not cost much just by existing. The official pricing docs clarify that Eve usage is billed through the Vercel resources and third-party services the agent uses: Functions, Workflows, Sandbox, AI Gateway or model providers, plus any external APIs.

Session volume

More sessions and turns create more function and workflow activity.

Model usage

Prompt length, tool results, reasoning, cached tokens, and output length drive token cost.

Tool calls

External APIs and tool execution increase duration and third-party usage.

Sandbox use

Command execution, provisioned resources, snapshots, and network use add cost.

Implications For Your Agentic AI Platform

Eve is a useful reference architecture for the platform you are building because it decomposes agent systems into objects that BA users and engineers can reason about separately. The important product lesson is not to expose one giant prompt box. Expose durable, inspectable building blocks.

My Read

Eve's strongest idea is the filesystem contract. It makes an agent inspectable in the same way a web app is inspectable: you can see where instructions live, where tools live, where channels live, where subagents live, and where skills live. That matters for teams because agent behavior must be reviewable, versioned, and testable.

The second strong idea is that runtime infrastructure should be boring. Durable sessions, sandboxing, observability, approvals, evals, and deployment should not be reinvented for every agent. Eve's opinionated stack is valuable because it turns production concerns into defaults.

For your platform, I would steal the object model more than the exact implementation. BA users should not see folders and TypeScript first. They should see Master Agent, Sub-Agent, Skill, Tool, Channel, Connection, Eval, Approval, Memory, and Flow. Under the hood, those can compile to filesystem-like artifacts, schemas, and deployable runtime pieces.

Bottom line

Eve is a strong example of agent-platform architecture: code-first for engineers, file-first for inspectability, channel-first for deployment, eval-first for iteration, and workflow-backed for durable execution.
