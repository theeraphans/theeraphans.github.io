How Anthropic Builds With AI

Claude Code engineer Thariq Shihipar explains why better models demand stronger harnesses, how Anthropic extends agents across the software lifecycle, and why verification, taste, and technical judgment become more valuable as code gets cheaper.

The Peterman Pod · Thariq Shihipar1h 10m 55sPublished September 7, 2026Summary run September 9, 2026 · 18:20 ICT

This article was prepared from the complete public English caption track (1,888 rows; about 13,902 words) and checked against the official episode page and timestamp map. Internal-practice descriptions and forward-looking predictions remain the speaker's perspective, not audited Anthropic policy.

Executive summary

The engineer increasingly builds the system that builds the system

Thariq Shihipar describes an engineering environment where Claude performs much of the direct code writing, but human work has not collapsed into one-line delegation. Engineers shape problems, gather context, define product intent, design harnesses, create verification environments, inspect evidence, and decide what should land. The abstraction level rises from implementing a feature to building the machinery that can repeatedly implement, review, test, and maintain features.

The model and harness evolve together. As models become capable of working for hours, the surrounding system must handle permissions, sandboxing, long-running state, useful progress representation, and safe autonomy. Shihipar argues against the idea that smarter models make harnesses disappear; greater capability exposes more valuable tasks and therefore requires more sophisticated control.

Anthropic's emerging “loop engineering” pattern turns a direct prompt into a recurring system: collect feedback, triage it, plan changes, implement, verify, and report. Such loops are valuable only when skills, data sources, and verification are strong enough to support them. Otherwise, automation multiplies plausible-looking mistakes.

Cheap code also changes maintenance. Style and naming may receive less manual attention, while executable evidence, fixtures, replay, recordings, rollback, and architectural direction matter more. Shihipar provocatively suggests teams may need roughly 100 times more testing code than before. The exact multiplier is rhetorical, but the direction is important: code-generation throughput requires verification throughput to rise with it.

The operating model

Model capability creates potential. The harness shapes behavior. Context and skills make work specific. Verification converts output into evidence. Human judgment decides whether the evidence is enough.

Onboarding · 00:29

Claude replaces technical lookup, not human belonging

New engineers are encouraged to treat Claude as a thought partner, provide the context it needs, and begin by asking whether the model can do a task. If it cannot, the next question is why: missing context, unclear intent, unavailable tools, weak verification, or a genuine capability limit. Technical onboarding can happen largely through the model's ability to search and explain the codebase.

Anthropic still uses onboarding buddies, but Shihipar says their value shifts toward social and cultural integration: understanding how a team collaborates, earning buy-in, interpreting local norms, and simply having a colleague. This distinction is useful for any multi-agent workplace. Information retrieval is automatable; trust, sponsorship, and organizational context remain relational.

Higher abstraction

Move from doing work to designing repeatable capability

1 · GoalDefine value

Clarify the user outcome and unknowns before implementation.

2 · ContextShape the task

Supply code, history, constraints, examples, and product direction.

3 · HarnessEnable action

Provide tools, permissions, sandboxing, skills, and durable state.

4 · LoopRun repeatedly

Let agents triage, plan, implement, review, and report.

5 · EvidenceVerify outcomes

Use tests, recordings, fixtures, replay, and human judgment.

This is the “system that builds the system.” The engineer is not merely writing a product or prompting a model once. They design an environment in which the model can produce useful changes repeatedly, while failures remain visible and recoverable.

Model and harness · 06:16

Better models increase harness requirements

ModelReasoning and generation

Understands goals, explores options, writes code, and uses tools.

HarnessAction boundaries

Controls permissions, sandboxing, tools, state, and representation.

VerificationTrust boundary

Tests behavior and produces evidence before changes are accepted.

Short agent turns made repeated permission prompts tolerable. Multi-hour work does not. Shihipar uses auto mode as an example: a classifier evaluates actions that would otherwise need manual permission. Sandboxing limits impact, while artifacts summarize hours of work in a form a human can inspect. Even representation is a kind of prompting because the system chooses what evidence and progress to show.

Harness engineering is therefore a mix of science and art. It is evaluated through behavior, yet many design choices concern how an agent communicates, requests authority, recovers from failure, and keeps a person meaningfully in the loop.

Autonomy · 08:55

“Fully autonomous” depends on how much human intent came first

A well-specified ticket can often be implemented without further interaction. Real product work is rarely that clean. Issues mix bugs, requests, symptoms, and competing solutions; teams have not always decided what they want. A one-line instruction followed by endless correction is a failure to shape the task, not evidence that prompting needs more enthusiasm.

Shihipar recommends spending human effort on unique work and delegating repeated translations or previously solved patterns. Even when Claude writes an entire pull request, the human may have supplied product direction, clarified unknowns, designed the specification, created verification, and selected the result. Counting generated lines misses where the consequential decisions occurred.

Intern work also moves. Highly specified implementation tasks are easier to automate, but new problem classes keep appearing. The risk is apprenticeship: organizations must give junior engineers ownership of exploration, evaluation, tools, and new systems instead of removing the experiences from which technical judgment grows.

Computer use · 14:51

Browser interaction covers gaps, but APIs remain more controllable

Computer-use models are improving, yet edge cases such as password managers can halt a workflow. UI interaction is slow because the model needs broad knowledge and because the environment behaves like a state machine the agent does not fully control. A mistaken cart action creates a new recovery path; code and API operations often provide more explicit, reversible state.

Shihipar expects APIs, MCP servers, and products that expose agent-friendly operations to absorb many browser-use cases. Visual interaction remains important where no structured interface exists, but it should not be romanticized when a safer and more deterministic tool is available.

Compute · 17:42

Task shape matters more than indiscriminate token volume

He pushes back on the idea that Anthropic productivity comes mainly from unlimited compute. Smart models can accomplish a great deal within ordinary limits when the problem is well shaped. Users often burn budget by starting with a narrow implementation instruction, discovering cascading consequences, and repeatedly correcting the result.

A better sequence is to step up a level: explain the goal, explore the environment and unknowns, choose an approach, define a schema or plan, create verification, and then let the model run. For genuinely difficult work, explicitly permit deeper exploration, subagents, or workflows. The point is not motivational language; it is telling the system that latency and compute are acceptable tradeoffs for this task.

Loop engineering · 20:45

A loop is a system that prompts the model repeatedly

Instead of directly prompting Claude for every task, engineers can set up recurring systems: watch an issue source, classify feedback, gather context, implement an eligible change, run checks, and return evidence. Shihipar says Anthropic uses such patterns to monitor work that humans could never continuously cover.

ObserveCollect signals

Issues, feedback, telemetry, CI results, or scheduled inputs.

TriageChoose candidates

Apply skills and policy to decide what warrants action.

BuildPlan and implement

Use the repository context and available tools.

VerifyTest behavior

Run deterministic checks and collect inspectable evidence.

EscalateLand or ask

Submit a change, request review, or stop on uncertainty.

Ten autonomous loops are not ten free employees. They require carefully maintained skills, reliable data, strong verification, ownership, and monitoring. The setup cost is justified only when the repeated work is valuable enough.

The next workflow · 22:47

Agents expand from implementation into the full SDLC

Shihipar positions Claude Code as strong at implementation and describes the broader direction as agents operating across feedback intake, code review, CI/CD supervision, issue triage, release work, and maintenance. As task duration grows, text alone becomes a poor interface. Artifacts can present plans, diagrams, schemas, snippets, progress, or task-specific interactive views.

The broader product principle is adaptive interfaces: the agent should create the right representation for the current decision, not force every workflow through a scrolling transcript. Keeping humans in the loop becomes an information-design problem as much as a model problem.

Models and prompting · 26:02

Optimize for frontier capability and the skill of adapting

Shihipar does not view model routing as the most durable expertise. Compute becomes more abundant and model generations change quickly. He would use a strong planning model for brainstorming, finding unknowns, and producing a detailed specification, then a strong implementation model inside a verification harness. The specific names will age; the workflow survives.

Experience with old models still compounds because users learn how to discover a model's behavior. He recalls the difficulty of eliciting structured output from GPT-2; the model is obsolete, but the habit of testing, observing, and adapting transfers. For current models, useful prompts may explicitly say not to implement yet, ask for exploration, or authorize more compute and subagents for a hard task.

Taste · 35:04

References help the model; expertise helps the human judge

For subjective work such as interface design, Shihipar recommends references rich in structure: HTML is more useful than a screenshot, and a Figma file is more useful than a raster image because dimensions, components, spacing, and tokens are directly inspectable. A non-designer can first ask the model to teach the relevant vocabulary, gather references, explain preferences, and generate multiple HTML explorations.

The hard part is deciding when the output is good. In mathematics, only an expert can recognize whether a purported proof matters or is correct. In design, domain knowledge lets a person explain what is weak and push beyond the model's first plausible result. AI increases the leverage of taste but does not automatically create it.

Writing · 39:00

Automate context assembly; keep consequential thinking legible

Shihipar's rule is: if he would be comfortable showing someone the prompt, he is comfortable sending the output. Claude can gather Slack messages, pull requests, and work history into a one-on-one update or data readout. The human still sanity-checks the facts and may edit to show understanding.

Novel pitches and internal essays are generally expected to be human-written because writing is part of forming the thought and each word signals intention. If a model produced an idea, the sender should disclose that and personally endorse it. The issue is not purity; it is avoiding the false impression that someone performed reasoning they did not inspect.

Review provenance · 43:30

A large AI-written change should include its prompt history

A single prompt is not sufficient provenance because output also depends on context, tools, skills, and failed attempts. When submitting a substantial pull request, Shihipar attaches an artifact containing every prompt, including approaches that failed. If the change was genuinely one-shot, he says so.

This gives reviewers a view into the operator's decisions and helps answer a critical question: did the author understand, steer, and verify this 10,000-line change? Prompt history does not replace a diff, tests, or ownership, but it can explain how the result was produced.

Maintenance · 45:36

Maintainability shifts from hand-crafted style toward executable confidence

When agents read and write much of the code, some naming and stylistic debates may matter less. Architectural direction still matters: teams must tell the system what the codebase is good at, how operations should compose, and which properties cannot regress. Skills can encode these expectations.

Shihipar describes a generate-then-simplify workflow. The model first seeks a correct approach; after that is established, a simplification skill can remove complexity. Simplifying unverified code risks polishing the wrong solution and wasting effort.

FixturesRepresent real states cheaply.

Create database fixtures, mocks, and production-shaped examples on demand.

Visual evidenceRecord the feature being used.

A pull request can include a replay showing the agent exercising its change.

Multiple surfacesTest each interaction form.

Storybook, APIs, browser flows, and lower-level tests expose different failures.

RecoveryDesign undo, replay, and rollback.

Higher velocity needs faster diagnosis and safer reversibility.

His “100 times more testing code” statement should be read as a directional challenge, not a measured universal ratio. Generated tests can also be wrong or coupled to the implementation. What matters is independent behavioral evidence with enough coverage to match the expanded change rate.

Breakages · 52:04

Higher velocity can raise incident volume unless verification scales too

Shihipar acknowledges that Anthropic's uptime is not exactly where the company wants it. Rapid growth and more products create operational strain. His response is to imagine a “dream” test and deployment environment: replay requests across realistic fixtures, inject failures, run chaos experiments, observe production behavior, and use Claude to strengthen reliability itself.

This is an honest and important qualification. AI-generated code is not automatically safer because AI can generate tests. Organizations need production indicators, staged delivery, rollback, incident learning, and clear accountability in addition to pre-merge evaluation.

Career and learning · 55:24

Share real work, expand luck, and remain technical

Shihipar advises engineers to choose an interesting project, work deeply, ship it, and write about it. Authentic public work expands the “surface area of luck”: more people can discover what someone can do and offer collaboration, funding, or a role. Asking an agent to manufacture social posts is not a substitute for doing work worth discussing.

Despite claims that coding is largely solved, he strongly recommends learning how computers, languages, services, caches, and memory work. Technical knowledge is what enables someone to direct tools and detect whether generated software is genuinely good. Learning should require effort; merely nodding along to an explanation creates recognition, not mastery.

His final advice is to believe in one's capacity while staying grounded in deliberate work. Models create unusual openings for younger engineers because new categories have no established experts. Opportunity still favors people who explore, develop judgment, and finish what they start.

Critical assessment

What transfers beyond Anthropic, and what requires caution

TransferableStart with the goal and unknowns.

Task shaping reduces waste regardless of model or organization.

TransferableScale verification with generation.

More code requires more behavioral evidence and faster recovery.

TransferablePreserve human intent and provenance.

Prompt history and disclosure help reviewers understand large changes.

Context-boundAnthropic operates at the frontier.

Its compute, models, talent, and incentive to experiment differ from most teams.

RiskGenerated tests can confirm generated assumptions.

Critical checks need independent oracles and production feedback.

RiskWaiting for future rewrites can accumulate operational debt.

Security, reliability, data integrity, and compliance cannot be deferred on faith in the next model.

The strongest lesson is not that engineers should stop coding. It is that the unit of engineering work grows: from code to specification, from tool use to harness design, from one task to an operating loop, and from reviewing implementation to reviewing evidence.

Practical playbook

Apply the interview without copying Anthropic blindly

  1. Begin each task with the outcome, constraints, unknowns, and acceptance evidence.
  2. Ask whether the agent lacks intelligence, context, tools, permission, or verification before retrying.
  3. Use the strongest practical model on well-shaped work before investing in complex routing.
  4. Turn repeated prompts into loops only after the manual workflow is valuable and understood.
  5. Keep consequential permissions scoped and observable during long-running work.
  6. Require inspectable artifacts for long tasks: plans, decisions, progress, and evidence.
  7. Attach prompt history and failed approaches to unusually large AI-generated changes.
  8. Separate context-gathering prose from writing whose purpose is original thought.
  9. Generate broadly, verify correctness, then simplify.
  10. Increase fixtures, replay, visual checks, and failure injection as code throughput rises.
  11. Protect learning paths for junior engineers by giving them novel problems and verification ownership.
  12. Keep technical fundamentals strong enough to judge what the agent produces.

Takeaways

Twelve ideas worth keeping

  1. Treat the model as a thought partner and give it the context needed to reason.
  2. Build the system that builds the system, not only the next output.
  3. More capable models require richer harnesses for autonomy and oversight.
  4. A precise spec can be automated; discovering what should exist remains difficult.
  5. Prefer structured tools and APIs when computer use adds uncontrolled state.
  6. Well-shaped tasks often matter more than raw compute.
  7. Loop engineering is valuable only with strong skills, data, and verification.
  8. Use task-specific artifacts to keep humans informed during long work.
  9. Taste depends on references and domain expertise, not prompting alone.
  10. Automate context gathering while keeping original thinking and endorsement explicit.
  11. Scale executable evidence with generated-code velocity.
  12. Technical fundamentals remain essential for judging abundant software.
