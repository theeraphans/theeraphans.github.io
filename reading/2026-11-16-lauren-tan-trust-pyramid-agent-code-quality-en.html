All Code Is Slop Until the Environment Makes It Trustworthy

Lauren Tan's argument is not that agents should write more code. It is that teams must move trust out of prompts and reviews, then encode it in architecture, static constraints, runtime evidence, and formal checks.

17:31 videoYouTube automatic English transcriptPublished November 14, 2026Summary run: November 16, 2026 · 09:54 ICT

Executive summary

The real product is the environment that makes good code the default

Lauren Tan, known online as Poteto, opens with a deliberately provocative claim: all code is slop, including ours. The point is not that software quality no longer matters. It is that neither a human author nor an AI author deserves automatic trust. Code earns trust through the environment around it: coherent architecture, narrow APIs, static analysis, tests, runtime verification, and evidence that the change works in the real product.

That framing changes the job of an engineer using coding agents. The goal is not to inspect an ever-growing pile of generated diffs. The goal is to make whole categories of bad change difficult or impossible, then give agents a closed loop for proving what remains. Tan's team can pursue unusually high throughput because it invests heavily in those foundations.

  • The codebase is the largest prompt. Agents imitate nearby patterns, including shortcuts, architectural leaks, and accumulated technical debt.
  • Static constraints beat reminders. Types, dependency rules, linters, compilers, tests, and CI are more dependable than prose in an AGENTS.md file.
  • Verification is where most of the work moves. Agents must operate the product, gather evidence, and show that the user-visible outcome is correct.
  • Repeated correction should become infrastructure. If the same mistake needs another comment or review note, the team should look for a structural rule that removes the failure class.
  • Automation is the final layer. An outer-loop agent can safely open or merge work only when the inner engineering loop already produces trustworthy evidence.

Evidence boundary. The talk reports 11,000 team PRs in October, 227 contributors, roughly a 0.5% revert rate, daily stable releases, and performance improvements. These are Tan's public claims and slide figures, not independently audited measurements. PR volume is evidence of throughput, not proof of product value or universal safety.

The trust pyramid

Put the most investment in the layers agents cannot bypass

Tan's pyramid is inverted. The widest and most important layer is the codebase itself: API design, architecture, and refactoring. Beneath it sits static analysis: linters, types, compilers, tests, and CI. Runtime and formal verification come next. Prose such as rules, skills, and AGENTS.md appears near the narrow bottom. Human review is last.

The ordering is about cost and leverage. A reviewer can catch one bad change. A rule in a prompt may influence one session. A linter blocks every future instance it recognizes. A well-designed type or module boundary can make the invalid state unrepresentable before the agent starts reasoning about it.

Codebase as context

Agents reproduce the system they encounter

A coding agent reads far more repository code than explicit instructions. That makes the repository the strongest piece of context it receives. When a codebase contains one obvious route for adding a feature, the agent is likely to follow it. When it contains four generations of architecture, temporary workarounds, and unexplained exceptions, the agent learns that inconsistency is normal.

Tan describes architecture as organic because it grows through repetition. One shortcut is local. Ten copied shortcuts are a pattern. Soon the pattern is treated as precedent, and the next contributor has even less reason to question it. AI increases the speed of that feedback loop in both directions: good structure compounds quickly, but so does debt.

This is why refactoring becomes part of agent infrastructure rather than optional cleanup. Removing two competing patterns reduces ambiguity for every future task. A cleaner API does more than help a human reader; it narrows the search space for an agent and lowers the probability that it will invent a third route.

Enforceable architecture

Dune turns architectural preferences into repository physics

Tan presents Dune as an application framework built for agent-heavy development. Its visible formula is simple: an app framework, one folder per feature, strict import bans, and no comments in product code. The value does not come from those four choices being universally correct. It comes from turning local decisions into constraints that every contributor experiences consistently.

The talk gives Electron as an example. Renderer code, main-process code, and feature code have defined places and permitted dependency directions. An import ban can stop expensive or privileged main-process behavior from leaking into the UI. The agent receives an immediate, deterministic error at the exact boundary it crossed.

Tan also says the team bans useEffect in product code. That is an intentionally strong local policy designed to avoid scattered synchronization logic and hard-to-reason-about state. It should not be copied blindly into every React application. The transferable pattern is to identify a high-cost construct, provide a supported alternative, and make the unsupported path mechanically visible.

Why “no comments” exists here

Prose can become an escape hatch for unresolved design

Tan's most controversial rule is the ban on comments. Her criticism is not that explanatory writing has no value. It is that agents can use comments and Markdown as a place to rationalize an exception: “this is temporary,” “the architecture requires it,” or “do not change this.” The repository then preserves the excuse while the underlying problem remains.

In this environment, Grokbot and Dune reportedly removed nearly all comments from the codebase. The slide compares 65,824 comments at the end of July with 1,229 at the time of the talk. Tan treats the remainder as liabilities to inspect rather than documentation to celebrate.

Do not generalize the rule without context. Comments remain valuable for non-obvious invariants, legal requirements, safety constraints, public APIs, and decisions that cannot be encoded directly. Tan's useful challenge is narrower: if a comment repeatedly explains why invalid structure is acceptable, improve the structure.

Runtime verification

Completion means evidence from the real product

Once architecture and static checks remove predictable failures, the remaining question is behavioral: did the change actually work for the user? Tan argues that coding agents need their own verification loop. They should launch the application, navigate the relevant workflow, inspect state, collect traces or screenshots, and compare the observed result with the requested outcome.

A feature map gives the agent a shared vocabulary for the product: which capabilities exist, how users reach them, what controls matter, and what success looks like. Stable CLIs and browser-control tools give it repeatable hands. Together they are stronger than asking every session to improvise a test script from scratch.

Control surface

Deterministic commands for launching, navigating, inspecting, tracing, capturing, and resetting the product.

Product map

Versioned knowledge of features, paths, expected states, evidence requirements, and escalation conditions.

This also changes code review. A reviewer should not need to infer correctness from a diff alone. The pull request can carry a short video, screenshots, a state diagram, test output, a trace comparison, or another artifact that shows what the agent observed.

Formal and generative checks

Cheap agent labor makes previously expensive verification practical

Tan says the team is experimenting with TLA+, Lean, and property-based UI testing. TLA+ models state machines and explores whether all modeled states are handled correctly. Lean checks whether an implementation satisfies a proof obligation. These tools are not replacements for ordinary tests, but they can expose edge cases that are difficult to reach through example-driven testing.

The economics are the interesting part. Formal methods often fail to spread because writing models, properties, and proofs costs expert time. Agents can reduce that setup cost, generate candidate invariants, and iterate on failed checks. Humans still decide whether the model matches reality and whether the property is worth enforcing.

Tan also mentions Bombadil, a property-based approach to UI testing. Instead of scripting one happy path, a system can generate action sequences and search for invariant violations. This is especially useful in stateful interfaces where bugs emerge only after an unusual ordering of actions.

Verification economics

The token budget shifts from writing to proving

One slide quotes an engineer saying that about 90% of daily token spend goes into verifying patches, while only 10–20% goes into creating them. The percentages are informal and internally inconsistent as a total, but the direction matters: when generation becomes cheap, verification becomes the dominant cost.

That is a healthy inversion. A weak agent workflow optimizes for the first patch. A strong one optimizes for the shortest path from uncertain patch to justified completion. More tokens spent after generation can reduce much more expensive human review, incident response, and rollback later.

Reported outcomes

Throughput is meaningful only beside quality and operational signals

Tan reports that the Grokbot team merged roughly 11,000 pull requests in October, following a steep month-over-month increase. She also cites 227 contributors, daily stable-client releases, a relative revert rate around 0.5%, and improved application performance. The framing matters: the team did not accept quality loss as the price of speed.

Before the software factory

Do not automate an inner loop you do not trust

Tan asks whether a team should build a software factory: a system that automatically writes, ships, and deploys code. Her answer is conditional. First, make the manual-with-agents loop produce good changes by default. Only then add the outer loop that discovers work and launches it automatically.

In her example, Grokbot connects external signals to bounded engineering work. A report or detected bug can launch a coding project. The agent reproduces the problem, makes a change, verifies it, and opens a pull request. Auto-merge becomes conceivable only because architecture, static checks, and runtime evidence already constrain the result.

Practical playbook

Build trust downward, one repeated failure at a time

  1. Inventory repeated human interventions. Record what reviewers repeatedly explain, repair, run, or reject.
  2. Fix architecture before prompts. Remove duplicate paths, narrow APIs, and make ownership and dependency direction explicit.
  3. Encode known failures mechanically. Add types, linters, import rules, compilers, tests, and CI checks with useful remediation messages.
  4. Give agents a real control surface. Provide maintained commands for running the product and collecting evidence.
  5. Define completion artifacts. Require screenshots, traces, state transitions, test results, or formal checks appropriate to the risk.
  6. Measure quality beside velocity. Track intervention rate, repeat defects, escaped regressions, rollback, recovery time, and user outcomes.
  7. Automate only bounded, observable workflows. Start with reversible tasks and explicit escalation conditions before adding auto-merge or deployment.

For agent-platform teams. Treat persona prompts as the lightest layer. The durable product is a versioned work contract: allowed tools, repository boundaries, state transitions, verification requirements, evidence schema, escalation rules, and ownership. A BA can compose agents safely when those contracts are visible and testable.

My take

The strongest idea is categorical elimination

The most useful part of this talk is not the PR count or any single Dune rule. It is the habit of asking: can this failure category disappear? A better prompt might reduce the error rate. A better abstraction, type, or dependency boundary can remove the choice that causes the error.

That does not make prose, skills, or human judgment obsolete. Novel work still needs interpretation. Local rules can be wrong. Formal models can omit reality. A test suite can prove only what it asserts. The pyramid works when its layers challenge one another: structure narrows possibilities, static checks reject known invalid states, runtime evidence tests the real product, and humans remain accountable for whether the system is solving the right problem.

The talk is best read as a software-quality strategy for an era of abundant code. When generating another implementation is cheap, the competitive advantage moves to deciding which implementations are legal, which evidence is sufficient, and how quickly the organization learns from every failure.
