Visual Product Recognition & Shelf Analytics

Convert shelf photos into product and availability data, reducing the work needed for a store audit.

Turn a shelf photograph into an audit

A store photograph contains useful information about products, placement, and availability, but a person still has to identify what is on the shelf. At TSPACE Digital, I worked on a production computer-vision system to reduce that manual audit work across more than 750 SKU classes.

The task has two parts: find each product in the image, then identify which product it is. Similar packaging makes the second part particularly difficult.

Find the product before naming it

YOLO locates products in shelf photographs. Recognition then combines classification models, including CNNs and Vision Transformers, with similarity search using FAISS and KNN. These components address different parts of the recognition problem rather than asking one model to handle the entire photograph.

OpenCV post-processing prepares predictions for shelf analytics. Flask APIs expose the pipeline, and Docker packages the serving environment. Downstream systems can use the product and availability data instead of interpreting raw model outputs themselves.

The API is part of the product

A recognition model is useful only when the audit workflow can use its result. My contribution included the model pipeline, API, and deployment. That meant connecting detection and recognition to an output the wider system could consume.

The public architecture shows classification and similarity search as contributors to recognition. It does not specify unpublished fusion rules, thresholds, or training data. Those details should not be inferred from the simplified diagram.

A bounding box and a product identity are different predictions

A detector can locate a package accurately while recognition assigns the wrong SKU. Conversely, a classifier can work well on clean product crops while the shelf detector misses partly hidden items. Looking only at one stage obscures that difference.

For this system, YOLO locates products, and classification and similarity search contribute to recognition. The public account names CNN and Vision Transformer models but does not publish their training configuration or fusion rule. The architecture describes those responsibilities without reconstructing confidential implementation details.

Consider two packages that differ only by a small volume label. This fabricated example explains why a crop can contain enough evidence to identify the brand but too little to identify the exact SKU. Lighting, occlusion, and crop resolution affect whether that label is visible at all.

Downstream shelf analytics needs to know the consequence of that uncertainty. An uncertain item, a confidently identified item, and an undetected item represent different evidence about availability. They should not all become the same default SKU.

Use neighbors as evidence, with a clear distance meaning

FAISS provides efficient similarity search over dense vectors. Its documentation describes several index choices, trading search speed, memory, and exactness. This establishes what the library can do; it does not reveal which index or parameters this project used. FAISS documentation.

A feature vector represents a crop in the embedding space created by a model. Nearby reference vectors can supply candidate identities. Whether “nearby” is useful depends on the embedding model, normalization, distance function, and reference data.

The practical comparison is between visually similar candidates. A nearest neighbor always exists when the index is populated, including when the crop is a product the system has never seen. A candidate result alone should therefore not be interpreted as proof of identity.

A public evaluation plan could include known products, similar packaging, unreadable crops, and unknown products. The test would inspect recognition and uncertainty behavior separately. This plan is proposed analysis, not an assertion that the production system uses a specific rejection threshold.

Measure the full path from image to audit

Detection quality, recognition quality, and audit time answer different questions. A detector evaluation checks localization and missed objects. Recognition evaluation checks identity on a defined set of crops or detections. Audit time measures the work needed by a person using the complete system.

Evaluation targetWhat it revealsImportant scope
DetectionMissed items and incorrect boxesShelf conditions and annotation policy
RecognitionConfusion between product identitiesKnown classes and crop source
End-to-end auditCorrections and time spent by a userStore workload and workflow conditions

The reported recognition accuracy is 90%, while audit time fell from 45 to 15 minutes. Those results describe the project record. Without the unpublished evaluation conditions, the accuracy cannot be equated with a detector benchmark or used to rank another system.

A stronger public benchmark would define the split by capture session or store, specify the class distribution, and report uncertainty. Near-duplicate images from the same shelf should not appear on both sides of a split. Otherwise the test may reward familiar photographs rather than generalization to a new audit.

The user experiences the serving pipeline

The API needs to accept an image, run the pipeline, and return information the audit workflow can use. Failure at image decoding, model inference, similarity lookup, or output preparation should be distinguishable in an investigation.

A proposed reliability test suite would include invalid files, very large images, empty shelves, partly hidden products, and simultaneous requests. These cases inspect service behavior around the model, not merely its performance on a clean offline dataset.

Model changes and reference-index changes also need compatible versions. Updating one without the other can alter the meaning of distances or candidate identities. A deployment record should make the pairing inspectable and allow a rollback to a known pair.

The public materials establish Flask API serving, Docker deployment, and the recognition components. The operational checks above describe what I would examine in a release review; they are not a claim that every listed test exists in the original implementation.

Less time spent on each audit

Store audit time fell from 45 minutes to 15 minutes—about 67% less time. The system covered more than 750 SKU classes, with reported recognition accuracy of 90%. Detailed evaluation conditions are not public, so that accuracy should be read as a reported project result, not a comparison with another benchmark.

The practical outcome was a shorter path from shelf images to usable retail data. The project also shaped how I approach AI systems: model quality matters, but so do the interface, serving pipeline, and work that the result replaces.
