Hermes Enterprise AI Workspace

Give teams a workspace to configure agents and run conversations without exposing backend credentials.

By Theeraphan Sukchok · Independent project · in development · Updated October 2026 · 7 min read

A runtime needs a place for people to use it

An agent runtime can execute tasks, but a team still needs somewhere to configure agents, manage knowledge, and hold conversations. Hermes Enterprise AI Workspace is my independent project exploring that user-facing layer.

It is a local prototype in development, not a production enterprise deployment. The focus is on making the boundary between browser, application backend, and agent runtime explicit.

Keep runtime credentials out of the browser

The Next.js portal talks to a FastAPI backend-for-frontend. That backend owns the runtime credential, checks session ownership, and proxies execution. The browser does not need direct access to the Hermes backend credential.

SQLite stores portal records that map users to sessions and agent versions. For conversations, the backend proxies server-sent events from the runtime so the interface can show streamed responses and tool activity. Honcho supplies persistent memory context.

These are application boundaries, not evidence of completed enterprise security. SSO, RBAC hardening, and live multi-user reliability remain work to verify.

Publishing is not the same as starting a conversation

The workspace lets a user define an agent, validate its configuration, and publish a version. That version becomes available for runtime team selection. Publishing alone does not start a chat.

Keeping those steps separate gives configuration its own lifecycle. A conversation selects the agents it will run, while the factory handles the version that was made available. This avoids treating an editable definition and an executing agent as the same thing.

Fallback retrieval should not hide failed document changes

The knowledge integration can use Cognee with isolated datasets. During chat retrieval, a user-scoped local index can provide a fallback. Document creation and deletion behave differently: if the service is unavailable, those operations fail explicitly.

That distinction prevents the interface from appearing to save or delete a document when the backing knowledge service did not make the change. A degraded read path can be useful; silently diverging document stores are much harder to explain.

Follow a conversation across the boundary

An illustrative conversation begins when a user selects an available team and submits a message. The portal sends it to the application backend, which checks the session mapping and forwards execution to the runtime. The backend then streams runtime events to the interface.

That sequence contains separate identities: the portal user, the conversation session, and the runtime credential. Collapsing them into one browser-supplied identifier would make ownership difficult to enforce. The backend needs to derive access from its authenticated context and stored records.

The prototype's session-ownership checks are useful application behavior, while its local mock mode limits what a demonstration proves. A working interface in mock mode does not validate the real provider's authentication, timing, cancellation, or failure behavior.

A stream is delivery, not a completion record

Server-sent events carry server-to-client messages over an HTTP stream. MDN documents the event-stream format and browser event handling. That helps explain the transport used by the workspace, although this application's authenticated proxy should not be assumed to use a particular browser client simply because SSE is involved. MDN: using server-sent events.

A disconnected tab leaves an important question: did execution stop, or did the user merely stop receiving its events? The interface needs a way to distinguish delivery state from execution state. Reconnecting to a stream should not silently launch a new conversation run.

My proposed integration test would close the client connection during a fake long-running response, inspect the backend and runtime state, then reconnect. The expected behavior needs to be declared before the test: cancellation, continued execution with later inspection, or another explicit policy.

A visible partial answer also needs a status. Treating an interrupted response as a completed answer hides the failure from the user. A completion event or durable run status would provide stronger evidence than the last text token that arrived.

Read fallback and document mutation have different risks

The optional knowledge path uses Cognee, with a user-scoped local retrieval fallback during chat. A temporary failure can therefore still allow some context retrieval. Document creation and deletion fail explicitly when the service is unavailable, preserving a visible error instead of pretending both stores changed.

That policy reflects different costs. A read can return degraded information with a stated limitation. A write that appears successful can leave the interface and backing service disagreeing about which documents exist.

An illustrative test adds a document, checks its retrieval scope, simulates a service outage, and attempts deletion. The UI should show the failed deletion honestly. A later successful deletion should remove the document from the relevant retrieval path. This is a recommended end-to-end scenario, not a released test result.

Memory and knowledge also have different ownership questions. Conversation memory preserves context across interactions; uploaded documents supply reference material. Each needs a clear lifecycle and isolation rule rather than inheriting access merely because the user can open the chat page.

Test the boundary with two users

A single-user demonstration cannot expose cross-user access problems. A useful verification fixture creates two users, two sessions, and separate knowledge records. It then tries to read, stream, modify, or delete resources across those identities.

Both allowed and rejected paths matter. A correctly denied request should leave the destination unchanged and provide an understandable error. A successful request should operate on the intended resource, rather than pass because the fixture contains only one session.

Version publishing deserves similar scrutiny. Editing a draft, validating it, publishing a version, selecting a team, and starting execution are distinct operations. An old session should remain explainable even after a later version is published. The prototype explores that lifecycle; a real-provider release still needs to verify the exact selected version at execution time.

Enterprise SSO, completed RBAC hardening, and multi-user production reliability remain outside the current public claim. The next meaningful milestone is verified real integration across these boundaries, not additional interface screens.

What the prototype proves—and what it does not

The local portal and backend explore agent configuration, conversations, knowledge, tasks, approvals, and schedules. The default local setup uses mock mode. It demonstrates the workspace flow without establishing live-provider behavior or production readiness.

My next priority is to verify the real integration across those boundaries before adding enterprise claims. The workspace should make the system easier to understand for its users, while keeping ownership and runtime responsibilities clear.
