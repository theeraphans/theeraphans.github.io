Agentic AI Platform

Build agents, connect business tools, and review improvements before publishing a new version.

An agent is more than its prompt

A useful business agent needs to understand a request, find the right information, call a tool, and know when to stop. A convincing answer is not enough if the agent looks up the wrong order or takes an action it should not take.

I started this independent project to make those responsibilities explicit. Rather than building a new application around every agent, I am building a common runtime for agent definitions, business tools, execution records, and version evaluation. The implementation is local; the platform is not presented here as a deployed enterprise product.

Keep the conversation separate from execution

The chat service owns the channel and conversation: receiving messages, maintaining conversation state, identifying an inquiry, and collecting missing information. Once a request is ready, it hands the runtime a task and its context. That separation lets a conversation change channels without making the execution engine responsible for every webhook and messaging format.

The core loads a selected agent configuration and builds its execution graph. Routers and loaders prepare the required data before execution; graph nodes work with the state they receive and return updates. Database access belongs in the preparation layer rather than being scattered through the graph.

An agent definition has distinct parts: persona, rules, skills, and tools. A persona describes its role. Rules set constraints. Skills describe how to approach a task. Tools define which external capabilities it can use. Keeping these separate makes a proposed change easier to inspect than a single growing prompt.

Make business actions visible

The runtime connects to MCP servers instead of embedding every business integration in the agent itself. A tool can expose an order lookup, shipment information, a document operation, or another bounded capability. The public diagram groups those tools; it does not mean each request calls every integration.

The implementation separates read-only data tools from business tools that can change state. That boundary matters because retrieving information and taking an action carry different risks. A tool call should be an inspectable operation with an explicit input, not a side effect hidden inside an answer.

Execution records preserve the run and tool activity. They provide a way to investigate what the agent actually did, beyond reading its final message. This is also the evidence an evaluation service needs when the answer sounds reasonable but the workflow is wrong.

Evaluate the version, not just the answer

Evaluation runs beside the core. The design starts with curated cases and reviewable expectations, then executes a selected agent version in a sandbox. Scoring can inspect answer structure, tool evidence, and behavioral constraints separately. A missing tool call and an incorrect answer should not collapse into the same unexplained score.

The improvement loop is harness engineering, not model fine-tuning. It diagnoses failures and proposes changes to the agent configuration. A person reviews the proposed difference before a new version is promoted. Immutable snapshots make the tested configuration identifiable and allow an earlier version to be selected again.

Held-out cases belong outside the diagnosis loop. Expected answers are supplied to scorers, not to the agent prompt. Otherwise an apparently better score could reflect access to the test rather than a better agent.

Follow one request through the system

Consider an illustrative shipment inquiry: “Has my order shipped?” This is an explanatory example, not a recorded customer interaction. The channel service collects enough information to identify the order. The core receives the prepared task, loads the configured team, and coordinates a capability. A shipment tool returns business evidence, and the conversation layer presents a response.

The local loader assembles an orchestrator prompt from the flow definition and agent configuration. Its routing tool exposes an explicit list of agent names. The orchestrator can route a task or complete the flow with a summary. An allowed agent name constrains the choice, although it does not prove the task was routed correctly.

Useful evidence includes the selected version, the order reference supplied to the lookup, the returned shipment status, and the answer shown to the user. A failed lookup needs a different explanation from a successful lookup that found no shipment.

Conversation history and execution state have different jobs

A transcript records what people and agents said. Execution state records where a workflow is and which results it already has. A generated sentence saying that an action happened is weaker evidence than the business system's acceptance record.

LangGraph documents checkpoints as thread-scoped snapshots that support resuming execution and inspecting earlier state. Long-term stores serve a separate role across threads. This is background for the design, rather than a claim that every persistence feature has been verified in the project. LangGraph persistence documentation.

My proposed recovery tests interrupt a run after a read-only lookup, after an action is proposed, and after an action succeeds but before its response arrives. Each resumed run needs inspection. Repeating a lookup may be acceptable; repeating a customer-facing action may be harmful.

A checkpoint preserves workflow state. An idempotency record answers whether a particular external action has already been accepted. I would verify both with a fake business endpoint that records accepted actions and deliberately delays responses. This is a test plan, not a claim of exactly-once execution.

A tool call needs an authorization decision

The model proposes an operation; the business boundary decides whether the caller can perform it on the requested resource. A valid schema and a human approval each provide useful information, but neither independently establishes permission.

MCP security guidance discusses audience validation and the risks of passing upstream tokens through to unrelated services. Application authorization still needs to constrain the business operation. MCP security best practices.

For an email action, approval should identify the recipient and content that will actually be sent. If the payload changes afterward, the old decision should not authorize the new payload. The execution gateway needs to bind the decision to the operation and reject missing or mismatched authorization. This is a requirement to verify across the project, not a declaration that all paths already satisfy it.

Read operations need ownership checks too. A valid order number is not enough to grant access to another customer's information.

Separate the failure before changing the prompt

A case can fail because of retrieval, routing, tool inputs, service availability, response formatting, or the evaluator itself. Labeling all of those “prompt quality” can hide an integration bug behind a configuration change.

Here is a proposed diagnostic record. It is an illustrative format, not a published API schema or an actual result.

case_id: shipment-inquiry-example
expected_capability: shipment_lookup
observed_capability: order_lookup
answer_check: insufficient shipment evidence
failure_category: wrong_capability
review_action: inspect routing definition

A deterministic check can identify an absent field or required tool call. A model-based judge can assess answer quality against a rubric, but its judgment should remain attached to the evidence it saw. Disagreement across repeated judgments deserves investigation rather than a precise-looking average.

Candidate and baseline versions should run against the same cases and evaluator configuration. Development cases help diagnosis; held-out cases check generalization. Answer keys must stay outside the agent's prompt and retrieval context. Otherwise the experiment measures access to answers rather than the intended capability.

More agents mean more boundaries to inspect

Splitting work across agents can make specialized instructions easier to maintain. It also adds routing decisions, handoff context, model calls, and possible failure points. A short lookup may need one bounded capability rather than several agents exchanging summaries.

The local orchestrator favors the configured step sequence. That gives a readable workflow, but the design still needs evidence that the sequence is appropriate for a given task. A useful comparison would hold the task set constant and compare a single-agent baseline with the configured team on answer quality, tool correctness, latency, and cost. No such comparative result is reported here.

The evaluation loop should also preserve the baseline configuration. A proposed improvement that passes answer checks but repeats a business action should fail promotion. Authorization and replay tests need acceptance criteria independent of prose quality.

What I am working toward

The repository contains runtime, chat, and evaluation services with local implementation and tests. That is different from proving the complete system reliable against live providers and real users. The next step is to verify those boundaries together: the version a run used, the evidence an evaluator captured, and the exact change a reviewer approved.

The goal is a platform where an agent can improve without losing the ability to explain what changed. Execution, evaluation, and promotion remain separate responsibilities throughout that process.

Research context and references

Lilian Weng's discussion of harness engineering examines improvement in the software around a model. My project's narrower scope is a reviewable configuration loop with separate execution, evaluation, and promotion responsibilities. The research motivates questions; it does not supply performance results for this implementation.
